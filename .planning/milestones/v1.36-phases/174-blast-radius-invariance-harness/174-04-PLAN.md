<objective>
Turn the two things this phase currently assumes into measured, committed, drift-tested artifacts: the
filed dev-test history that a re-key forks, and the raw-CLI-token to `part_number` delta across the
shipped database.

Purpose: GATE-04 says the delta must be an artifact rather than an assumed number, and D-06 says the
filed history must be committed with a reproduction assertion rather than recorded inertly. Both are
measurement work, and both were measured this planning session — including a correction: all 26 filed
hashes reproduce from their own issue bodies through the current hash grammar, which makes the historical
corpus a live continuity gate rather than the four-chip sample the research pass concluded was reachable.

Scope amendment, ratified by the operator on 2026-09-03: D-06 reduced builder reproduction to four
named chips, on the stated ground that several rows would need issue bodies parsed — the loader D-01
declines to build. That ground no longer holds. Task 1 commits each row's `steps`, `run_counts` and
`coverage_tag` as data, so nothing is parsed at test time and no deserializer is written. The enabling
discovery is that a step's `fingerprint` serialises as a bare classification string rather than an
object: read as an object, 0 of 26 rows reproduce; read as a string, 26 of 26 do. D-06's four-chip
reproduction reduction is therefore superseded by that ratification and the gate stands at 26 of 26.
What widens is the corpus reproduction assertion only — the four chips D-06 names keep their dedicated
builder shapes in the frozen table, and the `SHAPE_IDS` set is untouched.

Output: two generators, two committed artifacts, two test modules with the full three-leg anti-vacuity
contract, and two evidence transcripts.
</objective>

Extract each row's report from the body by locating the fenced JSON blocks and taking the last one that
parses to an object carrying a `dedup_fingerprint` key. Then record, per row: `issue` (int), `state`,
`raw_token`, `verdict`, `filed_hash`, `schema_version`, `host_version`, `chip` (from the report's

classification, with the classification as `null` when the body's `fingerprint` value is null),
`run_counts` (an object mapping op to integer, present only when the body's steps carry the key),
`repeat_policy_tag` (the derived value), `coverage_tag` (the solved value), `coverage_tag_source`
(the string `derived` when the body determined it, `solved` when the two candidates were tried), and
`recomputed_hash`.

The load-bearing extraction detail, which is where a naive implementation silently fails: a step's
`fingerprint` value in the fenced JSON is a BARE CLASSIFICATION STRING, not an object with a
classification key. Reading it as an object yields an empty classification for every step and no row
reproduces. Measurement this planning session confirmed both directions of that: read as a bare string,
all 26 rows reproduce; read as an object, 0 of 26 do.

The tag handling. Derive the repeat-policy value from the body's per-step run counts using the same
predicate the production function uses — the degraded marker when any step whose op is in the
repeat-policy op set carries a run count of exactly 1, and empty otherwise. Where the body carries no run
count key at all, which is every row filed under schema 1.2 or earlier, the derived value is empty. For
the coverage value, try both possibilities — empty and the full-device marker — and record which one made
the row reproduce, with `coverage_tag_source` set to `solved`. Measurement found the resulting split:
sixteen rows need neither tag, one needs only the degraded repeat marker, three need only the coverage
marker, and six need both.

Validate before emit, and fail closed on a non-reproducing row: recompute each row's canonical string
from the recorded fields, hash it, and if the result differs from `filed_hash` raise and exit non-zero
naming the issue number. All 26 reproduce at the branch base, so a failure here is real news, not an
expected shortfall. Also assert during validation that the row count is exactly 26, that all 26 hashes
are twelve lowercase hex characters, and that no two rows carry the same issue number.
