## Note on the halving

total_steps and unsupported_steps both landed at EXACTLY half their prior
value (8124 = 16248/2, 4652 = 9304/2). This is a real, measured property of
the domain, not an assumption substituted for a measurement: at the
reachable scope, `write_execute` is True either way (full or partial), so
every chip's step COUNT and each step's `supported` flag are identical
between its full-scope and partial-scope derivation -- only the write op's
literal string (`write` vs `write-partial`) and its `write_region` differ,
neither of which this count touches. The old two-scope-per-chip corpus was
therefore counting each chip's step population twice over; the new corpus
counts it once. This was verified by direct measurement (re-running
`tools/measure_plan_shapes.py` against the shipped database), not derived
by halving the old number in the editor.

## Real bug fixed by the re-key, not merely a mechanical rename

tests/test_derive_plan_structural_sentinel.py's 28C-family carve-out test
built `carveout_chips = {name for name, _scope in carveout_plans}` --
valid only when `carveout_plans` held (name, scope) tuples. Under the new
single-key corpus this line would raise (`too many values to unpack`, a
plain string is not a 2-tuple) rather than silently produce a wrong
answer -- caught by running the test, not by inspection. Fixed to
`carveout_chips = set(carveout_plans)`.

## shape family membership (why distinct_shape_families stayed 8)

Measured directly: none of the 8 shape families mixes a UV and a non-UV
chip. A family's identity is the (id, blank-check-position, erase, SDP)
structural boolean combination, which is scope-invariant -- so grouping by
family at the single reachable scope produces the same 8 families the old
full+partial sweep found, and no family's recorded step-token list needs
to represent two conflicting write-op spellings ("write" vs
"write-partial") for the same label. `tools/measure_plan_shapes.py`'s
validate() now asserts this directly (a UV/non-UV mix inside one family
would raise ValidationError, exit 1) rather than leaving it an unstated
assumption.

## Generator update (tools/measure_plan_shapes.py, not in the plan's <files>
## but authorized by its own action text: "Update the generator only if it
## hard-codes a scope list of its own")

The generator's derive() and validate() both hard-coded
`corpus[(name, "full")]` / `corpus[(name, "partial")]` per chip, and its
shape_families schema stored a {"full": [...], "partial": [...]} pair per
family. Both are re-keyed to the single corpus[name] lookup and a single
"steps" list per family; aggregate["plans"] changed from `len(chips) * 2`
to `len(chips)`. Without this update the generator would raise KeyError
against the re-keyed corpus and could not run at all -- this was not a
discretionary style choice.
