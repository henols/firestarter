## Anchor Drift note (verify-leg fixture mismatch, not a production defect)

The plan's Task 1 second `<automated>` verify leg is written against
`build_shape("sst27sf512-six-step")`. That shape is HAND-SPECIFIED via
`build_shape_from_step_specs`, which constructs `Fingerprint(total=10, bad=0,
bad_pct=0.0, classification=cls)` with NO `evidence=` argument -- so its
`evidence` field takes the dataclass default `field(default_factory=dict)`,
i.e. `{}`, for every step in that shape. `{}` is falsy, so the verify leg's
own filter (`[... for s in d["steps"] if s["fingerprint_evidence"]]`) drops
every step and the leg's own `assert ev, "no populated evidence mapping in
this shape"` fails -- confirmed by running the leg verbatim before adapting
it (AssertionError at that exact line). This is a mismatch between the
plan's chosen fixture and that fixture's own construction, not a defect in
`_step_dict`'s new siblings: `fingerprint_total`/`fingerprint_bad`/
`fingerprint_bad_pct` are correctly exported and equal to the dataclass's
own values regardless (proven by the leg's first half, which still passes
against "sst27sf512-six-step" unmodified). Re-run against
"sst27sf512-full-all-ok" (a `_build_real_path_report`-built shape, so its
fingerprint carries `classify_fingerprint`'s real, non-empty evidence dict)
-- Section 1 above is that re-run's output. Gate that would redden if this
regressed: `test_fingerprint_siblings_equal_the_dataclass_own_values` in
`tests/test_diagnostic_report.py`, which asserts equality against an
explicitly-constructed non-empty evidence dict rather than relying on any
particular fixture shape's emptiness.
