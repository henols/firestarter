Build the execution half of D-10's no-drop proof: run every one of the 1,354 shipped plans through the
real `run_plan` with a hardware-free operator double, and assert both halves of PRUNE-05's sentence —
that every step yields a `StepResult`, and that every unsupported step's result carries the `NA`
verdict.

shapes did not move; it says nothing about whether an unsupported step actually produces a result with
`NA`. Conversely this sweep cannot catch a prune, because a prune shrinks both sides together — which
is why plan 175-03's frozen half is mandatory and why that argument goes in this module's docstring,
where a later simplification cannot delete the frozen half without reading it.

Build the execution half as its own module, and raise the cap it breaks, in one commit.

**Why its own module, and not a marker.** Splitting the sweep into
`tests/test_derive_plan_no_drop_sweep.py` makes
`pytest tests/ --deselect tests/test_derive_plan_no_drop_sweep.py` a one-flag escape hatch without
inventing a convention. No `markers` key exists in `pyproject.toml` and no `mark.slow` appears anywhere
in `tests/`, so a marker would be a new convention while a module split is not. The answer to
CONTEXT.md's deferred "does the sweep run on every push?" is therefore: **yes, it runs, and it is one
path away from not running.** Record the corrected cost figures in the module docstring — the sweep is
about 37 seconds against a 302-second suite, so roughly **12 percent**, not the 3 percent the
discussion assumed against an inherited 737-second suite figure that does not reproduce.

**Module preamble.** A module docstring carrying four blocks:

1. **What this proves and what it does not.** It proves step and result alignment and NA-on-unsupported
   across the whole shipped database. It does NOT exercise the write path on most chips: the shared
   `mock_operator`'s `check_eprom_id` returns a fixed `(True, 0x1234)` which mismatches most real chip
   IDs and closes the destructive gate, so 2,545 of the 6,944 supported steps come back SKIPPED,
   dominated by the write, write-partial and erase steps reporting a chip-ID mismatch and by verify
   steps reporting no write target available. A SKIPPED step still yields a `StepResult`, so PRUNE-05 is
   unaffected — but the module must say this plainly rather than overclaim.
2. **Why the frozen half in `tests/test_plan_shapes_drift.py` cannot be simplified away.** An
   alignment-only proof cannot catch the change PRUNE-05 forbids: if a future phase prunes unsupported
   steps inside `derive_plan`, both `Plan.steps` and the results list shrink together, alignment still
   holds, and the six SDP ballast steps on 637 chips silently vanish from the dedup hash. Put this here
   in full, because this is the module a later reader will find first.
3. **Why `runs=2`.** `run_plan` returns exactly one `StepResult` whose op is `__plan__` and whose verdict
   is `BAD` when `runs < 1 or (runs < 2 and not allow_single_run)`, so a bare `runs=1` sweep fails
   alignment for a reason unrelated to PRUNE-05. The default is used deliberately and a named leg proves
   the guard is real.
4. **Cost and the escape hatch.** About 37 seconds, roughly 12 percent of the 302-second suite; it runs
   on every push and `--deselect` on this path is the one-flag opt-out.

**The helpers.** Two unannotated functions, so the sensitivity legs have something to weaken.

- `alignment_violations(plan, results)` — returns a list of `(name, len_steps, len_results)` tuples,
  empty when the two lengths are equal.
- `na_verdict_violations(plan, results)` — zips `plan.steps` with `results` positionally and returns a
  list of `(index, op, verdict)` tuples for every step whose `supported` is False and whose
  corresponding result's verdict is not `chip_test.VERDICT_NA`. Guard the zip: if the lengths differ,
  return a single violation naming the mismatch rather than silently truncating, which is what `zip`
  would otherwise do.

**The green legs.** Build and discard results as the sweep goes, one plan at a time, so peak memory
stays flat; do not hold all 16,248 results in a module-scoped fixture. Import the cached corpus from
`tests.plan_corpus` so the 1.26-second build is shared with the other modules in the same pytest
process. Nothing is monkeypatched anywhere in this module: the database is injected, the operator is
injected, and the corpus mutation in Task 2 is on copies.

- `test_every_plan_yields_one_result_per_step` — assert the corpus size is exactly `1354` first, then
  sweep, accumulating the total result count and the violation list. Assert the violations list is empty
  and the total result count is exactly `16248`, with a message naming the failure mode as a step
  silently dropped or added.
- `test_every_unsupported_step_result_carries_the_na_verdict` — the same sweep shape, accumulating the
  unsupported-step count and the violation list. Assert the unsupported count is exactly `9304` and the
  violations list is empty. The absolute count is the anti-empty floor: a sweep that visited no
  unsupported steps would otherwise report zero violations and pass.
- `test_a_single_run_returns_only_the_plan_guard_result` — one shipped plan, `runs=1`, assert the result
  list has length 1, its single op is the literal `__plan__` and its verdict is `chip_test.VERDICT_BAD`;
  then the same plan with `runs=1, allow_single_run=True`, assert one result per step. This documents
