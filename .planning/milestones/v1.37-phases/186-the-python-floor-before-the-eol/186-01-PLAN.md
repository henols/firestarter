<objective>
Move the advertised Python floor to 3.11 in every place this repository states it, and delete every
claim the move falsifies rather than rewriting one.

Purpose: `requires-python = ">=3.9"`, `target-version = "py39"` and mypy `python_version = "3.10"` have
disagreed since 2026-05-27, and the advertised floor has never been type-checked. Python 3.10 EOLs
2026-10-31. D-01 resolves the disagreement in the raise direction, at the version CI already executes,
so the floor stops being advertised and starts being proven.

This is the phase's TRACER slice. It wires the whole path this phase touches — published metadata
(`requires-python`, classifiers) → lint target → type-check target → the executed CI interpreter → the
runtime refusal inside the shipped wheel — end to end, in one coherent move, and proves it with the
project's own gate running on the project's own py3.11 replica interpreter. Everything else in this
phase expands out from this slice: plan 186-02 absorbs the lint consequence of the new target, plan
186-03 installs the check that stops the four statements drifting apart again, plan 186-04 records why.

Output: four floor statements in agreement, a classifier list that claims only what is tested, a runtime
guard whose two halves agree with each other and with the metadata, and four falsified prose sites
deleted.
</objective>

  <context>

    What is one-way: `requires-python` is published metadata on a live PyPI package. Once a release
    carries `>=3.11`, lowering it later does not un-publish the releases that advertised the higher
    floor, and pip's candidate filtering for 3.9/3.10 users is changed by the first upload. Note the
    timing precisely: within this phase the change is a git revert away. The door actually closes at the
    operator's next beta cut, which is out of this phase's scope and already operator-gated.

    The new fact (C-5, measured against a local wheel index, pip 25.0.1). D-12 says "pip already refuses
    on 3.9/3.10". The quoted error string is verbatim-correct but it only fires on a **pinned or exact**
    request. An unpinned `pip install firestarter` on 3.10 emits no error at all: pip silently selects
    the newest release that still advertises a compatible floor and exits 0. So the real consumer
    experience is not a refusal — it is a silent pin to the last release advertising `>=3.9`, with
    updates quietly ceasing. That is a materially different user impact from the one D-12 assumed.

    Nothing else changed. The three rejected alternatives in D-02 all re-verified: `PYTHON3_VERSION_MIN`
    is `(3, 10)` in the pinned mypy 2.3.1, so holding 3.9 remains unreachable; 3.10 would be EOL on the
    day it lands; 3.12 would force a CI change and drop 3.11 users. The mypy error count does not move
    at all between 3.10 and 3.11 (35, byte-identical).
