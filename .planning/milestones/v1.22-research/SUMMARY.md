# Project Research Summary

**Project:** Firestarter — v1.22 AT28C Software Data Protection Lifecycle
**Domain:** Embedded dual-repo device programmer (AVR C++ firmware + Python Click host CLI) — write-protection (SDP) lifecycle on protocol `0x0D` / `PROTO_EEPROM_PARALLEL` / `configure_eeprom28c`
**Researched:** 2026-07-27
**Confidence:** HIGH on every in-tree code claim and on the AT28C/AT28C64B datasheet semantics · MEDIUM on cross-manufacturer timing (`tBLC`) and on the XICOR/CATALYST magic-address audit · UNPROVABLE-WITHOUT-SILICON on all silicon-state claims (stated as such, never softened)

## Executive Summary

v1.22 was chartered as "complete and expose SDP" — add the missing lock half, expose unlock, make today's silent auto-unlock observable. **All four research streams independently concluded that the milestone's own premise is falsified: the SDP-disable path that `PROJECT.md:53` records as "shipped in `3.0.0b11`" is true of the source and almost certainly false of the silicon.** `eeprom28c_write_init` (`eeprom_28c.cpp:104`) issues the 6-write sequence through `flash_execute_command` → `flash_util_byte_flipping` (`flash_utils.cpp:21-28`) → `fu_flash_fast_address` (`flash_utils.cpp:62-67`), which writes the raw address straight into the LSB/MSB latches and **never calls `mem_util_remap_address_bus`** (`memory.cpp:331-354`). It therefore applies no pin remap, no `rw_line` polarity and no `static_high_mask`. It hard-codes `/WE` as `CTRL_READ_WRITE` (`0x40`, `rurp_pinout.h:82`) — correct only for `DIP32_SST39SF040` (`rw-pin: [31]` → bus line 22), the pinout every bench-proven `0x05`/`0x06` chip uses. **Every one of the four `0x0D` pinouts has a different `rw` line (11 / 14 / 14 / 20, derived from DIP pins 21 / 27 / 27 / 30), so on all 84 `0x0D` chips at least one command write in the shipped sequence is emitted with `/WE` high — a documented Write Inhibit (AT28C256 DS20006386B Table 6-1).** Both STACK and ARCHITECTURE reached this by executing the project's own `database.py`/`pinouts.json`, and their per-pinout numbers agree. v1.22 therefore opens with a **FIX**, not a feature — and that is good news, because it yields the one thing a silicon-less milestone needs: a native register-trace test that is RED today and GREEN after.

The second falsification is the success check. `eeprom28c_wait_for_write(handle, 0x5555, 0x20)` (`eeprom_28c.cpp:106`) is not a weak proxy — it is **inverted**. AT28C64B DS20006432B §6.6.2 p.10 and AT28C256 DS20006386B p.10 both state the command-sequence data "are not actually written into the device," so the poll can only pass when the sequence was *not* recognised (the bytes fell through as ordinary writes, corrupting `0x5555`) and must fail when it *was*. On a blank part it times out → `MSG_ERR_EEPROM_TIMEOUT` → `RESPONSE_CODE_ERROR` → INIT aborts before a single data byte is sent. Hence the **highest-value PREDICTED item in the milestone: `firestarter write at28c256 <file>` on `3.0.0b11` aborts at INIT today.** That prediction is native-testable and must be settled in Phase 116, because the entire auto-unlock policy trade-off collapses if it holds (there is no working behaviour to preserve). It also reverses the milestone's framing of gh#11/gh#12: those 2024 reports **may describe live defects**, and the planned closeout comments must be reworded from "we already fixed this in b11" to "we found a second defect — please re-test."

The recommended approach is unanimous across the four streams and needs **zero new dependencies on either side of the wire**: build the trace oracle first, fix the emitter and the completion signal second, make the existing auto-unlock observable third, add the lock half and its command surface fourth, close the host lockstep fifth. The key risks are (a) **harness hollowness** — `rurp_write_data_buffer` is a no-op stub (`host_stubs_common.inc:98`), so no existing test can distinguish lock from unlock from chip-erase, which abandoned commit `0052c42` proved by swapping tables and reporting "22 tests PASS (zero-diff)"; (b) **timing versus observability**, in direct tension, since one COBS-framed log at 250 kbaud costs ~320–640 µs against a 100 µs `tBLC` budget; and (c) **overclaiming at close** — nothing in this milestone can prove silicon changed protection state, so `0x0D` stays `UNVERIFIED` in PROTOCOL-LEDGER and no chip's `support_status` moves.

## Adjudicated Conflicts

The four streams converged strongly but conflicted on three load-bearing points. Each gets a verdict, not an average.

### CONFLICT 1 — does SDP-enable (lock) require a data payload?

**VERDICT: NO. `AA→0x5555`, `55→0x2AAA`, `A0→0x5555` plus a `t_WC` wait latches SDP-enable with no data payload. Confidence HIGH.**

Why STACK outweighs ARCHITECTURE here: STACK cites a datasheet note *verbatim, by document number, revision, section and page*, three times over —

- Atmel **doc0270** rev `0270L–PEEPR–2/09` §19 note 2 p.10: *"Write Protect state will be activated at end of write even if no other data is loaded."* STACK identifies this as the cleanest citation because its note→flowchart-terminal-box mapping is unambiguous (terminal box `ENTER DATA PROTECT STATE / WRITES ENABLED(2)` references exactly note 2).
- Microchip **DS20006432B** (AT28C64B) §6.18 note 2 p.16: same sentence.
- Microchip **DS20006432B** §6.6.2 p.10: *"After writing the 3-byte command sequence and waiting `t_WC`, the entire AT28C64B will be protected against inadvertent writes."*

ARCHITECTURE's P-1 ("the lock body must be `3-cycle prefix → ≥1 data byte → tWC`") is an **inference** from the correct observation that `AA-55-A0` is dual-purpose, with no note-2 citation attached. It reasons "SDP-enable *is* a protected page write, therefore it needs a page." The datasheets contradict the "therefore": the internal write cycle triggered by the third command load is itself the "end of write" that note 2 refers to.

Two corroborations that this is not a 2-vs-2 split. **PITFALLS agrees with STACK** — it quotes AT28C256 §6.11 note 2 with the same wording and states flatly (Pitfall 2, "How to avoid"): *"So `lock` = the 3 loads + wait `tWC`, and **nothing else**"*, adding that a dummy data byte both modifies user data and drags the `pulse_delay`-aware `memory_set_data` path into the `tBLC` window. **FEATURES also quotes note 2** ("even if no other data is loaded", §0.3) and describes the payload branch as "0–64 data bytes" — its "≥1 data byte" framing in the §1 F1 row is inconsistent with its own citation. So the documentary evidence is 3 documents + 3 streams' own quotations against one uncited inference.

STACK additionally warns that the in-tree `AT28C256.pdf` has a copy-paste error in its notes 2/3 that makes it misleading on exactly this point — which is the likely origin of ARCHITECTURE's reading, and the reason doc0270 is the citation of record.

**Consequences for the roadmap.** (i) The lock body is a sequence, not a sequence-plus-write; a read-modify-write-identical body is *not* required and should not be planned. (ii) "Just wiring up the existing table" does **not** ship a no-op *for this reason* — but it still ships a no-op **for the CONFLICT-1-independent reason that `flash_util_byte_flipping` inhibits `/WE`** (finding 1). ARCHITECTURE's conclusion "a roadmap that just wires up the existing table ships a no-op" survives; only its mechanism was wrong. (iii) `FLASH_ENABLE_WRITE_PROTECTION ≡ FLASH_ENABLE_WRITE` remains **datasheet-correct duplication**: `AA-55-A0` with no payload locks, and with a payload is the write-while-protected prefix (AT28C64B §6.6.2). The name is the only discriminator; the `0052c42` dedup would destroy real semantics. All four streams agree on this and it must not be re-litigated.

**Residual experiment, for completeness.** The documentation settles it, so no experiment is required. If positive proof were ever demanded, the only thing that could supply it is silicon: emit `AA-55-A0` with no payload on an AT28C part, wait `t_WC`, then attempt an unprefixed byte write to a scratch address whose target value differs from its current value; unchanged ⇒ lock latched. That is not available this milestone.

### CONFLICT 2 — command surface: new `CMD_*` bytes, or `ctrl_flags` bits?

**VERDICT: BOTH — adopt ARCHITECTURE's hybrid. Two new `CMD_*` at the free slots 9/10 for the standalone lock/unlock operations, PLUS two high `ctrl_flags` bits (`0x100` `FLAG_SKIP_SDP_UNLOCK`, `0x200` `FLAG_SDP_RELOCK`) for the write-path modifiers. Confidence HIGH on the mechanism, MEDIUM on the risk judgement.**

Why ARCHITECTURE outweighs STACK: STACK's flags-only recommendation cannot satisfy a locked milestone target. `PROJECT.md:42` requires SDP disable to be *"invocable in its own right, not only as an invisible side effect of `write`."* ARCHITECTURE's disqualifying argument is mechanical, not aesthetic: `CMD_WRITE` routes to `_process_incoming_data` (`eprom_operations.cpp:23-26,58-107`), which pulls data chunks from the host. A flag on `CMD_WRITE` cannot be invoked without a payload, and a dataless "write" requires the host to immediately send `DONE` — **which is precisely the desync shape that produced the `0xA4` "Empty input" regression** already in this project's incident record. STACK does not address that path; it reasons only about wire legality. Wire legality is necessary, not sufficient.

Both streams identify the same trap and agree on it: `firestarter.cpp:79`'s `if (handle->cmd < CMD_DEV_ADDRESS)` guard means `cmd` 9/10 parse the full memory command but **never reach `configure_memory`**, leaving `firestarter_operation_main` NULL → `MSG_ERR_UNKNOWN_CMD` (`firestarter.cpp:244`). ARCHITECTURE adds the finding that decides the risk question: the guard is `#ifdef DEV_TOOLS`-gated, so **a non-DEV_TOOLS build already behaves differently** — 9/10 would reach `configure_memory` there. That is a latent build-config divergence in a safety-relevant admission gate that exists today, independent of v1.22.

**Is touching the guard acceptable risk? Yes — replacing an ordinal comparison with an explicit `is_memory_cmd()` predicate enumerating `{READ, WRITE, ERASE, BLANK_CHECK, CHECK_CHIP_ID, VERIFY, SDP_UNLOCK, SDP_LOCK}` is a small, fully enumerable, native-testable refactor that *removes* an existing divergence.** It must carry its own test asserting the predicate accepts exactly the pre-existing set plus the two new commands, **identically with and without `-D DEV_TOOLS`** (ARCHITECTURE §7 item 10).

Constraints carried from both streams: do **not** renumber `CMD_DEV_*` to make room at 7/8 (a stale host's `cmd:7` "set address" would land as SDP-lock on new firmware — AP-5/T-3). `ctrl_flags` is `uint32_t` (`firestarter.h:96`) parsed via `extract_long`/`simple_strtoul` (`json_parser.c:471-473`), so bits ≥ `0x100` are wire-legal today with no protocol change — but audit host display sites for uint8 truncation, and note the cosmetic namespace collision with `constants.py`'s existing `CTRL_VPP_VPE_DROP_ENABLE = 0x100` (a control-register bit, different namespace). Add `default:` → `MSG_ERR_NOT_SUPPORTED` to `configure_eeprom28c`'s switch (`eeprom_28c.cpp:39-47`, currently no default) plus a host pre-wire refusal, closing ARCHITECTURE's T-2 silent-finish trap in both places. If the Leonardo flash budget bites (3348 B headroom, 88.3 % at 25324/28672 B measured 2026-07-27), the first lever is collapsing to one `CMD_SDP` + a selector flag bit.

### CONFLICT 3 — the per-part SDP address question

**VERDICT: STACK is right on truncation; PITFALLS is right that a distinct, surviving gap exists. Both, on different axes. Confidence HIGH — this is arithmetic and it was checked.**

Truncation, verified: `0x5555 & 0x1FFF == 0x1555` and `0x2AAA & 0x1FFF == 0x0AAA` — **exactly** AT28C64B's documented `1555h`/`0AAAh` (DS20006432B §6.18/§6.19). The same holds downward: `& 0x3FFF` → `0x1555`/`0x2AAA`; `& 0x7FF` → `0x555`/`0x2AA`. This is not a coincidence to be tabulated — `0x5555` and `0x2AAA` *are* the alternating bit patterns, so truncation to any width lands on the family's documented pair by construction. AT28C010's "A14–A0" address-format note (doc0353 rev `0353G–PEEPR–10/06` §19) is the same phenomenon from the other side: upper lines are don't-care. **Verdict: do NOT add per-part SDP magic-address tables. 84 rows of redundancy plus 84 chances to typo an address into a wrong-pin write.** PITFALLS' own text concedes the arithmetic ("work on smaller parts *only* because `0x5555 & 0x1FFF == 0x1555`") and calls it "accidental correctness"; the datasheet cross-check shows it is *structural* correctness, which is a materially different risk profile. STACK verified the precondition by executing the real host code: `DIP28_28C64` declares pins 1 and 26 `nc-pin` and maps only 13 address lines, so chip A13/A14 genuinely do not exist.

**The A16–A18 gap is real, distinct, and survives.** `fu_flash_fast_address` writes **only** `LEAST_SIGNIFICANT_BYTE` and `MOST_SIGNIFICANT_BYTE` (`flash_utils.cpp:62-67`). A16/A17/A18 live in the control register (`CTRL_ADDRESS_LINE_16/17/18`) and are never touched by the sequence — they retain whatever the previous operation left. For the **18 chips at 64 KB–512 KB** on `DIP32_28C512_EEPROM` (`CAT28C512`, `AT28C010/LV010/MC010`, `M28010`, `X28C010`, `WE128K8/256K8/512K8`, `CAT28C020/040`, `AT28MC020`, `AT28C040`) the effective address is `<stale A16..A18> | 0x5555`. That is upward, not downward, so truncation says nothing about it. **However:** this gap is a *symptom of the same root cause as finding 1* — the bypass of `mem_util_remap_address_bus`. Routing the `0x0D` command bytes through `handle->firestarter_set_data` (= `memory_set_data`, `memory.cpp:228-306`) applies the full remap including the upper address register, so **the Phase-117 fix closes both the `/WE` inhibit and the A16–A18 gap in one change.** The residual after the fix is narrower and honest: *the SDP magic addresses for the 1 M/2 M/4 M parts have not been datasheet-verified* (STACK marks AT28C040 UNVERIFIED, datasheet not read), as have AT28C16/AT28C04 (24-pin). Handle that by recording UNVERIFIED per size band rather than by refusing 18 chips — PITFALLS' "restrict to ≤32 KB or refuse" is over-mitigation once the remap fix lands.

Also note the third, separate `DIP28_28C256` defect STACK found and PITFALLS did not: A14 sits on bus line 15, so `0x5555` reaches the chip as `0x1555` even ignoring `/WE` — two defects stacked on those 12 chips. Remap fixes it. And the `DIP24_2816` caveat: it has **no** `static-high-pins` key in `pinouts.json` (unlike `DIP24_2716`/`DIP24_2732`, both `[24]`), so `static_high_mask == 0` and VCC (bus line 13) is not force-driven for those 19 chips. The remap fix does **not** address that — treat it as a separate named finding, confirmed against the shield schematic before acting.

## Key Findings

### Recommended Stack

**No new technology, zero new third-party dependencies on either side of the wire.** Every mechanism v1.22 needs is in-tree: the `byte_flip_t` table type (`flash_utils.h:19-22`), the `uint32_t ctrl_flags` wire field, the codegen'd message catalog, the Click `dev` group, the v1.21 destructiveness gate, and a native register-recording stub. The "stack additions" are five small additive integration points plus one correctness fix. `click` and `rich` are already imported in `cli_handlers.py:29-32`; the wire encoding is stdlib `json`.

**Core technologies (all already in-tree — nothing to install):**
- **PlatformIO + Arduino AVR** (pinned in `firestarter/platformio.ini`) — firmware build for uno / leonardo / uno328pb. SDP work is ~50 lines of C; the constraint is the flash ceiling (88.3 %, 3348 B free, measured `pio run -e leonardo` 2026-07-27), not the toolchain.
- **Unity via `pio test -e native`** — host-side register-trace tests, no board needed. **The only validation path available with no AT28C silicon.** Requires the recording-stub capability upgrade (finding 5).
- **Click + rich `Confirm.ask`** — CLI surface and the TTY safety confirm, reusing the exact v1.21 `dev test` gate pattern (`cli_handlers.py:1833-1840`, with `_is_interactive` at `:1719-1726` as the patch point — `CliRunner.invoke` replaces `sys.stdin`, so patch the helper, not `isatty`).
- **`tools/catalog/messages.toml` + `codegen.py`** — the *only* edit locus for new message IDs. Free: INFO `0x44`–`0x50`/`0x5E`+, WARN `0x86`+, ERROR `0xBD`–`0xBF`. **`0xAE` is free but was deliberately retired in v1.20 — do not reuse.** Never hand-edit `messages.h`/`messages.py`; CI has a drift gate.

**Lockstep contract:** new `FLAG_*`/`CMD_*` values change in the same commit pair (`firestarter.h:34-68` ↔ `constants.py:54-99`), with `tests/test_revision_constants_parity.py` extended. Validate `ruff check` + `ruff format --check` against CI's py3.9/3.11, not the devcontainer's 3.12. Branch base: v1.21 **is** merged to `beta` in both sub-repos, so v1.22 forks off `beta` per standing policy — but verify with `git` at execute time anyway (every prior base exception began as a confident assumption).

### Expected Features

**Must have (table stakes):**
- **The `/WE`-collision fix** — not on any original feature list, and now the milestone's first deliverable. Without it nothing else is testable.
- **Honest completion proof** replacing the inverted `(0x5555, 0x20)` read-back. Preference order: (1) a `t_WC` wall-clock wait, `delay(10)`, which is the datasheets' own instruction and is provably correct with no read at all; (2) toggle-bit I/O6 polling (AT28C256 §6.16/§6.17 pp.19-20 — note 3 p.20: *"Any address location may be used but the address should not vary"*), the only in-band signal valid for a command sequence with no stored data; (3) for the *ordinary write* path only, DQ7 data polling — `flash_util_verify_operation` (`flash_utils.cpp:30-51`) already implements a correct DQ7-only double-read 150 ms-bounded poll and is not used by `0x0D` at all, a reuse candidate. Do **not** try to salvage the `0x5555`/`0x20` read-back; it has no valid form.
- **SDP-enable (lock) wired in firmware** — the declared milestone goal. Table exists with zero callers; needs a command arm + `t_WC` wait; **no data payload** (CONFLICT 1); does not touch array data, so it is non-data-destructive.
- **SDP-disable (unlock) as a standalone operation** — *exactly and only* what gh#12's reporter asked for (he built a second Arduino to run the disable algorithm once, then used firestarter normally).
- **Today's auto-unlock becomes observable** — one line before and one after the sequence, never inside (finding 10). The cheapest, highest-value item in the milestone.
- **Honest "SDP state is not readable on this family" reporting** — reusing the v1.21 `NOT_MEASURED` discipline (`diagnostic_report.py:59`, D-03) with the same single-substitution locus. Three fields, not one boolean: `sdp_command_issued` / `sdp_sequence_ack` / `sdp_state_after` (default: the honest refusal).
- **Native trace harness with a RED baseline** — the oracle. See finding 5.
- **gh#11 / gh#12 closeout** — best-effort, no requirement depends on a reply. The re-test ask on gh#11 was already posted 2026-07-27 (meta `ae6bfbe`), which also asked whether that chip ever had SDP enabled; **gh#12 has had no response**, so the community-ask scope is gh#12 plus following up gh#11.

**Should have (competitive):**
- **`--skip-sdp-unlock`** opt-out on `write`. Neither minipro nor flashrom documents an opt-out of auto-unlock.
- **`--sdp-relock`** post-write re-lock, **opt-in only**, gated `if verify passed` — an unconditional step in a conditional pipeline is the Phase-112 `if destructive:` lesson repeating (fix `7a74fcc`). A re-lock after a failed verify strands the user with a locked chip they cannot retry on.
- **First-class "cannot confirm"** reporting. flashrom and minipro both surface nothing; this is the clearest differentiator in the milestone.
- **The `dev test` phantom-erase fix** (finding 8) — small, and load-bearing for the closeout's value.

**Defer (v1.23+):**
- `dev test` SDP step — perturbs `dedup_fingerprint` for all `0x0D` chips and pulls the locked D-03/D-04 ladder + orchestrator-only AST gate into a milestone with no silicon. Triples the blast radius.
- Write-probe SDP *inference* — the only real state observation available, but destructive and an honest-labelling design problem.
- `lock-status` + hand-curated protection table — **out of scope by operator decision**, stays planted at `.planning/seeds/lock-status-command-hand-curated-protection-table.md`.
- The datasheet 6-byte software chip-erase for `0x0D` — a real gap (it would close No-Hazmats' gh#12 comment) but an *erase* feature riding an *SDP* milestone, and it needs `OE = V_H = 12 V`, the T-93-CANERASE hazard class.
- SDP handling for AT29C / SST39SF / W29EE families — multiplies the no-silicon problem across settled bench evidence.

**Anti-features (do not build):** auto-relock by default (unverifiable + manufactures the gh#12 bug for the next user); "leave it as you found it" as a default (physically unimplementable — restoring an unreadable state is a guess wearing a promise); populating `chip_id_value` for AT28C (finding 7); a generic `locked` DB boolean (`lockable-proms.md` closing rule); fail-loud-by-default on a locked chip; deleting `FLASH_ENABLE_WRITE_PROTECTION`; a `--force` path that widens *which chips* a lock can reach.

**Auto-unlock policy — FEATURES recommends option (d):** auto-unlock stays the **default**, becomes **reported**, gains an explicit **`--skip-sdp-unlock` opt-out**, with `--sdp-relock` opt-in only. Rationale: the attractor should be the state the user can recover from; unprotected-attractor is self-evidencing (the write+verify that just succeeded *is* the proof) while a re-lock claim can never be substantiated on this family; unprotected is also the factory state (*"the AT28C256 is shipped with SDP disabled"*). Precedent is split — minipro's older CLI re-locks by default (`-P` = *do not* enable write-protect) while flashrom auto-unlocks silently with no documented opt-out, and minipro **reversed its own polarity between forks**, so there is no industry polarity to appeal to. **Findings 1/3 collapse the backward-compatibility objection to (d) and to any change:** if AT28C writes already abort at INIT, there is no working behaviour to preserve and the cost of changing the default is ~zero. Naming candidates surfaced: `firestarter dev sdp <chip> <enable|disable>` (FEATURES, on the maintainer's own "don't overshadow more common functionality" constraint from gh#12) versus top-level `lock`/`unlock` (STACK, on the flat `read`/`write`/`erase` grammar). FEATURES' `dev`-group placement has the stronger warrant: it cites the maintainer's constraint verbatim, and `sdp` is the datasheet's own term — family-honest, and it leaves `lock-status` free for the out-of-scope seed. Flag naming follows the in-tree rule: `--skip-X` skips a *chip-state-modifying operation*, `--no-X` skips a *check* (v1.16 HARD-01 / Phase 92) — hence `--skip-sdp-unlock`, not `--no-sdp-unlock`.

### Architecture Approach

Keep the SDP work **scoped to `eeprom_28c.cpp`; do not promote it to shared code.** The shared implementation is the broken one, so extending `flash_util_byte_flipping` to serve both families would change the emitted register stream for the bench-proven `0x05`/`0x06` chips — the wrong direction of risk. Leaving `flash_utils.{h,cpp}`, `flash_5v_page.cpp` and `flash_nor_unlock.cpp` byte-untouched makes the non-regression argument trivial. The dedup is worth ≤48 B against 3348 B of headroom; not worth it. `handle->protocol` remains the sole dispatch axis (`memory.cpp:42-113` untouched); `handle->cmd` remains the operation selector *inside* a handler, extended exactly as v1.13 Phase 74 extended `flash_5v_page.cpp:54-57` — so the hybrid command surface does **not** create a second dispatch axis, and does not violate the v1.20 invariant.

**Major components:**
1. **`eeprom_28c.cpp` — a new `0x0D`-local, remap-aware command emitter** built on `handle->firestarter_set_data` (= `memory_set_data`, `memory.cpp:228-306`), the function `eeprom28c_write_execute:123` already uses for page data. It applies remap + `WRITE_FLAG` + `/CE` pulse. ~10 lines; no new primitive. `pulse_delay` is already 0 for `0x0D` (`eeprom_28c.cpp:39-40`) so per-byte cost stays ~5–10 µs, an order of magnitude inside even the 100 µs floor. Plus `EEPROM_SDP_ENABLE[]` co-located beside `EEPROM_SDP_DISABLE` (`:26-33`), and a `default:` arm.
2. **Command surface** — `CMD_SDP_UNLOCK 9` / `CMD_SDP_LOCK 10` on the proven `op_execute_simple_operation` rail (`operation_utils.cpp:58-60`, `_single_step_operation_callback:271-295`), the archetype `eprom_erase`/`eprom_check_chip_id`/`eprom_blank_check` all ride (`eprom_operations.cpp:34-55`). Set **only** `firestarter_operation_main`; leave `init`/`end` NULL so those phases are skipped without an ACK round-trip. Plus `is_memory_cmd()` replacing the `firestarter.cpp:79` guard, and the two high `ctrl_flags` bits.
3. **Host surface** — `EpromOperator.sdp_lock/sdp_unlock` copying `erase_eprom`'s shape verbatim (`eprom_operations.py:1628-1652`); CLI command(s) behind the v1.21 confirm + `-y` + the SAFE-04 absent-chip hard-fail; `write --skip-sdp-unlock` / `--sdp-relock`; `constants.py` `COMMAND_*` **plus mandatory `COMMAND_NAMES` entries** (`eprom_operations.py:301` `KeyError`s otherwise). Everything routes through `resolve_chip` + `convert_to_programmer` + an `EpromOperator` method; never hand-assemble a command dict.
4. **Trace oracle** — `HOST_STUBS_RECORD_BUS` (`host_stubs_common.inc:54-80`) extended behind a **new opt-in flag** so the existing suites stay byte-exact, recording `rurp_write_data_buffer` bytes and `/CE`//`/OE` edges **into the same ordered stream** as register writes (without ordering, `(addr, data)` pairing cannot be reconstructed).
5. **SDP-capability resolution — host-side, code-level, zero DB change.** ARCHITECTURE proposes a new `firestarter/sdp.py` three-valued resolver (`SDP_CAPABLE`/`SDP_ABSENT`/`SDP_UNKNOWN`, `UNKNOWN` refuses), in the shape of the existing in-code family tables `_SRAM_PROTO_IDS` (`eprom_operations.py:1656`) and the D-30 pre-wire short-circuit (`:1661-1676`). A DB field is an anti-pattern: `infoic.xml` **cannot** supply it (pinned negative result, `.planning/notes/infoic-xml-protection-flags-research.md` — `W29C020C` and `W29EE011` carry identical flags `0x0040c078`), it would resurrect the override stack v1.16 deleted, and it competes with `support_status`, whose single-write-locus is machine-guarded. **Caution:** a curated 84-row partition is itself a hand-curated protection table — adjacent to the out-of-scope seed. Recommend the minimal version (refuse the 2 FRAM parts and flag the pre-SDP class) rather than a full per-family audit, and record the boundary explicitly at plan time.

### Critical Pitfalls

1. **The false-success trap** — a success condition of the form `get_data(<command address>) == <command byte>` is anti-correlated with success. Delete the idiom; do not "improve" it. Warning signs: a test that satisfies a poll by scripting the expected byte into a call-ordered mock — which is exactly what `test_eeprom28c_chip_id.cpp:104` does (`s_mock_bytes[2] = 0x20; /* satisfies eeprom28c_wait_for_write(0x5555, 0x20) */`), cementing the defect as expected behaviour. Retire the address-blind scripted mock; make `mock_get_data` address-keyed.
2. **The harness cannot see what it claims to prove** — finding 5. The strongest existing assertion is `test_val_5v_page.cpp:200`, address-MSBs only. Minimum bar: assert the full ordered `(LSB, MSB, data, CE-pulse)` tuple stream as a literal expected array per sequence, plus first-class negatives — unlock-table-mutated-to-`0x10` goes RED, lock-table-swapped-for-write-prefix goes RED, a planted `LOG_` inside the window goes RED, `protocol != 0x0D` reaches `configure_not_implemented()`/`0xBB`.
3. **One nibble from a chip-erase** — `FLASH_ERASE` is `AA-55-80-AA-55-`**`10`**; `EEPROM_SDP_DISABLE` is `AA-55-80-AA-55-`**`20`**. Add a native test pinning each table's terminal byte and asserting the two are not the same object. Mitigating (do not lean on it): AT28C chip-erase requires `OE = V_H = 12 V`, a rail `0x0D` never routes — but the class spans 20+ manufacturers whose erase gating may differ.
4. **Timing versus observability, in direct tension** — finding 10. Budget to **100 µs** (Xicor/Catalyst floor; 8 XICOR + 11 CATALYST chips are in class), not Atmel's 150 µs. Introduce a named `AT28C_TBLC_MAX_US = 100` constant cited at every call site — constants get grepped, physics in a datasheet does not. Add a source-scan test with a planted `LOG_` fixture. Measure with `micros()` and log *after* the sequence: **this is one of the few v1.22 claims provable without an AT28C**, since the duration is a property of the host code path with any chip in the socket. `noInterrupts()` bracketing only after measuring, and mind the Leonardo USB-CDC consideration.
5. **Misidentification with no identity gate to catch it** — finding 7. Combined with a *standalone* op that skips `write_init` (and hence the blank check), the sole remaining identity signal is "the user typed a chip name." A user with an SST39SF040 seated who types the lock command gets a JEDEC-prefixed sequence delivered to a different command set. Mitigations: firmware `protocol == 0x0D` scoping with a fail-closed default; never expose a generic byte-flip-sequence primitive on the wire; `resolve_chip` on the path (v1.21 SAFE-01, CI-enforced); `--force` narrowed to its one existing meaning (ERROR→WARNING on ID mismatch) and for *lock* prefer refuse-over-warn — the v1.16 Phase 89 CR-01 regression was exactly an ERROR→WARNING slip the golden traces missed.
6. **Irreversibility, correctly scoped** — AT28C SDP is fully software-reversible; say so plainly, because over-warning invites guards that block legitimate use. The genuinely irreversible neighbours (W29C020C boot-block lockout, W29C040's permanently locked first-16K block per v1.17 RCA, PPB/password/OTP families) are in *adjacent buckets*, and misidentification is the only route to them.

## Implications for Roadmap

### The reconciled spine — ONE recommendation, Phases 116–122

ARCHITECTURE proposed 116–121; PITFALLS proposed 116–122 (ground truth → harness → firmware primitives → wire → host → observability/`dev test`/docs → close). ### Phase Ordering Rationale

- **Oracle → fix → observe → feature → host → integration → close.** The harness leads because it is the only oracle available with no silicon, and because it has zero production-code risk. The fix follows immediately because nothing else is testable until unlock reaches silicon, and because it is where the RED→GREEN proof — the milestone's headline evidence — is realised.
- **Firmware leads the host, unambiguously.** 116–119 and 121's firmware half are individually half-landable and backward-compatible; 120 is the single host phase that closes the wire contract. The reverse order silently ignores the user's opt-out flag.
- **Observability before lock, fix before observability.** Advertising a sequence that does not reach silicon is worse than silence; and lock is the only new *state-mutating* capability, so it lands on top of proven observability rather than under it.
- **The `dev test` fix precedes the closeout, not the milestone.** It is ~10 lines and it is the difference between usable community evidence and a spurious `community-fail`.
- **Branch/base and submodule checkout are the first executing phase's setup step**, not an assumption.

## Findings That Must Not Be Dropped

1. **The shipped SDP-disable almost certainly never reaches silicon** — `fu_flash_fast_address` bypasses `mem_util_remap_address_bus`; `/WE` inhibited on ≥1 write on all 84 `0x0D` chips per the per-pinout table. v1.22 opens with a FIX, and it yields the software-only deliverable: a native register-trace test RED today, GREEN after.
2. **The `eeprom28c_wait_for_write(handle, 0x5555, 0x20)` success check is INVERTED**, not weak — the datasheets state command-sequence data is not written to the device.
3. **gh#11/gh#12 may be LIVE defects, not stale 2024 reports.** This reverses the kickoff framing and must reword the planned closeout comments. PITFALLS supplies a **separate candidate root cause for gh#11**: `eeprom28c_write_execute` polls only **1 byte in 64** (page end or last byte), and on a protected chip the datasheet says an unprefixed write starts the timers and writes nothing — so the poll reads back the *old* value, which passes whenever old == new (e.g. `0xFF` in a mostly-blank image). That is a complete, still-shipping mechanism for *"accepts the write, only part of the image burned"* — **a better fit for gh#11's symptom than SDP.** Do not write a requirement treating "gh#11's symptom disappears" as proof the SDP work landed; three candidate causes are in play (SDP, the 1-in-64 poll, and the long-gone byte-at-a-time path behind the 339 s).
4. **`FLASH_ENABLE_WRITE_PROTECTION ≡ FLASH_ENABLE_WRITE` is datasheet-CORRECT** — same silicon command, two intents (lock with no payload; write-while-protected prefix). The name is the only discriminator; the tempting dedup (`0052c42`) destroys real semantics. Retain both and add a header comment saying *why*, to defuse a future "dead code" cleanup. Consider a name that makes intent unmissable.
5. **The native harness cannot currently distinguish lock from unlock from erase** — `rurp_write_data_buffer` is a no-op stub (`host_stubs_common.inc:98`) so command bytes are never recorded, and all four sequences walk the same addresses. `0052c42` proved this by swapping tables and reporting "22 tests PASS (zero-diff)". **The harness capability upgrade must PRECEDE any firmware behaviour change** or every trace claim is hollow.
6. **`0x0D` membership is not an SDP predicate** — the 84-chip bucket includes 2 FRAM parts (`CYPRESS FM28V020`, `FUJITSU MB85R256H` — no SDP, no write cycle) and ~19 pre-SDP `2804`/`2816`/`2817`-class parts, all of which today receive 6 magic-address writes anyway.
7. **All 84 `0x0D` chips carry `chip_id_check: false`** (`chip_id_value: "0x00000000"`), and `database.py:399` only emits `chip-id` when `chip_id_check` is truthy, so `eeprom_28c.cpp:95`'s `if (handle->chip_id > 0)` never fires. The A9-12V identity gate and its D-08 identity-before-unlock ordering are **dead in production** (458/746 chips DB-wide *do* have an ID check — this class has zero). **Any safety argument resting on "a mismatch leaves the chip protected" is currently void.** Populating `chip_id_value` would be an anti-feature: those 64 bytes are user-writable identification space, not a factory signature, and read `0xFF` on a virgin part — activating the check would make every factory-fresh AT28C fail identity across 84 entries.
8. **v1.21 `dev test --destructive` derives an `OP_ERASE` the `0x0D` handler cannot serve** — `database.py` sets `FLAG_CAN_ERASE` for `electrical.type ∈ {EEPROM, Flash/EEPROM}`, `derive_plan` plans `OP_ERASE`, `configure_eeprom28c` has no `CMD_ERASE` case → `operation_main` NULL → returns with `response_code` still OK. A step that does nothing and reports OK, then auto-tags `ladder_state = "community-fail"` — poisoning the gh#11/#12 closeout. Fix before the comments go out.
9. **Corrections to the briefs:** **W29EE has zero entries on `0x0D`** (`W29EE011`/`W29EE012` are AT29C-class page-program flash on `0x05`/`0x06`) — do not pull it into scope. **`page-size` does NOT exist on the wire**: `constants.py:107-111` claims "Firmware sync: json_parser.c (key_page_size)" and that comment is **false** — `json_parser.c:67` has no such key and the firmware silently discards it. Do not plan against it. (Related, deferred: `PAGE_SIZE 64` is hard-coded at `eeprom_28c.cpp:19` while AT28C010's page is 128 B and AT28C040's is 256 B, affecting 18 chips — the same class as the v1.17 W29C040 bug. Real, adjacent, and an explicit named deferral, not silence.)
10. **Timing:** the `tBLC` budget is **100 µs** (Xicor/Catalyst parts in class), not Atmel's 150 µs — and **observability is the likeliest way to blow it**, since one COBS-framed log at 250 kbaud is ~320–640 µs, 3–6× the entire budget. - **`DIP24_2816` has no `static-high-pins: [24]`** (unlike `DIP24_2716`/`DIP24_2732`), so `static_high_mask == 0` and VCC (bus line 13) is not force-driven for 19 chips. The remap fix does not address this. Confirm against the shield schematic before acting; treat as a separate named finding, possibly a FUT.
- **`PAGE_SIZE 64` vs AT28C010's 128 B / AT28C040's 256 B** — 18 chips, same class as the v1.17 W29C040 bug. Recommend an explicit named deferral, and note that "reuse the existing `page-size` wire field" is not available (finding 9), so in-scope would mean real lockstep work.
- **XICOR `X28C` per-family magic-address audit** — 8 XICOR entries; addresses reportedly differ on some variants. Datasheet-verifiable, not silicon-gated. Record UNVERIFIED per family rather than inferring.
- **`is_flag_set` on bits `>0x80`** — audit host and firmware display sites for uint8 truncation before relying on `0x100`/`0x200`.
- **Minimum-firmware capability gate** — `_validate_firmware_version` only enforces `major >= 3`; decide in Phase 120 whether the host should refuse SDP commands below a known-good FW version or accept the `UNKNOWN_CMD` failure as sufficient.
- **The capability-resolver scope boundary** — a curated 84-row SDP partition is adjacent to the explicitly out-of-scope `lock-status` protection table. Recommend the minimal version (refuse the 2 FRAM parts, flag the pre-SDP class) and record the boundary at plan time so the seed is not squatted on.
- **Gate/`default:`-arm flash budget** — whether defence-in-depth `default:` arms in the non-`0x0D` handlers are worth their bytes against 3348 B of Leonardo headroom. Decide with a measured delta, and record as accepted debt if skipped.
- **AT28C 6-byte software chip-erase** — a genuine `0x0D` gap that would close No-Hazmats' gh#12 comment, requiring `OE = V_H = 12 V` (T-93-CANERASE hazard class). File as a follow-up anti-feature-for-now, explicitly.
