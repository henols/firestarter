# Milestone v1.41 Audit — Verification Moves to the Host

**Audited:** 2026-09-21
**Status:** `gaps_found` — 14 of 34 requirements satisfied. Two phases of six delivered, both verified `passed`. Four phases (204–207) were never planned, so 20 requirements are orphaned.

## Why this audit reads `gaps_found`

**The milestone is mid-flight, not finished.** `STATE.md` reads `current_phase: 204`,
`status: planning`, `stopped_at: "Phase 203 complete, ready to plan Phase 204"`, `percent: 33`.
This audit was run four phases early. The `gaps_found` verdict is therefore a statement about
*where the milestone is*, not a defect report against what was built — the FAIL gate fires because
20 requirements are unsatisfied, and they are unsatisfied because nobody has done them yet.

**Nothing is wrong with the delivered half.** Phases 202 and 203 both verified `passed`
(8/8 and 5/5 must-haves), the integration checker found zero blockers across eight seams and five
E2E flows, and the live app suite is green at **2308 passed, 36/36 snapshots** (re-run by this audit,
not quoted from a report).

## Milestone Goal

The Arduino stops deciding whether a chip is blank or matches an image. The host reads the chip and
compares in Python — one comparison implementation, a named diagnosis instead of a single address,
and the flash the removed command surfaces were costing.

## Outcome So Far

The **host half is done and standing on its own.** `compare.py` is the single streamed comparison
engine, import-pure (`{__future__, dataclasses}` only), and `verify`, `blank`, the pre-write blank
guard and `write --verify` all genuinely route through it — the integration checker confirmed there
is no second comparison implementation anywhere. `write_blank_guard.py` is a fail-closed pure
predicate pinning `GUARDED_PROTOCOL_IDS` to `{0x06,0x07,0x08,0x0B,0x10}` with a test proven RED on
both narrowing and widening.

The **firmware half has not started**, and that is the deliberately safe resting point rather than a
half-finished removal. The milestone's stated design — *"ordering is a safety property, not a
preference: the host gains each capability before the firmware loses it"* — means the current state
is the intended redundant one: the host now never sends ordinal 4 or 6, while the firmware still
carries `CMD_VERIFY` (6), `CMD_BLANK_CHECK` (4) and every in-algorithm pre-flight blank check.
**Both sides check. At no point is there a window where neither does.** The integration checker
verified the firmware is byte-for-byte untouched with no partial removal, no dead branches and no
orphaned includes.

**What stopping here costs:** none of the flash reclamation — the milestone's stated "why now" on the
flash axis — has happened, because that is entirely Phase 205's work. And with REL-01 unmet, neither
repository carries `3.1.0b1`, so none of the delivered host work is shippable or publishable under
this milestone's version.
