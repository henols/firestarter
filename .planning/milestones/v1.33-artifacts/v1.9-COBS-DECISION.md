**Milestone:** v1.9 Read-Bug RCA + Cleanup (evaluation) → **v1.10 Serial Transport Hardening (implementation)**
**Decided:** 2026-06-01
**Revised:** 2026-06-01 — verdict flipped DEFER → **ADOPT** (see §2.0 Revision Note)

## 1. Context

### 1.1 The Serial Data Path (4 framings, one 250000-baud line)

All serial traffic on the Firestarter data path rides a single 250000-baud UART connection.
Four distinct framings coexist on that line. [VERIFIED against current code, 2026-06-01]

| Direction | File | Framing |
|-----------|------|---------|
| host→fw JSON command | `firestarter.cpp:162-172` | ASCII JSON; firmware peeks for `{`, discards non-`{` bytes |
| host→fw data block | `rurp_serial_utils.cpp:44-79` | `[len_u16 big-endian][xor_checksum][payload]`, 2 s timeout |
| fw→host data block | `rurp_serial_utils.cpp:81-93` | same `[len_u16][xor][payload]` structure |
| fw→host log/telemetry | `rurp_serial_utils.cpp:92-224` | `[0xAA55AA55][len_u16][id][params][crc8][0x0A]` (magic preamble, D-05 CRC8-CCITT) |

Host-side demux lives in `serial_comm.py:_read_and_parse_lines` (GATE-1.8d ring-fenced).
CRC8-CCITT byte-level contract is pinned by the `test_messages` Unity suite.

**The root `CLAUDE.md` mandates `rurp_serial_utils.cpp` ↔ `serial_comm.py`/`frame_parser.py`
change in lockstep**; any framing change is a coordinated dual-repo milestone, not a fast-sized patch.

### 1.2 The Resync Motivation

The current length-prefixed data-block framing has one known robustness gap: if a `len_u16` byte
is corrupted in transit, the firmware reads the wrong number of payload bytes, the checksum
fails, and the stream stays desynced until the 2-second timeout fires. The host then retries
from the next JSON command. This desync-on-corruption behaviour is the robustness problem
COBS framing would solve: a `0x00`-delimited (or `0xC0`-delimited for SLIP) framing lets a
receiver skip to the next frame delimiter after any error, bounding corruption to one packet.

**However: no field report of this desync has been observed in the Firestarter bench session
corpus** (see Section 5 — Open Questions). The gain is real but currently theoretical.

### 1.3 Uno RAM Baseline (re-measured 2026-06-01) [VERIFIED]

```
pio run -e uno  →  RAM: [=======   ]  73.4%  (used 1503 bytes from 2048 bytes)
                    Flash: [=======   ]  69.7%  (used 22492 bytes from 32256 bytes)
```

Free RAM: **545 bytes** (2048 − 1503). Note: this is a slight decrease from the
2026-05-27 todo baseline (553 B free) due to Phase 44 read-timing knobs addition.
The existing `data_buffer[512]` is inside the 1503 B used total — it is the dominant
on-stack allocation during read/write operations. Any COBS-related second encode buffer
targeting 512 B of payload would require ≈ 514 B extra RAM, leaving only ~31 B free — a
stack-collision crash on the Uno. **This constraint is binding for every off-the-shelf
COBS library that builds the encoded form in a separate buffer.** [VERIFIED: live build]

### 1.4 The SERIAL_ON_IO `0x00` Bus-Aliasing Risk (Uno only) [VERIFIED]

On the Arduino Uno, PD0 doubles as both UART RX and data-bus bit 0. During programming
operations, `rurp_set_programmer_mode()` in `uno_rurp_shield.cpp` sets `com_mode = false`
and disables Serial, switching PD0 to output mode to drive the data bus.

The `rurp_log_id()` **strong override** in `uno_rurp_shield.cpp` (lines 85-89) gates ALL
frame emission on `com_mode`:

```cpp
void rurp_log_id(uint8_t id, const uint8_t* params, uint8_t param_count) {
    if (com_mode) {
        _firestarter_emit_frame(id, params, param_count);
    }
}
```

The same gate covers the wide variant `rurp_log_id_wide` (lines 92-97). [VERIFIED: live code review]

This means: while PORTD drives the data bus (programmer mode), no log/telemetry frame bytes
are emitted — including any COBS `0x00` frame delimiter that would otherwise appear in those
frames. The risk of a bus-driven `0x00` creating a false COBS frame boundary is therefore
gated by `com_mode` architecture, not by byte-level filtering. A future COBS adoption path
MUST prove that **the host side** also cannot send a `0x00` delimiter byte while the firmware
is in programmer mode (see Section 5 — Open Question 2).

### 1.5 CRC8-CCITT Integrity Layer [VERIFIED]

CRC8-CCITT (polynomial 0x07, seed 0x00, no reflection, no final XOR) exists in both repos:

- **Firmware:** `rurp_serial_utils.cpp` lines 109-131 — 256-byte lookup table in PROGMEM,
  comment "CRC8-CCITT (poly 0x07, seed 0x00)"; used in log/telemetry frame emission.
- **Host:** `frame_parser.py` lines 28-54 — `_build_crc8_table()` docstring pins
  "polynomial 0x07, seed 0x00, no reflection, no final XOR"; verified by `test_messages`.

Per D-05: **CRC8-CCITT is kept regardless of any COBS decision.** Any candidate framing
mechanism must coexist with this integrity layer. PacketSerial has no checksum — one of
the reasons it was rejected (D-01, below).

## 2. Decision

**ADOPT** a custom serial-framing + automatic-resync layer on the data path, delivered as a
dedicated milestone (**v1.10 Serial Transport Hardening**).
**REJECT** all off-the-shelf COBS/resync libraries (the Uno-fit constraints below are unchanged
and still disqualify every surveyed library — Section 4).
**DEFER** the framing-mechanism choice (hand-rolled streaming COBS vs SLIP vs other) to v1.10
plan research — see §2.0.
**KEEP** the existing CRC8-CCITT integrity layer intact under whatever framing is chosen (D-05).

### 2.0 Revision Note (2026-06-01) — why DEFER became ADOPT

The original verdict (DEFER-concept) rested on the absence of observed field desync defects
(§1.2). The milestone direction has since changed: the operator has elevated transport
hardening to a **prerequisite for the read-bug RCA**, not a robustness nice-to-have. The
reasoning is methodological — make the Arduino↔host serial transport *provably byte-exact*
so that serial corruption can be **ruled out as a confounding variable**, leaving any residual
read failures unambiguously attributable to the board/shield hardware.

Scope note on what this does and does not prove:
- COBS/resync guarantees the link delivers *exactly the bytes the firmware read off the parallel
  bus*. It cannot correct a byte that was already wrong before framing.
- **Bug A** (Modified Rev 0) was localised by Phase 44 to the *parallel read path* (read-strobe-
  causal) — downstream of serial. A hardened link mostly **exonerates** the transport there.
- The hardening bites most on the **uno328pb timeout + ~99 % 0xff-drift** instability (timeouts
  are transport-shaped) and on **Bug B (Rev 2.0)**, which is not yet root-caused. The v1.10
  phase hypothesis must be written so a green post-hardening re-test states clearly what it does
  and does not conclude.

This ADOPT verdict supersedes the DEFER line for execution-planning purposes. The library
rejection (below) and all Uno-fit analysis in Section 4 remain valid and carry forward as the
binding constraints on the v1.10 implementation.

### Rationale summary

Every off-the-shelf framing library surveyed fails at least one binding constraint (D-04: must
fit Uno RAM with no second ~512 B encode buffer; no CRC polynomial swap; no forced re-chunking
to ≤254 B). The viable path is therefore a **custom** layer — e.g. a hand-rolled ~70-line
streaming COBS encoder/decoder that fits the Uno, or the simpler 0xC0-delimited SLIP variant —
implemented as a milestone-sized coordinated dual-repo change (`rurp_serial_utils.cpp` +
`serial_comm.py` + `frame_parser.py` + `test_messages` contract), plus bench verification of the
`0x00` host-side timing guarantee (Section 5, Q2). The mechanism choice is deferred to v1.10
plan research; this doc commits only to *adopting a custom framing layer*, not to which one.

Decisions traceable here:
- **D-01**: PacketSerial — LOCKED REJECT (Section 4.1); not re-argued.
- **D-02**: Fresh comparative survey from scratch — Section 4.
- **D-03**: No preset candidate list — seven candidates enumerated in Section 4.
- **D-04**: Binding Uno RAM filter applied throughout Section 4.
- **D-05**: CRC8-CCITT kept — Section 1.5 and throughout Section 4.
- **D-06**: This file is the standalone ADR deliverable for COBS-01.

## 3. Consequences

### What stays the same

- All four framings on the serial data path remain byte-identical.
- CRC8-CCITT (poly 0x07, seed 0x00) on log/telemetry frames is unchanged.
- `rurp_serial_utils.cpp` ↔ `serial_comm.py`/`frame_parser.py` lockstep mandate is unchanged.
- `test_messages` Unity suite pins the frame contract as before.
- The 2-second timeout desync scenario remains a theoretical risk (no field evidence, Section 5 Q1).

### Future path if auto-resync becomes necessary

If the 2-second timeout desync is observed in field use (Section 5 Q1), the **recommended
future-milestone path** is the hand-rolled streaming COBS encoder/decoder:

- Firmware (~40 lines in `rurp_serial_utils.cpp`): streaming encode — emit COBS bytes
  directly to `SERIAL_PORT.write()` reading from `data_buffer` without materializing
  the encoded form; zero extra RAM; handles 512 B (Uno) and 1024 B (Leonardo) frames.
- Host (~30 lines in `serial_comm.py`): matching streaming decoder.
- Keep CRC8-CCITT and `len_u16` header; COBS replaces only the payload-boundary delimiter.

Reference snippet (for documentation only — NOT a production implementation):

```c
/* Zero-extra-buffer streaming COBS encoder for AVR.
   Reads data_buffer[0..N-1], emits COBS-encoded bytes to SERIAL_PORT.
   RAM cost: 3 local variables (~6 bytes stack). Works for any N. */
size_t i = 0;
while (i < N) {
    size_t run_start = i;
    uint8_t run_len = 0;
    while (i < N && data_buffer[i] != 0 && run_len < 254) { run_len++; i++; }
    SERIAL_PORT.write((uint8_t)(run_len + 1));
    SERIAL_PORT.write(&data_buffer[run_start], run_len);
    if (i < N && data_buffer[i] == 0) i++;
}
SERIAL_PORT.write((uint8_t)0x00);  /* frame delimiter */
```

**Alternative simpler future path:** SLIP / RFC-1055 byte-stuffing (Section 4.2). Uses
`0xC0` as delimiter (no `0x00` bus-aliasing concern at all), pure streaming, no 254 B
run-length constraint. If the `0x00` bus-aliasing host-side timing proof turns out to be
architecturally difficult (Section 5 Q2), SLIP avoids the entire problem.

## 4. Candidate Survey

This is a fresh from-scratch survey per D-02/D-03. Candidates are evaluated against the
Uno RAM binding filter (D-04) and the CRC8-CCITT coexistence requirement (D-05).
PacketSerial is included as a locked-reject baseline entry (D-01); not re-argued.

### 4.1 PacketSerial (bakercp) — LOCKED REJECT (D-01)

**Status:** LOCKED REJECT. Not re-derived here per D-01 — this entry records the settled
disposition only.

**Disposition summary:** PacketSerial-the-library fails the Uno RAM filter (D-04).
Its `send()` builds a fully COBS-encoded copy (~`n + n/254 + 2 ≈ 516 B` for a 512 B
chunk) before writing, consuming RAM that does not exist (545 B free, 512 B needed for
payload copy). Additionally: no checksum (incompatible with D-05 CRC8-CCITT keepgoing
requirement), requires coordinated dual-repo rewrite, and uses `0x00` as delimiter
(secondary `SERIAL_ON_IO` bus-aliasing concern per Section 1.4).

**Uno-fit verdict:** FAIL (second-buffer RAM collision). LOCKED REJECT (D-01).

---

### 4.2 SLIP / RFC-1055 Byte-Stuffing

**What it is:** Simple Link-layer IP Protocol (RFC-1055, 1988). Two special bytes:
`0xC0` (END — frame delimiter) and `0xDB` (ESC). Payload bytes `0xC0` → `0xDB 0xDC`;
`0xDB` → `0xDB 0xDD`. No checksum in the protocol itself. Pure streaming — no second
buffer. [ASSUMED: SLIP encoding is inherently byte-streaming; no separate encode buffer
is required by the algorithm definition]

**Uno-fit analysis:**
- RAM: streaming encoding — one byte at a time, zero extra buffer beyond a state byte.
  Fits with room to spare. [ASSUMED — streaming, no hidden buffers]
- Frame size: no limit. A 512 B Uno payload can expand at most 2× in the pathological
  all-`0xC0` case; in practice overhead is negligible.
- Resync: `0xC0` delimiter provides packet boundary. A garbled byte corrupts one packet;
  resync on next `0xC0`.

**`0x00` bus-aliasing:** SLIP uses `0xC0` as its sole delimiter — NOT `0x00`. The
`SERIAL_ON_IO` bus-aliasing concern (Section 1.4) does not apply to SLIP. This is
the cleanest framing option from a bus-aliasing standpoint.

**CRC8-CCITT coexistence:** SLIP has no built-in checksum. The existing CRC8-CCITT
byte is appended to each payload before SLIP escaping — zero change to the integrity layer.

**Integration cost:** Dual-repo rewrite of `rurp_serial_utils.cpp` + `serial_comm.py` +
`frame_parser.py` + `test_messages` frame contract. Milestone-sized.

**Uno-fit verdict:** PASS (streaming; no second buffer; no 0x00 concern).
**Overall verdict:** DEFER — Uno-fits and resync win is real; integration cost is
milestone-sized and adopting any framing layer is an explicit non-goal of v1.9.

### 4.3 Hand-Rolled Streaming COBS Encoder/Decoder

**What it is:** Custom ~40-line C encoder (firmware) + ~30-line Python decoder (host)
that stream COBS bytes directly to/from the serial port without materializing the
encoded form. No library dependency. See reference snippet in Section 3.

**The streaming-to-Serial insight (corrected from 2026-05-27 todo CRUX section):**
The 254-byte run limit is per *internal COBS run*, not per frame. A 512 B frame is
encoded as at most `⌈512/254⌉ + 1 = 3` groups, all streaming. The encoded form never
exists in memory simultaneously — RAM cost is 3 local variables (~6 bytes stack).
[VERIFIED: streaming algorithm reviewed; no second buffer needed for any frame size]

**Uno-fit analysis:**
- RAM: ~6 bytes stack overhead; no second buffer. Fits. [VERIFIED]
- Frame size: no limit imposed by the streaming approach. 512 B Uno and 1024 B
  Leonardo frames both work without re-chunking.
- Resync: `0x00` delimiter provides packet boundary. One garbled byte → corrupt one
  packet → resync on next `0x00`.

**`0x00` bus-aliasing concern:** The `0x00` delimiter is only emitted by the COBS
framing layer under `com_mode` gate (Section 1.4). The gate prevents `0x00` emission
during programmer mode. However, a host-driven `0x00` byte arriving while the firmware
is in programmer mode requires explicit handling proof (Section 5 Q2). [ASSUMED — the
`com_mode` gate analysis is from code review; host-side timing guarantee requires
bench verification for full correctness proof]

**CRC8-CCITT coexistence:** CRC8-CCITT byte appended to payload before COBS encoding;
existing CRC8 table in `rurp_serial_utils.cpp` and `frame_parser.py` reused unchanged.

**Integration cost:** ~70 lines total. Still requires dual-repo rewrite of
`rurp_serial_utils.cpp` + `serial_comm.py` + `test_messages` contract. Lower LOC
than any library but still a coordinated dual-repo change.

**Uno-fit verdict:** PASS (streaming; ~6 bytes stack; no second buffer; CRC8 preserved).
**Overall verdict:** DEFER pending field evidence that the resync win justifies the
dual-repo rewrite cost. This is the **recommended future-milestone path** (Section 3).

### 4.4 nanocobs (charlesnicholson/nanocobs)

**What it is:** C99 COBS implementation, no malloc, no libc. Two API modes:
standard (`cobs_encode` — encodes into a separate destination buffer) and tinyframe
(`cobs_encode_tinyframe` — encodes in-place, but payload capped at ≤253 bytes).
Version v0.2.0, February 2026. [VERIFIED: GitHub status, API modes, no-malloc claim]

**Uno-fit analysis:**

*Standard mode (`cobs_encode`):*
- Encodes into a separate `COBS_ENCODE_MAX(n)` destination buffer.
- For n=512: `COBS_ENCODE_MAX(512) ≈ 514 bytes`.
- 514 B does NOT fit in 545 B free RAM alongside the stack. **ELIMINATED by D-04.**

*Tinyframe mode (`cobs_encode_tinyframe`):*
- Encodes in-place; zero extra RAM.
- BUT enforces payload ≤ 253 bytes by design.
- A 512 B Uno frame requires re-chunking into ≥2 segments, each with its own CRC
  and delimiter. Changes `eprom_operations.py` data-block loop, firmware
  `rurp_communication_read_data` timeout window, and `test_messages` contract.
- FITS Uno RAM but forces re-chunking — higher integration cost than the custom
  streaming path in Section 4.3.

**CRC8-CCITT coexistence:** nanocobs has no checksum; CRC8-CCITT layered on top.

**`0x00` bus-aliasing:** Same as Section 4.3 — uses `0x00` as delimiter; same
`com_mode` gate analysis applies.

**Uno-fit verdict:**
- Standard mode: FAIL (D-04 — second buffer ≈ 514 B).
- Tinyframe mode: PASS (in-place, zero extra RAM) BUT forces re-chunking to ≤253 B.

**Overall verdict:** Standard mode ELIMINATED (D-04 filter). Tinyframe mode: DEFER
as runner-up if library adoption is preferred over hand-rolled code, but integration
cost exceeds the custom streaming path (Section 4.3).

**Uno-fit verdict:** FAIL on both dimensions (firmware: D-04 second buffer;

### 4.6 SerialTransfer + pySerialTransfer (PowerBroker2)

**What it is:** Arduino C++ library (SerialTransfer, v3.1.5, July 2025) paired
with Python library (pySerialTransfer, v2.6.11, PyPI confirmed). Uses CRC-8
polynomial 0x9B. Payload capped at 1–254 bytes by design (single-byte length
field). [VERIFIED: GitHub SerialTransfer 254-byte limit and CRC poly; pip index
confirmed pySerialTransfer v2.6.11 exists]

**Uno-fit analysis:**
- 254-byte payload cap forces re-chunking of 512 B Uno frames into ≥2 packets.
  Changes `eprom_operations.py` loop, firmware `rurp_communication_read_data`,
  and frame contract.
- **CRC polynomial swap:** SerialTransfer uses CRC-8 poly 0x9B, not 0x07.
  This breaks the `test_messages` suite (which asserts poly 0x07 byte-for-byte)
  and requires rewriting `frame_parser.py`'s `_build_crc8_table`. Incompatible
  with D-05 (CRC8-CCITT kept).
- Replaces ALL framing including the JSON command path — the most disruptive
  adoption path across all candidates.

**Uno-fit verdict:** Fits Uno RAM (internal buffering), but: 254 B cap, CRC
polynomial swap, and largest dual-repo diff of all candidates.

**Overall verdict:** ELIMINATED. CRC polynomial incompatibility (D-05) is the
decisive filter; the 254 B cap and all-framing replacement reinforce it.

### 4.7 MIN Protocol (min-protocol/min)

**What it is:** Microcontroller Interconnect Network (MIN) protocol. Uses CRC32
(4 bytes per frame). Includes transport-layer retransmission buffers.
[ASSUMED — from the 2026-05-27 todo survey and general knowledge; specific MIN
buffer sizes not verified from live code review]

**Uno-fit analysis:**
- CRC32 (4 bytes per frame overhead) vs CRC8 (1 byte) — higher overhead, incompatible
  with D-05 (CRC8-CCITT kept without modification).
- Transport retransmission buffers require additional RAM. With only 545 B free RAM on
  the Uno, any retransmission buffer (even a minimal 64 B sliding window) almost
  certainly causes a stack collision. [ASSUMED — specific sizes not verified; risk
  assessed "very likely" per training knowledge consensus and todo survey]
- Maximum frame payload ~255 B — forces re-chunking of 512 B Uno frames.

**Uno-fit verdict:** Probably FAIL (retransmission RAM; CRC32 overhead; 255 B cap).
**Overall verdict:** ELIMINATED. CRC32 incompatibility (D-05) is decisive; RAM
pressure reinforces it; overkill for this use case.

### `0x00` / SERIAL_ON_IO Bus-Aliasing Note

The Uno's `SERIAL_ON_IO` aliasing (PD0 shared between UART RX and data-bus bit 0) creates
a unique concern for COBS's `0x00` delimiter. Per Section 1.4, the `com_mode` gate in
`uno_rurp_shield.cpp` (verified present — lines 85-97) prevents ALL serial frame emission
while PORTD is in programmer mode. A COBS `0x00` delimiter can therefore only appear on the
wire while `com_mode = true` (communication mode). The residual risk — a host-originated
`0x00` byte received while the firmware momentarily transitions to programmer mode — requires
explicit host-side timing proof before a `0x00`-delimited framing layer can be safely
adopted. SLIP's `0xC0` delimiter avoids this concern entirely. [VERIFIED: com_mode gate in
uno_rurp_shield.cpp; host-side timing analysis: ASSUMED/deferred to future milestone]

## 5. Open Questions for Future Milestone

These questions are open at the v1.9 close; they gate the adopt/defer line for any
future protocol-quality milestone:

**Q1: Is the 2-second timeout desync observed in field use?**
The 2 s timeout fires if a `len_u16` byte is corrupted and the firmware reads the wrong
payload length. The desync cascades until the next JSON command arrival. If this ever
manifests during normal bench use (e.g., during consistency-check 64 KB read runs), that
is the signal to prioritize the auto-resync concept. Current status: no field reports in
the v1.6/v1.7/v1.8/v1.9 bench session corpus. The feature stays deferred until a field
incident provides evidence.

**Threshold recommendation:** One confirmed timeout desync in a bench read session should
trigger the streaming COBS path (Section 4.3) as a targeted fix — the integration cost
is bounded (~70 lines, dual-repo) and the resync win is then field-justified.

**Q2: Host-side `0x00` timing guarantee (COBS only; not needed for SLIP)**
If streaming COBS (Section 4.3) is ever adopted, the decision doc must include a
formal analysis or bench proof that the host side (`serial_comm.py`) cannot send a
`0x00`-containing byte sequence to the firmware during the transition window between
programmer mode and communication mode. The `com_mode` gate prevents the firmware from
*emitting* a `0x00` frame boundary during programmer mode; the open question is whether
the host can *receive* one it sent moments earlier as a false frame boundary. If this
proof is unavailable, SLIP (Section 4.2) is the safer choice.

**Q3: SLIP vs COBS — which to adopt if resync becomes necessary?**
SLIP is architecturally simpler (no run-length scan; pure two-byte escape table) and
completely sidesteps the `0x00` bus-aliasing concern (Q2). COBS is more widely recognized
in embedded contexts and has the streaming insight from Section 4.3. The choice depends
on the answer to Q2 at the time of adoption; both are fully Uno-fitting options.
