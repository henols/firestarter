## 2. What the milestone set out to do, and what it did

A write to a 5V page-write flash part either preserves the bytes it was not asked to
change, or refuses — and never reports success while destroying data.

Two firmware defects on protocol `0x05`, both filed by the operator on 2026-09-11 with
bench evidence, both tracked by no milestone until this one.

**gh#68** — the firmware wrote only the bytes it was given and then committed the page. The
device erases the whole physical page and programs only the loaded bytes, so every byte of
that page outside the write was erased to `0xFF`, in **both** directions. All 27 protocol-
`0x05` parts, the four validated ones included.

**gh#67** — `flash_5v_page_page_size()` derived a page size from total device size instead
of reading the part's real page from the database. On **9 of the 27** that derivation was
smaller than the physical page, so a plain contiguous write ran two page cycles into one
physical page and the second erased the first.

**Both were fixed by refusing.** D-2 permitted either refusal or read-modify-write, and the
deciding measurement is recorded rather than assumed: a firmware page-staging buffer leaves
**142 bytes** of RAM on `uno` for the entire call stack, and only a host pre-connect refusal
can claim the device is unchanged, because the firmware never learns the total payload
length. The milestone fixes the outcome, not the mechanism, and says which it chose.

## 4. PAGE-03 is open by design, and the record says so three times

PAGE-03 wants a contiguous multi-page write to one of the **9** previously under-sized parts,
read back byte-identical on real silicon. It did not happen, and it could not have.

The bench part was a `W29C020`. That part is one of the **18** whose derived page size was
already correct — which is exactly what made it the right part for Phase 195, because it
isolates gh#68 from gh#67, and exactly what makes it incapable of proving anything about
gh#67. The ordered `W29C512` has not arrived.

So the record reads **0 of 9 on hardware, 9 of 9 on the database comparison**, in
`194-page-size-27-row-record.md` §2, in `194-w29c020-bench-transcript.md` §5, and in
`REQUIREMENTS.md`'s PAGE-03 status note. All three agree and none merges the two evidence
classes into one claim. The `W29C020` run proves the fix did not regress an already-correct
part. It proves nothing about the 9.

This is the whole of the `override_closeout`. It is a missing measurement with a named
blocker, not an unsatisfied requirement anyone forgot.

contains.

**A gate leg was unsatisfiable by the pipeline that was supposed to satisfy it.** 196-03
asserted on `.planning/graphs/.last-build-status.json`, which is written only by a hook gated
on `current branch == default branch` — inert on a milestone branch. The executor hand-wrote
the file the gate reads, which is a self-attested proof. The verifier said so plainly and
corroborated the rebuild from four independent sources instead: matching mtimes across
`graph.json`, `graph.html` and `GRAPH_REPORT.md`, the report's own "Built from commit"
line, the absence of the deleted script's file node, and the commit ordering.

**A gate leg failed closed on its own filename.** 196-02's `SEED-AT-CANONICAL-PATH` leg
matched `case "$ST" in R*|*D*)` against the whole porcelain line including the path, and
`SEED-claim-firestarter-slug.md` contains an uppercase `D`.

**"Describe, do not cite" became a plan-wide rule that is in no CONTEXT.md.** Phase 196's
own residue gate scans `.planning/notes/`, so the retirement note and the `CLAUDE.md`
paragraph would each have turned it red by naming what they retire. Every live document now
names the artifact by description, and the path lives only in the commit body — which means
a future reader greps for it and finds nothing, so the note carries a signposted
`git log --diff-filter=D -- tools` recovery route.

## 6. Accepted debt, filed rather than fixed

**A negative write start address is silently clamped to 0.** The host guard uses Python's
`%`, and `-256 % 128 == 0` reads as aligned; the firmware's `simple_strtoul` consumes only
`[0-9]`, so a leading `-` makes it return 0. Confirmed by compiling the function verbatim
and running it. The consequence is narrower than the code review could establish and the
classification matters: address 0 is page-aligned and the length was already proven a whole
multiple of the page, so it erases nothing outside what it writes. It is a **wrong-
destination** defect, not a page-destruction one — it writes where the operator did not ask
and still reports success. Accepted as known debt at UAT and filed as
`todos/pending/2026-09-16-reject-negative-write-start-address.md`.

`require_page_alignment` also does not itself validate `page_size` membership before using it
as a modulus, relying on both call sites invoking `require_page_size` first. No live defect;
fragile against a future standalone caller.
