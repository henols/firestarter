    `## D-153-02 — The 0x0D chip erase emits an SDP-disable prefix`

    Settle Open Question 1 as **yes: emit SDP-disable first**, and record the reasoning, which is
    an asymmetry argument, not an appeal to the application note:
    - Atmel AN 0544B Rev. 0544B-10/98 is **silent** on whether the six-byte chip-erase code is
      decoded on a software-data-protected part. It says only that protection remains enabled
      *after* the erase, and that no byte loads are allowed *after* the six-byte code.
    - If the code is **not** decoded while protected, the failure mode is an erase that reports OK
      having erased nothing. On protocol `0x0D` that failure is **undetectable**: Phase 151
      established that the SDP protection state is unreadable on this family, so no oracle exists
      that could ever catch it. Silence is not permission when the failure mode is invisible.
    - The cost of being wrong in the chosen direction is six extra bus writes and one `t_WC` wait
      on an already-unprotected part: harmless. The cost of being wrong in the other direction is
      a silent no-op destructive command — the exact phantom-erase class Phase 121 D-12 fought and
      the class Phase 119 D-06's op-layer guard exists for.
    - Consistency: `eeprom28c_write_init` already SDP-disables before every page load, so an erase
      that did not would be the only bus-writing operation on this protocol that skips it.
    - Mechanism: reuse `eeprom28c_sdp_unlock_execute(handle)` verbatim as the prefix. It is already
      the SDP-disable emit plus `eeprom28c_wait_for_sdp_completion`, it reuses the existing
      `EEPROM_SDP_DISABLE` `.data` table so it costs **0 B additional RAM**, and it reuses the
      existing `MSG_INFO_SDP_UNLOCK` / `MSG_INFO_SDP_UNLOCK_DONE_US` ids so **no new catalog id is
      minted**.
    - State the consequence binding on plan 03: because
      `eeprom28c_wait_for_sdp_completion` ends in reads through `handle->firestarter_get_data`,
      the data bus is left as an input, so `rurp_set_data_output()` **must** be called after the
      prefix and before the first erase write.
    - State the resulting observable stream shape for plan 04 to pin: the SDP-disable six-write
      stream followed by the chip-erase six-write stream, so the **last** command payload written
      is the chip-erase terminal byte and the sixth is the SDP-disable terminal byte. Do not
      assert a wall-clock property anywhere: native stubs do not stub `delay()` and record no
      time.

    `## D-153-03 — GATE-03: the stated mechanism does not hold; the real control is a negative source scan`

    State the correction in writing, as L-03 requires, without softening it:
    - The roadmap's criterion 3 implies `tools/check_dispatch.py` is what prevents the hardware
      12 V-on-OE path. It is not. That checker is **database-and-dispatch-table** scoped: its
      GATE-03 guard fires only on a `configure_eprom` handler paired with a no-VPP-pin pinout, and
      it **structurally cannot** observe a control-register write inside a handler body.
    - The hardware path already exists in this tree, at `flash_5v_page.cpp` lines 196-231, in the
      very file an executor edits for ERASE-02 — so proximity, not absence, is the risk.
    - Therefore the **primary** GATE-03 control for this phase is a **brace-matched negative
      source scan** of `eeprom28c_erase_execute`'s body asserting zero occurrences of the VPP/VPE
      control-register tokens, planned as a real gate in plan 05, with a planted-violation leg
      that is **observed** to fail before the gate is trusted.
    - `check_dispatch.py` is nonetheless **not weakened, not exempted and not re-baselined**, and
      `git diff --quiet -- tools/check_dispatch.py` must hold at phase end. Record that this is
      an independently required invariant, not the control.
    - Record the honest statement: the software path is chosen because it is the correct
      engineering choice, and `check_dispatch.py` could not have stopped the wrong one.

    `## D-153-04 — erase -b does not get a post-erase blank check on 0x0D (L-05)`

    Record the disposition as **not wired**, with reasons: ERASE-05 keeps `blank` as its own step;
    an `operation_end` arm costs flash against a target with 0 B MERGE-05 headroom; and both
    closest siblings decline it — `flash_5v_page` has no `operation_end`, and
    `flash_nor_unlock` carries a commented-out one, which is this project's own written record of
    *not* wiring it. Record that `erase -b` on `0x0D` is therefore a documented no-op rather than
    a discovered one. Also record, per RESEARCH A7, that the `0x0D` erase is a device-global chip
    erase by construction and **ignores** `erase --sector-address`, which exists for the `0x06`
    sector erase.

    `## D-153-05 — erase stays out of write's auto-set path and out of write_init (L-06)`

    Record two dispositions:
    - Restoring `FLAG_CAN_ERASE` must **not** cause `write` to start erasing implicitly. No
      `FLAG_CAN_ERASE`-gated erase block is added to `eeprom28c_write_init`, even though both
      sibling handlers have one and an executor mirroring the sibling pattern will be tempted.
      D-07 asks for erase as a **standalone** step.
    - `erase` stays out of `write`'s D-04 `FLAG_SKIP_SDP_UNLOCK` auto-set path and gains no
      `--skip-sdp-unlock` option; that flag is scoped to `write` by D-17's reasoning. The
      auto-set is not silently extended.
