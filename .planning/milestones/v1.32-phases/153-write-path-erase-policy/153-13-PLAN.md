new write-path policy for both auto-erasing protocols.

reordered the phases to prevent. Neither paragraph is gated by any test, so it must be fixed
deliberately.

ERASE-02 and ERASE-03.

and `D-153-04` (device-global; no post-erase blank check).

  <action>
    Rewrite the `0x0D` erase-model paragraph. It currently states that the firmware implements no
    erase operation for this protocol, that the handler exposes no erase entry point of any kind,
    that the host deliberately does not set the erase-capability advertisement for it, and that the
    blank-check skip flag is **required** to write a non-blank AT28C part. Every one of those is now
    false, and the last is the one that matters most.

    The replacement paragraph must state:
    - the firmware implements a standalone chip erase for this protocol, reachable as
      `firestarter erase`, dispatched through a `CMD_ERASE` arm in the `0x0D` handler;
    - the mechanism is the **software** six-byte load sequence from Atmel Application Note
      *Software Chip Erase*, Rev. 0544B-10/98, internally timed with a 20 ms maximum cycle time, with
      every byte going to `0xFF` and software data protection remaining enabled afterwards;
    - per `D-153-03`, the datasheet's hardware Chip Erase mode — which drives the OE pin to 12 V on
      this 28-pin layout — is **deliberately not implemented**, and this handler energises no
      programming rail, consistent with the VPP-behavior paragraph in the same section;
    - per `D-153-02`, the erase emits an SDP-disable sequence before the erase code, because the
      application note is silent on whether the erase code is decoded on a protected part and this
      family's protection state is unreadable, so a failure in that direction would be a silent
      no-op reporting success;
    - per `D-153-04`, the erase is device-global by construction, so `erase --sector-address` does not
      apply to it, and `erase --blank-check` is a no-op on this protocol because no post-erase blank
      check is wired — `blank` remains available as its own command;
    - the write path now performs **no blank check at all** on this protocol, so the blank-check skip
      flag is unread here and is **not** needed to write a non-blank part. Say this in terms that
      cannot be read as a recommendation to pass a flag.
    - the erase capability advertisement is set for all 84 chips in this bucket, and the host and the
      firmware now agree; and
    - the honesty statement, in the phase's own words: this erase ships **software-proven and
      unvalidated on silicon**. No AT28C part was involved. State plainly that the sequence is proven
      to be emitted correctly on the bus by native stream-equality tests, and that nothing here
      claims the part actually erases.

    Keep the existing citation line under the paragraph and extend it to name the application note
    alongside the datasheet reference already there.

    Then add one sentence to the `0x05` subsection's write-algorithm or erase-model paragraph stating
    that the write path performs no blank check on that protocol either, for the same reason — the
    silicon auto-erases per page — and that its capability-gated bulk erase is unchanged and remains
    deliberately unadvertised by the host because it energises a 12 V rail on a 5 V-only part.

    Do not touch the section-0 table, the handler table, or any other protocol's subsection.
  </action>
