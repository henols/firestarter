**Section 2 — why `erase` refused, and what was actually wrong.** This is the FIX-06-shaped answer.

firmware disagreed about this family in three places at once — the `info` view derived its
"can be erased" row from the chip's electrical type and said yes; the wire flags cleared the erase
capability bit for this algorithm; and the firmware handler had no erase arm at all, so the command
returned not-supported. The capability was real in the silicon and real in the upstream chip data; what
was false was only that firestarter could perform it. Cite the datasheet by document number and table
— Microchip **DS20006386B**, Table 6-1 Operating Modes on p11, with the optional software chip-erase
paragraph on the same page — so the reader can check it. Name the two documented mechanisms and say
which one shipped.

**Section 3 — what shipped, and the honest limits of it.** A standalone erase step is now available on
this protocol, implemented by the software six-byte chip-erase sequence from the Atmel application
note, with the erase-capability bit restored on the wire so the command reaches the handler at all.
Say why the software path rather than the datasheet's hardware path: the hardware path drives a
programming voltage onto a pin of this pinout, and this project does not do that on a 5 V part. Then
state the limit plainly: the timing constant used for the erase cycle is an Atmel-family maximum from
that application note, the algorithm bucket it applies to spans other vendors, and a part with a
longer actual cycle time would read non-blank after an erase that looked successful — with nothing in
the test suite able to catch it. Also state that no test can prove the wall-clock wait is honoured,
because the native test harness records no time; that assertion is structural, not temporal.

Use the D-11-exempted phrasings for shipped behaviour — say the step **is now available**, not that it
works.

**Section 4 — the write path, and the page-write analysis.** Answer the 2025-09-28 analysis directly:
the page-write mechanism described there is the reason the pre-write blank check was wrong on this
protocol, and that check is gone — a page write auto-erases internally and every page is read-back
verified, so the check was never a safety net. State honestly what the page-size work did and did not
change for this part: the firmware now reads the page value from the chip database instead of a
hardcoded constant, and for this part that value is the same as the constant was, so nothing about
this part's behaviour changed and the page-size work explains nothing about the failures in this
thread. Then the matched-firmware consequence: the host's test step sends no override flag, so this
only takes effect on a board running v1.32 firmware.

**Section 5 — what remains unproven.** Transcribe, do not paraphrase, RESEARCH §B-10's list, including

erase sequence is the only person who has ever run any of this on real silicon of this family, and
