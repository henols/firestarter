<objective>
Author the pure resolution function that turns one database entry into one gate token and one
reason — the half of the pure/impure split that structurally cannot produce a state claim.

Purpose: LOCK-03, LOCK-04, D-06, D-09 and OD-2. `PATTERNS.md` records this two-function split
as having **no analog in the tree**: `sdp_capability.py` is pure-only and `sdp_honesty.py` is
prose-only, so the split must be authored rather than copied. The design constraint that makes
it worth authoring is D-12 leg 4: `protected` and `unprotected` must be *structurally*
unreachable without a silicon read, and the mechanism for that is a signature that does not
accept a device response. This plan writes the function whose signature has no response
parameter; plan `151-11` writes the one that does.

D-06's unanimity rule is inherited from `sdp_capability_for_entry`'s own reasoning — a single
DB entry can only be answered once, never token-by-token — but the third readability state
makes refusals actionable: curating `W29C022` later flips the
`W29C020,W29C020C,W29C022` entry with no rule change.

Output: `protection_gate_for_entry` in `protection_readability.py`, and
`firestarter_app/tests/test_protection_resolution.py`.

**Requirement flips owned by this plan: none.** It advances LOCK-03 and LOCK-04; both flip at
`151-13`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied dict → `protection_gate_for_entry` | A programmer dict from `resolve_chip()` lacks `protocol-id` and `name`; accepting it silently would produce a verdict from missing data. |
| curated table → gate token | The gate token is the permission to run a silicon read; a wrong token is either a fabricated refusal or a fabricated permission. |
| pure module → state claim | If the pure path could emit `protected`/`unprotected`, LOCK-04's central guarantee would be unenforceable. |
