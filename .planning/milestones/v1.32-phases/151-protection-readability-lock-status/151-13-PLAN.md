<objective>
Register `dev lock-status` as a beta-only `dev` subcommand, wire the pure predicate to the
response classifier, and prove the whole surface: the class-token ⊗ exit-code matrix, the
`--force` path, the channel gate on a simulated stable build, and the `dev --help` snapshot.

Purpose: LOCK-02, LOCK-03, LOCK-04, D-01, D-07, D-08, D-10. D-01 chose a real silicon read
exposed only on a pre-release install, deliberately overruling the host-only recommendation, so
a stable install never sees the command and cannot be over-promised to. Channel gating is
host-side only — the firmware has no notion of channels and `-D DEV_TOOLS` lives in the shared
`[env]` block inherited by all three AVR targets — so the bytes were paid regardless and this
plan is where the user-facing half of that decision lands.

D-07 makes `--force` the only path to an unadjudicated read, and the measured consequence is
that **no `0x05` row answers by default**: the `W29C020,W29C020C,W29C022` entry refuses because
`W29C022` appears nowhere in `lockable-proms.md`, so even the operator's own part is
`--force`-only. That is accepted, not a defect, and the CLI's tests encode it.

Output: the command, the channel-tuple extension, a class ⊗ exit-code matrix test, updated
gating tests, and one regenerated snapshot row.

**Requirement flips owned by this plan: LOCK-02, LOCK-03 and LOCK-04.** This is the only plan in
the phase that flips any of the three. Plans `151-02` through `151-12` advance them; nothing
before this point may tick them.
</objective>
