<objective>
Source both read sequences from datasheets, pin them as literal byte tables with full
citations, and record in one committed artifact exactly what a test over those tables can and
cannot establish — before any firmware transcribes them.

Purpose: OD-4. `infoic.xml` is **closed** as a source, measured at the project's own pinned
revision through `tools/derive_sdp_partition.py`'s `_load_infoic_xml()`. The decisive field is
`config`, the only blob-shaped attribute, and it is the literal string `"NULL"` on all 101
`protocol_id="0x05"` entries and all 897 `protocol_id="0x06"` entries. Per-chip data is 20
attributes with zero child elements across all 11,510 `INFOIC2PLUS` entries; no attribute name
matches `cmd|seq|unlock|protect|addr|command`; the magic bytes `aa55`/`5555`/`2aaa` appear in
no attribute value. It is a chip-**parameter** database — `protocol_id` *selects* an algorithm
whose bytes live in programmer firmware. It supplies exactly one relevant datum, `chip_id`,
which is a positive control for mode entry and says nothing about the status read.

So both sequences are datasheet-derived, and the consequence is categorical: no element-wise
proof against a machine-readable upstream is possible for either of them. The strongest
available test is a pinned literal byte table plus a citation comment — **a change detector,
not a correctness proof**. This plan says that in those words and funds the sourcing
explicitly rather than letting an executor infer bytes at implementation time.

Output: `.planning/phases/151-protection-readability-lock-status/151-SEQUENCES.md`.

**Requirement flips owned by this plan: none.** It advances LOCK-02.
</objective>
