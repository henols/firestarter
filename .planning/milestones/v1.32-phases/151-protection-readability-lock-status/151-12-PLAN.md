<objective>
Land the D-12 invariant: walk every row of the committed database through the resolution
function, assert the partition exhaustively, pin the census as literals, and prove the two state
tokens are structurally unreachable from the pure path.

Purpose: LOCK-04, D-12, OD-2. D-12's whole argument is that LOCK-04 cannot be enforced by
careful authoring — a prose-level guarantee rots the first time someone edits a sentence, and a
class distinction that lives in wording can be collapsed by a rewrite nobody notices. Asserting
class **tokens** over the whole database tests the mechanism instead: it goes red when a new row
lands in no class, and it is indifferent to wording.

Two legs in this file are the ones most easily authored vacuously, and both have a specific
non-vacuous form recorded in `151-VALIDATION.md`. The exhaustiveness leg was **red by
construction** before this phase assigned a class to the `XICOR/X88C64P,X88C64S` row: D-09's seven
named no-mechanism algorithms sum to 405, not 406, and that row lands in no class under D-09's
literal enumeration. Its acceptance is therefore phrased as *seen red on the `0x34` row, then
seen green after the class is assigned* — never "the leg exists". The unreachability leg passes
trivially as an absence assertion, so it requires a planted fixture that genuinely returns a
silicon-only token from the pure path, fed through the gate's environment seam and asserted to
fail. Plan `151-09` already committed exactly that fixture.

Output: `firestarter_app/tests/test_lock_status_class_partition.py`.

**Requirement flips owned by this plan: none.** It advances LOCK-03 and LOCK-04; both flip at
`151-13`, which is sequenced after this plan precisely so the CLI cannot ship a token the
partition does not cover.
