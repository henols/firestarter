<objective>
Mint the one catalog id this phase needs — `MSG_DATA_PROTECTION_STATUS` — and propagate it
through the codegen path so all five tracked files across the three repositories move
together.

Purpose: LOCK-02 and `151-DESIGN.md` §1. The lock-status response is a two-byte DATA id-frame:
byte 0 the raw byte read from silicon, unmodified, and byte 1 a decode code (`0x00`
reads-as-unprotected, `0x01` reads-as-protected, `0xFF` indeterminate, reusing
`hw_get_version`'s established `0xFF` sentinel convention). The raw byte is on the wire
because D-03's probe legs must record the raw result either way, so a wrong decode must not
destroy the observation.

Two hard constraints shape this plan. First, `firestarter/include/messages.h` is
codegen-generated and **ID-only**: a wording edit there produces a zero diff and is silently
lost. The source is the meta repo's `tools/catalog/messages.toml`. Second, the **ERROR band
has exactly one free id, `0xBF`**, with no documented band-extension procedure — so this phase
spends a DATA-band id (26 free) and leaves `0xBF` alone. The two already-existing
boot-block ids, `MSG_WARN_FL4_BOOT_BLOCK_LOCKED 0x85` and `MSG_ERR_FL4_BOOT_BLOCK_LOCKED
0xBC`, are emitted by nothing today and are the preferred vocabulary for any boot-block
outcome; plan `151-08` may give them an emit site without minting anything.

Output: one new catalog row, four regenerated/synced files, and a committed catalog-presence
test.

**Requirement flips owned by this plan: none.** It advances LOCK-02.
</objective>
