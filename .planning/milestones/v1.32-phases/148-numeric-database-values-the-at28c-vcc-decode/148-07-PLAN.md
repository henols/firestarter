<objective>
Re-derive the frozen schema inventory that the migration moved — and prove the gate can still fail
before trusting it green.

**D-13.** `tests/golden/chip_database_field_inventory.json`'s own `meta.how_to_update` forbids
hand-editing a count: *"Re-derive every number in this file with an independent traversal of the
live chip_database.json (two levels deep) — **never hand-edit a count to make a surprise
disappear**. State in the commit message which key changed, on which level, and why. If
`tools/build_db.py`'s `chip_entry` construction **or `tools/extra_chips.json`** changed, also
re-derive `generator_emitted_chip_entry_keys` … rather than editing the list by hand."` **Both**
triggers fire this phase.

The golden's own `meta.why_not_diff_db` explains why this gate is deliberately *not* derived from
the diff baseline: a baseline that can be regenerated is a gate that can be silenced. So a golden
regenerated without a fail proof is indistinguishable from a golden silenced. Precedent: Phase 140
Plan 03 shipped four RED / one GREEN for this same gate.

This plan adds a **fifth planted leg** that Phase 140 did not have — a key planted inside
`extra_chips.json`'s record — because RESEARCH F-1 made the supplement's contribution to the
generator key union load-bearing for the first time.

Purpose: move a frozen schema honestly.
Output: a re-derived golden plus six committed transcripts (five RED, one GREEN).
</objective>
