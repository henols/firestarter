<objective>
Land the firmware half of the seam and prove it with a flush-count oracle, not with a completion
check.

Six edit points, an in-repo template for five of them, and one novel measurement. `eeprom_28c.cpp:599`
is the **only** code use of the 64-byte floor in all of `src/`, and the Phase 44
`read-settling-delay` knob is the line-for-line template for the parser side — plus a sixth point
Phase 44 skipped: the per-command reset. Without that reset, writing AT28C010 at 128 and then a floor
chip in the same session leaves the second chip flushing on 128-byte boundaries, which is exactly the
page overrun PGSZ-02 exists to prevent. `firestarter_handle_t handle;` is a single file-scope global
with no per-command `memset`, so the reset is the only defence.

Criterion 1 says the delivered value must be **observed** to be used. A test asserting "a
128-byte-page handle completes without error" passes whether or not the 128 was used. The oracle is a
call count inside the mocked read seam: for a clean write,
`total get_data calls == 2 * flushes + data_size`, so on base 0 / `data_size` 128 the numbers are
**132** at page 64 and **130** at page 128. Three distinct, non-timing numbers on one geometry — and
because they are counts, the native stubs' missing clock cannot weaken them.

Purpose: make PGSZ-01's last hop and all of PGSZ-02 real, with the fallback exercised by a test rather
than asserted in a comment.
Output: the parser key, the handle field, the validated mask, the corrected floor comment, and ten new
cases in two existing suites. The change is **software-proven and unvalidated on silicon** — no AT28C
part was involved, `0x0D` stays `UNVERIFIED`, and no `support_status` changes.
</objective>

Settled here so no executor re-opens them. These are the `### Claude's Discretion` items and the
research's open questions that bind this plan.

- **Names, all single-sourced.** Handle field `page_size` (`uint16_t`, matching `chip_id` at
  `firestarter.h:201` and `vpp_mv` at `:196` as the in-struct width precedent). PROGMEM key identifier
  `key_page_size`. Getter `get_page_size`. Renamed floor constant `AT28C_PAGE_SIZE_FALLBACK`.
  Validation ceiling `AT28C_PAGE_SIZE_MAX`. Mask resolver `eeprom28c_page_mask`. Hoisted local
  `page_mask`.

- **The validation upper bound is the board-invariant literal 512, not `DATA_BUFFER_SIZE`.** Measured:
  `DATA_BUFFER_SIZE` is 512 on `uno`, `uno328pb` and `native`, and 1024 on `leonardo`
  (`platformio.ini:67`). Using it would make the *validation contract* board-dependent — one rule that
  is really two — and a native test could never observe the leonardo bound at all, so coverage would
  be partial by construction. 512 makes the contract identical on all four envs, makes the native
  test's coverage total, and is still ≥ the largest page any of the 746 rows carries (256). Both
  delivered values (64, 128) are inside every candidate range, so this choice changes nothing for this
  phase's data — it changes what a future value means. **Do not write a native case asserting 1024 is
  accepted**: it would pass on leonardo and fall back to 64 on native/uno, a divergence no native test
  can see.

- **The mask is resolved as a hoisted local at the top of `eeprom28c_write_execute`, above the per-byte
  loop — not stored on the handle and not resolved in `write_init`.** Record this in
  `149-PAGE-SIZE.md` as **mechanism-corrected / intent-satisfied** against D-06's literal "at
  write-INIT", never as failed; `configure_eeprom28c:194-204` already carries a precedent comment in
  exactly that voice for LOCK-04. Three measured reasons:
    1. `--policy merge05` requires `ram_used` **exactly unchanged** (`check_size_baseline.py:316-320`),
       and the exemption D-12 authorises is a **flash** allowance that explicitly does not touch that
       clause. `handle->page_size` already costs 2 B of `.bss`; a second stored field or a file-scope
       `static` for the mask would cost 2 B more for no behavioural gain.
    2. `eeprom28c_write_init` has an early `return` at `:454` on a chip-ID mismatch, so a mask resolved
       after it is **conditionally** initialised — not exploitable today, but a refactor hazard.
    3. The existing native cases call `configure_memory(&h)` then `h.firestarter_operation_main(&h)`
       and **never** `firestarter_operation_init` (`test_val_eeprom28c.cpp:218,249,269`). A mask
       resolved in `write_init` would leave all three `test_fix06_*` cases at mask 0, which flushes
       every byte and would silently change `test_fix06_page_boundary_window_readback`'s two-window
       geometry. `write_execute`-top is reached by every existing case and every new one.
  D-06's substance is preserved exactly: the mask is resolved **once, above the loop**, never per byte,
  so no runtime modulo by a variable divisor enters the hot path and `__udivmodsi4` is not pulled in.

- **Rejecting 0 comes before the subtraction.** `page_size - 1` on an unsigned type with
  `page_size == 0` yields an all-ones mask, which would flush almost never — the dangerous direction.
  The host cannot send 0 (both emit guards are truthiness tests, so 0 is unreachable from our own
  host), but the firmware must not rely on that.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host → firmware JSON command | an untrusted integer crossing a repo and process boundary into a memory-unsafe C parser and then into a loop bound's operand |
| one command → the next, through a single file-scope global handle | `firestarter_handle_t handle;` has no per-command `memset`, so any optional field not explicitly reset leaks across commands |
| an operator's `~/.firestarter/database.json` override → the wire | bypasses the generated database and every host-side invariant that iterates it, so the firmware check is load-bearing rather than belt-and-braces |
| the flush mask → the physical page boundary on the die | a mask that is too large is the direction that can overrun a page; too small only issues extra legal write cycles |
