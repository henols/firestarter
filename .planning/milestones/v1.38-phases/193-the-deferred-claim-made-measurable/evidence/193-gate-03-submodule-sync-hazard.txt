procedure's own routine-hygiene step is exactly what an operator following it would run into: an
operator who has internalised "run `submodule sync --recursive` after repointing .gitmodules" will
undo the GATE-03 workaround with no warning and no error the moment they run it at a pre-rename
ref.

Durability check -- re-running `sync` at the same HEAD immediately re-clobbers both:

  $ git submodule sync firestarter
  Synchronizing submodule url for 'firestarter'
  $ git config --get submodule.firestarter.url
  git@github.com:henols/firestarter.git

  git@github.com:henols/firestarter.git

Both back on the old slug immediately. The two-command sequence above is a repair, not a fix -- it
undoes one run of `sync`, and any further `sync` at the same pre-rename ref undoes it again. The
only durable answer at a pre-rename ref is not to run `sync` there at all.
