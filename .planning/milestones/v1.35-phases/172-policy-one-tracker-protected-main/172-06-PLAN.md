  <decision-context>
    D-10 is this phase's only `one-way` decision. Everything else here can be undone with another API
    call or another commit; this cannot.

    **What is destroyed.** Ruleset id `4998759` on `henols/firestarter`, created 2025-04-22, last
    updated 2025-06-05. Deleting it destroys the id, the creation history and the ruleset's identity
    in GitHub's audit surface. There is no undelete endpoint. The only recovery is a new ruleset with
    a new id — which is exactly what this plan then creates, so the *protection* is recoverable in
    seconds while the *identity and history* are not recoverable at all.

    **What was captured first.** Plan 172-05 wrote its full JSON to
    `.planning/phases/172-policy-one-tracker-protected-main/evidence/172-05-ruleset-4998759-pre-delete.json`
    and committed it before issuing any other API call. Its measured pre-state: `target: branch`;
    `conditions.ref_name.include: ["~DEFAULT_BRANCH"]`; rules `deletion`, `non_fast_forward` and
    `pull_request` with zero required approvals; one `bypass_actors` entry of type `DeployKey` with a
    null actor id; and `enforcement: "disabled"`.

    **Why delete rather than amend.** Amending would leave the `DeployKey` bypass to reconcile and
    would make `firestarter`'s ruleset the odd one out — created at a different time, from a
    different body, carrying a field the other two never had. D-10 chooses one body for all three so
    that a three-way read-back equality is a real check rather than a formality. The `DeployKey`
    entry grants nothing today: all three repositories have zero deploy keys, measured.

    **The window.** Between the DELETE and the POST that follows it, `henols/firestarter`'s `main`
    has no protection at all. Task 3 issues them back to back with no intervening work, and the
    read-back proves exactly one active ruleset afterwards. If the run is interrupted inside that
    window, `main` is unprotected and the captured JSON is the only record of what was there — the
    recovery is to re-run the POST from `evidence/172-05-ruleset-body.json`.

    **What plan 172-05's canary already established.** prom's ruleset was created from this same body
    and read back with `enforcement=active`, `bypass=Integration:15368:always` and
    `can_bypass=never`. So the body is known-good against the API and known to be accepted on a
    user-owned repository; the remaining uncertainty is D-09's, recorded in
    `evidence/172-05-actions-bypass-probe.txt`, and it is not resolved by declining this delete.
