<objective>
Put the three standing checkers on a trigger, verify the app on the Python version its CI actually
uses, and close the phase with a record of what was proved and what was not.

Purpose: three separate things converge here. The checkers built in waves 4 through 6 have no
trigger yet, and wiki edits produce no pull request to gate on, so a schedule plus a manual dispatch
is the only mechanism available. MIGRATE-03 has to be observed on the CI Python version because the
devcontainer's interpreter has provably masked app CI breakage in this project before. And the
phase's central claim — that a migration upgraded no claim — is only worth as much as the record
that says which parts of it were checked and which were vacuous.

**One measured correction has to survive into the phase record rather than being quietly smoothed
over.** The premise that three documentation files ship inside the published package is **false**.
A package built from a clean checkout contains zero documentation entries, and so do the two most
recently published releases. The file everyone has been citing is a stale, untracked build artefact.
The packaging delta is therefore a genuine no-op and must be reported as one. Claiming three files
left the package would be a false claim made inside the milestone whose entire purpose is preventing
false claims.

Output: one workflow, two measured evidence files, one gate sweep, one corrected state file, and one
honesty ledger.
</objective>

    Rewrite the file. Its current trigger is a pull request filtered to a directory this phase
    deleted, so the trigger is dead; and both of the commands it runs were deleted in wave 1.
    Delete its live-drift job entirely, which invoked one of them.

    New shape: `schedule` with a weekly cron plus `workflow_dispatch`; `permissions: contents: read`;
    a single job. A schedule is the only trigger available because wiki edits produce no pull
    request. The earlier objection to a cron trigger applied to a drift check that would have sat red
    by construction between two events; it does not transfer, because these checkers can only go red
    for a real reason.

    Steps, in order:

    1. Check out the meta repository to a named path.
    2. Resolve the sub-repo ref with the same-branch-else-default resolver, copied near-verbatim from
       the sibling workflow. **State in a comment that under a scheduled trigger the head-ref
       expression is empty and the ref-name expression is the default branch, so the resolver lands
       on the integration branch for both sub-repos** — that is the correct standing-gate behaviour,
       but the resolver's own comment text was written for a pull-request trigger and would mislead a
       reader otherwise.
    3. Check out both sub-repositories by name at the resolved ref, to named paths. The host
       application is needed for the shipped database and its dispatch tool; the firmware is needed
       for the dispatch test file.
    4. Clone the published wiki with a plain shallow `git clone`. It is anonymous and needs no token,
       proven by an anonymous clone this session. The checkout action cannot address a wiki
       repository — its repository input resolves the code repository, not the wiki — so this must be
       a plain clone step.
    5. Three **separate** checker steps, one per checker: reachability, truth, and dispatch mirror.
       They share the clone and nothing else, which is exactly what D-05 asks for. Keeping them separate is
       the point: a database
       disagreement and a navigation failure must arrive as two attributable red steps rather than as
       one indistinguishable verdict. The retired combined-check subcommand is the anti-pattern here
       — it collapsed independent legs into a single result.

    **Do not use recursive submodules.** Three measured reasons, all of which belong in the file's
    rationale comment: the sub-repositories are registered as submodules but their gitlinks pin
    commits that predate this phase, so a recursive checkout would assert against stale trees and
    could pass while the real branches are broken; the submodule configuration uses SSH URLs that
    would need rewriting to authenticate; and this repository has already been bitten by exactly
    this and wrote the record — a sibling workflow's own comment describes an accidental gitlink
    killing the checkout before any assertion ran.

    Give the new workflow its own rationale comment naming the failure it prevents. Meta-repository
    infrastructure keeps long rationale comments by documented convention. Write the new file's own
    reasoning; do not copy the sibling's comment block verbatim. End each checker step with an
    explicit success line naming the property it proved, matching the sibling's assertion style.
  </action>
