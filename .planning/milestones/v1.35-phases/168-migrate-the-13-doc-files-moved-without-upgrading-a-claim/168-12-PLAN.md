<objective>
Build the standing gate that keeps the wiki honest: for every published page that makes a per-chip or
per-protocol claim, assert a stamp is present, assert the claims inside its delimited region resolve
against the shipped database, and assert the stamp still matches the database it was taken from.

Purpose: after the model reversal this is **the only automated guard on wiki content**. There is no
publishing-integrity check any more, wiki edits produce no pull request, and there is no diff and no
review on an edit. A green result from this checker therefore has to mean something, which is why it
is to be demonstrated failing before it is trusted — and why it must never be described as covering
publishing integrity, which nothing now does.

**One part of the design was falsified by measurement and is corrected here, with the correction
stated.** The original shape asked that every part number and algorithm value a stamped page asserts
must resolve in the database. Measured over the real corpus, that is unimplementable as free text in
two independent and equally fatal ways: only 3% of the part-shaped tokens on one page resolve,
because the rest are correct family wildcards and elided suffixes the codebase documents as a
deliberate convention — so the gate would be red on roughly two hundred correct statements and would
be ignored within a week; and on a page with **zero** database chips, eleven of its twenty hex tokens
"resolve as algorithms" by pure numeric coincidence with control-register and analog-band values —
so a page making no chip claim at all would report a plausible-looking pass. The resolve leg is
therefore scoped to an explicitly delimited claim region, with a reasoned allowlist for the
exceptions. Everything outside a region is out of scope by construction, and the checker prints that
scoping so the bound is visible rather than implied.

Output: a checker, a reasoned allowlist, a fixture failure, and one live run recorded whatever its
outcome.
</objective>

    Write `tools/wiki/honest02_truth.py` in the D-07 standalone-checker shape, matching its two
    siblings: stdlib only, module
    constants, failure lists, and `main()` returning 2 for any unmet precondition. Flags:
    `--wiki-dir`, `--db` and `--allowlist`. Load the database and the allowlist at one parse point
    each and exit 2 on either failing, following the sibling precedent. **Non-vacuity first:** the
    database must load and yield more than zero rows, and the wiki directory must contain more than
    zero pages, before anything is compared.

    Build two resolution sets from the database once: the uppercased set of every part number across
    all vendor keys, and the set of every distinct programming-algorithm integer. Note in the module
    docstring the trap that a promoted algorithm row's programming sub-fields belong to a different
    algorithm, so nothing in this checker may read those sub-fields off a row and assert anything
    about them.

    Three legs, each with its own distinct outcome vocabulary so a database disagreement and a
    navigation-shaped problem never arrive as one indistinguishable red:

    **Leg 1 — stamp present.** A page matches the claim signature if it contains at least one
    part-number-shaped token or at least one algorithm reference. Every matching page must carry a
    `firestarter-claim-stamp` comment. Report `MISSING STAMP` naming each page that matches the
    signature without one. Print the count of pages scanned and the count that matched the signature.

    **Leg 2 — delimited claims resolve.** For each page carrying a `firestarter-claims-begin` /
    `firestarter-claims-end` pair, extract the part-number-shaped and hex-algorithm-shaped tokens
    **inside the region only**, and resolve each against the corresponding set. A token that does not
    resolve and is not in the allowlist is reported as `UNRESOLVED` with the page and the token.
    A stamped page carrying **no** region is reported as `UNCHECKED (stamp only)` on its own line —
    a named, printed outcome, never folded into the success line. Print the count of claims checked,
    the count of regions found and the count of pages reported unchecked.

    **Leg 3 — stamp freshness.** Compute the truncated sha256 of the database file and compare it to
    each stamp's recorded value. A mismatch is reported as `STALE STAMP` naming the page, the
    recorded hash and the current one. Stale is a **distinct outcome from wrong** — it means nobody
    has re-verified the page since the database changed, not that the page is false — and it must
    read that way in the message.

    Any failure from any leg exits 1. The success line names all three legs and carries each leg's
    count, so a run that checked nothing is visible on its face.

    Write a rationale comment at the top of the file naming the failure it prevents. Meta-repository
    infrastructure keeps long rationale comments by documented convention; that convention does not
    reach either sub-repository, where the operator's no-comments rule is absolute.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public wiki edit → published claim | Anyone with write access can change a claim with no pull request, no diff and no CI on the edit |
| allowlist entry → suppressed failure | An allowlist is a mechanism for making a gate green without fixing anything |
| shipped database → resolution truth | The gate's notion of "resolves" is only as good as the database it reads |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-168-44 | Repudiation | a resolve leg that passes by numeric coincidence | critical | mitigate | Resolution is scoped to explicitly delimited regions; a page with no region is reported as unchecked by name rather than passing; leg 2 prints its region and claim counts |
| T-168-45 | Repudiation | an allowlist used to silence a real failure | high | mitigate | Every entry requires a non-empty reason and the checker exits 2 without one; the seeded set is bounded to what the three regions need and its size is recorded |
| T-168-46 | Tampering | an unreviewed wiki edit introducing a false claim | high | mitigate | This checker is the mitigation, and it is demonstrated failing three distinct ways before its green is believed; plan 168-13 puts it on a schedule because there is no pull request to gate on |
| T-168-47 | Repudiation | a stale stamp read as a correct one | high | mitigate | Leg 3 compares the stamp hash to the current database and reports stale as a distinct outcome with a message asserted to be textually different from the unresolved message |
| T-168-48 | Denial of service | fixture-green tooling failing on first real contact | high | mitigate | A live run against a fresh clone and the real database is required, and its outcome is committed whatever it is |
| T-168-SC | Tampering | package installs | low | accept | Standard library only |
</threat_model>
