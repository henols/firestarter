<objective>
Rebuild the three-way dispatch-mirror gate as a standalone meta-repository checker that reads its
canonical leg from the **published wiki page**, its tool leg from the host application, and its
firmware leg from the firmware repository — and make it fail loudly when the page it depends on is
reformatted.

**This settles the phase's largest open design question**, and the trade-off is stated rather than
buried. The gate could have read the frozen pre-deletion git blob instead of the wiki. It reads the
wiki, because:

- the whole point of relocating the gate is that the wiki is now where the documented truth lives,
  and a gate pointed at a frozen blob can never catch a wiki edit that contradicts the firmware — it
  would be a second copy of the one-shot claim comparison rather than a standing gate;
- a frozen source makes the gate assert firmware behaviour against a document nobody can update,
  which turns every legitimate future firmware change into a permanent red.

The price is real and is priced, not waved away: the gate now depends on the shape of a table on a
page anyone with write access can reformat with no review. That is mitigated by wrapping the table
in the claim-region sentinels and by making a missing or unparsable region **exit 2 — precondition
unmet — rather than exit 0**, so a reformat reads as "the check could not run", never as a pass.

Output: one checker, one selftest case with a green control and two planted mutations, and the
recorded red.
</objective>

    `wiki.py`: `from __future__ import annotations`, module constants for every path, name and
    regex, a check function returning a list of failure strings, a `cmd_*` wrapper turning that list
    into 0 or 1, and `main()` returning 2 for any unmet precondition before dispatch. This is D-07's
    standalone-checker shape and it is why no pytest harness enters the meta repository. Copy the
    exit-code contract into the module docstring verbatim. Introduce no pytest, no project metadata
    file and no test directory in the meta repository — the repository has none of those and this
    plan keeps it that way.

    Flags: `--wiki-dir` (the wiki clone), `--app-dir` (a `firestarter_app` checkout) and `--fw-dir`
    (a `firestarter` checkout), all three required, each defaulted to nothing. Import the host tool
    leg by inserting `--app-dir` onto `sys.path` and importing the dispatch module, taking its
    dispatch function and its algorithm map rather than reimplementing either.

    Three legs, in this order.

    **Leg 0 — non-vacuity, and it is the whole mitigation for the design trade-off above.** Locate
    the `firestarter-claims-begin` / `firestarter-claims-end` region on the published protocol page.
    If the page is missing, the region is missing, or the region parses to fewer than 12 bucket rows,
    **return 2** with a message naming which of those three it was. Twelve is the measured number of
    algorithm values in the database and the measured row count of the page's bucket table; a parse
    yielding fewer means the table was reformatted, not that the firmware changed. The failure mode
    this prevents is concrete: a reformat that reduces the parse to an empty mapping would otherwise
    make the comparison pass against nothing.

    **Leg 1 — doc against tool.** Parse the region's bucket rows with the recorded 7-column regex,
    reading the hex algorithm value from column 1, the handler family from column 6 and the phantom
    marker from column 7, and the handler-family rows with the recorded 4-column regex. Exclude
    phantom rows, exactly as the retired module did — they are absent from the host's known-protocol
    set and route to the not-implemented handler for a host-side reason unrelated to naming. Compare
    the resulting protocol-to-handler mapping against the host dispatch function's output.

    **Leg 2 — doc against firmware.** Compare the same mapping against the firmware dispatch test,
    with the same phantom exclusion.

    Report failures as `ERROR: ` lines on stderr, one per disagreeing protocol, each naming the
    protocol value and both sides of the disagreement. On success print one `OK: ` line on stdout
    carrying the **count of protocols actually compared** — that count is what makes a vacuous pass
    visible, and it is why the count belongs in the success line rather than in a debug flag.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public wiki page → firmware correctness gate | Anyone with wiki write access can reformat the table this gate parses, with no review and no CI |
| host tool import across repositories | The checker executes code from a sub-repo checkout it was pointed at |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-168-36 | Repudiation | a reformatted claim region parsing to zero rows | critical | mitigate | Leg 0 returns 2 when the region is absent or yields fewer than 12 bucket rows; a reformat therefore reads as "could not run", never as a pass, and both sub-cases are asserted |
| T-168-37 | Tampering | wiki edit contradicting firmware dispatch | high | mitigate | This is the gate's purpose: the doc leg reads the live published page, so a contradicting edit produces exit 1 on the next scheduled run |
| T-168-38 | Elevation of privilege | importing host code from a checkout path | medium | mitigate | The import is limited to the named dispatch module from an explicitly supplied `--app-dir`; the workflow supplies a checkout of a first-party repository at a resolved ref, never an arbitrary path |
| T-168-39 | Repudiation | a gate whose green was never paired with a red | high | mitigate | The selftest case requires a green control and two planted mutations, and the red is captured to an evidence file with its exit status |
| T-168-SC | Tampering | package installs | low | accept | Standard library only, plus a path-injected import of first-party host code |
</threat_model>
