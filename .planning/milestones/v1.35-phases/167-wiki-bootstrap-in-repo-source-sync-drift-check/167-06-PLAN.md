**Part 1 — `.github/workflows/wiki-publish.yml`.** This is D-05's second publish path and it is in
scope for this phase; dropping it would silently drop half of a locked operator decision.

- `name: Wiki publish`, job id `wiki-publish`, `runs-on: ubuntu-latest`.
- Triggers: `push` with `branches: [beta]` and `paths` of `wiki/**`, `tools/wiki/**` and
  `.github/workflows/wiki-publish.yml`; plus `workflow_dispatch`. Keyed to `beta`, never `main`
  (D-06). `workflow_dispatch` is what makes the token question measurable on demand rather than only
  after a merge.
- Job-level `permissions:` with `contents: write` and nothing else. This is **mandatory**, not
  stylistic: `henols/firestarter_prom` has `default_workflow_permissions: "read"`, so without this
  declaration the push returns 403 with `Permission to henols/firestarter_prom.wiki.git denied to
  github-actions[bot]`.
- Steps:
  1. `actions/checkout@v4`. No `submodules`, no extra fetch depth.
  2. A step named `Publish wiki` with an `env:` block defining exactly one token variable,
     `WIKI_TOKEN: ${{ secrets.WIKI_PUSH_TOKEN || secrets.GITHUB_TOKEN }}`. This single expression is
     the pre-planned fallback: if the first live run returns 403, the operator creates a **classic**
     PAT with `repo` scope as a repository secret named `WIKI_PUSH_TOKEN` and the workflow starts
     using it with **no workflow edit**. Fine-grained PATs are not recommended here — their wiki
     support is undocumented. There is no `wiki:` scope; wiki access rides on `contents`.
     The step's `run:` composes the remote from the env var at use time — the
     `x-access-token` HTTPS form for `henols/firestarter_prom.wiki.git` — and passes it to
     `python3 tools/wiki/wiki.py publish --push --require-wiki --wiki-remote "$REMOTE"`.
     `--require-wiki` makes an absent wiki a hard failure here rather than a distinguishable exit-2
     state: in CI there is no human to act on the distinction. No `set -x`, no `echo` of the remote,
     no `run:` line that prints the composed URL.
  3. A step named `Assert wiki matches source after publish` running
     `python3 tools/wiki/wiki.py publish --require-wiki --wiki-remote "$REMOTE"` — the dry-run of the
     command that just ran, asserting exit 0. This is D-08 used as a post-condition: because the
     check and the publish are one code path, a publish that pushed nothing, pushed to the wrong
     branch, or silently no-op'd cannot report success. Compose the remote the same way and do not
     print it.

No `continue-on-error`, no `|| true`, no `if:` that could skip an assertion, no force refspec, no
third-party action beyond `actions/checkout@v4`. Zero comment lines.

**Part 2 — the live comparison job in `.github/workflows/wiki-check.yml`.** Add a second job,

  which is not the same as an `if:` that lets an assertion be skipped inside a running job — the
  assertion itself has no escape hatch.
- Steps: `actions/checkout@v4`, then a step named `Assert published wiki matches source` running
  `python3 tools/wiki/wiki.py publish --require-wiki`. No `--push`. `--require-wiki` because in CI an
  absent wiki must fail hard.
- Add `.github/workflows/wiki-check.yml` to nothing new — its `paths` filter already includes its own
  filename.
