## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** The in-repo wiki source tree is **`wiki/` at the repository root**. Tooling lives separately under `tools/wiki/`. Rationale: content is not tooling — a contributor editing a page should never have to open a tooling directory — and a top-level `wiki/` is self-evident to anyone landing on the repo once Phase 169 makes `firestarter_prom` the front door. Rejected: `docs/`; `tools/wiki/pages/`.

- **D-02:** `wiki/` is **flat — a single directory, no subdirectories**. GitHub addresses wiki pages by bare filename regardless of directory, so flat means *source path == published page* and the drift check reduces to a plain directory diff. Accepted cost: in-repo browsability degrades once ~16 pages accumulate after Phase 168. Rejected: nesting with a publish-time flattening step; nesting published as-is.

- **D-03:** Filenames use **`Title-Case-With-Hyphens.md`**. GitHub renders hyphens as spaces, so `Shield-Revisions.md` becomes the page title "Shield Revisions" at URL `/wiki/Shield-Revisions`. This produces readable titles *and* readable URLs — and those URLs get written into the READMEs Phases 169 and 170 author. Accepted cost: every migrating file is renamed, so Phase 168 must produce a real old-path → page mapping. Rejected: keeping existing filenames verbatim; all-lowercase.

- **D-04:** The wiki page name is **derived mechanically from the filename** at publish time. There is no manifest for the publish path to consult, so publishing cannot drift from a registry. Migration provenance — original repo path → wiki page — lives in a **separate checked-in table** that Phase 168 fills in. Rejected: a `PAGES.toml` the publish script reads; convention-only with the mapping in 168's SUMMARY.md.

- **D-05:** Publishing happens **two ways**: a local one-command script *and* a CI publish on merge. The local path satisfies WIKI-03 literally and is required for the criterion 2 overwrite demonstration; the CI path stops the wiki drifting behind the integration branch.

- **D-06:** The CI publish is keyed to **`beta`, not `main`**. Measured: `origin/beta` is **2,842 commits ahead of `origin/main`**. **Accepted cost, and it must be stated on the wiki rather than left implicit:** the wiki tracks `beta`, so it can describe behaviour that `main` has not shipped.

- **D-07:** The drift check runs as a **path-filtered PR check on `wiki/`** (plus its own workflow file) into `beta`, with `workflow_dispatch` for on-demand runs — the same shape as the existing `catalog-sync-check.yml`. The identical command is runnable locally. Rejected: a scheduled cron against the live wiki; local-only with no CI.

- **D-08:** The publish command is **dry-run by default; `--push` publishes**. Critically, **the dry-run *is* the drift check** — one code path with two entry points, so the check can never diverge from what publish actually does. Rejected: push-by-default; push-by-default-refusing-on-hand-edits-without-`--force`.

- **D-09:** `_Sidebar.md` is **generated** from `wiki/`; `Home.md` is **hand-authored**. The combination leaves the reachability check something real to catch: a page present in the generated sidebar but absent from the hand-written Home. Rejected: generating both (would make criterion 5 a tautology); hand-authoring both.

- **D-10:** The generated `_Sidebar.md` is **committed to `wiki/`**, regenerated by the publish command, with a **CI freshness leg** asserting it is up to date. Matches the `messages.h` / `messages.py` precedent. Keeps the drift check **exclusion-free**: every exclusion is a hole in an integrity check. Rejected: generate-at-publish-only; generate-and-reconstruct-in-the-checker.

- **D-11:** The reachability check asserts **orphan detection + internal link resolution**: every page in `wiki/` is linked from `Home.md` or `_Sidebar.md`, and every internal wiki link in every page points at a page that exists. Deterministic and offline. Rejected: orphan-check-only; adding external link liveness.

- **D-12:** At the end of this phase the wiki holds **`Home.md` plus a "How this wiki is published" page**. Home names the pages Phase 168 will bring; the second page states the in-repo-is-authoritative rule and warns that edits made in the wiki web UI are overwritten on the next publish. Justified as **pipeline scaffolding, not documentation**. Rejected: Home-only; Home + a placeholder deleted in 168.

## Summary

Everything this phase needs is already installed and every mechanism it depends on was executed and measured during this research session. There is no library to choose, no package to install, and no new runtime. A GitHub wiki is an ordinary git repository at `<repo>.wiki.git` whose default branch is `master` — verified first-hand against three public wikis — and whose pages are flat markdown files whose filenames become page titles with `-` rendered as a space. D-02 and D-03 are not merely defensible, they are exactly what the wiki engine's own project wiki does. The entire publish/drift/idempotence design was implemented as a 12-line shell prototype and run to completion against a local bare repository: two runs produced one commit and an unchanged `HEAD`; a deliberate wiki-side edit was overwritten by the next publish; a source-side deletion propagated. All three of criterion 2, 3 and the deletion-mirror property therefore have a proven mechanism before a line of the plan is written.

The interesting findings are the traps. First, this repository's existing sync script contains a **tautological verification** — `tools/catalog/sync_to_subrepos.sh` lines 88–90 and 100–102 `diff` a file against *itself* and print "OK" — which is the same class of defect as the `catalog-sync-check.yml` scar the CONTEXT tells you to read, and it lives in the very file the planner is told to model the publish command on. Copying its shape without copying that bug is a named requirement. Second, GitHub's wiki is aggressively forgiving at read time in ways that make a *live* check useless: a nonexistent page returns HTTP **200** (a create-page stub), page lookup is **case-insensitive**, and a link written as `Page-Name.md` **302-redirects to raw markdown on `raw.githubusercontent.com`** rather than rendering the page. So the check must be offline, strict, and case-sensitive — deliberately stricter than GitHub — and the link-form convention must be an enforced allowlist, not a best-effort parse. Third, criterion 5 is a tautology trap: because `_Sidebar.md` is generated to contain every page (D-10), accepting a sidebar link as reachability evidence makes the orphan check incapable of ever failing. Only `Home.md` links may count as evidence.

On the open question CONTEXT handed to research: pushing to `<repo>.wiki.git` from Actions with the default `GITHUB_TOKEN` **does work for the same repository** provided the workflow declares `permissions: contents: write` — and that declaration is **mandatory here**, because `henols/firestarter_prom` has `default_workflow_permissions: "read"` (read back from the API this session). A classic PAT is needed only if that fails on the first live run; there is no `wiki:` permission scope, wiki access rides on `contents`. Because the wiki does not exist, this cannot be proven until the operator acts — so the plan must treat the token choice as a *measured outcome recorded in the phase*, not a settled fact.

**Primary recommendation:** Build one stdlib-only Python file, `tools/wiki/wiki.py`, with subcommands `publish` (dry-run default, `--push` to publish), `sidebar`, `links` and `check`, whose wiki remote is a **parameter** (`--wiki-remote`) defaulting to the real URL so a local bare repo can be substituted; prove every criterion through a bash fixture driver `tools/wiki/selftest.sh` that asserts **exit codes on 11 negative cases**; add **only the offline legs to CI now** and wire the live wiki-comparison leg in the operator-gated re-run — never a fail-open skip, never a red-by-default check. Do not stand up pytest. Install nothing.

### Pattern 1: Mirror publish (wipe-and-relay, not copy-over)

**What:** Clone the wiki, delete everything in the worktree except `.git`, copy `wiki/*` in, `git add -A`. The wiki becomes a byte-exact mirror of the source directory.

**When to use:** Always. This single choice delivers three separate criteria: WIKI-02's authority direction (a wiki-side edit is destroyed, not merged), the deletion-mirror property (a page removed in-repo disappears from the wiki), and the drift check's reduction to `git diff --cached` (D-02's flat layout is what makes this a plain diff).

**Why not copy-over:** `cp -a src/. worktree/` without the wipe leaves a page deleted in-repo alive on the wiki forever. Criterion 4's drift check compares a whole directory, so a stale wiki page reads as permanent drift that the publish cannot clear — the check would go red with no way for the author to make it green.

**Example:** `[VERIFIED: executed end-to-end this session]` — see `## Code Examples` → Verified idempotent mirror publish.

### Pattern 2: Commit only on a staged diff

**What:** `git diff --cached --quiet` after `git add -A`. Exit 0 means nothing staged; skip the commit and the push entirely.

**When to use:** Every publish. This is the whole of criterion 3.

**Measured:** run 1 pushed; run 2 printed `no-change`; `git rev-parse master` was byte-identical across both. `[VERIFIED: executed this session]`

**Why `HEAD`-unchanged and not "no error":** the criterion is explicit. Assert `rev-parse` equality before and after, not the absence of a traceback.

### Pattern 3: One code path, two entry points (D-08) expressed as an exit-code contract

**What:** `publish` computes the staged diff and then branches on `--push`. The comparison logic exists exactly once.

| Invocation | Exit 0 | Exit 1 | Exit 2 |
|------------|--------|--------|--------|
| `wiki.py publish` (dry-run = the drift check) | wiki matches source | wiki differs from source (prints the diff) | wiki remote does not exist |
| `wiki.py publish --push` | pushed, or nothing to push | push failed | wiki remote does not exist |
| `wiki.py sidebar --check` | `_Sidebar.md` is fresh | stale (prints the delta) | — |
| `wiki.py links` | all pages reachable, all internal links resolve, all names legal | any orphan / broken link / illegal name / disallowed link form | — |
| `wiki.py check` | all offline legs pass | any offline leg fails | — |

**Why exit 2 is separate:** conflating "wiki absent" with "drift" is what turns the operator-gated blocker into a mysterious red check. Exit 2 must print the literal operator action ("save one page at `https://github.com/henols/firestarter_prom/wiki`") and the requirement id (WIKI-01).

**`--require-wiki`:** in the gated live re-run, absence must be a hard failure rather than a distinguishable state. One flag, no second code path.

**`--wiki-remote <url|path>`:** the remote is a **parameter with the real URL as its default**. This one design choice is what makes criteria 2, 3 and 4 testable before the operator acts — the fixture driver passes a local bare repo path. Without it, the tool is untestable and the phase cannot meet its own criteria.

### Pattern 4: Offline link walker with an enforced link-form allowlist

**What:** Parse each page in `wiki/`, extract internal links, resolve them against the filename set, and detect orphans.

**The non-tautology rule (load-bearing):** reachability evidence comes from **`Home.md` only**. `_Sidebar.md` is generated to contain every page (D-10), so counting sidebar links as evidence makes the orphan check structurally incapable of failing — the exact tautology D-09's rejected alternative was rejected for, and what the ROADMAP means by "a check seen only green proves nothing." WIKI-05 is still satisfied for readers by both files; the *check* only trusts the hand-authored one.

**Allowlist, not best-effort parse.** The single legal internal link form is `[Text](Page-Name)` or `[Text](Page-Name#anchor)`. Everything else internal is a failure:

| Rejected form | Why |
|---------------|-----|
| `[Text](Page-Name.md)` | `[VERIFIED: curl, this session]` `/wiki/Installation.md` returns **302 → raw.githubusercontent.com** — the reader gets raw markdown, not a page. The corpus Phase 168 imports contains 3 such links (`community-validation.md`, and 2 with `#protect-flags-bits-14-15` anchors) `[VERIFIED: grep over firestarter/doc + firestarter_app/doc]`. |
| `[[Page]]` / `[[Page\|Text]]` | MediaWiki syntax; valid on GitHub but a second convention to maintain and invisible to a plain markdown reader in-repo `[CITED: docs.github.com/.../editing-wiki-content]` |
| `[Text](sub/dir/Page)` | D-02 forbids subdirectories; a path separator is also illegal in a page title |
| `[Text](page-name)` with wrong case | `[VERIFIED: curl, this session]` GitHub resolves `/wiki/installation` case-insensitively (HTTP 200, no redirect), so GitHub will *never* tell you this is wrong; the checker must be case-**sensitive** to catch drift the service silently tolerates |
| Reference-style `[Text][ref]` | Resolvable but doubles the parser's surface; ban it in `wiki/` and say so in `--help` |

Anchors (`#fragment`) are stripped before page resolution. Optionally verify the anchor against the target page's headings — cheap, and the 2 imported anchor links make it immediately useful to Phase 168.

External links (`scheme://`, `mailto:`) are ignored — liveness is deferred (Phase 172's grep).

**Filename legality leg:** reject any name containing `\ / : * ? " < > |` `[CITED: docs.github.com/.../adding-or-editing-wiki-pages]`, and reject a name whose intended title needs a literal hyphen (see `## Pitfall 4`).

**Skip fenced and inline code.** A ```` ``` ```` block or a `` `[x](y)` `` span is not a link. Getting this wrong produces false failures, and a check that goes red for reasons unrelated to the change gets ignored — this repository has already demonstrated that failure mode.

### Pattern 5: Deterministic sidebar generation (following the `codegen.py` determinism contract)

**What:** `_Sidebar.md` is a sorted list of `- [Title](Page-Name)` derived from the `wiki/` filename set, `Home` first, `_Sidebar.md` and `_Footer.md` excluded from the list but present in the directory.

**Determinism contract** — carry `codegen.py`'s explicitly, because D-10's freshness leg depends on it: sort deterministically; no timestamps, hostnames or hashes; LF endings via `Path.write_text(..., newline="\n")`. Two runs must be byte-identical, or the CI freshness leg flaps.

**Freshness leg:** `sidebar --check` regenerates into memory and compares against the committed file. It must **not** rewrite the file — a checker that fixes what it is checking reports green forever.

### Pattern 6: CI shape (following `catalog-sync-check.yml`, with its scar corrected)

```yaml
on:
  pull_request:
    branches: [beta]
    paths: ['wiki/**', 'tools/wiki/**', '.github/workflows/wiki-check.yml']
  workflow_dispatch:
```

Copy from the existing workflow: path filters scoped to what the check guards, the workflow's own file in the filter set, `workflow_dispatch`, `actions/checkout@v4`, checking out only what the job reads, no `submodules: recursive`.

Do **not** copy: `branches: [main]` (D-06 — `main` is 2,842 commits behind, `[VERIFIED: git rev-list --count origin/main..origin/beta = 2842, this session]`), and do not copy the comment blocks (project hard rule).

### Anti-Patterns to Avoid

- **A verification that compares a thing to itself.** `tools/catalog/sync_to_subrepos.sh:88-90` and `:100-102` run `diff -q "$X" "$X"` and print "OK: … regenerated." This is always true and asserts nothing. It sits in the file the planner is told to model. Do not carry it forward — and consider filing it, since it is a live latent defect in the repo's only sync tooling.
- **A CI leg that fails open when the wiki is absent.** Emitting a warning and exiting 0 makes the drift check unable to fail for the one reason it exists. Recommended alternative in `## Discretion Areas — Settled` → CI sequencing.
- **`git commit --allow-empty`** or `git commit || true` in the publish path — either one destroys criterion 3.
- **Force-pushing the wiki** — destroys history and makes the `HEAD`-unchanged proof impossible.
- **`git init` without `-b master`** in a fallback path. `init.defaultBranch` is unset in this container (`[VERIFIED: git config --get init.defaultBranch`, empty]`), and a wiki only serves its default branch — `master` `[VERIFIED: git ls-remote --symref on three public wikis]`. A publish that lands on `main` "succeeds" and changes nothing a reader can see. This is the single most dangerous silent failure in the phase.
- **Interpolating a token into a URL that gets logged.** Never `set -x` around the push; never `echo` the remote.
- **A checker that regenerates the artifact it checks.**
- **Explanatory comments in any authored script or workflow** — project hard rule. Explanation goes in `argparse` help text and in D-12's "How this wiki is published" page.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Detecting whether the wiki differs from source | A file-by-file hash/mtime comparator | `git add -A` + `git diff --cached --quiet` in the wiki worktree | Git already handles rename detection, mode bits, LF/CRLF, and empty-directory semantics. It also gives you the human-readable diff for the failure message for free, and it is the *same* computation the publish performs — which is D-08's entire point. |
| Publishing | A wiki page REST client | git push to `<repo>.wiki.git` | There is no REST API for wiki pages `[CITED: REQUIREMENTS.md §Constraints; corroborated by search]` — this is also precisely why WIKI-01 is operator-gated. |
| Rendering page titles | A title-rendering preview | Nothing — reject lossy filenames instead | Gollum owns rendering. Re-implementing `-`→space in order to *display* it invites divergence; implement only the *rejection* of names that round-trip lossily. |
| Verifying wiki links | An HTTP link checker | Offline resolution against the filename set | `[VERIFIED: curl, this session]` a nonexistent wiki page returns **HTTP 200**, so an HTTP checker cannot detect a broken wiki link at all. It would be a check that can only ever be green. |
| Committing from CI | A custom identity scheme | `git -c user.name=… -c user.email=…` on the commit, or the `github-actions[bot]` identity | Missing identity is a common first-run CI failure (`Please tell me who you are`), and per-invocation `-c` avoids mutating global config on the runner. |
| A test harness | pytest + conftest + sys.path shims for a single-file tool | `tools/wiki/selftest.sh` driving real git fixtures | See `## Discretion Areas — Settled`. Every property under test is a git/filesystem side effect or an exit code; a Python harness would either shell out to git anyway or mock it, and mocking is the failure mode this project has scars about. |

**Key insight:** every hard part of this phase is already solved by git, and every part git does not solve (rendering, page creation) is either GitHub's or the operator's. The tool's real job is not synchronisation — it is **refusing** things: refusing an illegal filename, refusing a `.md`-suffixed link, refusing an orphan, refusing a stale sidebar, refusing to pretend the wiki exists.

## Common Pitfalls

### Pitfall 1: The verification that asserts nothing (this repo has two, in the file you are told to copy)

**What goes wrong:** `tools/catalog/sync_to_subrepos.sh:88-90` and `:100-102`:

```
if diff -q "$FS_ROOT/include/messages.h" "$FS_ROOT/include/messages.h" >/dev/null 2>&1; then
    echo "  OK: firestarter/include/messages.h regenerated."
fi
```

The same path twice. Always true. It prints a success line for a property it never tested. This is the same defect class as the `catalog-sync-check.yml` scar (5 runs, 5 failures, never once asserting its property) and as v1.34's ~20 fixture-green rig defects.

**Why it happens:** the shape of a verification is easy to copy; the *reachability* of its failure branch is invisible on inspection.

**How to avoid:** for every assertion this phase authors, the plan must name the mutation that makes it fail and require that mutation to be **run and observed red**. That is what turns criteria 2, 4 and 5 from assertions into evidence. `## Validation Architecture` enumerates all 11.

**Warning signs:** a comparison whose two operands are derived from the same variable; a check whose failure branch has no test; a green CI leg whose red state nobody has seen.

### Pitfall 2: Publishing to the wrong branch, successfully

**What goes wrong:** the publish pushes `main` (or whatever `init.defaultBranch` resolves to) instead of `master`. Git reports success. GitHub serves only the wiki's default branch, so the wiki shows nothing new. Everything looks fine; nothing happened.

**Why it happens:** wiki repos are `master` — `[VERIFIED: git ls-remote --symref: gollum/gollum.wiki.git, nodejs/node.wiki.git, microsoft/vscode.wiki.git all report ref: refs/heads/master, this session]` — while the containing repo's default branch is `main` `[VERIFIED: gh api]`, and `init.defaultBranch` is unset in this container.

**How to avoid:** clone (never `init`) so the branch comes from the remote; push with an explicit refspec `origin master`; assert `git -C <worktree> rev-parse --abbrev-ref HEAD == master` before pushing, and fail loudly if not.

**Warning signs:** the wiki UI unchanged after a "successful" push; `git ls-remote` showing two branches.

### Pitfall 3: `GITHUB_TOKEN` 403 on the wiki push

**What goes wrong:** `remote: Permission to henols/firestarter_prom.wiki.git denied to github-actions[bot]`.

**Why it happens** — in descending order of likelihood here:
1. **The workflow omits `permissions: contents: write`.** `henols/firestarter_prom` has `default_workflow_permissions: "read"` `[VERIFIED: gh api repos/henols/firestarter_prom/actions/permissions/workflow]`, so the token is read-only by default. This will bite unless declared.
2. Reusing `actions/checkout`'s `http.https://github.com/.extraheader` credential for a different remote.
3. Genuinely needing a PAT — reported for cross-repository wiki pushes; the widely-used `github-wiki-action` documents `${{ github.token }}` as sufficient for the *same* repository's wiki with `contents: write` `[CITED: github.com/Andrew-Chen-Wang/github-wiki-action]`.

**How to avoid:** declare `permissions: contents: write` at job level; clone the wiki into a directory *outside* the checkout with an explicit tokenized URL (`https://x-access-token:$TOKEN@github.com/OWNER/REPO.wiki.git`); never `set -x`; make the token source a single variable so swapping `secrets.GITHUB_TOKEN` for a PAT secret is a one-line change. **Record in the phase which one actually worked** — this cannot be known until the wiki exists.

**Warning signs:** 403 on push only, clone fine (the wiki is public, so anonymous clone works — `[VERIFIED: anonymous clone of gollum's wiki with global config disabled]`).

### Pitfall 4: A page title that needs a literal hyphen

**What goes wrong:** Gollum replaces U+002D `-` in the filename with a space in the displayed title. `AT28C04-Adapter.md` renders as "AT28C04 Adapter", not "AT28C04-Adapter". The hyphen cannot be recovered `[CITED: gollum/gollum issue #764 — "dashes in wiki page titles are silently replaced with spaces"; U+2010 is the documented workaround]` and `[VERIFIED: the page title of gollum's own `5.0-release-notes.md` renders as "5.0 release notes"]`.

**Why it matters here:** Phase 168 renames 13 files into this scheme, and several carry meaningful hyphens or slashes in their conceptual titles — `AT28C04-ADAPTER`, `PY32F071-FIRMWARE-INSTALL`, `sram-nvram-behavior` (conceptually "SRAM/NVRAM", and `/` is an **illegal** title character), `infoic-field-dictionary`, `protocol-id`.

**How to avoid:** the `links`/name-legality leg flags any filename whose stem contains a hyphen adjacent to a digit-or-uppercase run that reads as a part number, and requires the author to confirm the rendered title. Simpler and more honest: the phase writes down the rendered title for every page it creates, and Phase 168's migration table (D-04) carries a **rendered-title column** so the loss is visible at review time rather than discovered on the live wiki. Do not use U+2010 to smuggle a hyphen through — an invisible non-ASCII character in a URL that Phases 169/170 must hand-write into READMEs is a worse problem.

**Warning signs:** a page title in the sidebar that reads as two words where one was intended.

### Pitfall 5: GitHub's read path is far more forgiving than the check

**What goes wrong:** a link, casing error or `.md` suffix works on GitHub, so nobody notices, and then a rename or a Phase-168 import breaks it invisibly.

Measured this session with `curl`:

| URL | Result |
|-----|--------|
| `/wiki/Installation` | 200 |
| `/wiki/installation` | **200, no redirect** — lookup is case-insensitive |
| `/wiki/Installation.md` | **302 → `raw.githubusercontent.com/wiki/…`** — raw markdown, not the page |
| `/wiki/Installation/` | 200 |
| `/wiki/Known%20limitations` | 200 (space form of `Known-limitations`) |
| `/wiki/No-Such-Page-Xyz` | **200** — a nonexistent page is not a 404 |

**How to avoid:** the checker is deliberately stricter than the service — case-sensitive, extension-free, one link form. And no live HTTP check anywhere: the 200-for-missing-page result means an HTTP check would be structurally incapable of failing.

### Pitfall 6: A red-by-default or fail-open CI check

**What goes wrong:** a drift check that compares against a wiki which does not yet exist is red from the day it merges until Phase 168 publishes. D-07 rejected cron for exactly this, and `catalog-sync-check.yml` proves red checks get ignored here. The reflexive fix — warn-and-exit-0 when the wiki is absent — is worse: the check can no longer fail for its own reason.

**How to avoid:** the recommendation in `## Discretion Areas — Settled` → CI sequencing: ship only the offline legs to CI now; author the wiki-comparison leg's *code* now and prove it against the fixture; wire its CI trigger in the operator-gated task. Nothing red, nothing fail-open, nothing unproven claimed as proven.

### Pitfall 7: Idempotence broken by incidental bytes

**What goes wrong:** the publish is idempotent in principle but a timestamp, a trailing-newline difference or a CRLF conversion makes every run produce a commit.

**How to avoid:** the `codegen.py` determinism contract applies to `_Sidebar.md` (no timestamps, LF via `newline="\n"`, deterministic sort). Consider `.gitattributes` in the wiki source if any tool ever touches line endings. Assert the property directly: two `--push` runs, `rev-parse` equal.

### Pitfall 8: Committing the phase's own scaffolding into the wrong repo or branch

**What goes wrong:** the meta repo *is* `firestarter_prom` (`origin = https://github.com/henols/firestarter_prom.git`, `[VERIFIED: git remote -v]`), and work is on `gsd/v1.35-documentation-consolidation-wiki-migration`. `wiki/` and `tools/wiki/` are new **tracked top-level paths in the meta repo** — a first for a repo whose `CLAUDE.md` says it tracks only `.planning/` and `.claude/`.

**How to avoid:** commit in the meta repo on the milestone branch (no submodule involvement at all in this phase), and update `CLAUDE.md` + `.planning/codebase/STRUCTURE.md` in the same phase so the documents of record stay true.

## Discretion Areas — Settled

### 1. Wiki push authentication

**Recommendation:** `secrets.GITHUB_TOKEN` + `permissions: contents: write`, with a PAT as a pre-planned, one-line fallback.

| Option | Cost | Verdict |
|--------|------|---------|
| `secrets.GITHUB_TOKEN` + `permissions: contents: write` | Zero new secrets, zero rotation, scoped to this repo and this job. Documented as working for the same repo's wiki `[CITED: github-wiki-action]`. Unprovable until the wiki exists. | **Recommended.** |

| Local push (the criterion 2/3 demonstrations) | Nothing to do: `gh auth git-credential` is already the credential helper for `https://github.com` and the token carries `repo` `[VERIFIED: git config --get-regexp credential + gh auth status]`. | Already solved. |

### 2. Language for `tools/wiki/`

**Recommendation:** one stdlib-only Python file, `tools/wiki/wiki.py`, plus a bash fixture driver `tools/wiki/selftest.sh`. No bash wrapper around the Python.

- The tool's four jobs are: git orchestration (bash-natural, but trivial via `subprocess`), markdown link extraction that must skip fenced/inline code (materially awkward in bash), deterministic sidebar generation (the `codegen.py` determinism contract is Python), and one shared comparison path (D-08 — one language, or D-08 is a fiction).
- Precedent supports it: `codegen.py` is stdlib-only Python with `argparse`, and the project convention is `#!/usr/bin/env python3`, module docstring doubling as usage text, `from __future__ import annotations`, stdlib only, Black-formatted `[CITED: .planning/codebase/CONVENTIONS.md]`.
- A `publish.sh` wrapper adds a file that can drift from the Python for zero gain; `python3 tools/wiki/wiki.py publish --push` is one command and satisfies WIKI-03 literally.
- The bash driver is right for the *tests*: it builds bare repos and asserts exit codes with no mocking.

### 4. CI sequencing (resolving Pitfall 6)

**Recommendation, in this order:**

## Fixture Faithfulness

**What the local bare-repo fixture does prove** (all executed this session):

- The publish is idempotent: two runs, one commit, `HEAD` unchanged.
- In-repo source overwrites a wiki-side edit (the authority direction of WIKI-02).
- A source-side deletion propagates (the wiki stays a true mirror, which criterion 4's whole-directory diff requires).
- The dry-run detects drift and exits non-zero; the same code path pushes with `--push`.
- Sidebar staleness, orphans, broken links, illegal names and disallowed link forms are each detected — because these are pure filesystem/text properties with no service tier at all.
- `master` is the branch that gets pushed.

**What it does NOT prove** — the residual risk list for the gated live re-run:

| Residual risk | Why the fixture cannot cover it | Detected by |
|---|---|---|
| Push authorization from Actions (`GITHUB_TOKEN` vs PAT) | No GitHub auth layer in a local bare repo | First live CI publish; record which credential worked |
| Local push authorization to a real wiki | `gh auth git-credential` is configured but never exercised against `.wiki.git` | First local `--push` |
| That pushing `master` actually makes pages **live** | A bare repo has no renderer | Load `https://github.com/henols/firestarter_prom/wiki` and read it |
| That `_Sidebar.md` renders as the sidebar | Gollum-side behaviour | Visual check on the live wiki |
| Rendered page titles (the `-`→space loss, Pitfall 4) | No renderer | Visual check; record rendered titles |
| Wiki-side server hooks / rejected refs / size limits | Absent locally | First live push |
| Operator's hand-created first page colliding with `Home.md` | The wiki does not exist | First live publish — expect it to be **overwritten**, which is criterion 2 happening for real |
| GitHub's case-insensitive / `.md`-redirect read behaviour interacting with real reader links | Fixture has no HTTP layer | Already measured against a third-party wiki this session; re-confirm once on ours |

## Open Questions

1. **Does the CI publish need a PAT?**
   - What we know: `default_workflow_permissions` is `read` on this repo, so `permissions: contents: write` is mandatory either way; a widely-used wiki action documents `github.token` as sufficient for same-repo wiki pushes.
   - What's unclear: whether GitHub's wiki endpoint accepts the Actions token for this account/repo. Unknowable until the wiki exists.
   - Recommendation: build for `GITHUB_TOKEN`, keep the token source a single variable, and treat the first live run as the measurement. Record the outcome in the phase record — do not pre-write "verified".

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | Push credential is `secrets.GITHUB_TOKEN` with least-privilege `permissions: contents: write`; classic PAT only on a measured 403. Never a credential in a tracked file. |

### Known Threat Patterns for this stack (bash + python + Actions + git push)

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Token leakage via logged remote URL | Information disclosure | Compose the URL at push time from an env var; no `set -x`; no `echo` of the remote; prefer `git -c http.extraheader=` or a credential helper over an in-URL token |
| Over-privileged CI token | Elevation of privilege | Job-level `permissions: contents: write` on the publish job only; `contents: read` on the check job |
| `rm -rf` on the wrong directory during the mirror wipe | Denial of service / destruction | Resolve the worktree path absolutely, assert it is a git worktree, assert its `origin` matches the expected wiki remote, then delete with `-mindepth 1 -maxdepth 1 -not -name .git` |
| Command injection through a page filename | Tampering | `subprocess` list form, no shell; validate names against the legality allowlist before use |
| Untrusted PR content reaching a privileged job | Elevation of privilege | Use `pull_request` (not `pull_request_target`); the check job has no write permission and pushes nothing |
| Force-push destroying wiki history | Tampering / repudiation | Never force-push; clone-based publish only |
| Unpinned third-party action | Tampering (supply chain) | Use only `actions/checkout@v4`; introduce no wiki-publishing marketplace action — the whole publish is ~15 lines of git |
| A silently-passing integrity check | Repudiation (false assurance) | The 11 observed-red negative cases. This is the phase's primary security-of-process control and the one this repository has historically failed. |
