# Phase 118 Plan 07 — OBS-04 Leonardo SDP Emit Duration Measurement

**Written:** 2026-07-28 (Plan 118-07)
**Firmware build uploaded:** `firestarter` HEAD `1880054` on branch `v1.22-at28c-software-data-protection-lifecycle`

---

## 1. What was measured, and what it is not

This document records the wall-clock duration of the firmware **emitting the six SDP-disable
command writes** — `EEPROM_SDP_DISABLE[6]` — measured with two `micros()` reads placed
immediately outside `eeprom28c_emit_command_sequence(...)` in `eeprom28c_write_init`
(`firestarter/src/proms/eeprom_28c.cpp`), captured from one real Arduino Leonardo, on one
`firestarter write at28c256 --force` invocation.

**The subject of this measurement is the emitter, never the chip.** `micros()` bracketing six
latch writes says nothing about AT28C silicon: it does not show that the sequence is accepted
by a die, that any part enters or leaves the software-data-protected state, or that t_BLC is
met **as accepted by the die** — `.planning/REQUIREMENTS.md`'s §"Validation Ceiling" lists that
last item explicitly, by name, as **not provable without an AT28C part**. There was no AT28C
part on the bench for this run — the socket was empty (see §5). Everything below this line is a
measurement of code running on a microcontroller driving its own output latches, not an
observation of any chip's electrical or protection state.

Exit code: `0` (the CLI process itself exited 0; the *operation* reported failure via its own
`ERROR:` lines and `Write to AT28C256 failed.` — see the note on this divergence in §5).

**A note on the expected chip-id mismatch warning that did NOT appear.** The plan anticipated a
`--force`-demoted chip-id-mismatch warning ahead of the unlock lines. It did not occur, for a
reason visible in the captured `EPROM data` line above: `at28c256`'s database entry carries
`'chip-id': 0`, and per `firestarter/CLAUDE.md` / the wire-field convention, `chip-id: 0` means
"skip ID check" — so `eeprom28c_check_chip_id`'s early-return path is never reached for this
chip at all, matching or mismatching. This is a **stronger** confirmation of D-01, not a weaker
one: the two report lines (`I: SDP unlock: disabling write protection` /
`I: SDP unlock emitted in 572 us`) are emitted **unconditionally**, with no identity-check gate
of any kind in front of them — exactly what "unconditional INFO-band call sites" means. The
downstream failure that *does* appear (`ERROR: Not blank, at 0x000000, v: 0x40`) is the blank
check reading a non-0xFF value off the empty socket's floating bus — an **expected** consequence
of an unpopulated socket, not a defect, and it occurs strictly after the unlock sequence and its
two report lines have already completed and been logged.

## 4. The number

```
MEASURED SDP EMIT DURATION: 572 microseconds
```

**t_BLC budget it was compared against:** `sdp_seq_len × AT28C_TBLC_MAX_US` =
`6 × 100 = 600 microseconds` (`EEPROM_SDP_DISABLE[6]` — six command writes — and
`AT28C_TBLC_MAX_US 100`, both in `firestarter/src/proms/eeprom_28c.cpp`).

**`MSG_WARN_SDP_TBLC_EXCEEDED` did NOT fire.** Confirmed by the absence of any `W:` line in §3's
raw log. 572 µs is under the 600 µs budget, with 28 µs of headroom. A non-firing latent
invariant here is the **expected and correct** outcome on a 16 MHz AVR under the post-Phase-117
bare `set_data` loop (`pulse_delay = 0`, no inter-byte wait) — it is not an absence of evidence;
it is the runtime check (D-09) actually running, evaluating true-negative, and staying silent
exactly as its own source comment predicts (`eeprom_28c.cpp` around the `sdp_tblc_budget_us`
comparison: *"this branch should never fire ... that is exactly what a latent invariant looks
like"*).

## 5. Socket state, stated plainly

The socket was empty for this entire run, per the operator's statement on 2026-07-28 ("Leonardo
is connected with an empty socket"). This does not affect the measured number: §4's duration is
the time the Leonardo's own MCU spends driving its own output latches through six writes —
nothing about that timing depends on what, if anything, is seated in the socket. This is also
exactly why no operator confirmation was needed or requested before this run (D-12): the
socket's contents are not a variable this measurement depends on.

The run's downstream `ERROR: Not blank, at 0x000000, v: 0x40` and the overall
"Write to AT28C256 failed." outcome are exactly what an empty socket produces on the very next
step (the blank check reading a floating, non-erased-looking value) — and that failure occurs
*after* the number in §4 was already captured, so it does not compromise the measurement.

## 6. Validation ceiling

Quoted verbatim from `.planning/REQUIREMENTS.md` §"Validation Ceiling":

> **Permitted claim at close:** *"The SDP lock and unlock sequences are emitted exactly as
> specified, verified byte-exact by golden register trace across all four `0x0D` pinouts, with a
> documented and measured host-side timing assumption."*
>
> **Forbidden claim:** *"SDP lock/unlock works on an AT28C256."*

This measurement sits entirely inside the permitted claim's *"documented and measured host-side
timing assumption"* clause — the 572 µs figure, its 600 µs budget comparison, and this document's
full provenance chain are precisely that documentation and measurement. It supports **nothing**
in the forbidden claim: this run does not, and cannot, show that SDP lock/unlock works on an
AT28C256, because no AT28C256 was present.

`0x0D` stays **`UNVERIFIED`**. **Zero** chips change `support_status` as a result of this
document. The **84-chip** count is unchanged. This number must **NOT** be recorded in the
`PROTOCOL-LEDGER`: that file records bench-verification status against silicon, and entering a
software-emitter timing figure there would invite exactly the ceiling-crossing misread this
milestone's validation ceiling exists to prevent — a reader skimming the ledger could mistake
"a duration was measured on real hardware" for "the sequence was verified against real silicon,"
which is precisely the forbidden claim above. The number's only correct home is this standalone
document, cross-referenced by name from wherever it is needed next.
