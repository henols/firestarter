Six steps, in order. Capture the verbatim stdout of every command; Task 2 writes it up.

**Step 1 — enumerate and identify the port.** List `/dev/ttyACM*` and `/dev/ttyUSB*`. At plan time
three devices were present (`/dev/ttyACM0`, `/dev/ttyACM1`, `/dev/ttyUSB0`) and their numbering
shuffles across replug, so **do not assume** which is the Leonardo. For each candidate `ACM` port, run
`firestarter fw` against it and capture the `Current firmware version: ..., for controller: ... on port
...` line. The Leonardo is the port whose `controller:` value identifies a Leonardo. Record the
identity line for the port you select, verbatim. This is standing bench discipline and it is a
Claude-side check — do not ask the operator which port to use.

**Step 2 — build and record build identity.** `cd /workspaces/firestarter && pio run -e leonardo`.
Capture the flash and RAM figures and confirm they match the figure Plan 118-06 recorded — if they
differ, the working tree has drifted since the sweep and you must stop and report. Record the firmware
git SHA (`git -C /workspaces/firestarter rev-parse --short HEAD`) and its branch as the build identity.

**Step 3 — upload.** `cd /workspaces/firestarter && pio run -t upload -e leonardo`, targeting the port
identified in Step 1 if the upload needs it explicitly. The Leonardo is **exempt** from the Uno-class
chip-OUT-before-sideload rule (that rule exists because Uno-class uploads drive the shield bus), so no
socket manipulation is required and none may be requested. Re-run `firestarter fw` after the upload and
capture the identity line again — it proves the board is running the firmware you just built.

**Step 4 — prepare a payload.** `firestarter write` needs an input file. Create a small deterministic
file in the scratch directory — 64 bytes is enough, because the SDP unlock happens once in
`eeprom28c_write_init` regardless of payload size. Record the exact byte count and content pattern you
used. If the host rejects a file shorter than the chip's `memory-size`, pad to the full 32768 bytes for
`at28c256` and record that instead. Do not use a repo file as the payload; the record must state
exactly what was written.

**Step 5 — the one run.** Issue `firestarter write at28c256 --force <payload>` against the identified
port, and capture the **complete verbatim output**. `--force` is load-bearing here: with an empty
socket the chip-id check mismatches, and `--force` demotes that to a warning so
`eeprom28c_write_init` proceeds past its early return into the unlock path. Without it the run returns
before the SDP emit and measures nothing.

Expect in the output: the chip-id mismatch warning, then `MSG_INFO_SDP_UNLOCK`'s rendered line, then
`MSG_INFO_SDP_UNLOCK_DONE_US`'s rendered line carrying the measured microsecond value, then the write
failing further downstream because the socket is empty. **The downstream failure is expected and is
not a defect** — the measurement is complete the moment the duration line is emitted. Record the
measured microsecond value exactly as printed; do not round it.

Also note whether `MSG_WARN_SDP_TBLC_EXCEEDED` appeared. On a 16 MHz AVR it should not; if it did,
record the value and state that a real board exceeded the t_BLC budget — that is a genuine finding and
Phase 119's LOCK-06 judgement needs it, but do not fix it here.

**Step 6 — if anything fails, take D-14.** If the board does not enumerate, the upload fails, the
identity line never names a Leonardo, or the run never reaches the duration line: **PROCEED**. Do not
retry more than twice, do not fall through to the Uno, and do not fabricate a value. Record
not-measured with the exact failure and the exact command that produced it. OBS-04 then closes
software-complete with the gap stated explicitly, following this project's CI-PENDING /
structurally-green discipline from Phase 98 and Phase 103. Hard-blocking a requirement on one USB
enumeration was explicitly rejected.

Do not run any other command against the board. One write, one measurement. No monitor loop, no
voltage-rail command, no repeated sweeps.
