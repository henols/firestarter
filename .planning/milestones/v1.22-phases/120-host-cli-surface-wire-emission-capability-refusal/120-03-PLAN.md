## ⚠ Two CONTEXT.md corrections established by research — these override CONTEXT.md

1. **The target function is `_log_rurp_feedback`, not `_log_response`.** CONTEXT.md D-09 names `_log_response`; no such function exists. The line numbers CONTEXT gives (`serial_comm.py:232-247`, mapping at `:233-238`) are correct; only the name is wrong (RESEARCH F-12).
2. **The blast radius is SIX unconditional INFO-band ids, not five.** CONTEXT.md D-09 names `0x5E`, `0x5F`, `0x60`, `0x61`, `0x62`. The sixth is **`MSG_INFO_HW` (`0x5B`)**, emitted through `LOG_WARN_ID_U8` at `rurp_hw_rev_utils.h:96` — which `logging_id.h:115` makes a plain **unconditional** alias for `LOG_ID_U8` — while its *catalog* severity is `INFO`. Firmware intended WARN; the host takes severity from the catalog, so the frame arrives as `INFO` and is discarded today. That is Phase 35's CR-02 "hard-fail-loud" revision warning, **invisible at default verbosity**, and it fires exactly on shields whose revision detect is inconclusive with no EEPROM override — the operator's Rev 2.2 / Rev 2.0 / modified-Rev-0 rotation. So D-09 also partially fixes a second, older observability defect (RESEARCH F-07).

**Existing-test impact: none.** The whole suite was searched for level assertions on the `SerialComm` logger and for record-count assertions (`not caplog.records`, `len(caplog.records) ==`, `caplog.records == []`) — zero hits. `tests/test_decoder.py` asserts at `logging.WARNING` on the codec's own warnings and `test_severity_routing_preserves_response_shape` asserts only that `Response.type` is a string label. `tests/test_serial_comm.py:103` uses `caplog.at_level(logging.DEBUG, ...)`, unaffected by a promotion. **Zero existing tests move; this plan's tests are purely additive.**
