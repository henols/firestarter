## ⚠ The highest-severity finding this plan defends against

`resolve_chip(name, db)` returns `db.convert_to_programmer(db.get_eprom(name))`, whose measured keys are exactly `memory-size`, `algorithm`, `pin-count`, `vpp_mv`, `pulse-delay`, `chip-id`, `flags`, `bus-config`. **No `protocol-id`, no `electrical-type`, no `name`.**

`check_eprom_blank`'s SRAM/FRAM short-circuit reads the two absent keys and was measured returning `False` for a real SRAM part. Both its production callers pass that dict (`cli_handlers.py:576`, `chip_test.py:737`), so **the `_SRAM_PROTO_IDS` short-circuit is vacuous in production.** PROJECT.md SIXTH CORRECTION item 6's KEEP disposition stands; its stated *reason* — that the short-circuit fires and produces a better message — is false. Do not fix it, do not delete it. Record it (plan 120-11 carries the PROJECT.md correction).

The point for this plan: a `sdp_capability` implementation that read `eprom_data_dict["protocol-id"]` would reproduce that identical silent vacuity. The shape leg below is the validation surface this phase **invents**, because the existing in-tree precedent lacks it and is vacuous as a result.
