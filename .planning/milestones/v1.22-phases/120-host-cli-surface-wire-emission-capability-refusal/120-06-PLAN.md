## Two facts to pin so nobody later reads them as bugs

1. **The emitted `flags` value on the SDP path will be `2`, not `0`.** `_setup_operation` does `command_dict["flags"] = eprom_data_dict.get("flags", 0) | operation_flags`, and `database.py:570-595` sets `FLAG_CAN_ERASE` (`0x02`) for every `EEPROM` / `Flash/EEPROM` part with `algorithm != 5` — including all 84 `0x0D` chips, where `configure_eeprom28c` never reads it (documented firmware-inert in that comment block). Pin `flags == 2` in a test with a comment saying why, so a future reader does not read it as a defect. Do **not** attempt to suppress it — the wider `0x0D` flag-surface honesty problem is deferred.
2. **NULL `init`/`end` in firmware does not skip the INIT and END frame pairs.** Phase 119 corrected that reading: `_execute_phase("INIT", ...)` and `_execute_phase("END", ...)` both run and both `send_ack()`. What is absent is the `DONE` round-trip and any `#` data frame. `erase_eprom`'s shape already survives this.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host operation layer → serial wire | The composed `command_dict` is the last host-side artifact before bytes reach hardware. A wrong `cmd` or `flags` value drives the wrong physical operation. |
| flag-mapping function → every command | `build_flags` is shared by every operation, so a positional insertion corrupts unrelated commands' flags. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
