<objective>
Expose `--skip-sdp-unlock` on `write`, thread the bit through the one function that maps wire flags, and apply HOST-04's capability refusal to the `write` path's **automatic** unlock with a mandatory report line (HOST-02 D-17/D-18/D-19; HOST-04 D-04). Closes HOST-02 and HOST-04.

Purpose: firmware keys its auto-unlock on **protocol**, not on part. So on a capability-refused `0x0D` part, today's `write` already emits the SDP sequence before the payload — leaving `0x2AAA` set to `0x55` and `0x5555` set to `0x20` as stored data at the bus-truncated magic addresses. A full-image write overwrites both; an address-ranged or short write does not. The auto-unlock **is** an SDP command reaching those parts, so HOST-04's intent covers it.
Output: the CLI option, the auto-set with its report line, D-18's warn-and-proceed, tests, and HOST-02 + HOST-04 ticked.

## Own the divergence — it is deliberate, and it is not a no-op

`write` behaviour for the capability-refused `0x0D` subset **diverges from `3.0.0b11`**. That must be stated in the SUMMARY as a deliberate host-side change, never as a no-op.

The cost argument, restated on the derived partition: over-refusal would cost a working `write` only on a part that genuinely **has** SDP and is genuinely **locked**. For a part with no SDP there is nothing to unlock, so suppressing its auto-unlock is a no-op *for that part* and additionally avoids the three stored bytes. **On the derived 43/41 partition, refusal has no cost for the parts it refuses** — the trade-off is dissolved, not decided. Residual risk is confined to `120-WATCHLIST.md`'s nine entries.

## Where the auto-set lives, and why

In the `write` **Click handler**, not in `write_eprom`. The handler is the last place that has both the chip **name** and `app.db`; `resolve_chip`'s programmer dict has neither (RESEARCH F-06, measured). It is also where the report line belongs, because the line must be visible at default verbosity.
