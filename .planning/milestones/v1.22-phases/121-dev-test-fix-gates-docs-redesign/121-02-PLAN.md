<objective>
Close the host-side phantom-success dispatch class before this phase adds an op string that would trigger it.

Purpose: RESEARCH Pitfall 1a is the single highest-risk item in Phase 121, and it was reproduced empirically: `_dispatch_multi_run("write-partial", "AT28C256", {"memory-size": 32768}, op, runs=2)` calls `erase_eprom` twice and returns `verdict=OK`. On a UV-EPROM that surfaces as `BAD`; on an EEPROM it silently erases the part and reports success. `_dispatch_step` tests `OP_ID`, `OP_BLANK_CHECK`, `OP_READ` and then falls through unconditionally, and `_dispatch_multi_run`'s dispatch ends in a bare `else: # OP_ERASE`.

This is the same architectural shape LOCK-04/D-06 fixed at the firmware op layer in Phase 119 (`op_execute_stateful_operation`'s NULL-`main` refusal). The host has the identical defect and nobody has looked.

Output: two refusing arms, a live `_MULTI_RUN_OPS`, and a RED-then-GREEN proof whose load-bearing assertion is `erase_eprom.assert_not_called()` — never an exit code.

Repo: `/workspaces/firestarter_app` on branch `v1.22-at28c-software-data-protection-lifecycle`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plan step (`Step.op`) → operator method | An op string chooses which chip-mutating operator method runs; an unmapped string currently selects erase |
| dispatch result → diagnostic report | A fabricated `OK` verdict becomes community-facing evidence |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-121-05 | Tampering | `_dispatch_multi_run`'s terminal `else` arm | critical | mitigate | Explicit `elif op == OP_ERASE:` plus a refusing `else:` hoisted above every side effect; proven by `erase_eprom.assert_not_called()` on a real unmapped op |
| T-121-06 | Repudiation | `StepResult.verdict` on an unmapped op | critical | mitigate | Refusal returns `VERDICT_BAD` with `run_count=0` and a reason naming the op — the report can never claim `OK` for an action not performed (117 D-05, 118 D-02, 119 D-12, 120 D-11) |
| T-121-07 | Tampering | `_dispatch_step`'s unconditional fall-through | high | mitigate | Membership test against the now-live `_MULTI_RUN_OPS` allow-list; anything outside it refuses |
| T-121-08 | Denial of Service | temp-file creation on an unmapped op | low | mitigate | The refusal is hoisted above `NamedTemporaryFile`, so no orphan file is created on the refusal path |
</threat_model>
