<objective>
Land DEVTEST-01's host half at its root cause: clear `FLAG_CAN_ERASE` for protocol `0x0D`, and give the resulting `NA` erase step a reason a community tester can act on.

Purpose: `firestarter/src/proms/eeprom_28c.cpp` contains no erase-capability reference at all — `configure_eeprom28c` has no erase operation whatsoever. The host nonetheless advertises the capability for all 84 protocol-`0x0D` chips, so `dev test` plans a real erase step that reports OK having done nothing, auto-tagging otherwise-passing runs `community-fail`. Phase 119 closed the firmware half with a generic op-layer NULL-`main` refusal; this is the host half.

D-12 chose the root-cause fix over a `derive_plan`-local branch, and that choice reverses `database.py`'s explicit standing note that the flag must stay set on `0x0D`. Per project convention (119 D-18, 120 D-20) a reversal is recorded as a reversal, in-source and in-test, with its constraints named.

One real behavioural change, benign and worth recording: today `firestarter erase at28c256` passes the firmware's erase precondition and is then refused by Phase 119's NULL-main guard. After D-12 it is refused one layer earlier, at that precondition. Both emit the same not-supported message id, so the observable wire id is unchanged.

Output: a one-condition change in the DB transform, a family-fact NA reason, two inverted pinned tests, and a re-verified blast radius.

Repo: `/workspaces/firestarter_app` on branch `v1.22-at28c-software-data-protection-lifecycle`. No firmware source is edited by this plan.
</objective>
