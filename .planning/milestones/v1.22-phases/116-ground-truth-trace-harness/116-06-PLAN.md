**Suite body — seven cases.**

Cases 1-3, one per DIP28/DIP24 pinout (`AT28C256`, `AT28C64`, `AT28C16`): build the handle from the
matching `SDP_BUS_CONFIGS` row with `chip_id` 0 and `FLAG_SKIP_BLANK_CHECK`; call
`configure_memory(&h)`; re-assign **both** `firestarter_get_data` and `firestarter_set_data` to the
address-keyed mocks (the retired suite's comment covered only the read pointer); reset the register
cache to `(0x00, 0x00, 0x00)`; clear strobes; call `h.firestarter_operation_init(&h)`; then assert
the recorded stream equals `SDP_FIXED_<PINOUT>` element-wise via the shared comparator.

Using the address-keyed mock for the completion poll is what makes full-stream equality possible
rather than a prefix assertion: the mock satisfies no bus traffic, so the 2000-iteration timeout
loop contributes zero strobes and the recorded stream is exactly the command window. Assert
`strobe_overflowed()` is 0 and record this choice in `RED-BASELINE.md` — it resolves RESEARCH Open
Question 2 in favour of the stronger assertion.

Cases 4-5, the two `DIP32_28C512_EEPROM` size bands (`AT28C010` 128 KB and `AT28C040` 512 KB), each
a **deliberate stale-upper-address case** per CORRECTION 3. A plain DIP32 trace is decorative: that
pinout's `rw` line lands in CONTROL, which the shipped path never writes, so shipped and fixed
address bytes are byte-identical and the case would be GREEN today and stay GREEN after the fix,
proving nothing. Instead, establish a register state in which CONTROL's upper-address bits
`CTRL_ADDRESS_LINE_17` and `CTRL_ADDRESS_LINE_18` are HIGH before the sequence runs, simulating a
preceding high-address operation. Then the shipped path leaves them set — write-inhibited and with
the chip's upper address wrong — while the fixed path writes CONTROL and clears them, producing a
large, unambiguous divergence that is FIX-03 made visible.

Per RESEARCH Open Question 1, establish that state **two different ways** so a reviewer cannot
object that a directly-seeded cache is unrepresentative:
- case 4 seeds it directly through the cache-reset seam
- case 5 reaches the same state by performing a real preceding high-address read through
  `memory_get_data` before clearing strobes and driving the sequence

Both then assert against the corresponding `SDP_FIXED_DIP32_*` array. Document which mechanism
produced the state in each case's header comment and in `RED-BASELINE.md`.

Cases 6-7, the two migrated identity-gate assertions D-12 routes here (with CORRECTION 2's fix
applied): the matching-identity case asserting the response code is not `RESPONSE_CODE_ERROR`, and
the mismatching-identity-with-force case asserting `RESPONSE_CODE_WARNING`. Both are RED today.
CORRECTION 2 measured why the second one is RED and D-12 did not anticipate it: the identity helper
sets `WARNING` under the force flag, then `eeprom28c_write_init` continues — the completion wait is
unconditional, there is no flag to skip it — and the wait overwrites the response code with `ERROR`.
State in that case's comment that its RED-ness is **second-order evidence of the inverted check**:
the check does not merely fail, it destroys severity information. Do not weaken this assertion; the
force/severity fork is exactly what the v1.16 Phase-89 CR-01 regression slipped through.
