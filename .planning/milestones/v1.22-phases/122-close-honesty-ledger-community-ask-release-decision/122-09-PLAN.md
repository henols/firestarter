Cover, in this order:

1. **What this prerelease is.** A beta of the firmware for the RURP shield, carrying three board builds as
   `.hex` assets: `firestarter_leonardo.hex`, `firestarter_uno.hex`, `firestarter_uno328pb.hex`. Name the
   normal way to install them (`firestarter fw --install`, which pulls the firmware matching the host
   app's channel) and note that the three files are also attached directly.

2. **The headline: the AT28C Software Data Protection sequences now actually reach the chip.** State the
   defect honestly and in the past tense: the SDP-disable sequence that shipped for years was emitted
   through a shared helper that bypassed the address-bus remap, so on the 28C-family pinouts at least one
   command write went out with `/WE` held HIGH — a documented Write Inhibit — and the sequence's own
   success check was *inverted*: both datasheets state the command bytes are not written to the device, so
   the check could only pass when the sequence was **not** recognised. Both are now fixed: a
   family-local, remap-aware command emitter, and a completion signal that is not anti-correlated with
   success.

3. **A second, separate defect fixed in the same area — the one more likely to have caused reported
   write failures.** Per-page write verification previously sampled a single byte per 64-byte page, so a
   partial write could report success. Verification is now per-byte with the failing address attributed,
   and page completion polling is split from readback verification. Say plainly that this is a
   *conflation* fix, not a sampling-rate tweak.

4. **New capability: SDP lock as well as unlock.** The lock (enable) sequence is emitted as three loads
   followed by the write-cycle wait with no data payload; both lock and unlock are invocable as standalone
   commands. The auto-unlock that always ran on a 28C write is now **reported** — one line before the
   sequence and one after, never inside it — and can be declined.

5. **What is proven, stated exactly.** In substance: the SDP lock and unlock sequences are emitted exactly
   as specified, verified byte-exact by golden register trace across all four 28C-family pinouts, with a
   documented and measured host-side timing assumption. Give the measured timing: the unlock sequence
   takes 568 µs on a Leonardo, 412 µs on an Uno and 424 µs on a 328PB-Uno, against a 600 µs budget derived
   from the 100 µs-per-byte datasheet maximum. Do not average or round these, and do not present the
   separately-measured 572 µs Leonardo figure as a different result — mention it, if at all, as a second
   observation of the same emitter.
