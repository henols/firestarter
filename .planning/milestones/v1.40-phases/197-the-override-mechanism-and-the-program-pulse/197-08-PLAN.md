<objective>
Answer the community report that started this milestone, honestly, and decide with the operator when
a version exists to name.

gh#70 is a `dev test` failure on `MBM27C1000` — `id` OK, `read` OK twice, `write-partial` bad with a
byte failing to program within 25 pulses at the top of the address space, and `verify` bad at the
same address. The reporter attached the part's real datasheet. This phase corrected the database
defect that datasheet reveals: the program pulse was 100 µs against a 500 µs specification, five
times short.

That correction is real and it is almost certainly not the cause of the reported failure. The
maintainer has already posted a competing hypothesis on the thread and explicitly asked that it not
harden the wrong way. Research then surfaced something neither party had: the MBM27C1000's own pin
assignment is the mirror image of the pinout the database gives it, and it explains a deterministic
stop at the top of the address space far better than any timing margin does. That finding is
inferred, unbenched, and contradicts an earlier cross-check published on the same thread — which was
drawn from the sibling part's datasheet, before this one was available.

An answer that says "we fixed the pulse" and stops would be the same class of error the maintainer's
own comment warns against. So the answer carries all of it: what was corrected, what it does not
explain, what the firmware still does not do, and what is being routed separately.

**PULSE-04 needs a version this phase cannot produce.** A push to `beta` in `firestarter_app`
publishes to PyPI and can never be undone. The checkpoint in Task 2 is where that is settled, not a
place where the executor guesses.

Purpose: close the loop with the reporter without over-claiming, and put the version question to the
person who owns releases.
Output: a committed answer artifact and either a posted comment or a recorded, reasoned deferral.
</objective>
