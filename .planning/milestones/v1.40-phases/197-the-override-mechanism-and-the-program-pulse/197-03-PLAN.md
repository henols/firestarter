<objective>
Harden the override mechanism the tracer proved, and move the first hardcode into it.

Plan `197-02` landed three per-field fail-closed legs because they are inherent to the substitution
loop. This plan lands the two that need whole-file knowledge — an override key that matches no row
anywhere in the 746, and two keys resolving to the same row and field — plus the sort-order gate and
the type check, and puts every one of them under a unit test. Against a correct override file none of
these branches ever fires, so a green regeneration proves nothing about them; the test module is
their only coverage. That is the same reachability argument
`tests/test_build_db_interpret_timing.py` already records for its own fatal branch.

Then `NMOS_TRUE_VPP_MV` leaves the generator. Its three keys reach six rows today through a
"highest VPP wins" tie-break that exists only because bare alias is ambiguous within a row. Under
D-01's `MANUFACTURER/ALIAS` key each entry names one row and the tie-break dissolves entirely. The
generated values do not change: this move is measured to contribute zero diff, and the byte-identical
regeneration is the proof.

**Known-red window.** The same two `tests/test_wire_dict_equivalence.py` tests plan `197-02` left red
stay red here, because the database does not move in this plan. Plan `197-06` closes them.

Purpose: make the mechanism refuse everything it cannot apply, and evacuate the first of the three
part-specific hardcodes.
Output: five fail-closed legs with tests, six NMOS override entries, and a `build_db.py` with one
fewer part-number literal block.
</objective>
