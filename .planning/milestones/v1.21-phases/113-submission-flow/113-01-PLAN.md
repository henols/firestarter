<objective>
Add the SUB-03 dedup fingerprint to the diagnostic report model so every `dev test` run
carries a deterministic short-hash a maintainer can key repeat reports on. The fingerprint
lives in `diagnostic_report.py` (not `submit.py`) so it lands in `to_dict()` automatically —
the single-source JSON both renders consume — and Phase-114 triage can parse it there.

Purpose: A triager scanning the `gsd-inbox` label must be able to tell "same chip, same
outcome, seen it" from "same chip, new failure mode" at a glance (D-02). Folding the per-step
byte-mismatch fingerprint classes into the hash makes two DIFFERENT fault modes on the same
chip produce DISTINCT ids — the finer grain is deliberate (D-02).

Output: `dedup_fingerprint(report) -> str` helper + a `"dedup_fingerprint"` key in `to_dict()`,
proven deterministic and volatile-field-free by tests. This is the upstream dependency Plan 02
reads back for the issue title.
</objective>

    - Determinism: two DiagnosticReports built with identical AutoCapture.chip, identical

    - Volatile exclusion: mutating only the report's generated timestamp, host_version, or any

      StepResult.reason string → equal hash), so scrubbable PII never influences the id.
  </behavior>

    sibling of `is_submittable` (D-02). Build a canonical join: `parts = [ac.chip or "",
