<objective>
Formalize the community graduation-ladder vocabulary as a report-side derived tag (GRAD-01),
extending the shipped advisory `DbDiff`/`build_db_diff` pipeline in `diagnostic_report.py`
with a `ladder_state` field, and document the full taxonomy + human-gated promotion process.

Per D-01, the ladder is (a) documented vocabulary + (b) an automatic report-side tag derived
from sweep verdicts; there is NO promotion tool and NO code that writes chip state. Per D-02,
`community-reported` / `community-confirmed` / `community-fail` live ONLY on the report / `DbDiff`
object -- `chip_database.json`'s `support_status` never carries a community-* value.

Purpose: Give a single community `dev test` report an honest, machine-readable ladder tag
(`community-reported` or `community-fail`) while keeping `community-confirmed` a human-only target,
so INBOX-01 triage (Plan 02) and the maintainer can act on it without any auto-graduation.
Output: extended `diagnostic_report.py`, new ladder tests, new `doc/community-validation.md`.
</objective>
