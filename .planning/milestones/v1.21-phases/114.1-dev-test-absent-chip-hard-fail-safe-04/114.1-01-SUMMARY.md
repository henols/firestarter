# Phase 114.1 Plan 01: dev test Absent-Chip Hard-Fail Summary

**`dev test <chip>` now hard-fails before energizing hardware when the chip name is absent from the database, via a 2-line `get_eprom`-keyed guard reusing the existing `ChipNotFoundError` path — while a present-but-unsupported chip still runs the full community-validation sweep.**

## Accomplishments
- Added the SAFE-04 guard in `dev_test` (`cli_handlers.py`): `if not app.db.get_eprom(chip): raise ChipNotFoundError(f"{chip}: not found in database")`, placed after the `--destructive` confirm block and strictly before `derive_plan`/`AutoCapture`/`read_hardware_revision_value()`.
- Added `test_dev_test_absent_chip_hard_fails_before_hardware` (case A): asserts exit 1, the bare `Error: ... not found in database` message, `read_hardware_revision_value.assert_not_called()`, and the operator never touched.
- Added `test_dev_test_present_but_unsupported_still_sweeps` (case B): drives AT28C16 (in DB, `resolve_chip` refuses with `ChipNotImplementedError` "adapter required") and confirms the sweep runs — hardware read reached, report rendered — with `id=NA`, `read=SKIPPED`, `blank-check=SKIPPED` findings whose reason contains "adapter".
- Verified RED->GREEN: temporarily reverted the guard and confirmed the case-A test fails (wrong message; hardware would have been touched) on pre-guard code, then passes with the guard restored.
