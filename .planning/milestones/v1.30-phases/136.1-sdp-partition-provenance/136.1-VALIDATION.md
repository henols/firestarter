⚠ **`tools/`, including `build_db.py` and this phase's new `derive_sdp_partition.py`, is OUTSIDE both
CI-scanned paths.** `.github/workflows/ci.yml` runs `ruff check firestarter/ tests/` and
`sys.executable -m mypy firestarter/ tests/` — neither includes `tools/`. Plan `136.1-01`'s `build_db.py`
edit and Plan `136.1-02`'s new `tools/derive_sdp_partition.py` are therefore expected to have ZERO
mypy/ruff-CI delta; this is a reasoned, measured expectation (stated in both plans), not an assumption.

⚠ **Two of this phase's scripts require a live network fetch by design** (`build_db.py`, and the new
`tools/derive_sdp_partition.py`) — both pinned to minipro commit `a8efaedc236c1d9718bd28299dfbb99536b010ff`,
both support reading a local file instead via an env var, neither is wired into the standing pytest
suite or CI. A cached copy of the pinned XML exists at
`/tmp/claude-1000/-workspaces/567ad46d-dc13-4977-a55b-4d782f814e87/scratchpad/infoic-a8efaed.xml`
(verified 2026-08-05, 17.8 MB, `INFOIC2PLUS` section present) — usable via the env var, never hardcoded
into either script's source.

⚠ **This phase's proof mechanism for PROV-03 is a LIVE, on-the-real-file demonstration, not only a
synthetic pytest fixture.** Plan `136.1-02` Task 2 plants a real single-chip re-bucketing directly in the

test in Task 1.

⚠ **No hardware is involved anywhere in this phase.** Every behavior here is a data-provenance and

## Non-Vacuity Obligations

A pre-authored gate proves nothing until it is seen to fail. This project has shipped unreachable-green
gates before (v1.23 P129/P130) — treat that as the standing failure mode to guard against. Each must be
**observed RED once** (or, where noted, demonstrated live on the real committed file), then **restored
byte-identically**:

| # | Planted break | What must go RED |
|---|---------------|-------------------|
| 1 | Plan `136.1-01` Task 2: any hypothetical mutation that reorders, removes, or edits a pre-existing `chip_database.json` value during regeneration | the blast-radius script (`136.1-check-blast-radius.py`), naming the offending entry — proven capable of failing by its own design (it must exit non-zero on ANY violation, not merely a declared-clean pass) |
| 2 | Plan `136.1-02` Task 1: a synthetic in-memory chip's `protect_on_after` field flipped between "before"/"after" DBs | `test_partition_flags_a_moved_chip_via_db_field_non_vacuous`, naming the moved chip and not the control |
| 3 | Plan `136.1-02` Task 2: a REAL planted single-chip re-bucketing on the actual committed `chip_database.json` (`AT28C256`'s `protect_on_after` flipped `true`→`false`) | `test_sdp_partition_matches_infoic_derived_field_element_wise`, naming the exact chip key — captured verbatim, then the file restored byte-identically |
| 4 | Plan `136.1-03` Task 2: a small hand-constructed synthetic set of `(protect_on_after, infoic_page_size_raw)` pairs with a KNOWN disagreement count | the counting helper, proven to return exactly the hand-counted number before it is trusted against the real 84-entry data |
