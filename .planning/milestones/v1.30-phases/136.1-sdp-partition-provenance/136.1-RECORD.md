# Phase 136.1 — SDP Partition Provenance — Close Record

**Phase goal, restated:** every chip's SDP ALLOW/REFUSE verdict is traceable, in-repo, to what
`infoic.xml` actually says — reproducible by anyone with a checkout, and gated so the committed
partition can never silently diverge from its upstream source.

**What this phase proves, stated plainly:** the 43 ALLOW / 41 REFUSE / 84-total `0x0D` SDP partition
now has an in-repo, committed, fetch-based, independently-runnable derivation path
(`tools/derive_sdp_partition.py`) and a fail-closed CI gate (`test_sdp_db_invariant.py`'s GATE-08)
proving the production transcription equal — element-wise — to a genuinely `infoic.xml`-derived
`chip_database.json` field (`programming.protect_on_after`), in addition to (never instead of) the
pre-existing hand-curated snapshot check. Two stale/unverified claims recorded elsewhere in the tree
were checked against measurement and corrected or refuted in-tree with durable, automated gates.

**What this phase does NOT prove, stated plainly:** it does not, and was never scoped to, change any
chip's ALLOW/REFUSE verdict, make any previously-refused chip newly writable, or produce silicon
evidence for any of the 84 `0x0D` chips — `0x0D` stays `UNVERIFIED` in `PROTOCOL-LEDGER`, unaffected
by this phase. It does not touch the firmware submodule, the wire protocol, or any dispatch code
path. It is a pure provenance/documentation/gate-hardening phase over already-shipped data.

## 2. Findings the record must carry forward (not tidied away)

### Finding 1 — PROV-05's premise was stale, not the file

`doc/lockable-proms.md` §17 already stated the corrected AT28C16/AT28C64B/AT28C256 SDP-capability
distinction **before Phase 136.1 was scoped** — landed by **Phase 121 plan `121-13`, commit
`c3c9424`**, five phases and one milestone number earlier. `PROV-05`'s own requirement text (a
maintainer memory note) was itself the stale artifact. Plan `136.1-03` did not re-author the doc; it
verified the correction's presence, confirmed (whole-tree grep) no stale copy of the wrong claim
exists anywhere else in `firestarter_app`, and shipped the durable automated gate
(`tests/test_lockable_proms_doc_claims.py`) that did not exist before. This is recorded as a finding,
not an embarrassment: the requirement was written in good faith from a real historical error that had
already, separately, been fixed.

### Finding 2 — PROV-02's runtime-derive branch was deliberately not taken

`tools/check_sdp_capability_invariants.py` fails closed unless `SDP_CAPABLE_TOKENS` is bound as a
literal `frozenset` (its Class 2(b) AST gate). A runtime read of `chip_database.json` at dispatch time
would both trip that gate and reopen the exact permit-by-default hole it exists to close — a user's
local `~/.firestarter/database.json` override could otherwise vote itself ALLOW. Plan `136.1-02` took
the static-transcription-plus-equality-gate branch instead: `SDP_CAPABLE_TOKENS` stays an untouched
frozenset literal, and GATE-08 now proves it equal, element-wise, to the infoic-derived DB field. This
also **closes the gap `_COMMITTED_SDP_ALLOW_ENTRIES`'s own comment has named since Phase 131** —
"leg 1... not implementable... chip_database.json contains ZERO occurrences of the string flags" —
since Plan `136.1-01` supplied the field that comment said did not exist.

### Finding 3 — PROV-06's "12 of 84" was re-measured by a genuinely different methodology

Plan `136.1-03`'s `tests/test_b15_page_size_corroboration.py` measures the disagreement between
`protect_on_after` (bit 15) and `infoic_page_size_raw > 1` via a **per-row, single-value** comparison
— reading each of the 84 `algorithm==13` chip_database.json entries' own two fields directly. Phase
120's original "12 of 84" figure was produced by a **cross-token-set matching** methodology (matching
possibly-multiple XML `<ic>` elements per part-number alias). Both measure 12. This agreement is
recorded as a **corroboration across independently different methodologies**, never assumed to have
to hold just because the number matched a prior phase's finding.

### Finding 4 — 136.1-01 broke and repaired a pre-existing gate

Regenerating `chip_database.json` to add the three new `protect_off_before`/`protect_on_after`/
`infoic_page_size_raw` fields caused GATE-02's `tools/diff_db.py` (a pre-existing per-chip diff gate,
unrelated to this phase's own `files_modified` list) to report all 744 upstream-decoded chips as
"unexplained diffs" — it had no root-cause rule recognizing the three new keys. Fixed, in the same
task, by adding a `PROV01_PROTECT_METADATA` rule following the file's own established per-phase
pattern (same shape as `PGSZ_PAGE_SIZE`, `RC1_DIP32_27C020`) — not by re-pinning the baseline or
suppressing the gate. This is the kind of measured, blast-radius-driven fix hard requirement 8 ("measure,
don't assume") exists to surface.

### Finding 5 — a process failure worth recording plainly

Mid-phase, an orchestrator dispatch note told Plan `136.1-03`'s executor that a crashed prior attempt
"committed NOTHING," having checked only `git status` in the meta repo. Two correct, complete
submodule commits (`c9f98b8`, `31b5d74`) already existed in `firestarter_app`, made by the crashed
session before it died — only the meta-repo bookkeeping (gitlink bump, requirement ticks, SUMMARY,
STATE update) was actually missing. **A clean working tree does not mean no commits were made** — the
submodule carries its own independent commit history that `git status` in the meta repo cannot see.
This plan's own `<submodule_commit_protocol>` explicitly names this exact incident as the reason to
verify state via git logs, not just `git status`.

## 5. Context worth stating in the record (per this plan's own framing)

The operator's original request, at this phase's inception, was **"no ICs refused."** The honest
answer this phase delivers instead: `infoic.xml` says 41 of the 84 protocol-`0x0D` parts have **no
SDP command decoder** in minipro's own upstream data, and on those the SDP sequence is not inert —
its bytes are stored as data at the bus-truncated magic addresses. Forcing them to ALLOW would corrupt
parts and report locks that never existed. What was actually missing was **provenance** — an in-repo,
reproducible, gated derivation path from upstream data to the committed verdict — and that is this
phase's entire delivered scope. The refusals are upstream's answer, now reproducible in-repo rather
than transcribed once and trusted forever.
