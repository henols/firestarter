<objective>
Build the fail-closed op-registration gate LEG-15 asks for, sized to the registries that measurably
exist rather than to a count the ROADMAP inherited.

Purpose: this is criterion 5, and it is one of the two criteria most likely to be quietly
mis-satisfied — because an exemption table is the classic way a fail-closed gate becomes fail-open. The
four guards are therefore acceptance criteria in their own right, not implementation detail.

The census must be measured, not inherited. An exhaustive repo-wide grep found that outside
`chip_test.py` the entire production surface contains exactly **one** op-keyed line of code, and it is
`OP_ID`-specific — a new op cannot "join" it. `dedup_fingerprint`, the `diagnostic_report.py` renderer
and `parse_devtest_issue.py` carry **no op vocabulary whatsoever**: they are fully generic over
`StepResult.op`, so there is nothing a new op could be omitted from. Asserting "membership or exemption"
against a registry that cannot have members is theatre that inflates the declared count. So the plan
splits the accounting in two — policed registries, and **declared non-registries** whose zero-op-vocabulary
status is itself asserted, in the other direction. That inversion is the genuinely valuable guard: without
it, a Phase-134 renderer that does start switching on op strings would silently inherit a permanent
exemption, which is exactly the fail-open shape LEG-15 exists to remove.

Output: `tests/test_op_registration_parity.py` — the phase's **second and final** new source file.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| op vocabulary -> registry set | A new op string must join every registry that keys on ops. Every registry it misses is a silent behaviour hole; the pre-Phase-121 instance routed an unmapped op to `erase_eprom()` and reported OK. |
| exemption table -> gate verdict | Each exemption is a deliberate hole. Mandatory reasons, the stale-row inversion, and the declared count are the three controls that stop the holes from widening or outliving their cause. |
| declared non-registry -> future registry | A file recorded as "no op vocabulary" could acquire some in a later phase and thereby inherit a permanent exemption. The inversion guard is the control on this boundary, and it is the one P-23's table has no equivalent for. |
| test module -> firmware sibling | This module must not read any firmware path. Its template does, via `@requires_fw`, and inheriting that decorator would make the gate SKIP in standalone CI — a gate that skips is a gate that does not exist. |
