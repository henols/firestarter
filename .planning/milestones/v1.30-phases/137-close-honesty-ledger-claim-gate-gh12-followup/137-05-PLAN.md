<objective>
Discharge CLOSE-06 in full for the review half, and handle the posting half honestly given a real
temporal constraint the draft itself states: **"the removal must have actually shipped"** before this
reply may be posted (`.planning/v1.30-GH12-REPLY-DRAFT.md`'s own precondition 1). Under this project's
standing close process, the beta push/PyPI publish (operator batch item A-2, "push the branch and open
the PR to beta") happens as part of `/gsd-complete-milestone`, AFTER every phase including this one
finishes — so precondition 1 is essentially never true yet at the moment this plan's tasks run.

Therefore this plan:
1. Assembles the review packet and copies the reviewed-pending draft into this phase's own
   `137-GH12-COMMENT.md` as the candidate text (Task 1, auto).
2. Presents it to the operator as a genuinely-blocking `checkpoint:human-action` gate — not
   `checkpoint:human-verify`, because this project's own established practice
   (`reference_auto_mode_autoapproves_outward_facing_gates`) is that `--auto`/`--chain` auto-approve
   EVERY `human-verify` checkpoint but present `human-action` checkpoints regardless — and an outward
   -facing, irreversible GitHub post is exactly the class that memory note names explicitly (Task 2).
3. Applies exactly the named corrections (if any), freezes the file (blob SHA + byte length), and THEN
   attempts to post ONLY if a live, mechanical check confirms the removal has shipped (the Phase 132
   deletion commit is an ancestor of `origin/beta`, AND the currently-published PyPI version differs
   from the pre-v1.30 baseline) AND the operator's own Task-2 verdict explicitly authorized posting now
   (Task 3, auto but fail-closed on either missing signal).

**No task in this plan posts to GitHub without both an explicit, freshly-recorded operator instruction
to do so now AND an independent mechanical confirmation that the stated precondition holds.** If either
is absent — the overwhelmingly likely case today — this plan freezes the reviewed text and records a
precise, actionable follow-up in `.planning/v1.30-OPERATOR-BATCH.md`, rather than posting early (which
would itself be exactly the overclaim class this milestone exists to prevent — naming a command as
gone in a thread while it still exists on the published channel) or silently doing nothing.

**This plan, and this phase, must NOT be executed under `--auto`/`--chain`** (ROADMAP's own explicit
instruction for Phase 137). Task 2 below is written so that even if a future execution session runs
under one of those flags anyway, the `checkpoint:human-action` type is never auto-approved by this
project's own execution machinery — but the correct operational answer is: do not pass either flag for
this phase at all.
</objective>
