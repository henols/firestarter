Module-level names to add:

  `firestarter/`, `tests/` in that order. Build it at call time so `sys.executable` is not frozen at
  import. Plan 131-02 asserts this list by whole-list equality, so the element order and the trailing

- `MIN_CHECKED_SOURCE_FILES = 120` — a **literal**, never derived. A derived count (a glob over
  `firestarter/**/*.py` plus `tests/**/*.py`) equals whatever is there and so cannot catch a run

  returncode guard**: measured, a rejected `python_version` in a config *file* is a non-fatal note,

`run_mypy()` returns a `subprocess.CompletedProcess`. It calls `subprocess.run` with `mypy_argv()`,
`capture_output=True`, `text=True`, `cwd=REPO_ROOT`, and does nothing else. Keep
`REPO_ROOT = Path(__file__).resolve().parent.parent` exactly as it is; `.resolve()` is already
correct and must not regress to a bare `os.path.dirname(__file__)` — that is the `_HERE` trap which
made `check_permitted_claims.py` scan nothing and exit 0 on v1.23's only outward-facing gate.

`classify_mypy_result(returncode: int, output: str) -> int` is pure: no subprocess, no file I/O, no
environment reads. Keep the `-> int` signature exactly as D-01 specifies. Guards in this order, each
hoisted above the guard it would otherwise be vacuously satisfied by, mirroring
`check_no_exists_proxy.py`'s ordering:

  1. `returncode` not in `(0, 1)` — print a tool/config-failure message naming the exit code and
     echoing the captured output, then exit 2. This single reordering is the fix.
  2. `_CONFIG_REJECTION_RE` matches — a config rejection is never a clean run; exit 2, naming the
     offending line.
  3. `_CLEAN_RE` matches — count 0, checked from the capture group.
  4. otherwise `_FOUND_RE` matches — count and checked from the capture groups.
  5. neither matched — mypy produced no parseable *completion* clause; exit 2. The truncated path is
     exactly this case: measured, it emits `(errors prevented further checking)` and no `checked`
     clause. Requiring the completion half is strictly stronger than a canary fixture (D-04) because
     it holds even if a future mypy returns 1 on that path.
  6. `checked` below `MIN_CHECKED_SOURCE_FILES` — exit 2, with a message naming both numbers and
     saying a run that checked far fewer files than the tree contains is a truncated run wearing a
     plausible number.
  7. Before returning, print a coverage line naming `checked` — the analogue of
     `check_no_exists_proxy.py`'s PASS line, so an outside reader sees the *coverage* of the check,
     not only its verdict.

`enforce_watermark(count: int, watermark: int) -> None` is pure. It prints the existing line
`mypy errors: {count} (watermark: {watermark})` with that exact prefix unchanged — plan 131-02's
end-to-end leg keys on it. Then: over watermark, print the FAIL line and exit 1; at watermark, print
the OK line; below watermark, print a **reworded** INFO line rendered from a single module-level
`_INFO_TEMPLATE` so 131-02 can assert the whole message by equality. The current message names a
bypass as the remedy; it is part of the fail-open, not decoration, and it is what invites baking a
broken run's number in permanently. The replacement must contain the exact substring
`only if this run is complete`, must state that the run *is* verified complete and name the
checked-file count as the evidence, and must say the watermark may be lowered to the new true count
**in the same commit as the fixes that reduced it**, never to make a failing gate pass. Follow the
