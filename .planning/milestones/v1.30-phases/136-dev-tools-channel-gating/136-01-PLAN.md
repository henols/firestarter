Define a throwaway `_SpikeGatedGroup(click.Group)` with a class-level frozenset of one gated name
(`"reg"`) that is deliberately never registered as a real command on the group. Override only
`get_command(self, ctx, cmd_name)`: call `super().get_command(ctx, cmd_name)` first; if it returns a
real command, return it; if the name is in the gated frozenset, raise `click.UsageError` with a fixed
message string, passing `ctx=ctx` so Click renders its normal `Usage: ... / Try '--help' ...` framing;
otherwise return `None` (so a genuine unknown name still falls through to Click's own generic error).
Register exactly one real command named `"read"` on this spike group so there is something to invoke
that is not gated.

Using `click.testing.CliRunner`, prove all of the following against this spike group — this is the
"real measurement," not a description of expected behavior:
1. Invoking the gated-but-unregistered name (`"reg"`) exits non-zero, and the output contains this
   task's fixed refusal text and does NOT contain Click's own generic phrasing — proving `get_command`
   intercepts BEFORE `resolve_command`'s own fallback fires.
2. Invoking a name that is NOT in the gated set (a genuine typo, e.g. `"bogus"`) exits non-zero and the
   output DOES contain Click's own generic "No such command" phrasing, and does NOT contain this task's
   refusal text — proving the override does not swallow real typos.
3. Invoking the one real registered command (`"read"`) exits 0 and runs normally.
4. `"resolve_command" not in vars(_SpikeGatedGroup)` — recording, structurally, that only `get_command`
   needed overriding; `resolve_command` was never touched.
5. `_SpikeGatedGroup(...).list_commands(ctx)` (with `ctx` built via `click.Context(spike_group)`)
   returns only `["read"]`, even though `"reg"` is a known gated name in the class's frozenset — proving
   `list_commands` needs no override at all, because a gated name that was never registered is simply
   absent from `self.commands` by construction.

Record the finding explicitly in the test module's docstring: **`get_command`, not `resolve_command`,
is the hook** — this is the exact mechanism plan `136-02`'s `_DevGroup` implements. State this is Click

| developer shell → host process | `FIRESTARTER_DEV_TOOLS` is read from the local environment; the developer already controls it |
| package build → channel decision | `__version__` is fixed at wheel-build time; nothing at runtime can change which channel a shipped wheel reports |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-136-01 | Tampering | `FIRESTARTER_DEV_TOOLS` spoofed to force-enable bench tooling on a real stable install | low | accept | Requires local shell/env access the operator already has; fails closed on every value except the exact literal `"1"` — mirrors the accepted-risk shape of the other `FIRESTARTER_*` dev-only overrides already in this codebase |
| T-136-02 | Elevation of Privilege | A broadened truthy check (e.g. `bool(os.environ.get(...))`) silently reopening the gate on `"0"`/`"false"`/garbage | critical | mitigate | Exact-match fail-closed test matrix; non-vacuity obligation plants exactly this `bool()` mutation and observes it RED |
