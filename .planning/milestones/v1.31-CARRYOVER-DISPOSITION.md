## Two defects promoted out of debug sessions

Both sessions were closed *as debugging activities* — their investigations are complete —
and their unfixed defects promoted to trackers so they are visible as work instead of
blocking every milestone close.

1. **`config-version-not-bumped-strands-stale-eeprom-calibration.md`** — `CONFIG_VERSION`
   is still `"VER06"` while `VALUE_R1` changed `1000 → 270000` in Phase 44, so
   `rurp_validate_config` never re-applies defaults on an already-calibrated board. Stale
   `r1` causes a 6.8x VPP under-read. **Re-confirmed present 2026-08-09.** Carries
   `needs_decision: true` — the obvious fix (bump the version) would wipe the operator's
   real per-board calibration, so three options are laid out with a recommendation
   (range-validate rather than version-gate) but no choice made.
2. **`fm1608-byte0-write-never-lands-register-cache-elision.md`** — byte 0 never programs
   because the register cache-skip elides all three shift-register strobes on the first
   `memory_set_data` of a block. Hardware-gated on an FM1608 sample. Includes the note that
   any test for this **must assert strobe counts**, since a native trace that doesn't model
   the elision cannot reproduce it.

## Findings for v1.31 itself

Surfaced by this sweep; not carry-over debt, but they bear on live decisions.

### 1. Datasheet evidence corroborating correction C2 — and qualifying D-02

Read off the actual title pages:

- **Am27C020 p.1** — "supports AMD's **Flashrite** programming algorithm (**100 µs pulses**)
  resulting in typical programming times of 32 seconds." This is **independent vendor
  confirmation of C2**: the measured modal `0x08` pulse in the shipped DB is 100 µs on 104
  of 127 chips. gh#15's `0x08` constant disagrees with both.
- **TMS2516 p.1** — "all programming signals are TTL level, requiring a **single 50-ms
  pulse** … Total programming time for all bits is 100 seconds." `Vpp = +25 V`.

  This **qualifies D-02's rationale**. D-02 justifies its 50 ms per-byte cap as "`100 × 500 µs
  = 50 ms` is exactly the classic 2716 total programming time". The datasheet says 50 ms is
  the **per-location single pulse width**; the *total* is 100 seconds (≈ 2048 × 50 ms). The
  **cap value of 50 ms per byte is datasheet-correct** — but for a different reason than the
  one recorded. Worth correcting in the decision record before Phase 141 cites it.

### 2. Risk to Phase 145 (0x0B bench validation)

The 2516 is the canonical `0x0B` part and its **read** oracle has been unstable since v1.15
(3 distinct SHAs over 3 reads, 1.9% byte jitter). Phase 145 cannot prove anything about
`0x0B` programming through an unstable read oracle. This should be faced during Phase 145
planning, not discovered on the bench.

### 3. Gap in `0x08` datasheet coverage

`0x08-EPROM-QUICK/W27E040.pdf` is the **same git blob** as
`0x07-EPROM-STD/W27C512.pdf` (`1a1c2800c49dbfe47029019099c105d39e8aaf1f`) — one file
committed under two names. The README declares the substitution honestly, but the `0x08`
bucket therefore carries **no W27E040-specific programming timing**: a 512Kx8 part
documented by a 64Kx8 datasheet. v1.31 needs per-datasheet `0x08` pulse evidence, and
W27E040 is one of the parts with recorded stuck-bit FAILs.

exists only on the unmerged branch `v1.16-protocol-first-architecture-rebuild`:

```
$ git ls-files | grep -c datasheet          # on gsd/v1.31-…  ->  0
$ git ls-tree -r --name-only beta | grep -c datasheet   ->  0
$ git ls-tree -r --name-only v1.16-protocol-first-architecture-rebuild | grep -c datasheet   ->  21
```

**31.0 MB across 21 files** (18 PDFs + README + `datasheets-check.sh` + `.gitkeep`). Phase
85's verification was performed by reading blobs out of that branch via `git show` — no
branch was modified.

This is consistent with the v1.16 close record: gitlinks were left **PINNED at b10** and the
lockstep beta cut was explicitly **operator-gated**. So v1.16's sub-repo work — the
datasheets *and* the Phase 89 primitives recompose — was deliberately never landed.

**Why this was not "fixed" automatically:**

1. It is **31 MB of third-party vendor PDFs**. Landing them on a branch headed for a public
   beta has redistribution implications and permanently bloats git history.
2. It was an **explicit operator gate** at v1.16 close, not an oversight to be quietly undone.
3. Merging that branch would also drag the **unmerged primitives recompose** — a substantial
   firmware change, far outside any reading of this task.

**But v1.31 needs these datasheets.** The three EPROM buckets stranded there —
`0x07-EPROM-STD` (W27C512, W27E512, SST27SF512, ST-M27C512), `0x08-EPROM-QUICK` (W27C020,
W27E040, AM27C020), `0x0B-EPROM-LEGACY` (2516) — are exactly the protocols v1.31 is
rewriting, and the AM27C020 is its own FUT-08 marginal chip.

Options: cherry-pick only the three EPROM buckets (~1.5 MB) onto the v1.31 branch; land the
whole tree; keep reading them out of the v1.16 branch as this sweep did; or move them out of
git entirely (external store + provenance-only in-repo). **Awaiting your call.**
