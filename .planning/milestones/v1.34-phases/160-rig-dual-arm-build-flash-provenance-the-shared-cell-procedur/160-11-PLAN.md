<task type="checkpoint:human-action" gate="blocking">
  <name>Task 3: Operator seats the W27C512 and sets the pot, one confirming reading taken</name>
  <what-built>
    The Uno is carrying the v1.33 arm, proven by an independent read-back whose judged prefix
    hashes equal to that arm's own image extent. The provenance block for this position is
    captured and gate-green. The socket is still empty and the chip-out window is therefore

  <how-to-verify>
    This step is physical and operator-only. Following `PROCEDURE.md` steps `P-05` and `P-06`:

    1. Seat the **W27C512** chip — the 28-pin part — in the socket, observing orientation, and
       confirm it is fully seated. Both bench chips declare the same programming-voltage target,
       so this is the only pot setting this cell needs and there will be no re-adjustment when a
       chip is swapped in a later cell.
    2. Set the programming-voltage pot to the target that will be stated to you before this
       gate is presented. Adjust it yourself, at your own pace. Nothing will poll the rail while
       you work — exactly one confirming reading is taken after you report, and there is no
       monitor loop.
    3. Report when the pot is set, and report the value you read on your own instrument if you
       took one.

    Two things worth knowing before you start. If the confirming reading comes back blank or as
    an obviously impossible value, that indicates a **contact fault** rather than a rail
    problem: the voltage monitors do not route through to the socket, so a bad seat reads as a
    bad rail. Re-seating is the response, and both the discarded reading and the re-seat will be
    recorded rather than quietly dropped. And if the firmware's own high-voltage guard refuses
    the operation, the response is to bring the pot into band and restart the run clean — the
    guard is never bypassed, since the permission to force past it was withdrawn and is not
    being restored here.
  </how-to-verify>
  <action>
Before presenting the gate, read the programming-voltage target for this chip from the pins file
and **state that target numerically in the gate text** — the operator sets the pot himself and
needs the number, not a reference to where the number lives. State the part as the 28-pin
W27C512 and note that no re-adjustment will be needed when a chip is swapped in a later cell
because both bench chips declare the same target.

Then present the gate and block. Do not poll, sample or monitor any rail while the operator
works.

After the operator reports, take **exactly one** confirming reading and stop. No loop, no
averaging pass, no second read for confidence. Write `POT.md` with the stated target, the
operator's reported value if given, the single confirming reading and the EEPROM calibration
values captured in task 2.

If the confirming reading is blank or an obviously impossible value, record it as a suspected
**contact fault** rather than a rail fault — the monitors do not route through to the socket — and
ask the operator for one clean re-seat, recording both the discarded reading and the re-run. Allow
at most one such re-seat; a second means the plan halts and reports.

If the firmware's high-voltage guard fires at any later step, the response is to bring the pot
into band and restart the run clean. Never pass a force flag; the permission to do so was
withdrawn and is not being restored.

This gate is never auto-approvable: seating a chip and turning a potentiometer have no CLI
equivalent, and an auto-approval would let a write proceed into an unset rail.
  </action>
