## The 512 KiB fallback ceiling, and why it is deliberately generous

`3920 s` is four times a `980 s` estimate. That estimate is itself derived, not measured: it assumes
a 512 KiB write on this part's algorithm behaves like the algorithm measured on the 64 KiB parts,
which **no figure on any current firmware supports**. The only 512 KiB anchor in the whole record is
a v1.15-era note describing this very part's write path as taking roughly four minutes — a same-rig
figure, but an **older-firmware** one quoted to no decimal.

Two consequences the record must carry:

- The `980 s` estimate is the **larger** of the two 512 KiB estimates available, chosen deliberately
  because neither of the two algorithms' write rates is measured on current firmware. That is a
  widening, and 161 D-08 requires a widening to be **stated** rather than silently exceeded — so it
  is stated here, in this plan, before the run.
- If the run approaches the ceiling, do **not** quietly let it run past. Either the ceiling fires
  and the kill is fully logged per PD-15 — numbered log, full stdout and stderr, the last progress
  frame, **which step was in flight**, and the record line stating it timed out at N seconds against
  a measured baseline of M — or the ceiling is widened with the new figure and its basis written
  into `CELL.md` first. Phase 160's single *unlogged* timeout kill is what produced the untraceable
  home-directory contamination this milestone still carries.

Remember that write progress is emitted **time-keyed per block with the clock restarting each
block**, so a last progress frame names a **block, not a byte offset** — and that one `dev test`
invocation covers twelve steps behind one timeout, so the log must also identify which step was in
flight.

## Prior dispositions — part 6, W27E040

- **Newest recorded disposition (D-04):** **FAIL (genuine)** — *"erase cannot clear bit 4 @0x7db
  (reads 0xef, want 0xFF) — DETERMINISTIC across initial run + 1 reseat (same offset/value), genuine
  stuck cell"*, described in the same entry as the **same stuck-bit-on-erase signature class** as
  the other stuck-bit part in this sweep, at a different offset. Source: **v1.15 Phase 82**,
  `.planning/v1.15/bench/EVIDENCE.md:99`. Explicitly **excluded from the Phase 84 FIX-01 re-bench by
  D-32** as genuine silicon wear: `.planning/v1.15/bench/EVIDENCE.md:256`.
- **All prior sweeps that touched the part (D-01):** v1.15 Phase 81 read sweep,
  `.planning/v1.15/bench/EVIDENCE.md:55` (**PASS**, N=3, no anomaly — the part reads clean and the
  defect manifests only on erase/write); v1.15 Phase 82 A→B write, `:99` (the FAIL above); v1.15
  Phase 84, `:256` (deliberately **not** re-benched). No v1.16 or v1.18 disposition exists.
- **Comparable steps:** `read` (PASS at Phase 81), `erase` and `write` (FAIL at Phase 82). `id` and
  `blank-check` were never measured separately — not flips.
- **D-05 applies.** The record calls this fault deterministic across a first run and one reseat, so
  **symptom identity counts**: an identical offset and byte value is `same`; a moved offset or a
  changed value is `diverges: symptom moved <from> → <to>` and earns a control re-run, because a
  stuck bit that **moves** is new silicon behaviour or a new addressing fault rather than the known
  one.
- **`known_carried`:** **yes** — SC#5. The text carries the verbatim symptom, both citations
  (`EVIDENCE.md:99` and `:256`) and the silicon-wear classification.
- **The pin-map note this row must carry.** This part is on the **standard** 32-pin map, **not** the
  scoped map v1.18's Phase 97–99 fix introduced for the other 32-pin EPROM in this inventory. That
  fix is size-gated to parts at or below a quarter of a mebibyte and this part is twice that, so the
  fix does not touch it. Record that in `anomalies`, so no reader infers that v1.18's improvement
  should have applied here.
- **Second data point on the fast-fail question.** Plan 162-05 measured the erase behaviour of the
  other stuck-bit part at 64 KiB. This is the same failure class on a part eight times larger, and
  the retry behaviour recorded in the v1.18 record for a different marginal part suggests retries
  can be substantial. Record the measured erase duration explicitly and compare the two data points
  in `CELL.md`.
