## Shared conventions for every bench task in this phase

Plans 162-06 through 162-10 reference this section unchanged rather than restating it.

**Cell identity.** `$CELL_ID` and `cell_slug` are both `CHIP`. `$CELL_DIR` is
`/workspaces/.planning/v1.34/bench/cells/CHIP`. `$TARGET` is `leonardo`, MCU `atmega32u4`,
signature `0x1e9587`, programmer `avr109` at 57600. `$POSITION_ID` is
`CHIP__<arm>__<slug>`. `$FIRESTARTER_CONFIG_DIR` is `/workspaces/.planning/v1.34/config`.

**Every arm-invoking command carries the config-dir variable inline, never exported.** The app
computes its home, database and pin-map paths as **import-time** constants, so a session-level
export is a partial fix that looks complete. A shell variable-assignment prefix is stripped before
exec and never reaches argv, so an argv check **cannot** detect a missing prefix — asserting
`~/.firestarter` unchanged at teardown is the only detector.

**Every arm binary is the pinned absolute path** from `rig-pins.json` `arms.<arm>.venv_bin`. The
bare name on `PATH` resolves to an editable install of the working tree — a third, un-named arm —
and `gate_record`'s argv0 rule refuses it at append time.

**Every `import firestarter` probe uses the arm's own `.venv/bin/python` with `-P`.** Without `-P`
the firmware repo wins as a namespace portion and the probe silently prints nothing useful.

**`pio` runs only with cwd `/workspaces/firestarter`,** and the cwd is recorded alongside the argv.
The generated, gitignored top-level PlatformIO config has a duplicate section that aborts the
parser, so the identical command string succeeds or fails on cwd alone.

**Logs are numbered per position** under `$CELL_DIR/logs/`, as a stdout/stderr pair per invocation,
with the wrapper's exit code recorded. A ceiling kill is logged per PD-15: full stdout and stderr,
the last progress frame, **which step was in flight**, and the record line stating it timed out at
N seconds against a measured baseline of M.

**The append-and-render pair.** Every position's row is appended by `append_chip_evidence.py` and
immediately followed by `render_chip_evidence.py --check` in the same step. Never one without the
other.

**One clean re-seat per position** is permitted, and **both** the discarded attempt and the re-run
are recorded, with `reseat_count` set accordingly.

**Nothing is fabricated.** A blocked reading is `not measured — <reason>` with the reason on the
same line, never a blank, never a plausible number. No SHA is transcribed by hand.

**Halt mapping.** A `dev test` **BAD on a part is a result — `P-H2`** — carried forward; that is
what the sweep exists to produce, and it is what the four known-carried parts are expected to give.
`P-H1` is reserved for **rig** faults: a null `fw_board_identity`, a read-back mismatch after a
correct flash, a blank or `0x303` VPP reading (a contact fault, because the VPP and VPE monitors do
not route to the socket), or a change to `~/.firestarter/config.json`.

**The `~/.firestarter/config.json` mtime is expected to change again.** It changed in all three of
Phase 161's cells and again before this phase began. Record the recurrence as a standing `P-H1`
finding handed to Phase 165; **do not attempt to fix or delete it** — the sandbox denies removal,
and Phase 160's one unlogged kill during a removal attempt is what contaminated the directory.

**The control interleave (`C-08`), when and only when a position's verdict begins with the
diverging prefix.** With the chip **unmoved**: check out the control firmware SHA with the pinned
git binary, assert an empty porcelain, `pio run -t upload -e leonardo` from the firmware repo, then
`judge_readback.py` with `--flashed-arm control --expect-arm control`; assert `judged_match` true
and the judged span equal to a **runtime read** of `hex_span_expected_by_arm.control`. Re-run
`dev test` on the same part with the control arm binary. Append the control row with
`--arm control` and `--control-rerun-for` naming the v1.33 position it arbitrates. Then re-flash to
v1.33 and repeat the read-back proof against `hex_span_expected_by_arm.v133`. Two flashes, two
proofs, **zero extra chip handlings**. If `judge_readback.py` needs the board in its bootloader for
its own direct read, run `touch_1200.py` in bare settle-only mode first — never `--wait-new-port`,
and work inside the measured window (touch to responsive 3.487 s, touch to completed judged
read-back 3.878 s).

**The divergence procedure** is PD-16, applied per position against the prior-disposition block
this plan gives for each part. A structurally-NA step is never a flip; a step the prior sweep never
measured is never a flip and is recorded inside `prior_dispositions_all` as having no comparable
prior measurement.

**Every per-step lookup keys on both `write` and `write-partial`.** The two UV parts emit the
latter, and a lookup on the former alone reads their write cell as empty.

## Prior dispositions — part 2, W27E512

- **Newest recorded disposition (D-04):** **FAIL (genuine)** — *"erase cannot clear bit 7 @0x3d
  (reads 0x7f, want 0xFF) — DETERMINISTIC across initial run + 2 reseats … identical offset/value
  every time = stuck cell, not contact/VPP"*. Source: **v1.15 Phase 82**,
  `.planning/v1.15/bench/EVIDENCE.md:97`. Explicitly **excluded from the Phase 84 FIX-01 re-bench by
  D-32** as genuine silicon wear: `.planning/v1.15/bench/EVIDENCE.md:256`.
- **All prior sweeps that touched the part (D-01):** v1.15 Phase 81 read sweep, `:53` (**PASS**,
  N=3, no anomaly — the part reads clean and the defect manifests only on erase/write); v1.15 Phase
  82 A→B write, `:97` (the FAIL above); v1.15 Phase 84, `:256` (deliberately **not** re-benched).
  No v1.16 or v1.18 disposition exists for this part.
- **Comparable steps:** `read` (PASS at Phase 81), `erase` and `write` (FAIL at Phase 82). `id` and
  `blank-check` were never measured separately — not flips.
- **D-05 applies.** The record calls this fault deterministic, so **symptom identity counts**: if
  the failure moves to a different offset or a different byte value, the verdict is
  `diverges: symptom moved <from> → <to>` and the position earns a control re-run, because a stuck
  bit that **moves** is new silicon behaviour or a new addressing fault, not the known one. An
  identical offset and value is `same`.
- **`known_carried`:** **yes** — SC#5. The text must carry the verbatim symptom and both citations
  (`EVIDENCE.md:97` and `:256`), so this red cannot enter Phase 165's failure set or Phase 166's
  findings as a v1.34 discovery.
- **The shared-DB-row trap.** `W27C512` and `W27E512` resolve to the **same** database row
  (`W27C512,W27E512`, chip-id `0xDA08`) but produce **different** report files, because the filename
  is keyed on the token as typed. There is therefore no filename collision — and **no way to tell
  the two reports apart by content**, since both record the token they were invoked with and both
  carry the same chip-id. The appender's cross-check of the report's own recorded chip against
  `--chip-token` is the only guard against copying part 1's report into part 2's row. Confirm the
  two rows' `report_json_sha256` values differ.
- **Assumption to test here, cheaply (RESEARCH A4).** The duration budget assumes a stuck-bit part's
  `erase` step **fails fast** rather than retrying long. Part 2 is the first and cheapest place that
  assumption meets silicon. Record the measured `erase` duration explicitly; if it is long rather
  than short, say so in `CELL.md` and **widen the later ceilings**, stating the widening rather than
  silently exceeding it.
