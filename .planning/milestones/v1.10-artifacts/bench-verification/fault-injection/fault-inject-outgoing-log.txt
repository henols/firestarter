## CAVEAT (measurement)
The outgoing fault corrupts the connection-SETUP command frame (the only corruptible host->fw
command frame — a READ's MAIN phase sends only plaintext acks). When it is rejected, find_and_connect
RETRIES ACROSS ALL PORTS, so the latency is connection-level, NOT a single-frame firmware error
latency. The outgoing latency numbers therefore do NOT measure the "sub-second per-frame error".
What IS proven: the firmware does not ACK a corrupt host->fw frame (no silent accept), and a fresh
clean transfer recovers byte-exact.
