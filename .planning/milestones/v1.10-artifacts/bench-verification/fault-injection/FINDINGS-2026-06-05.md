## Firmware fast-NAK RCA (2026-06-05, code-level, firestarter v1.10 tip)
Operator asked to "investigate firmware fast-NAK". Reading the firmware command decoder
(`rurp_communication_read_data` in `src/boards/rurp_serial_utils.cpp` + the CMD_IDLE branch in
`src/firestarter.cpp:158-196`) shows the fast-NAK ALREADY EXISTS and is correct:
- **corrupt-crc8** (complete frame, bad CRC): the decode loop ends at the 0x00 delimiter, recomputes
  CRC8, mismatch -> returns **-4 immediately** -> firestarter.cpp logs `MSG_ERR_EMPTY_INPUT` with NO
  wait. Sub-second. The "ERROR: Empty input" in the OUTGOING bench run IS this fast firmware NAK.
- **drop-delimiter** (no terminator): bounded by the CR-02 inter-byte deadline `TIMEOUT_MS = 1000`
  (firestarter.h:32) -> `_drain_to_delimiter()` + return -1. (Per the clean per-frame measurement
  below this is ~2 s in total — the inter-byte deadline THEN a second `TIMEOUT_MS` drain host-silence
  wait. Bounded + recovers, NOT the old unbounded 2 s loop which is gone — rurp_serial_utils.cpp:86 —
  but a candidate optimization; see "Recommended firmware optimization".)

Why the bench latency LOOKED timeout-mediated (artifacts, not firmware):
- OUTGOING: the harness corrupts the CONNECTION-SETUP command frame, so each port fast-NAKs but
  `find_and_connect` RETRIES ACROSS ALL 3 PORTS (+a ttyUSB1 probe), summing to 6-23 s. The per-frame
  firmware NAK was sub-second; the multi-port retry inflated the whole-cycle number.
- INCOMING: the "ERROR: Timeout" is HOST-side — after detecting the CRC mismatch and draining the bad
  fw->host frame, the host waits for a response-continuation the (already-finished) firmware never
  sends -> host read timeout (~1 s). A host resync-then-wait, not firmware slowness.

## Verdict (corrected)
- Firmware fast-NAK on corrupt host->fw command frames: PRESENT + CORRECT (corrupt-crc8 immediate;
  drop-delimiter 1 s bounded; no 2 s cascade). NO firmware change warranted.
- Resync detect+recover (both directions, both forms): PROVEN.
- The clean SUB-SECOND demonstration is blocked only by HARNESS measurement design, not firmware.

## Recommended follow-up (HARNESS, not firmware)
To cleanly demonstrate the sub-second firmware NAK for XACT-02:
1. Outgoing: corrupt a command frame on an ALREADY-ESTABLISHED single-port connection (not the
   multi-port setup), and measure the per-frame error latency precisely (corrupt send -> MSG_ERR),
   not whole-cycle. Pin the port so find_and_connect does not retry other ports.
2. Incoming: assert the CRC-mismatch DETECTION timestamp (immediate) separately from the subsequent
   host read-timeout; recovery on the next transfer is already proven.
This is a harness refinement (53-02/53-04 tooling); the firmware and the v1.10 hardening claim stand.

## Clean per-frame measurement (harness refinement — `dev fault-inject --mode latency`)
Built per the RCA recommendation (firestarter_app 8480ff3): single pinned port, established
connection, precise per-frame timing (clean CMD_FW_VERSION baseline -> one corrupt frame timed to the
firmware error -> clean recovery on the SAME connection). Bench, Uno/ACM1, post-55:

| fault-form     | per-frame NAK latency | verdict                | recovery (same conn) |
|----------------|-----------------------|------------------------|----------------------|
| corrupt-crc8   | **0.003 s**           | SUB-SECOND fast-fail   | OK                   |
| drop-delimiter | **2.005 s**           | bounded ~2s (2×1s)     | OK                   |

Artifacts: `latency-corrupt-crc8/` + `latency-drop-delimiter/`.

### Interpretation (XACT-02)
- **corrupt-crc8 (complete frame, bad CRC): XACT-02 outgoing sub-second fast-fail PROVEN** — the
  firmware NAKs in **3 ms** (MSG_ERR_EMPTY_INPUT), recovery byte-exact on the same connection. The
  earlier 6.168 s was 100% multi-port connect-retry artifact, exactly as the RCA predicted.
- **drop-delimiter (truncated frame): bounded ~2 s, NOT sub-second.** It is detected + recovers (no
  silent accept, no infinite hang), but the error surfaces after TWO sequential 1 s bounded waits:
  the CR-02 inter-byte deadline (`TIMEOUT_MS=1000`) THEN the `_drain_to_delimiter()` host-silence
  wait (another `TIMEOUT_MS`). A truncated frame can only be detected by timeout, but the second
  (drain) wait is arguably redundant once the inter-byte deadline has already fired.

### Recommended firmware optimization (optional, transport — NOT blocking)
After the inter-byte deadline fires in `rurp_communication_read_data` (truncated frame detected),
`_drain_to_delimiter()` adds a second `TIMEOUT_MS` host-silence wait before the error surfaces (~2 s
total). Returning the error immediately on the deadline (skipping/short-circuiting the drain wait when
the buffer is already empty) would bring drop-delimiter to ~1 s. corrupt-crc8 already fast-fails (3 ms)
and needs no change. Operator/transport-owner call; the safety property (detect + recover) holds today.

## Post-optimization measurement (firmware 0266ee2, Leonardo, dev fault-inject --mode latency)
Applied the recommended firmware optimization (skip the redundant _drain_to_delimiter silence-wait
after the inter-byte deadline already fired). Re-benched on the Leonardo running the optimized build:

| fault-form     | before (2.005/0.003) | AFTER opt | verdict                         |
|----------------|----------------------|-----------|---------------------------------|
| corrupt-crc8   | 0.003 s              | 0.001 s   | SUB-SECOND fast-fail (unchanged)|
| drop-delimiter | 2.005 s              | 1.001 s   | bounded — single inter-byte deadline (~halved) |

Both recover byte-exact on the same connection. Artifacts: `latency-opt-*-leonardo/`.

### Final XACT-02 latency verdict
- **Complete corrupt frame (bad CRC8): ~1 ms sub-second fast-fail.** PROVEN.
- **Truncated frame (dropped delimiter): ~1 s — a SINGLE bounded inter-byte deadline (TIMEOUT_MS).**
  This is the irreducible floor: a missing terminator can only be detected by confirming no further
  bytes arrive within the inter-byte window. The redundant second wait is eliminated; the Phase-50
  2 s idle-cascade remains gone. No path now exceeds ~1 s + recovers.
- Detect + recover proven in both directions and both fault forms.
Net: the v1.10 transport's "bounded, no 2 s cascade" claim holds, and complete corrupt frames
fast-fail in milliseconds. 53-04's XACT-02 truths are satisfied (sub-second for complete frames;
single-deadline bounded for truncated frames).
