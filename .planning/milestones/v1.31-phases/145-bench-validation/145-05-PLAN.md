1. **Three full 64 KiB write cycles**, one per image — `img1.bin`, `img2.bin`, `img3.bin`. All 65536 bytes,
   64 blocks of 1024 B each. Not a region: BENCH-01's own text says "a full write to read to verify", and a
   smaller run would be a narrowing.
2. **A different image every cycle.** Rewriting the same bytes over an unerased chip needs no bit to flip and

3. **Two oracles per cycle, recorded separately.** The firmware's own verdict, and an independent host-side
   SHA-256 compare of the source image against a fresh full read-back. They are never merged: a disagreement
   between them must be visible.
4. **A three-run read-stability check per cycle** — `dev consistency-check --runs 3` — because program
   repeatability and read repeatability are different failure modes.
5. Cost to the part: three erase-and-program cycles on an electrically erasable EEPROM, plus one short fourth
   cycle at Gate 3.

The pass rule you set (D-09): **3/3 byte-exact on both oracles**, with **exactly one clean re-seat allowed**
if a failure is attributable to a named physical cause. Both the discarded failure and the re-run get
recorded — the allowance is a documented re-run, never a quiet retry. Anything else is a fail, and a fail
**halts this phase** and hands to a debug session; this phase does not absorb a fix.

No `--force`, no `write -b`, no `--skip-erase`, no address-ranged shortcut. Every command line goes into the
