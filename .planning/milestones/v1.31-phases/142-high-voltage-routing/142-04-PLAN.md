**Why one plan, one task, one commit (L-2 / D-18).**
`tests/golden/protocol_branch_inventory.json` pins `eprom.cpp`'s **blob SHA**, and its working-tree
sites leg (`test_branch_sites_match_the_recorded_inventory`, reading `_SCAN_EPROM.read_text()`) goes RED
on the **first keystroke** in that file, while its blob-SHA leg
(`test_blob_shas_match_the_recorded_inventory`, reading `git rev-parse HEAD:<path>`) goes RED only
**after** commit. Landing the source change and the re-derived golden together is therefore the only way
the gate goes RED once, for one reason. That is achievable here because the golden's `meta.sources` is
exactly `["src/proms/eprom.cpp", "src/proms/eprom_params.cpp"]` — `memory.cpp`, `rurp_pinout.h` and
`platformio.ini` are **not** pinned, and `eprom_params.cpp` is read-only this phase (D-01).

**Why that means ONE TASK.** `gsd-executor.md`'s `<task_commit_protocol>` (`:410`) is unconditional:
*"After each task completes (verification passed, done criteria met), commit immediately."* There is no
deferral mechanism anywhere in `:409-529`, so a plan cannot ask an executor to carry edits across task
boundaries and commit them later — an earlier draft of this plan tried exactly that and the requirement
was unsatisfiable. Commit granularity is per **task**, so a single commit requires a single task. All
five files are therefore edited inside one task's own action and committed once at its end. That is the
same *constraint* this project's three existing multi-file atomic commits satisfy (`125-01` task 2,
`126-03` task 1, `134-01` task 2) but at **larger scale than any prior instance**: all three landed as a
single multi-file commit with no lettered sub-parts at all — except `134-01` task 2, which had two —
against this task's **20 lettered parts across 5 files**. The pattern is precedented; the size is not.
Two cautions if you go read those plans: `134-01` task 2's `<files>` names two files but the commit that
actually landed (`de08037`, in `firestarter_app`) touched a third to fix a regression the change caused;
and `126-03` task 1 produced a follow-up commit (`62b1b73`) after its split commit (`1d1ab28`), so it is
a precedent for the *shape*, not for a clean single commit. **Do not re-split this task** — a
split puts a commit between the `eprom.cpp` edit and the golden re-derivation, and the D-18 blob-SHA leg
is RED in that window by construction.

**If context runs short mid-task, halt clean — do not commit a partial.** There is no partial-commit
checkpoint here by design, so a commit taken at part K would be the exact defect this structure removes.
Stop, leave the working tree uncommitted, and report which lettered part you reached plus what remains,
so a fresh executor can resume from that letter and still land one commit. An uncommitted working tree
is a recoverable state; a split commit around a blob-SHA-pinned golden is not.

**What lands, and under which decision:**
- **D-05** — one resolver, not just shared constants. Sharing bit *constants* would satisfy VPP-03's
  literal wording at zero flash cost but leave the *selection* duplicated at two sites, which is
  precisely the duplication that let `eprom_check_vpp` and the write path drift apart on `0x08`.
- **D-06** — `--vpe-as-vpp` still overrides the table. It is a live user-facing flag set by **no**
  database entry, a pure human escape hatch for the 25 V NMOS parts and the manual-pot workflow.
  Keeping it means no host change in a firmware-only phase. Its predicate survives inside the resolver,
  demoted from a **tier-1** protocol-keyed site to a **tier-2** flag site.
- **D-04** — Phase 141's explicit `handle->pins >= 32` clear is **removed**, not preserved. Its own
  comment says it exists only to make the incidental stripping observable and that it deliberately does
  not pre-empt this phase's choice; keeping it would actively defeat the fix on Rev 2-class hardware
  now that plan 142-02 has landed.
- **D-10 as amended (operator-confirmed), resolving correction C-1** — a single-exit **wrapper**, and
  its disable is **conditional on `handle->response_code == RESPONSE_CODE_ERROR`**. The literal word
  "unconditionally" from D-10's original text is given up. The tiebreaker is a test that exists and
  passes today: `test_loop05_a_successful_block_does_not_disable_the_route`
  (`test_loop_eprom_v131.cpp:1286-1309`) asserts a **successful** block leaves
  `CTRL_VPP_REGULATOR_ENABLE` **set**, and its own comment says generalising disable-on-every-exit
  *"is Phase 142 / VPP-02's job"* — it was authored anticipating this phase and encodes D-09's
  success-exit exemption as an assertion. A literal unconditional disable was offered and **rejected**
  on D-09's cost: clearing the regulator at each block's success exit re-arms the `eprom.cpp:189` guard
  and re-pays `delay(500)` per block, about **64 s** added to a 64 K Uno write (128 blocks) against a
  typical `0x07` at 100 us total of about 32 s. **That assertion stays GREEN.**
- **D-09** — "success" in VPP-02 means the write **operation's** success exit, not each block's.
  `command_done()` (`firestarter.cpp:162-171`) is the operation-level disable; it zeroes
  `CONTROL_REGISTER`, `LEAST_SIGNIFICANT_BYTE` and `MOST_SIGNIFICANT_BYTE` on **both** the success and
  the abort paths, and because the top-address bits and the `vpp_line` bit all live in those three
  registers, that zeroing fully de-energises. Nothing tests it today; plan **142-06** owes that test.
- **D-12 (Claude's discretion, decided here)** — the guarantee covers exactly
  `eprom_write_execute` and `eprom_write_init`. Research's control-register assertion map found all
  **four** leaking exits in `eprom_write_execute` (`:226` `row == NULL`, `:268` `MSG_ERR_MAX_PULSES`,
  `:275` `MSG_ERR_ENERGY_CAP`, `:311` `MSG_ERR_VERIFY` — the headline gap, which today disables
  nothing at all). `eprom_write_init`'s two exits leak nothing today, so its wrapper is **defensive,
  not corrective** — say so — but its erase leg is the only write-path code that asserts
  `A9|VPE` (remapped to `A9|P1` on a `using_p1_as_vpp` handle) and its safety rests on there being no
  `return` between `:399` and `:409`, a property a future edit can break silently.
  **Do NOT widen to `eprom_erase_execute`, `eprom_check_chip_id_execute` or `eprom_get_chip_id`:**
  each already clears everything it asserts with no intervening `return`, so a wrapper there is not
  "required for safe shared cleanup" and is therefore forbidden by `PROJECT.md:189-190`.
- **VPP-03** — the four hand-rolled disables (`:174`, `:327`, `:393`, `:409`) become references to
  `EPROM_HV_ALL_OFF_MASK`. That is mask consolidation, not guarantee widening. The claim that those
  conversions are byte-identical on the wire is research assumption **A3** and must be **measured, not
  asserted**: plan 142-03 captured the pre-rewrite `CMD_ERASE` and `CMD_CHECK_CHIP_ID` control-value
  baselines for exactly this purpose, and they must still pass after this plan.
- **L-4, stated explicitly rather than left to be inferred.** `eprom_check_vpp` is reached from
  `eprom_generic_init`, the **default** `firestarter_operation_init` for every EPROM command, so
  changing its route resolution moves the emitted control byte for `0x08` on **six** commands —
  `CMD_READ`, `CMD_WRITE`, `CMD_VERIFY`, `CMD_ERASE`, `CMD_BLANK_CHECK`, `CMD_CHECK_CHIP_ID`, reads
  included. `PROJECT.md:189-190` permits this because **closing the measure-and-apply divergence IS the
  shared cleanup** that line licenses: today `eprom_check_vpp` measures `0x08` with the drop bit on
  (`:345`) while the write strips it before the first pulse, so the measured-and-validated voltage is
  not the voltage applied. `test_val_eprom`'s six cases guard this surface for all three protocols and
  will stay green, because they assert only `CTRL_VPP_REGULATOR_ENABLE` and `CTRL_VPP_P1_ENABLE`
  presence or absence, and **their handles have `pins == 0`** so any pins-keyed arm sees the `< 32`
  path.
- **D-08** — no new message id. `0xBF` is the last free `0xA0..0xBF` ERROR slot and Phase 143 wants it.
  Nothing in this plan needs one. If the implementation discovers a genuine need, that is a
  **checkpoint to the operator**, not a quiet claim.

**Open Question 4, decided: EXPOSE the resolver via `include/eprom.h`.** The `eprom_overprogram_us`
precedent (`eprom.h:18-35`) is the house form for exposing a pure helper to a native oracle. Exposing
it buys a direct `(protocol, ctrl_flags) → mask` truth-table oracle for a few bytes of flash and makes
the fail-closed NULL-row arm testable without a full drive; a file-static resolver could only ever be
tested through its effects on the strobe stream. `rurp_register_t` is already visible in `eprom.h`
(`eprom.h:11` includes `firestarter.h`, which includes `rurp_shield.h`, which includes `rurp_types.h`),
so **no new include edge** is needed.

**Open Question 6, decided: DELETE `eprom_internal_ensure_regulator_enabled` (`eprom.cpp:449-454`).**
It has **zero callers** anywhere in `src/`, `include/`, `test/` or `tests/` and duplicates the
`:189-198` regulator guard that the resolver now owns. VPP-03's purpose is non-divergence, and a dead
duplicate of the enable guard is exactly the divergence risk this phase exists to remove. The golden's
own corrected reason for its site records that the function survives in the linked binary only because
`--gc-sections` already collects it, so deleting it reclaims 0 B — there is no flash argument for
keeping it. Its tier-2 inventory site (`:450`) disappearing is precisely the "deliberate inventory
movement" `meta.frozen_for` demands of this phase by name. Silence was not an option (L-10).
