<objective>
Make the hardware honour the drop-resistor route on 32-pin parts, gated on board revision.

**D-01:** the `handle->pins < 32` exclusion in `mem_util_calculate_top_address_register`
(`memory.cpp:172`) is removed — it is a VPP *level* bug, not a routing guard. The operator's
correction, verbatim: *"no exclusion at all — 32 pin IC's with vpp on pin one is controlled with a
jumper."* Routing VPP to socket pin 1 on a 32-pin part is a **physical** decision; the drop bit
selects the VPP *level* (VPE dropped through the resistor to the ~13 V VPP level) and nothing else.
Excluding it for `pins >= 32` protects no route — it silently programs `0x08` on the **un-dropped**
rail. Phase 141's hand-off H1 already disproved the bit-collision theory the old comment gave as its
justification. **The drop bit is a level selector, not a route selector; any reasoning that treats it
as a route control is reasoning from the superseded model.**

**D-02, as amended 2026-08-11 (operator-confirmed):** the removal is gated on **revision alone** —
`REVISION_2_x` implies preserve for all `pins >= 32`. No new `handle` field (offered and rejected on
RAM plus a plumbing seam), and never `handle->protocol` (which would create a fourth tier-1
protocol-keyed site and violate TABLE-05). On Rev 0 / Rev 1 the mapper puts
`CTRL_VPP_VPE_DROP_ENABLE` and `CTRL_ADDRESS_LINE_16` on the **same physical bit** `0x01`
(`rurp_hw_rev_utils.h:30-31` with `rurp_pinout.h:106` and `:116`), so preserving the drop bit on a
32-pin part there would force A16 permanently high; on Rev 2-class they are distinct (`0x01` versus
`0x20`, `rurp_hw_rev_utils.h:24-25`). `JMP_VPP_P1_BYPASS` being `not-present` on Rev 0 and Rev 1
(`doc/SHIELD-REVISIONS.md:87`) independently reinforces the same gate.

The gate's nominal reach widens to every 32-pin protocol on Rev 2-class (`0x0E`, `0x29`, `0x10`,
32-pin flash), but none of them ever *sets* the drop bit, so there is nothing to preserve. **D-02's
amendment pays for that "nothing" with a proof, not an argument** — hence task 1's 32-pin non-EPROM
byte-identity case and the "preserve, never introduce" leg.

**Ordering (L-3) — this plan MUST land before plan 142-04's `eprom.cpp` work.** Landing `eprom.cpp`
first would delete the explicit `pins >= 32` clear while the preserve mask still strips the bit,
briefly leaving `0x08` with **no drop route at all**. The intermediate state this plan creates is
safe and observably a no-op on the `0x08` write path, because `eprom.cpp:217-219`'s explicit clear
still zeroes the bit before the first `set_address` and the preserve then preserves a zero. Prove
that empirically rather than asserting it: `pio test -e native_loop_v131` must still be 40/40 after
this plan, with `test_loop08_dip32_drop_bit_is_cleared_deliberately_before_the_first_pulse` still
green.

**Requirement ownership: this plan may mark NO requirement Complete.** It contributes the
hardware-side half of VPP-01. `requirements:` is deliberately empty and must not be repopulated —
plan **142-07** declares all four `VPP-*` IDs and flips them once all evidence exists (the 141-05 /
141-09 convention).

**Read-only in this plan:** `src/proms/eprom.cpp`, `src/proms/eprom_params.cpp`,
`include/rurp_pinout.h`, `scripts/baseline/size_baseline.json`, `platformio.ini`.

**L-1 working rule:** commit before running the full pytest suite —
`tests/test_flash_path_record_sync.py:1247` asserts the whole firmware repo is porcelain-clean
(F-141-11, orphaned, do not fix here).
