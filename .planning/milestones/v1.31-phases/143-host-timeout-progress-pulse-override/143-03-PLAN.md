## BF-1 reconciliation — D-08's premise is FALSE in this branch, and this plan is where it is fixed

`143-CONTEXT.md` **D-08** says the carrier is "a CAP-03 length-discriminated extension of `MSG_OK_READY`'s

`143-RESEARCH.md` §BF-1 established, with four independent oracles, that **there is no CAP-02 tail in this
branch to append to**:

| Fact | Where |
|------|-------|
| v1.31 firmware emits a bare 2-byte ack: `LOG_OK_ID_U16(MSG_OK_READY, (uint16_t)DATA_BUFFER_SIZE);` | `src/firestarter.cpp`, in `init_programmer_framed`, immediately before `op_reset_timeout()` — re-verified twice (RESEARCH and PATTERNS) |

**Corrected behaviour, and why:** the ack must be packed as **one** block emitting
`[buffer_size u16 BE][hw_revision u8][ver_len u8][ver bytes][write_budget_s u16 BE]`. CAP-02 is
**ported, not invented** — it is shipped code from `13eb350`, re-implemented here inside the CAP-03 pack
block so the `_ready[]` size and the pack sequence are written once (RESEARCH Open Question 2's
recommendation; cite `13eb350` in the commit message rather than cherry-picking and amending).
Attempting D-08 without CAP-02 present is not "graceful degradation" — offsets 2 and 3 belong to CAP-02's
host arm, so a budget written at offset 2 would be read as a hardware revision plus a version length. That
is a **misparse**.
