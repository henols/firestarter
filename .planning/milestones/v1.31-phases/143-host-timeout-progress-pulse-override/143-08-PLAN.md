<objective>
Pin BF-2's mitigation with a **source-contract** gate. This is the only kind of oracle that can prove a
`#ifdef`-scoped guard in this repository, and the reason is structural, not stylistic.

## Why a source-contract gate and not a behavioural test

`143-RESEARCH.md` §BF-2's corollary: `src/boards/uno_rurp_shield.cpp` — the file containing `com_mode`, the
strong `rurp_log_id` override and the 4-slot deferred buffer — is compiled in **no** native environment
(`build_src_filter` is `+<proms/> +<boards/rurp_serial_utils.cpp> +<json_parser.c> +<operation_utils.cpp>`),
and the native `rurp_log_id` capture stub has **no** `com_mode` gate at all. A native test therefore records
every emitted frame and proves **nothing** about Uno-class delivery. Phase 142's `command_done()` gate is the
in-repo precedent for exactly this situation, and its own docstring explains why a behavioural oracle is
impossible for an `#ifdef`-scoped guard. Label this module as a source contract in its docstring, in the
SUMMARY and in the phase record — never as behavioural evidence.

## What the guard protects, restated so the gate's assertions are legible

On `uno` and `uno328pb` (`-D SERIAL_ON_IO`), `rurp_set_programmer_mode()` tears the UART down for the whole
programmer-mode window and `rurp_log_id` **defers** frames into `deferred_log[4]`, flushed only when
communication mode is restored. A fifth frame is **silently dropped**. Progress frames emitted from inside the
per-byte loop would fill those four slots, so the subsequent `MSG_ERR_MAX_PULSES` frame would be dropped, the
firmware would go idle having emitted **no error frame**, and the host would raise `SerialTimeoutError` — a
transport error where HOST-03 requires a program failure naming the address. **HOST-03 works on Uno today**;
an unguarded emission would regress it. The guard is therefore load-bearing for a *different* requirement
than the one it appears to serve, which is exactly why it needs a gate rather than a comment.

Second, smaller thing the gate must pin: the `millis()` **state variable** is inside the guard too. An
unreferenced local on a `SERIAL_ON_IO` build produces an unused-variable warning, and
`scripts/baseline/size_baseline.json`'s policy is `avr_rule: "== 0"` — so an unguarded declaration turns
`check_build_warnings.py` RED on two targets. A leg that pins only the emit would let that regression back in.

## D-06's non-claim, recorded here as well

*Intra-block write progress is emitted on the EPROM path only, and delivered on `leonardo` only.* Both halves
belong in this plan's SUMMARY. This is the D-09/F-120-02 class of incident — a two-repo requirement that
passes its own phase's verification while being false end to end — so the non-claim is not optional prose.
