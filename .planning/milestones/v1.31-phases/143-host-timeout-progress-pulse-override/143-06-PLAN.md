## The four traps this plan exists to avoid

**1. The loop raises on a DATA frame today (D-05's second half).** `_main_phase_send_data`'s response loop
handles only `MAIN`, `ERROR` and `OK`, and then **raises** `EpromOperationError("Programmer did not request
data chunk, got {type}: {message}")` on anything else. A mid-block `MSG_DATA_PROGRESS` frame hits that raise.
The DATA branch is not an enhancement — it is what makes plan 143-05's firmware emission work rather than
break the write. Insert it **between** the ERROR branch and the `if response.type != "OK":` raise.

**2. Acking the frame aborts the write, silently (D-05).** `_handle_progress_response`'s `ack_data` defaults
to `True`. The firmware is mid-block waiting for nothing, so an ack desyncs the stream — and the failure mode
is worse than a desync: on a Leonardo the stray `OK` **is** buffered, `op_get_message` returns `OP_MSG_ACK`,
and `_process_incoming_data`'s `default: return false` aborts the write with **no error frame at all**. This
is the `#write-empty-input-regression` trap in a new place; that regression's fix was precisely
`ack_data=False` on the INIT/END progress frames. The write MAIN branch must not ack, and must **not** be
routed through `_handle_progress_response`, whose DATA arm both acks and calls `set_progress`.

**3. `set_progress` tears the bar down on every frame (D-04, verified real).** `set_progress(current, total)`
calls `self.start(total)` whenever `self.total_steps != total`, and `start()` **closes and re-creates** the
`tqdm` bar and zeroes `current_step`. The write bar is started with `file_size`, while `0xE0` carries
`handle->mem_size`. For a full-chip write they match; for a short input file or an `--address`-offset write
they do **not**, so every single frame would destroy and rebuild the bar. The write branch therefore applies
`current` **only** and performs the last three operations of `set_progress` directly, bypassing the
`start(total)` arm. **Fixing `set_progress` itself is a deferred idea** — it is shared code on the read and
blank-check paths, so the blast radius reaches operations this phase does not own. Do not fix it.

**4. Two progress sources fight over one bar (RESEARCH Pitfall 1).** The loop already calls
`progress.update(len(data_chunk))` when a chunk is **handed off**. Adding absolute positioning from `0xE0`
means the bar jumps to 1024 the instant chunk 1 is sent, then the firmware's frames set it back to 0..1024 as
bytes are actually programmed, then it jumps to 2048, then crawls again — and `tqdm` permits `pbar.n` to move
backward, so the bar **visibly rewinds**. The fix is a **latch**: once the first mid-block DATA frame is
observed, stop calling `update()` on handoff and let the firmware drive the bar absolutely; until then keep
today's handoff-based bar. This is the only shape that is correct on both boards — a Leonardo gets a
bytes-programmed bar, and a `SERIAL_ON_IO` board (which by BF-2 never delivers a mid-block frame) keeps
today's bytes-sent bar. **Do not simply delete the `update()` call** — that regresses Uno-class boards to a
bar that never moves.

| a mid-block frame to the write's flow control | an unexpected frame type in the MAIN window either raises or, if acked, desyncs the firmware's data-pull handshake |
