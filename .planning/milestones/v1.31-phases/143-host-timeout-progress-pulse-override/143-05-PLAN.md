## BF-2 reconciliation — D-02 is CONTRADICTED IN SCOPE, and a naive implementation would BREAK HOST-03

**Read this before touching `eprom.cpp`.** `143-CONTEXT.md` **D-02** says the firmware emits
`MSG_DATA_PROGRESS` from inside the per-byte loop, and **D-13** justifies HOST-01 partly on the grounds that
"the resets already fire on every yielded frame, which is *why* D-02's emission feeds the window for free".
`143-RESEARCH.md` §BF-2 falsified that on `uno` and `uno328pb`, with every link located in source:

| Fact | Where |
|------|-------|
| `-D SERIAL_ON_IO` is on exactly two envs, `uno` and `uno328pb` | `platformio.ini` |
| Without it both mode functions are typed **no-ops** | `include/rurp_shield.h` |
| With it, `rurp_set_programmer_mode()` sets `com_mode = false`, calls `rurp_serial_end()`, and drives PD0 as data-bus bit 0 | `src/boards/uno_rurp_shield.cpp` |
| The Uno's **strong** `rurp_log_id` override **defers** rather than emits while `com_mode == false`, into `deferred_log[DEFERRED_LOG_MAX]` with `DEFERRED_LOG_MAX 4`, `DEFERRED_PARAM_MAX 8` | same file |
| Overflow behaviour is a **silent drop** ("buffer full ... drop excess rather than risk emitting on the active bus") | same file |
| Deferred frames flush **only** in `rurp_set_communication_mode()` | same file |
| The whole per-byte loop runs inside one programmer-mode window (`rurp_set_programmer_mode(); callback(handle); rurp_set_communication_mode();`) | `src/operation_utils.cpp`, `_execute_operation` |
| `MSG_DATA_PROGRESS`'s payload is exactly 8 bytes — precisely `DEFERRED_PARAM_MAX` | host `messages.py` |
| The same trap is already documented in-tree **twice**, including at the only existing `0xE0` emitter | `src/boards/uno_rurp_shield.cpp`, `src/proms/memory.cpp` |

**The failure chain on an Uno, in order:** progress frames are deferred, not sent, so they cannot feed the
host's response window; after 4 of them the buffer is full; a byte that fails at `max_pulses` emits
`MSG_ERR_MAX_PULSES` and it is **dropped**; `response_code = RESPONSE_CODE_ERROR` still propagates so the
firmware goes idle having emitted **no error frame**; the host blocks in `get_response` and raises
`SerialTimeoutError`. **That is a transport error — exactly what HOST-03 forbids — and it is a regression:
HOST-03 works on Uno today** because without progress frames the 4-byte error frame fits in the deferred
buffer and is delivered on the flush.

**Corrected behaviour, shipped by this plan:** wrap both the emission **and its state variable** in
`#ifndef SERIAL_ON_IO`. Rejected alternatives, with reasons, to record in the comment: exposing `com_mode`
via a new accessor and gating at runtime (costs an accessor on every target, still delivers no intra-block
progress on Uno, still no mechanism to reserve error slots); raising `DEFERRED_LOG_MAX` (RAM cost on the
tightest-RAM target and still zero intra-block delivery); reserving headroom by emitting at most
`DEFERRED_LOG_MAX - 2` frames (a fragile invariant across two files, still no delivery).

**D-06's non-claim therefore gains a second dimension**, and both halves must appear in this plan's SUMMARY
and in the phase record: *intra-block write progress is emitted on the EPROM path only, and delivered on
`leonardo` only.* This is the D-09/F-120-02 class of incident — a two-repo requirement that passes its own
phase's verification while being false end to end — so the non-claim is not optional prose.

**The native oracle is structurally blind to this.** `src/boards/uno_rurp_shield.cpp` is in **no** native
env's `build_src_filter`, and the native `rurp_log_id` capture stub has **no** `com_mode` gate, so a native
test will happily show frames being emitted regardless. The guard therefore needs a **source-contract**
gate, which is plan **143-08**'s — not a behavioural one. Do not attempt a behavioural proof of the guard
here and do not claim one.
