## What was actually missing, and what is not

The machinery already exists and must not be rebuilt: `firestarter/messages.py` carries
`MSG_ERR_MAX_PULSES` (`0xBD`) and `MSG_ERR_ENERGY_CAP` (`0xBE`) with formats that already interpolate the
failing address, and `_main_phase_send_data`'s ERROR branch already routes through
`_raise_for_error_response` to an `EpromOperationError` carrying `error_code`. **What was missing is that the
10 s timeout fired first**, converting a program failure into a transport error — and plan 143-04 fixed that.
HOST-03's own delta is therefore: a hint appended on the `_boot_block_hint_message` seam for
`0xBD` / `0xBE` / `0xAE`, plus tests proving the id surfaces as a program failure naming the address.

Exact catalog formats, read this session — the hint adds **disposition**, not location:
- `0xBD`: `"Byte at 0x%06x failed to program within %d pulses"` — names the address.
- `0xBE`: `"Byte at 0x%06x exhausted its per-byte program-energy budget after %d pulses"` — names the address.
- `0xAE`: `"Pulse width %lu us exceeds this protocol's per-byte program-energy budget"` — names the refused
  **width**, not an address, because it is a **pre-flight** refusal raised before any byte is touched and
  before any high voltage is enabled. The hint for `0xAE` must therefore say something different from the
  other two: nothing was programmed at all and the chip is unchanged by the command.

`firestarter/messages.py` is **codegen-generated and must never be hand-edited**. No format changes here.

## D-20 — `0xB1` is a dead id on this family, and a test must prove no path keys on it

F-141-06: `MSG_ERR_WRITE_FAILED` (`0xB1`) is emitted by **nothing** on the 27C path any more — a whole-tree
grep finds zero references under `src/`. The budget reporter emits `0xBD`/`0xBE` with a different, smaller
payload shape (`u24 address, u8 pulse_count`) instead of `0xB1`'s three-param
`(u24 address, u8 retries, u16 bad bytes)`. **Any hint or test keyed on `0xB1` for this family is keyed on a
dead id.** The new hint must not name it, and one leg must prove no host path does.

## D-21 — what the hint must and must not say

`141-LOOP-RECORD.md` §4 traced the firmware's actual behaviour, re-verified against live source: on a budget
failure `handle->address` does **not** advance, `_process_incoming_data` returns `false` immediately,
`command_done()` fires and zeroes the control and address registers, and the firmware **accepts no further
blocks for that write**. "The write aborts" and "the firmware stops accepting blocks" are the same event. §4
says in terms that a host implementation assuming the firmware might continue past a failed block, or
auto-retrying the same block expecting firmware-side resumption, "would be building against a behaviour the
firmware does not have."

So the hint:
- states what **was** and **was not** programmed — bytes before this block landed, this block is partially
  programmed, no later block was attempted;
- states that the firmware **stops accepting blocks** for this write and the address counter does not advance,
  so re-running the write repeats the whole file from the start;
- offers **no** retry advice and implies **no** resumption;
- for `0xBD`/`0xBE`, points at the likely physical cause (insufficient program voltage or a worn/failing cell)
  rather than at a timing knob — a byte that will not converge is not a timing problem;
- for `0xAE` **only**, points at `--pulse-us` and names the refused value the firmware already reported, and
  says plainly that no byte was programmed by that command.

| a firmware error id to the user's mental model of what happened | a hint that implies resumption or invites a retry describes behaviour the firmware does not have, and the user acts on it |
