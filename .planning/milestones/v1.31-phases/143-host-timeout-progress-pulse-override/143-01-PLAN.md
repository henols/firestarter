## BF-3 reconciliation — D-11's formula is CONTRADICTED and this plan ships the correction

**Read this before writing a line of arithmetic.** `143-CONTEXT.md` D-11 states the per-byte bound as
`min(max_pulses x pulse, energy_cap_us)`, plus an overprogram term of
`min(3 x overprogram_factor x pulse, overprogram_cap_us)`. `143-RESEARCH.md` §BF-3 falsified both halves
against the shipped loop, and this plan implements the corrected forms:

1. **The pulse count ceils.** The shipped loop (`src/proms/eprom.cpp`, the inner `for (;;)`) does
   `accumulated += org_delay` **before** testing `accumulated >= energy_cap_us`, so the last pulse may
   overshoot the cap by up to `pulse_us - 1`. The real bound is
   `min(max_pulses, ceil(energy_cap_us / pulse_us)) x pulse_us`. At `--pulse-us 49999` on `0x0B` the true
   per-byte bound is **99 998 us** (two pulses), not 50 000 — a **2x** under-estimate on a host-legal,
   firmware-accepted input. `firestarter/CLAUDE.md` §"Algorithm Handlers"'s `0x0B` row already derives
   the same 99 998 us figure independently (F-141-10), so the correction is citable in-tree.
2. **The overprogram term has no literal `3`.** The shipped `eprom_overprogram_us(pulse_count, pulse_us,
   factor, cap_us)` computes `factor * pulse_count * pulse_us` clamped at `cap_us`. The `3` in
   `include/eprom_params.h`'s column comment is a documentation defect that double-counts the datasheet's
   `3xN` rule — `3` **is** the factor and `N` **is** the pulse count. Restating D-11's literal form would
   under-estimate **8.3x** for the first future row that sets a non-zero factor. This plan **calls** the
   shipped function with the computed pulse count so the budget cannot drift from runtime behaviour.

Why this matters more than an off-by-one: a budget that is too **tight** causes a spurious timeout on a
**working** write — a false failure on real silicon, which **D-09** names as strictly worse than a
generous ceiling. Do not "simplify" back toward D-11's wording.
