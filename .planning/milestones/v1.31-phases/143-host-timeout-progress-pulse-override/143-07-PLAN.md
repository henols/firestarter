## The one measured trap: `default=0` breaks every `write`

`click.IntRange(1, 65535)` type-casts the option's **default**. With `default=0`, `0` is out of range, so
Click raises `UsageError` **before the handler runs** and `firestarter write CHIP file.bin` exits 2 **with no
flag supplied at all**. `143-RESEARCH.md` measured all seven cases on the CI-parity interpreter with
click 8.4.2:

| Option shape | Invocation | Result |
|--------------|-----------|--------|
| `IntRange(1,65535)`, `default=0` | *no flag* | **exit 2** — `Error: Invalid value for '--pulse-us': 0 is not in the range 1<=x<=65535.` Every `write` breaks. |
| `IntRange(1,65535)`, `default=None` | *no flag* | exit 0, `pulse_us=None` |
| `IntRange(1,65535)`, `default=None` | `--pulse-us 100` | exit 0, `pulse_us=100` |
| `IntRange(1,65535)`, `default=None` | `--pulse-us 0` | exit 2 |
| `IntRange(1,65535)`, `default=None` | `--pulse-us 65536` | exit 2 |
| `IntRange(1,65535)`, `default=None` | `--pulse-us abc` | exit 2 — `'abc' is not a valid integer range.` |

Click short-circuits `type_cast_value` on `None`, which is why `default=None` works. **The nearest in-tree
precedent is the trap**: `--read-settling` / `--read-strobe` use `type=int, default=0` with **no** range, so
copying that shape and adding a range is the natural move and it is fatal. Those two options also live inside
the `if _DEV_TOOLS_ENABLED:` block on `dev consistency-check` — a **dev-gated** command — whereas
`--pulse-us` is on production `write` (D-18) and inherits none of that gating.
`143-PATTERNS.md` records that `click.IntRange` has **zero** existing usages anywhere in
`firestarter_app/firestarter/` or `tests/`, so the measured table above is the specification, not an analog.

**The CI smoke step will not catch it.** `firestarter --help` never invokes `write`. Only a `CliRunner`
invocation of `write` with **no** `--pulse-us` catches `default=0`. That test is mandatory here.

## D-15's rationale is corrected, but the guarantee holds

D-15 justifies `IntRange` as refusing "before `AppContext` builds". That is **false** — Click's `cli()` group
callback runs **first**, before `write()`'s parameters are type-converted. The **guarantee still holds** for
the reason HOST-05 actually needs: nothing in `cli()` or `AppContext` opens a serial port, so a parse-time
refusal is still structurally before any serial byte. State the corrected mechanism in the record and prove
it with a negative test (`find_and_connect` not called), not with the wrong rationale.

## D-16 — the `0x0B` over-cap window is the firmware's, deliberately

A `--pulse-us` between 50001 and 65535 is host-legal but firmware-refused **on `0x0B` only**, because
`configure_eprom`'s refusal is keyed on `energy_cap_us > 0` and only `0x0B` ships a non-zero cap. Warning
host-side would require mirroring `energy_cap_us`, which contradicts D-07's single-definition-site rule. The
firmware refusal already fires **before the first pulse** and reports the offending value via
`MSG_ERR_PULSE_TOO_WIDE` (`0xAE`); plan **143-09** makes that render actionably. `eprom.cpp`'s own comment
names itself "the firmware-side backstop for Phase 143's `--pulse-us` bounds, independent of host
validation" — this plan takes it at its word and adds **no** host-side over-cap warning.

## The bound's provenance, which the record must state (D-15)

`1..65535` is **minipro parity** (`-o pulse=N` is uint16), **not** the wire type. `pulse-delay` is parsed by
`extract_long` into an **unclamped** `uint32_t` on the firmware side (hand-off H3), so an over-ceiling wire
value is reachable **today**, independently of this flag. H3 is Phase 146 / CLOSE-04's to reconcile. This
plan must **not** imply the bound is a type constraint — put one clause in the `--help` text so a user who
never reads the docs is not misled, and leave the full reconciliation to CLOSE-04.

## A decided mechanical gray area: no `JSON_KEY_PULSE_DELAY`

Both upstream documents call a `constants.py` `JSON_KEY_PULSE_DELAY` **cosmetic**, and `143-PATTERNS.md`
requires it be used at *both* sites or not at all — which would force an edit to `database.py`'s
generated-database read path for zero behavioural gain. **Decision: skip it.** The `"pulse-delay"` literal
stays at its existing sites. Record the decision and this reason; do not add the constant and do not touch
