<gate_specification>
## Extraction rule (the module's own, independent, live re-parse)

Given a C/C++ source file:
1. Strip `/* ... */` and `// ...` comments and the contents of string/char literals, **preserving
   line numbers** (replace stripped spans with equivalent whitespace/newlines).
2. Find every branch-condition span: the parenthesised condition of `if`, `else if`, `while`,
   `switch`; the middle clause of `for (init; COND; step)`; and every ternary `? :` condition.
   Use bracket matching, not a flat regex — conditions contain nested parentheses.
3. Keep a span only if its text contains `handle->` **or** a call to one of the handle-taking
   predicate helpers: `is_flag_set(`, `using_p1_as_vpp(`, `is_operation_in_progress(`.
4. For each kept span record: 1-based `line`, whitespace-normalised `predicate` text, and
   `keyed_on` — the sorted set of `handle-><field>` names appearing in it, plus the literal token
   `ctrl_flags` for any `is_flag_set(` call, `pins+bus_config.vpp_line` for any `using_p1_as_vpp(`
   call, and `operation_state` for any `is_operation_in_progress(` call.
5. `tier` = `"protocol"` if `keyed_on` contains `protocol`, else `"other"`.

## Tier 1 — the load-bearing assertion (protocol-keyed sites)

In `src/proms/eprom.cpp` there are **exactly three** tier-1 sites, at lines **71**, **145** and
**218**. Note two locator traps:
- `eprom.cpp` does **not** include `proto_constants.h`, so `:145` and `:218` spell the value as raw
  `0x0B`. A locator matching only `PROTO_EPROM_24PIN` finds nothing today; one matching only `0x0B`
  breaks the moment Phase 142 adopts the token. The extractor must key on `handle->protocol`
  (which both spellings share) and the inventory must record the literal predicate text so either
  spelling change is visible as a divergence.
- The `switch` at `:71` has `case 0x08:`, `case 0x0B:` and `default:` — there is **no**
  `case 0x07:`. A locator requiring three `case` labels finds two.

## Tier 2 — every other handle-field predicate in the EPROM path

Derive the exact set with the extractor. It **MUST include at least** these `eprom.cpp` lines:
`46, 53, 70, 94, 96, 100, 101, 108, 119, 131, 132, 144, 229, 244, 252, 292, 295, 296, 303, 320, 328`
(21 sites; total across both tiers is expected to be 24). If the extractor finds fewer, the
extractor is wrong — fix the locator, never the assertion (D-15 trap 2).

## The table's own leg (D-13's "plus the new table")

`src/proms/eprom_params.cpp` is scanned separately, because its lookup compares the `protocol`
**parameter**, not `handle->protocol`. Assert: zero `switch` statements in the comment-stripped
source; exactly one comparison of a `pgm_read_byte(&EPROM_PARAM_KEYS[...])` expression against
`protocol`; and `EPROM_PARAM_KEYS` initialised with exactly the three keys `0x07`, `0x08`, `0x0B`.

## Env seams (documented, import-time)

- `FIRESTARTER_BRANCH_SCAN_SOURCE` — overrides the scanned `src/proms/eprom.cpp` path.
- `FIRESTARTER_BRANCH_SCAN_PARAMS_SOURCE` — overrides the scanned `src/proms/eprom_params.cpp` path.

Both exist **only** so a planted violation can be scanned without touching either repo. The blob-SHA
test and the default-target test always use the non-overridable `_REPO_ROOT`-derived paths, so a
stray env var cannot make the gate pass vacuously — it makes it RED. Document both seams in the
module docstring: this repository has no central environment-variable inventory, so the docstring is
the only place a reader can discover them.
