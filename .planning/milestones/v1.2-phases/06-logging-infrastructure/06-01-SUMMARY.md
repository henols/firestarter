# Phase 6 Plan 01: Catalog + Codegen Bootstrap Summary

**TOML catalog (68 entries) + Python 3.11+ stdlib codegen with 10-rule validator + sync script — generates firmware messages.h/messages.c + host messages.py byte-identically on re-run.**

## Performance

- **Duration:** ~10 min (start `2026-05-18T11:29:25Z`, end `2026-05-18T11:39:xx`)
- **Tasks:** 2/2 complete
- **Files created:** 10 (3 meta-repo + 4 vendored + 3 generated)

## Accomplishments

- Canonical log-message catalog covering every Phase 6 seeded message (68 entries spanning `OK / INIT / MAIN / END / INFO / WARN / ERROR / DATA` severity ranges) — committed at `.planning/catalog/messages.toml`.
- Deterministic codegen (`tools/catalog/codegen.py`) emits firmware `messages.h` + `messages.c` and host `messages.py` byte-identically on re-run; proven by running the same emitter twice and `diff`ing the outputs to `/tmp` for each of the three languages.
- `--check` mode runs all 10 catalog validation rules and exits 1 on any violation; verified against 8 distinct negative inputs (duplicate id, duplicate name, empty format, bad severity, bad wire_format, format-vs-param mismatch, 24-byte budget overflow, bad name shape, bad param type) — every error message names the offending entry by both id and name.
- `sync_to_subrepos.sh` is idempotent: `cp` + `diff -q` per file, plus a cross-sub-repo `messages.toml` byte-identity assertion at the end. Verified by running twice (no-op the second time) and by `cmp firestarter/tools/catalog/messages.toml firestarter_app/tools/catalog/messages.toml` returning identical.
- Generated files committed in both sub-repos at their canonical paths so downstream plans (06-02 firmware helper, 06-03 host decoder) can `#include "messages.h"` / `from firestarter.messages import CATALOG` directly.

## Decisions Made

1. **Catalog seed count is 68, not 52** — adopted the literal RESEARCH §"Full Catalog Seed" table contents verbatim (each row = one `[[messages]]` entry). The "52 entries" subtitle in the RESEARCH section header is a stale count from the earlier inventory paragraph ("84 raw call-sites → 62 distinct → 52 unique format-strings"); the table itself enumerates 68 rows including the `MSG_NONE` sentinel and the four state-machine prefix entries. The plan's acceptance criterion `grep -c '^\[\[messages\]\]' == 52` carries the same stale number.

2. **MSG_NONE (0x00) gets severity = "OK"** — the RESEARCH table shows severity=— for the reserved sentinel, but the validator (rule 7) requires a valid severity from the 8-member enum. "OK" was chosen as the least-misleading placeholder (the sentinel will never be emitted; downstream callers check `id != MSG_NONE` before dispatch).

3. **MSG_{INIT,MAIN,END}_DONE use placeholder format strings** — the RESEARCH table showed empty `(empty)` format strings, but rule 3 forbids empty `format`. The catalog uses `(init done)` / `(main done)` / `(end done)` as descriptive placeholders. These are state-machine acks with no payload; the host renders the descriptive text for INIT/MAIN/END responses.

4. **`u24` payload variable-length flag on the host: `param_bytes = -1`** — for ascii_str-containing messages where the wire byte count is variable. The PROGMEM table uses `0xFF` for the same case. Both encodings let callers distinguish "fixed 0 bytes" from "variable".

5. **Sync script asserts cross-sub-repo byte-identity** — beyond per-file `diff -q` after copy, the script does a final `diff -q firestarter/.../messages.toml firestarter_app/.../messages.toml`. This catches a class of corruption where the meta-repo edits forget to re-sync one sub-repo. Per the RESEARCH §"Authority Assertion" recommendation.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Doc-vs-Source Conflict] Catalog contains 68 entries instead of the 52 named in the plan acceptance criterion**

- **Found during:** Task 1, after authoring the catalog from the RESEARCH §"Full Catalog Seed" table.
- **Issue:** The RESEARCH section title says "Full Catalog Seed (52 entries)" and the plan acceptance criterion (`grep -c '^\[\[messages\]\]' .planning/catalog/messages.toml` returns `52`) repeats that count. The table itself enumerates 68 rows (`awk '/^## Existing Log Surface Inventory/,/^## Catalog Format/' 06-RESEARCH.md | grep -c '^| 0x'` → 68). The "52" appears upstream of the table in a paragraph about call-site dedup ("84 raw call-sites → 62 distinct → 52 unique format-strings") but is not the table's actual row count.
- **Fix:** Adopted the literal 68-row table contents (the plan's overriding instruction is "exactly per RESEARCH §"Full Catalog Seed (52 entries)" table"). Documented the discrepancy here and in the SUMMARY's "Decisions Made" section so the next plan author can fix the RESEARCH section title.
- **Files modified:** `.planning/catalog/messages.toml` (68 entries seeded).
- **Verification:** `grep -c '^\[\[messages\]\]' .planning/catalog/messages.toml` returns `68` (not the `52` the acceptance criterion expected). All 68 IDs sort and dedupe cleanly; codegen accepts the file.
- **Committed in:** `b188b4d` (Task 1 meta-repo commit).

**2. [Rule 2 - Missing Critical: Schema Conflict Resolution] `MSG_NONE` (0x00) given severity = "OK" instead of "—"**

- **Found during:** Task 1, first `--check` run.
- **Issue:** Validator rule 7 requires `severity ∈ {OK, INIT, ..., DATA}`. The RESEARCH table shows severity=— for `MSG_NONE` (reserved sentinel). The catalog cannot leave severity blank or use "—" without violating its own validator.
- **Fix:** Set severity = "OK" for `MSG_NONE` as a benign placeholder. This sentinel is never emitted, so the severity value is immaterial in practice. Alternative considered: extend the validator to allow severity="—" or omit-severity for `MSG_NONE` specifically; rejected because it adds a special-case to the validator that would propagate to firmware/host parsers.
- **Files modified:** `.planning/catalog/messages.toml`.
- **Verification:** `--check` passes; `CATALOG[MSG_NONE].severity == SEVERITY_OK == 0x01`.
- **Committed in:** `b188b4d`.

**3. [Rule 2 - Missing Critical: Schema Conflict Resolution] State-machine done messages get non-empty placeholder format strings**

- **Found during:** Task 1, validator development.
- **Issue:** Rule 3 forbids empty `format`. RESEARCH shows `MSG_INIT_DONE` / `MSG_MAIN_DONE` / `MSG_END_DONE` with `(empty)` placeholder format.
- **Fix:** Used `"(init done)"` / `"(main done)"` / `"(end done)"` as descriptive placeholders. The firmware emits these as 1-byte ID frames with zero params; the host can render either the placeholder text or substitute a more specific label by ID at format-application time.
- **Files modified:** `.planning/catalog/messages.toml`.
- **Verification:** `--check` passes for these three IDs.
- **Committed in:** `b188b4d`.
