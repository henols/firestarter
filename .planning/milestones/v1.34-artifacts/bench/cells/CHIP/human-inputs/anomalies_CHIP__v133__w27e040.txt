ERROR-IDENTITY FINDING (separate from the transport-integrity finding above -- itself a Phase
165/166 filing, NOT fixed here, D-16 boundary): `MSG_ERR_EMPTY_INPUT` (error_code 164/0xA4) is
OVERLOADED in firestarter/src/firestarter.cpp. Two emit sites: `:124`, a genuine empty-buffer
check; `:251-255`, the frame-integrity path (CRC mismatch, COBS violation, overflow, or read
underrun), which REUSES `MSG_ERR_EMPTY_INPUT` because a distinct `MSG_ERR_BAD_FRAME` was
deliberately deferred -- the code comment states verbatim: "messages.h is codegen; adding
MSG_ERR_BAD_FRAME requires a TOML catalog update -- deferred." An operator or triager reading
"ERROR: Empty input" on a blank-check will reasonably conclude something about the chip or the
input file; the actual condition is far more likely a corrupted serial frame. This misleading error
identity is filed here for Phase 165/166 on its own merits, separate from the transport-integrity
finding itself. NOT fixed here -- messages.h is codegen-generated from meta's messages.toml and
this is a Phase 165 boundary; no product-code edit made in either sub-repo.

BLANK-CHECK VERDICT SCOPE, STATED EXPLICITLY: because blank-check failed at the transport layer
before returning a result, this run carries NO EVIDENCE about whether the device is actually
blank -- and therefore NO independent confirmation that the preceding `erase: OK` actually erased
anything. `erase: OK` means the erase COMMAND was accepted and completed without the firmware
reporting an error; it is NOT itself proof the device was left blank, because the step that would
have checked that is precisely the one that died. This is stated explicitly so `erase: OK` is
never read as blank-check-confirmed-erase in this row.

STEP-ORDER HYPOTHESIS (operator question), checked and cleared: whether erase before blank-check
is the correct sequence for this part. Confirmed live against
firestarter_app/firestarter/chip_test.py:640-683 -- blank-check is appended AFTER erase (Case 2)
specifically for a part with an executable erase (this part: EEPROM, protocol 8, erase supported),
"only once erase has run does 'not blank' become a tool-health finding rather than a report of the
chip's prior state." The alternative position (before write, Case 4) applies only to
SRAM/FRAM-excluded or auto-erase-on-write parts, or UV-EPROM. W27E040 correctly uses Case 2 --
erase-before-blank-check is deliberate and correct here, not a step-ordering defect. Checked and
cleared; not re-investigated further; no product-code change.
