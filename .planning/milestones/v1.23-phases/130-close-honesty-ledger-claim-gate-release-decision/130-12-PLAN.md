<objective>
Hand-write both b15 release bodies as committed drafts, and stop.

D-02's reasoning is the whole design: the claim scanner's own module docstring says a green run is the
**mechanizable half only** — it cannot detect an implied overclaim, a misleading omission, or wrong tone. This
is the first release in the project's history to carry a py32 asset, and the asset is the milestone's only
user-visible deliverable. So the bodies are written by hand, checked by the scanner, and then read by a human
before either reaches a public release.

The rejected alternatives are recorded so a later reader sees they were considered: posting once the scanner
is green with no human read, and hand-writing the firmware body only — rejected because the **app** is the
half that gained `fw --board py32f071`, and a PyPI installer never sees the firmware body.

**Structural gating, not a flag.** This plan contains no command that can publish anything. `--auto` and
`--chain` auto-approve human-verify checkpoints, and `autonomous: false` does not protect an outward-facing
act, so the protection is that the posting command is not here. It lives in plan 130-14's written operator
procedure.

Purpose: get the outward-facing prose right before it is outward-facing.
Output: two committed drafts, both scanner-green, neither posted.

**Requirement ticking:** this plan ticks NO requirement ids.

**Open with the install command** and the zero-assets fact: this GitHub release carries no attached files — it
is a tag-and-marker page only; PyPI is the distribution channel for the host app; the matching firmware is
published separately and its `.hex` files are what `firestarter fw --install` pulls. This is factually true of
the app's release workflow, which has no `files:` step, and b14 confirmed it by carrying zero assets.

**What the app gained.** The py32 firmware-install path: `firestarter/py32_dfu.py`, a DFU 1.1 plus DfuSe
client on `pyusb` with no external binary and no `dfu-util`; the `flash_method()` router with unknown boards
still defaulting to avrdude and AVR asset names byte-identical; `fw --dfu-probe`; `--usb-id`; the
flash-envelope guard; the `[py32]` extra and the `pyusb >= 1.3.1` floor. Say what a user can actually run
today and what they cannot.

**The beta-only gate, stated as a feature.** The py32 board is hidden on a stable build: `_BOARD_CHOICES` is
computed at import time, so a stable `fw --help` renders only the three AVR boards, `--dfu-probe` and
`--usb-id` are rejected, and `firmware.py` refuses inside the install path too so a library caller bypassing
Click is blocked. There is no environment-variable escape hatch, deliberately, and an unparseable version
fails closed. Graduation is deleting one entry once a target is bench-validated.

**Two safety findings worth repeating**, both already fixed and both generalizable: a DFU **runtime**
interface is never touched unless named explicitly with `--usb-id` — the devcontainer's own webcam advertises
one — and a typed `--board` that disagrees with the attached programmer is refused, because previously the
detected board won silently.

The proven side: the host suite passes at its recorded collected total; the DFU sequence is exercised against
device descriptors and mocks; a CI leg installs the `py32` extra and exercises the real `pyusb` import and API
surface. The not-proven side: carry the canonical caveat sentence, then state that the readback verification
is asserted against a mock only, that the DFU dialect, sector and erase geometry, flash-envelope bounds and
