- **R1 — BOOT0 / nBOOT1 strap reachable.** Why: `PF8-BOOT0` defaults to input with its pull-down
  enabled, so the strap must actively pull PF8 high — a jumper, button or test point to VDD — for
  the tier-2 factory-DFU recovery route in §2 to exist at all; an external pull-down is optional
  but cheap insurance against a floating net; and while the self-flash route in §2 would remove
  the strap dance, it is FUT-N05 and does not exist, so the strap must stay reachable in the
  meantime. Breaks if omitted: the only recovery route that needs no probe is unreachable, and the
  board is SWD-only from the first bad image onward. Note that `PF8` is not bonded on QFN56, which
  is a second, independent reason that package is ruled out in R3.
- **R2 — SWD pads exposed, including nRST.** Why: PA13/PA14 are `SWDIO`/`SWCLK` after reset but
  both carry other alternate functions, so reassigning them is possible and forecloses the
  unconditional last resort; `nRST` belongs on the same header because §1.2's option-byte hazard
  (`nBOOT1 = 0` selects SRAM, so `BOOT0 = 1` reaches a boot area with nothing in it, and the
  factory value is unresolved — §9 Open Question 1) is precisely the state only SWD can recover
  from. Breaks if omitted: a single bad option-byte write bricks the board permanently. A usable
  header carries SWDIO, SWCLK, GND, a VDD sense and nRST.
- **R3 — Contiguous PB0–PB7 data bus, and a package that can carry it.** Why: the one-snapshot
  `IDR` read and atomic `BSRR` write design needs the eight data lines on one port in one
  contiguous run; PB2 and PB3 are not bonded on QFN56, and PB2 and PB3 are not bonded on QFN32, so
  this is a **part-selection** decision before it is a pin-assignment one — viable packages are
  LQFP64, CSP64, QFN64, LQFP48 and QFN48; QFN56 and QFN32 are ruled out. Breaks if omitted: the
  bus becomes a split-port read/write pair or a shift-and-mask, losing atomicity, and no layout
  change can recover it once the part is chosen. State in the row that this discharges the seed's
  own open instruction to confirm the bus against the final package and pin multiplexing.
- **R4 — HSE crystal footprint laid out and depopulated; HSE pins left unassigned.** Why: the port
  already runs `HSE_OFF` and derives USB's 48 MHz from HSI × PLL, and the part has a Clock Check
  System that can trim HSI against `USBD_SOF` — but the SDK exemplifies the LSE reference, not
  `USBD_SOF`, so untrimmed HSI meeting USB full-speed tolerance is unproven
  `[UNVERIFIED-UNTIL-SILICON]`. Breaks if omitted: retrofitting a crystal to a board with no
  footprint is a respin, whereas depopulating one costs two unplaced parts — and assigning the
  HSE pins to any other signal forecloses the hedge, which is the actual unrecoverable decision.
- **R5 — VPP sense on PA4 / ADC channel 4, with its divider a board decision.** Why: the
  provisional map puts the VPP measurement on PA4 because that matches the Puya ADC example, and
  every board must declare its VPP control mode — the v1.23 seam returns manual-adjustment on
  every board, so the sense path is the only VPP feedback that exists. Breaks if omitted: no
  voltage readback at all, and the divider ratio cannot be added after layout without cutting the
  board. Tag the pin choice `[ASSUMED — PA4 follows the vendor ADC example; no schematic has
  confirmed it]`.
- **R6 — Test points on the data bus and the control strobes.** Why: there is no bus-trace oracle
  on the ARM target — the golden-trace harness runs on `native`, not on ARM — so the ARM emitted
  sequences could diverge from the AVR ones with nothing able to notice; physical probes are the
  only oracle a first board will have. Breaks if omitted: first bring-up has no way to distinguish
  a firmware fault from a wiring fault, on a board whose pin map has never been checked against
  hardware.
- **R7 — USB connector on PA11/PA12, and the D+ pull-up decided before layout.** Why: PA11/PA12
  are the USB PHY pins for both the application and the factory bootloader, with no remap; whether

`__config_page_size` `256`; `__config_slot_a_start` `0x0801E000` (page 480);
`__config_slot_b_start` `0x0801E100` (page 481, a different page erase unit);
`__config_region_end` `0x08020000`. Under the table: the geometry — page `256` B, sector `8192` B,
main flash `0x08000000` to `0x0801FFFF` — with the citation chain
(`platform/py32f071/CONFIG-STORAGE.md` §"Flash geometry" → Puya PY32F07X Reference Manual V0.2
§4.1/§4.2.1/Table 4-1, corroborated against the pinned SDK header constants). Tag the table
`[VERIFIED: read from platform/py32f071/linker/PY32F071xB_FLASH.ld at the firmware HEAD this phase

estimate, which is the whole reason this record exists.

**(b) What the application uses today.** `text + data` = `27,372` B of the 122,880 B `FLASH`
region, and the vector table is exactly `192 B` (48 entries). Immediately follow both figures with
the honesty constraint, stated as its own sentence: these come from a **local** build and may be
compared only against another local build of the same tree with the same toolchain — never against
a CI figure, because the local and CI compilers differ and produced different absolute sizes for
the same source. Tag the figures `[VERIFIED: local ARM build, delta-comparable only]`.

**(c) The bootloader budget.** State the two independent anchors: Puya's own factory bootloader
occupies 12,032 bytes of system memory and serves USART, I2C *and* USB DFU without a HAL
`[CITED: Puya UM1503/UM1504 §1.1 Table 1-1]`; and this tree's own measured objects — the RCC, flash,
CherryUSB device-core and port, COBS/CRC framing, CDC glue, GPIO, NVIC, `SystemInit`, timing and
startup translation units — already total roughly `14.6 KiB` before any bootloader logic exists
`[VERIFIED: per-object arm-none-eabi-size from a local build]`. Add the not-counted list (the
receive/validate/program state machine, a page staging buffer, image CRC, jump-to-application,
descriptor `.rodata`, newlib fragments) and the resulting estimate of roughly 17 to 20 KiB
`[ASSUMED — components measured, the bootloader's own logic estimated]`.

Then the sector-quantised verdict, as a three-row table in the 8 KiB units the part actually
erases. **Every row must itself contain one of the words `migration`, `re-flash` or `ORIGIN`** —
make the third column's header read like a cost column, for example `Verdict, and the migration it
would cost`, and write each cell so the word appears in the cell text. This is not cosmetic: the
gate asserts that no line naming the figure sits more than two lines away from its cost, which is
D-10's rule and the linker comment's own standard. Rows: one sector / 8 KiB — infeasible, the USB,
flash and clock objects alone exceed it; two sectors / 16 KiB — reachable only by dropping the HAL
for direct register access as Puya's own bootloader evidently does, not a safe planning figure;
**three sectors / 24 KiB — the defensible reservation**, roughly 17 to 20 KiB measured-plus-
estimated with headroom, leaving `FLASH` at 96 KiB against today's 27,372 B application.

**(d) The cost, stated in its corrected form — D-12, as the operator corrected it.** This is the
paragraph the whole section exists to carry. D-12 asked for the cost stated and then a list of
candidate mitigations; the operator's decision on RESEARCH C-1 replaces the candidate list with the
corrected cost framing, because the three candidates D-12 names are workarounds for parts that lack
the register this part has. State the cost; do not list the candidates.
State: `BOOTLOADER` keeps `LENGTH = 0` today and giving it a real length is explicitly
rejected for this milestone (D-11) — the reservation above is an **intent**, and this paragraph is
the cost attached to it, never a number that reads as already paid for. The cost is that giving
`BOOTLOADER` a non-zero length moves the application's `ORIGIN`, which is a flash-map **migration**
rather than a resize: every already-flashed unit needs a full re-flash over DFU or SWD instead of
an in-place update — precisely the recovery paths a self-flash bootloader exists to avoid, and it
must be paid once before the self-flash path can ever pay for itself.
Then the correction, restated here because the firmware subset copies this section but not §1.6:
the vector table moving is the **cheap** half, because the part declares `__VTOR_PRESENT` and the
compiled `SystemInit` writes `SCB->VTOR` at every boot — earlier statements in this project's
planning record and in the linker comment attributed the cost to the absence of that register and
were wrong; §1.6 records how the correction was established, and Phase 130's CLOSE-01 sweep owns
the `REQUIREMENTS.md` and `ROADMAP.md` prose. Do **not** enumerate register-remap, RAM-vector-copy
or trampoline schemes: those are the workarounds for parts that genuinely lack the register, and
writing them here would document a problem this part does not have.

**(e) Supersessions and hand-offs.** One short list: this section supersedes the seed's "first few
KB" figure specifically and no other part of the seed; `CONFIG`'s 7680 B of deliberate slack is
reclaimable by FUT-N05 or by additional config slots without moving any address; FUT-N05 owns the
bootloader itself; FUT-N06 owns the raw-binary release asset a self-flash protocol would want.
Close with the shared-section note.
