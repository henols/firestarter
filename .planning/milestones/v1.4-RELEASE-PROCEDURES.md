# v1.4 Release Procedures

> **v1.5 update (2026-05-21):** This procedure remains the canonical release-engineer checklist for both v1.4 and v1.5+ beta cuts. The mechanics are unchanged. The only delta from v1.4 to v1.5: the **per-board verification step now expects three `.hex` artifacts** in the resulting GitHub Pre-release asset list (`firestarter_uno.hex`, `firestarter_uno328pb.hex`, `firestarter_leonardo.hex`) instead of two. The asset list is captured automatically by the unchanged `softprops/action-gh-release@v2` `files: .pio/build/**/firestarter_*.hex` glob in `beta-build.yml:92` and `build.yml:105`. No additional release-engineer action is required to pick up the third artifact. (See `MILESTONES.md` → v1.5 entry for full context.)

This document is the operational checklist for cutting a coordinated v1.4 beta release across
both Firestarter sub-repos (`firestarter_app` and `firestarter`). It is built on top of
`15-LOCKSTEP-PROCEDURE.md` (consumed verbatim where applicable), with corrections to that
procedure's stale workflow filenames and additional v1.4-specific verification and promotion
steps. A release engineer with no prior v1.4 context should be able to cut a beta by following
this document as a checklist.

## Overview

Three release types exist in the v1.4 milestone:

- **Stable** — push or merge to `main` in each sub-repo triggers the existing pipeline
  (`release.yml` + `publish.yml` for the app; `build.yml` for the firmware). Auto-bumps
  the patch version. GitHub Release marked `make_latest: true`. Existing behavior —
  GATE-01 + GATE-02 from v1.4 preserve this verbatim.

- **Beta** — PR → merge to the `beta` branch in each sub-repo (`beta-release.yml` for the app;
  `beta-build.yml` for the firmware). On merge, `update_version.py`'s git-tag-scan fallback
  auto-increments `bN` for the current base version. GitHub Release marked `prerelease: true`,
  `make_latest: false`. **Lockstep escape hatch:** `workflow_dispatch` with an explicit
  `BETA_VERSION` input is available when you need to pin a specific version (e.g. recovering
  from drift between the two repos) — documented in §Lockstep escape hatch below.

- **Promotion (beta → stable)** — currently manual: fast-forward merge from `beta` to `main`
  after the beta is validated, followed by a normal stable release cut. Auto-promotion
  deferred to v1.5+ per REQUIREMENTS.md Future Requirements.

## Prerequisites

Before cutting a coordinated beta, confirm each item:

- `gh` CLI installed and authenticated with write access to both sub-repos:
  ```bash
  gh auth status
  gh api repos/henols/firestarter_app --jq '.permissions.push'   # must be true
  gh api repos/henols/firestarter_fw --jq '.permissions.push'        # must be true
  ```

- Local clone of both sub-repos.

- `beta` branch exists in both repos (one-time setup; see §One-time setup below).

- Phase 15 `update_version.py` extensions are present in both sub-repos (verify by running
  the two `BETA_VERSION_RE.pattern` snippets from `15-LOCKSTEP-PROCEDURE.md` §Prerequisites
  step 2).

- **Base-version alignment** (recommended before first cut):
  ```bash
  grep __version__ firestarter_app/firestarter/__init__.py    # current app base
  grep '#define VERSION' firestarter/include/version.h         # current firmware base
  ```
  If the two bases differ (today: app `2.0.7_dev` vs firmware `3.0.0_dev`), Option 1
  auto-increment will produce DIFFERENT version strings across the two repos (e.g.
  `2.0.7b1` vs `3.0.0b1`) — that breaks VER-03's byte-equality contract. See §Base-version
  mismatch caveat below for the resolution.

## One-time setup

Create the `beta` branch in each sub-repo before the first cut:

```bash
# In firestarter_app/
git checkout main && git pull
git checkout -b beta && git push -u origin beta

# In firestarter/
git checkout main && git pull
git checkout -b beta && git push -u origin beta
```

`beta` now exists at the same commit as `main`. No workflow fires yet (no diff to merge).
Subsequent cuts use PRs targeting `beta` (Option 1) or `workflow_dispatch` (Option 2 escape hatch).

## Base-version mismatch caveat

The two sub-repos currently carry **different base versions**: `firestarter_app/firestarter/__init__.py`
has `__version__ = "2.0.7_dev"`, while `firestarter/include/version.h` has
`#define VERSION "3.0.0_dev"`. Under Option 1 auto-increment, each repo will emit `bN` against
its OWN base, producing `2.0.7b1` (app) + `3.0.0b1` (firmware) — NOT byte-identical, which
violates VER-03's string-equality contract.

**Three ways to handle this for the FIRST beta cut:**

1. **Reconcile bases first (recommended):** in your PR to `beta` in `firestarter_app`, change
   `__version__ = "2.0.7_dev"` to `__version__ = "3.0.0_dev"` (match firmware). Then both
   repos auto-increment to `3.0.0b1`. One-time reset; subsequent cuts work cleanly.
2. **Use Option 2 (lockstep escape hatch) for the first cut only:** `gh workflow run` with an
   explicit `BETA_VERSION` overrides each script's base-version reading and writes whatever
   string you pass. After the first cut anchors both repos to a common base, switch back to
   Option 1 for subsequent betas.
3. **Accept asymmetry (NOT RECOMMENDED):** publish `2.0.7b1` (app) + `3.0.0b1` (firmware) and
   reinterpret VER-03 as "both repos emitted `X.Y.ZbN` form" rather than "byte-equal." The
   verifier script's lockstep check will fail; you'd need to skip it manually. This pushes the
   lockstep problem to v1.5+.

## Version string format

Validation regex (identical in both `update_version.py` scripts, per VER-03):

```
^[0-9]+\.[0-9]+\.[0-9]+(b|rc)[0-9]+$
```

**Accepted:** `3.1.0b1`, `3.1.0b2`, `3.1.0rc1`, `0.0.1b1`, `1.2.3rc2`

**Rejected:**
- `3.1.0beta1` — pre-release label spelled out (use `b`, not `beta`)
- `3.1.0-b1` — separator before pre-release segment
- `3.1.0B1` — uppercase `B`
- `3.1.0a1` — alpha segment (out of scope for v1.4)
- `3.1.0` — no pre-release segment (this would be a stable version)
- `3.1.0.post1` — post-release segment (not supported)

**Monotonic increment rule:** The first beta on a base version line starts at `b1`
(e.g. `3.1.0b1`). Subsequent betas on the same base increment monotonically: `b2`, `b3`, etc.
Promotion from beta to release candidate requires an explicit operator decision — supply
`BETA_VERSION=X.Y.ZrcN` rather than relying on any automatic promotion.

**PyPI visibility:** PyPI stores pre-release versions normally. Consumers must pass
`pip install --pre firestarter==X.Y.ZbN` to opt in. Standard `pip install firestarter`
will NOT pull pre-release versions.

## Cutting a beta (Option 1 — canonical: PR → merge to `beta`)

This is the day-to-day flow. PRs land on `beta` in each sub-repo; on merge, the workflows fire
and auto-increment the beta counter. Use Option 2 (§Lockstep escape hatch) when you need to
pin a specific version explicitly (drift recovery, first cut on misaligned bases, etc.).

Each step is atomic; if any step fails, see **Failure recovery** before re-running.

### Step 1 — Confirm base-version alignment (skip on subsequent cuts)

```bash
grep __version__ firestarter_app/firestarter/__init__.py
grep '#define VERSION' firestarter/include/version.h
```

If the bases differ, resolve per §Base-version mismatch caveat BEFORE opening PRs. After
the first reconciled cut, both repos share a base and Option 1 auto-increment works cleanly.

### Step 2 — Open a PR in each sub-repo targeting `beta`

In each sub-repo, branch from current `beta`, make your changes, push, and open a PR with
`beta` as the base. The PR's diff must include changes to a path NOT covered by
`paths-ignore` (otherwise the merge won't trigger the workflow). Safe paths:
- App: any file under `firestarter/` (source), `tools/`, `.github/workflows/`,
  `pyproject.toml`, `setup.cfg`, etc. AVOID `**.md`, `**.sh`, `docs/**`, `images/**`,
  `.vscode/**`.
- Firmware: any file under `src/`, `include/`, `lib/`, `tools/`, `test/`,
  `platformio.ini`, etc. AVOID `**.md`, `**.sh`, `docs/**`, `documents/**`, `images/**`,
  `.vscode/**`, `.editorconfig/**`.

```bash
# App side (in firestarter_app/):
git checkout beta && git pull
git checkout -b feature/<short-name>
# ... make changes ...
git push -u origin feature/<short-name>
gh pr create --base beta --title "<title>" --body "<body>"

# Firmware side (in firestarter/):
git checkout beta && git pull
git checkout -b feature/<short-name>
# ... make changes ...
git push -u origin feature/<short-name>
gh pr create --base beta --title "<title>" --body "<body>"
```

### Step 3 — Merge both PRs close in time

```bash
gh pr merge <app-pr-number>   -R henols/firestarter_app   --squash --delete-branch
gh pr merge <firmware-pr-num> -R henols/firestarter_fw       --squash --delete-branch
```

On each merge, the push to `beta` triggers `beta-release.yml` / `beta-build.yml`:
- CI gates run (catalog validity, codegen drift, native Unity / pytest)
- `update_version.py` scans git tags for the highest `X.Y.Zb*` matching the current base
  version and emits `b(N+1)` — first-ever cut emits `b1`
- The new version is auto-committed back to `beta` via `stefanzweifel/git-auto-commit-action@v5`
- A GitHub Pre-release is created (`prerelease: true`, `make_latest: false`)
- App side: `publish.yml` fires on the `release: published` event and uploads to PyPI
- Firmware side: the `.hex` artifacts are attached to the release directly

Watch both runs:
```bash
gh run watch -R henols/firestarter_app
gh run watch -R henols/firestarter_fw
```

### Step 4 — Verify the cut

Inspect both releases:
```bash
gh release view -R henols/firestarter_app --json tagName,isPrerelease,isLatest
gh release view -R henols/firestarter_fw     --json tagName,isPrerelease,isLatest
```

Both should show:
- `tagName`: the same `X.Y.ZbN` string (if bases were reconciled per Step 1)
- `isPrerelease`: `true`
- `isLatest`: `false`

If `tagName` differs between the two repos, the base-version mismatch wasn't reconciled
in Step 1. Either reconcile it now and re-cut with Option 2 (§Lockstep escape hatch) to
anchor a common version, or accept the asymmetry (NOT recommended — see §Base-version
mismatch caveat option 3).

### Step 5 — Post-cut consumer verification

Confirm all of the following before declaring the beta cut complete:

| Check | Command / Location | Expected |
|-------|--------------------|----------|
| App PyPI version | `pip show firestarter` or PyPI web | `<emitted-string>` |
| App CLI version | `pip install --pre firestarter==<emitted-string> && firestarter --version` | `<emitted-string>` |
| App GitHub Release tag | GitHub Release `firestarter_app/<emitted-string>` | Tagged, Pre-release=true |
| Firmware GitHub Release tag | GitHub Release `firestarter/<emitted-string>` | Tagged, Pre-release=true |
| Firmware version.h | In release assets or `firestarter` beta-branch HEAD | `#define VERSION "<emitted-string>"` |
| Both tags are string-equal | Compare the two release tag names | Byte-identical (or document asymmetry per Step 4) |

## Lockstep escape hatch (Option 2 — `workflow_dispatch` with explicit `BETA_VERSION`)

Use this path when:
- The first cut needs to anchor a specific version (e.g. `3.1.0b1`) before Option 1's
  auto-increment can take over for subsequent cuts.
- Drift has occurred: app is at `b3` while firmware is at `b2` after a CI gate failure or
  `paths-ignore` skip in one repo. Run Option 2 with `beta_version=X.Y.Zb4` (or whatever
  next value re-anchors) in BOTH repos to restore lockstep.
- You're cutting a release candidate (`rcN`) — auto-increment won't promote `bN` → `rcN`;
  that's an explicit operator decision.

Steps:
```bash
# Land your changes on beta first (via PR → merge) — your beta branch must already have
# the code you want to ship.

# Then run both workflows with the same BETA_VERSION:
gh workflow run beta-release.yml \
  -R henols/firestarter_app \
  --ref beta \
  -f beta_version=<chosen-string>

gh workflow run beta-build.yml \
  -R henols/firestarter_fw \
  --ref beta \
  -f beta_version=<chosen-string>
```

`update_version.py` writes whatever string you pass — no auto-increment, no drift possible.
Both releases carry the same `X.Y.ZbN` tag.

### Optional pre-flight: lockstep dry-run fixture

Before running Option 2's `gh workflow run` commands, you can verify that both scripts
emit the same string for the same input:

```bash
BETA_VERSION=<chosen-string> bash .planning/phases/15-versioning-locked-step-coordination-foundation/lockstep-dryrun-fixture.sh
```

Expected output: `LOCKSTEP OK`. If it prints `LOCKSTEP FAILED`, the two `update_version.py`
scripts have drifted apart — stop and investigate before triggering CI.

## Verifying a beta (consumer-side smoke test)

On a fresh Python environment (clean venv or Docker container), run:

```bash
pip install --pre firestarter==<chosen-string>
firestarter --version                          # must print <chosen-string>
firestarter fw -i --pre                        # installs matching X.Y.ZbN firmware
firestarter fw -i --firmware-version <chosen-string>   # pins exact tag (alternative)
firestarter fw --list                          # enumerate; <chosen-string> appears in pre-release rows
```

Non-regression check — on a SEPARATE fresh stable install:

```bash
pip install firestarter                        # NO --pre flag → previous stable version
firestarter --version                          # X.Y.Z (no b/rc suffix)
firestarter fw -i                              # installs STABLE firmware, NOT <chosen-string>
```

Stable-installed app's bare `firestarter fw -i` must NOT pull the new beta — proves INST-01
non-regression.

## Promoting beta → stable (manual)

The promotion path is currently manual:

1. After the beta is validated (E2E + bench testing if applicable), fast-forward merge
   `beta` → `main` in each sub-repo:
   ```bash
   git checkout main && git merge --ff-only beta && git push origin main
   ```
2. The existing `main`-trigger pipeline (`release.yml` + `publish.yml` for the app;
   `build.yml` for the firmware) auto-bumps the patch version and produces a stable
   GitHub Release marked `make_latest: true`. GATE-01 + GATE-02 from v1.4 guarantee
   this stable-side behavior is byte-identical to pre-v1.4.
3. Delete the beta-tagged GitHub Release(s) if they are no longer needed (optional
   housekeeping; the stable release supersedes them functionally).

Auto-promotion workflow (e.g. a `promote.yml` that fast-forwards `beta` → `main` and bumps
to stable in one CI run) is deferred to v1.5+ per REQUIREMENTS.md "Future Requirements".

## Failure recovery

Under Option 1, lockstep is enforced by procedural discipline (merge both PRs close in time;
make sure both diffs touch non-`paths-ignore` files). Under Option 2, lockstep is enforced
mechanically by the explicit `BETA_VERSION` input. Most failure modes are recovered by
re-running Option 2 once to re-anchor a common version.

| Scenario | Recovery action |
|----------|-----------------|
| One repo's PR merged but workflow failed at CI gate (codegen drift, native Unity, pytest) | Fix the failing gate; re-merge OR re-trigger the workflow via Option 2 with the version the OTHER repo emitted. No drift on PyPI/GitHub yet — only the workflow run itself failed. |
| Both PRs merged; one repo emitted `bN` (e.g. `b3`), the other emitted `bM` (e.g. `b2`) because of base mismatch, paths-ignore skip, or a CI-gate fail in one | Drift. Recover with Option 2: pick `bMAX+1` (e.g. `b4`) and run `gh workflow run` in BOTH repos with `beta_version=<bMAX+1>`. PyPI and GitHub Pre-release each get a new tag at the common version. The drifted intermediate tags (`b2`, `b3`) remain in GitHub Releases history but no longer reflect a usable lockstep state. |
| Both PRs merged but doc-only / `paths-ignore` change in one repo → that workflow didn't trigger at all | Make a follow-up PR in the skipped repo with a non-`paths-ignore` change (e.g. touch a source file) and merge to `beta`. Auto-increment kicks in and produces `bN` on that side; the other repo is already at the previous `bN-1` so this may still drift. Easier path: Option 2 with explicit `BETA_VERSION` in BOTH repos. |
| App workflow succeeded and published to PyPI; firmware workflow failed at build or codegen gate | Fix the firmware issue; use Option 2 to re-trigger the firmware workflow with the **same** `BETA_VERSION` string the app emitted. PyPI side is already published; firmware catches up to the same string. |
| App workflow created a PyPI release; same workflow re-triggered and PyPI rejects the upload with HTTP 400 "File already exists" | PyPI does not accept re-uploads of the same version. Increment to the next `bN` and use Option 2 to re-cut **both** repos with the new string to restore lockstep. **Known gap** per Phase 15 D-03; idempotent re-publish is deferred to a future milestone. |
| Firmware GitHub Release exists; app PyPI publish failed in the same attempted cut | Either: (a) manually delete the firmware GitHub Release tag (`gh release delete <tag> -R henols/firestarter_fw`) and use Option 2 to re-cut both with the same `BETA_VERSION`; OR (b) increment to next `bN` and use Option 2 to re-cut both. Option (b) is simpler. |
| Both workflows failed before any publish | Fix both issues; merge new PRs OR use Option 2 to re-trigger both with the original intended `BETA_VERSION`. No published artifacts to undo. |

**Tip:** When recovering from drift, ALWAYS use Option 2 (`gh workflow run` with explicit
`BETA_VERSION`) to re-anchor. Letting Option 1's auto-increment run on a drifted state risks
compounding the drift.

## Known gaps

- **Auto-promotion beta → stable workflow** — deferred to v1.5+; manual fast-forward merge is
  the only promotion path today.
- **Branch protection rules on the `beta` branch** — not configured; accidental force-pushes
  are possible. Deferred per REQUIREMENTS.md Future Requirements.
- **Signed release artifacts** (sigstore / GPG) — out of scope for v1.4; would cover both
  stable and beta in a dedicated milestone.
- **Idempotent beta re-publish on partial failure** — re-triggering with the same `BETA_VERSION`
  after a PyPI publish succeeded fails with PyPI HTTP 400 "File already exists"; recovery
  requires incrementing the beta counter and re-cutting both repos. Phase 15 D-03 known gap.
- **TestPyPI publishing channel** — rejected for v1.4 (PyPI `--pre` is the cleaner UX);
  could be revisited if beta operators report needing isolated install testing.
- **Cross-repo `repository_dispatch` automation** — rejected for v1.4 (requires cross-repo PAT
  with `repo` scope); manually-paired beta-branch push is the chosen mechanism.
