## 2. What the milestone set out to do, and what it did

The Arduino stops deciding whether a chip is blank or matches an image. The host reads the chip and
compares in Python — one comparison implementation, a named diagnosis instead of a single address,
and the flash the removed command surfaces were costing.

**One comparison engine, on the host (Phase 202).** `firestarter_app/firestarter/compare.py` is the
only streaming comparison in the product. `verify` and `blank` both send `COMMAND_READ` and compare
per chunk as the data arrives: first mismatch by default, every mismatching range coalesced under
`--full`, a `classify_fingerprint` bucket with total and bad counts, and exit codes `0` match / `1`
mismatch / `2` transport or hardware failure. The device image is never held whole — peak host memory
at a full 512 KiB measured 776 B to 17,597 B across four fault patterns. The read-abort mechanic the
activation left open was answered in writing (`202-READ-ABORT-ANSWER.md`): the firmware's
`command_done()` teardown runs on the error path the abort produces, so the port is left clean and
the first-mismatch stop saves time, at a measured cost of about one second per abort.

**The write guard moved up a layer before the firmware lost it (Phase 203).**
`write_blank_guard.py` guards exactly the five protocol families the firmware's write-init used to
check — `0x06`, `0x07`, `0x08`, `0x0B`, `0x10` — and names its exemptions (`0x05`, `0x0D`, SRAM/FRAM)
with the reasoning at the exemption site. A pinning test fails if the set narrows **or** widens;
perturbation proved it reachable. `write --verify` is opt-in (D-3) and reports through the same
engine; the operator ruled the exit contract by cause (`confirm-d13`): `0` landed and matched, `1`
something decided to stop, `2` something failed.

**The command surfaces left the firmware (Phase 204).** `CMD_VERIFY` (6) and `CMD_BLANK_CHECK` (4)
are gone from both command ladders, with reserved-ordinal notes at both gaps. `memory_verify_execute`
survives, and a brace-matching source contract fails if its `VERIFY_PER_PULSE_PLUS_FINAL` call
disappears — its RED was reproduced three times. FWCMD-05 was amended by measurement (D-03): only
`memory_verify_execute` and `eeprom28c_verify_page_readback` raise `MSG_ERR_VERIFY` (0xAF), and
`flash_util_verify_operation` is a DQ7 poll that can never raise it. On the bench, the published
`3.0.0b49` host is refused by name against post-204 firmware in about 3.5 s, and the post-204 host
works against pre-204 firmware; three whole-device reads share one SHA-256.

**The pre-flights left the firmware (Phase 205).** The write-init and erase-end blank checks,
`mem_util_blank_check{,_region}`, `blank_check_saved_address`, `BLANK_CHECK_CHUNK_SIZE` and
`FLAG_SKIP_BLANK_CHECK` are gone, the bit reserved on both sides. `erase -b` was rebuilt on the host
first. Code review found a Critical (CR-01): protocol `0x06`'s erase exemption silently skipped the
guard at a non-zero address, where the firmware erases nothing — an irreversible silent overwrite on
190 of 190 shipped `0x06` rows. It was **fixed inside the phase rather than carried as an accepted
risk window** (`205-CR-01-DECISION.md`), because unlike D-04's skew it had no safe failure mode.

**`dev test` kept its fidelity, on one session (Phase 206).** `OP_VERIFY` and `OP_BLANK_CHECK` route
through the host engine. A `cmp=host` empty-default tag on `dedup_fingerprint` keeps host-path
reports apart from firmware-path ones; all 19 frozen literals are unmoved, and the 43 ALLOW chips
restart their promotion ladder, which the operator confirmed at UAT. The session lease was
**measured, not argued**: N=3 per arm on a Leonardo with a W27C512, leased median 228.283 s against
cold 268.992 s — **15.1 %** against a pre-registered 15.0 % threshold, with every run `COMPLETE` and

committed.

**The version and the record (Phase 207).** `3.1.0b1` in both repositories in one commit pair
(REL-01). The breaking change and the `write --verify` / `--full` surfaces are documented on the
wiki, the only documentation home (REL-04).

## 3. Why `override_closeout` with 34/34

All 34 requirements are Complete, and the three sources — REQUIREMENTS.md checkboxes, the
traceability table and the phase VERIFICATION.md files — agree. The override is mechanical and has
two causes, neither of them a requirement:

- **`init.manager` reads all seven phases as `verification_status: stale` and
  `phase_complete: false`.** All seven `VERIFICATION.md` files say `status: passed` (202 8/8,
  203 5/5, 204 6/6 + 8/8, 205 9/9, 206 10/10, 207 4/4, 207.1 22/22). The staleness is the known
  `covered_digest` mechanism — each digest was computed before later commits touched a covered file
  — and 207.1 accepted it as **D-19**, with the green gate run as the mitigation. The workflow's rule
  is that `verified_closeout` needs every phase to read `passed` there, and they do not.
- **Three Phase 207.1 code-review warnings are open.** WR-02 is a real edge-case defect: a lease
  drain that raises `SerialError` runs outside the handler that drops the link, so on a mid-run USB
  unplug the rest of a `dev test` plan is SKIPPED instead of reconnecting. WR-01 is a comment that
  names one of two routes to `runs=1`. WR-03 is `update_version.py --set-version` silently making a
  stable patch bump on a non-beta ref — on the publish path, outside every CI gate, and needing an
  operator decision. **All three were filed as todos by this close** (§ 5); none was filed before.

**Gates, as the third re-audit ran them on the live tree:** app ruff clean on Python 3.11, app
pytest **2373 passed** at 86.40 % coverage, firmware `native` and `native_nodevtools` **244/244**
each, firmware `tests/` **316 passed**, messages codegen byte-identical to both synced copies.
