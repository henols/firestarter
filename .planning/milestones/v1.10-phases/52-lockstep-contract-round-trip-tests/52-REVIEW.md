# Phase 52: Code Review Report

**Reviewed:** 2026-06-02
**Depth:** standard
**Files Reviewed:** 14
**Status:** issues_found

## Summary

Phase 52 establishes the shared golden-vector catalog (`frame-vectors.toml`),
the deterministic generator (`codegen_vectors.py`), the generated artifacts
(`frame_vectors.h`, `frame_vectors.py`), and the both-legs round-trip test
suites (firmware Unity + host pytest).

**The core contract holds and was verified empirically:**

- The two `codegen_vectors.py` copies are byte-identical (`diff` clean). The two
  `frame-vectors.toml` copies are byte-identical (`diff` clean). D-09 satisfied.
- Both generators reproduce their committed artifacts byte-for-byte
  (regen → `diff` clean for both `frame_vectors.h` and `frame_vectors.py`), so
  both repos' codegen drift gates pass.
- All 12 golden vectors validate against the production host
  `cobs_encode`/`cobs_decode`/`_crc8_ccitt` (encode leg + decode leg, CRC match,
  0 failures). CRC8 KAT values (`0x07` for `[0x01]`, `0x00` for `[]`) confirmed.
- The firmware native suite was built and run: all 3 cases
  (`test_crc8_known_answer`, `test_vector_encode_leg`, `test_vector_decode_leg`)
  PASS. The 511-byte decode cap (CR-01) correctly skips the four >511-byte
  data-block vectors on the decode leg.

**However, two CI gates are broken by the new host test file and the generated
host artifact**, both of which run *before* pytest in `ci.yml` and would fail
the build on the project's declared Python target (3.9 / 3.11 CI). These are
the BLOCKERs below. The local pass observed in development is an artifact of the
local interpreter being Python 3.12, which masks both issues.

## Critical Issues

### CR-01: Backslash-in-f-string is invalid syntax on the project's Python target — breaks `ruff check` AND `pytest` in CI

**File:** `firestarter_app/tests/test_frame_vectors.py:77`
**Issue:**
The encode-leg failure message uses a backslash escape inside an f-string
expression:

```python
f"got {(encoded + b'\\x00').hex()!r}, expected {vec.frame.hex()!r}"
```

Backslashes inside f-string replacement fields were only permitted starting in
**Python 3.12**. This project declares `requires-python = ">=3.9"` and ruff
`target-version = "py39"` (pyproject.toml), and CI provisions **Python 3.11**
(`.github/workflows/ci.yml` → `setup-python` `python-version: '3.11'`).

Confirmed two ways:
- `ruff check firestarter/ tests/` (the first gate step in ci.yml) emits:
  `invalid-syntax: Cannot use an escape sequence (backslash) in f-strings on
  Python 3.9 (syntax was added in Python 3.12)` at `test_frame_vectors.py:77`
  (two occurrences) → exit 1.
- Under Python 3.11 the module would raise `SyntaxError` at *import*, so the
  later `pytest tests/` step would also error (collection failure), not just
  ruff.

The test passes locally only because the local interpreter is Python 3.12
(`compile()` succeeds there). This is a hard CI failure on the supported target.

**Fix:** Hoist the escape out of the f-string. For example:

```python
got = (encoded + b"\x00").hex()
assert encoded + b"\x00" == vec.frame, (
    f"Vector {vec.name} (id=0x{vec.id:02X}): encode leg failed — "
    f"got {got!r}, expected {vec.frame.hex()!r}"
)
```

(Any variant that keeps the `\x00` literal out of the f-string brace works.)

### CR-02: Generated `frame_vectors.py` fails `ruff format --check` — breaks the CI format gate

**File:** `firestarter_app/firestarter/frame_vectors.py` (generated by
`firestarter_app/tools/catalog/codegen_vectors.py:269` `emit_python_vectors`)
**Issue:**
`ci.yml` runs `ruff format --check firestarter/ tests/`. The generated
`firestarter/frame_vectors.py` is **not** ruff-format-clean:
`ruff format --check firestarter/frame_vectors.py` → `Would reformat` → exit 1.

`ruff format --diff` shows the emitter's output diverges from ruff's canonical
formatting in at least two ways:
1. Missing the blank line ruff inserts between the module docstring and
   `from typing import NamedTuple`.
2. The hand-rolled multi-line `FrameVector(id=..., name='...', payload=...,
   frame=...)` layout (and single-quoted `name` from `{...!r}`) is reformatted
   by ruff.

This is a concrete regression versus the established pattern: the sibling
generated file `firestarter/messages.py` (emitted by the existing `codegen.py`)
**is** ruff-format-clean (`1 file already formatted`). There is no ruff
`exclude`/`per-file-ignores` entry covering `frame_vectors.py`. So the new
emitter produces output the repo's own gate rejects.

Note the drift gate (`git diff --exit-code firestarter/frame_vectors.py`) still
*passes* because the committed file matches the generator output — the failure
surfaces one step later at `ruff format --check`. So this cannot be papered over
by re-running codegen; the emitter itself must change (or an explicit ruff
exclude must be added).

**Fix:** Make `emit_python_vectors` emit ruff-format-stable output. Concretely:
- Add a blank line after the closing `"""` of the banner (before
  `from typing import NamedTuple`).
- Emit each `FrameVector(...)` in the layout ruff produces (or run the emitted
  text through a shape ruff leaves untouched — e.g. one field per line trailing
  comma style), OR
- Alternatively, add `firestarter/frame_vectors.py` to ruff's `extend-exclude`
  in `pyproject.toml` and document it as a generated artifact (mirrors how
  generated files are commonly excluded). Whichever path is chosen, verify with
  `ruff format --check firestarter/frame_vectors.py` returning exit 0 after a
  fresh codegen run, so the drift gate and the format gate agree.

## Warnings

### WR-01: `FRAME_VECTOR_COUNT` declared `PROGMEM` but read directly — latent AVR bug if the header is ever compiled into firmware

**File:** `firestarter/include/frame_vectors.h:51` (emitter:
`codegen_vectors.py:217-219`), consumed at
`firestarter/test/native/avr/test_frame_vectors/test_frame_vectors.cpp:198,227`
**Issue:**
`static const uint16_t FRAME_VECTOR_COUNT PROGMEM = 12;` is read directly as
`for (uint16_t i = 0; i < FRAME_VECTOR_COUNT; i++)` with no `pgm_read_word(...)`.
The test correctly uses `memcpy_P` for the `FRAME_VECTORS[]` array, so the
scalar read is inconsistent with the array access. On a real AVR (Harvard
architecture) a direct read of a `PROGMEM` scalar reads from the RAM address
space at the same numeric offset and returns garbage. This is harmless **today**
because `frame_vectors.h` is included only by the native host test (no
production firmware `#include`s it), and on the native host `PROGMEM` is a no-op
so the direct read works (suite verified PASSING). It is a latent trap: if this
catalog is ever pulled into AVR firmware, the count read is wrong.
**Fix:** Either drop the `PROGMEM` qualifier on the scalar count (it is a
single `uint16_t`; keeping it in RAM is cheap and removes the trap), or read it
via `pgm_read_word(&FRAME_VECTOR_COUNT)` consistently with the array access.
Prefer dropping `PROGMEM` on the scalar in the emitter.

### WR-02: Decode-cap boundary is a hardcoded `511` on the host vs `DATA_BUFFER_SIZE - 1` on the firmware — silent divergence if the buffer size changes

**File:** `firestarter_app/tests/test_frame_vectors.py:101,123` (host) vs
`firestarter/test/native/avr/test_frame_vectors/test_frame_vectors.cpp:233`
(firmware)
**Issue:**
The firmware decode-leg test derives the skip threshold from the firmware
constant: `if (vec.payload_len > DATA_BUFFER_SIZE - 1) continue;`. The host test
hardcodes the magic number `511` in two places (`if len(vec.payload) > 511`).
`CMD_FRAME_MAX`/`DATA_BUFFER_SIZE` is the binding contract value (its 512 floor
is itself asserted by `test_cmd_frame_max_parity` in
`test_revision_constants_parity.py`). If the firmware buffer floor ever changes,
the host magic `511` silently drifts out of sync and the two suites would
exercise different vector subsets, which is exactly the lockstep property this
phase exists to protect.
**Fix:** Derive the host cap from the host-side `CMD_FRAME_MAX` constant
(`from firestarter.constants import CMD_FRAME_MAX`; `cap = CMD_FRAME_MAX - 1`)
instead of the literal `511`, so both legs reference the same source-of-truth
value.

### WR-03: `# type: ignore[attr-defined]` on a valid import may be flagged unused by the mypy gate

**File:** `firestarter_app/tests/test_frame_vectors.py:28`
**Issue:**
`from firestarter.frame_parser import (...) # type: ignore[attr-defined]` — but
`_crc8_ccitt`, `cobs_decode`, and `cobs_encode` all genuinely exist in
`frame_parser.py` (verified). `ci.yml` runs the mypy watermark gate over
`firestarter/ tests/`. If `warn_unused_ignores` is enabled in the mypy config,
this becomes an `unused-ignore` error; even under the watermark gate it
needlessly raises the tolerated error count for a non-existent attribute
problem.
**Fix:** Remove the `# type: ignore[attr-defined]` comment — the imported names
are public-enough symbols that resolve cleanly. If a private-name access warning
is the real concern, address it directly rather than blanket-ignoring.

## Info

### IN-01: `codegen_vectors.py` validates the catalog but never verifies `frame_hex` is the COBS+CRC encoding of `payload_hex`

**File:** `firestarter_app/tools/catalog/codegen_vectors.py:77-116`
**Issue:**
`validate_catalog` checks structural validity (keys, u8 id range, name regex,
hex parseability, uniqueness) but does not assert the frozen-contract invariant
that `frame_hex == COBS(payload_hex + CRC8(payload_hex)) + 0x00`. This is
intentional by design (D-01: byte values are frozen literals, NEVER computed at
codegen time; the relationship is asserted by the test suites instead). Recorded
only so the `--check` gate's scope is explicit: a typo in a hardcoded
`frame_hex` is caught by the round-trip tests, not by `--check`. No fix
required; consider a one-line comment in `validate_catalog` noting the
deliberate omission.

### IN-02: `description` field is required by the validator but never emitted

**File:** `firestarter_app/tools/catalog/codegen_vectors.py:94` (required) — not
referenced in either emitter
**Issue:**
`description` is enforced as a required key but is dropped from both the C++ and
Python outputs (it serves only as in-TOML documentation). This is reasonable,
but means a vector's `description` can silently disagree with its bytes (e.g. a
description claiming `CRC8=0x19` while the literal differs) without any gate
catching it — the description is unverified prose. Low risk. Optional: have the
emitter pass the description through as a trailing comment so the human-readable
claim and the bytes live together.
