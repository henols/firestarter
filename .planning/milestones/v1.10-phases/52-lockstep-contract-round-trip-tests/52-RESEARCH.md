## Summary

Phase 52 is a test-only phase. No production transport code changes. The COBS frame contract was frozen in Phases 49–51; this phase writes the tests that make it impossible to silently break.

The mechanism is a **shared frozen golden-vector corpus** — a set of `(payload, exact_framed_bytes)` pairs that constitutes the single source of truth for what the framing contract means byte-for-byte. By vendoring byte-identical copies of the catalog into both sub-repos and asserting the same frozen bytes in both the Unity firmware suite and the pytest host suite, the phase proves all four directions of byte-compatibility transitively without requiring a cross-language test harness.

The golden corpus is generated by a new `frame-vectors.toml` catalog + a new `codegen.py` (or an extended version of the existing one) that emits a C++ PROGMEM header for the Unity suite and a Python module for pytest — exactly mirroring the v1.2 `messages.toml` → `messages.h` / `messages.py` codegen already proven in both repos. Each repo's CI gains two new steps: a catalog validity check and a `regen && git diff --exit-code` drift gate. CI is already structured to run `pio test -e native` (firmware) and `pytest tests/` (host).

The concrete work is: (1) author the `frame-vectors.toml` catalog with the D-05 corpus, (2) author the codegen for its output format, (3) generate the artifacts in both repos, (4) write vector assertions in the appropriate test files in each repo, (5) add a KAT in each suite, (6) extend the parity test with `CMD_FRAME_MAX`.

**Primary recommendation:** Mirror the v1.2 codegen mechanism exactly. The tooling, CI integration, and determinism contract are already proven and are the correct model — do not deviate from it.

### Pattern 1: v1.2 Codegen Determinism Contract (LCAT-05)

The existing `codegen.py` documents its determinism contract explicitly in its module docstring. The `frame-vectors` codegen must honor the same contract verbatim: [VERIFIED: source read]

- Sort entries by id ascending before emission (so output is stable regardless of TOML edit order)
- No timestamps, hostnames, or hashes in the banner
- LF line endings via `Path.write_text(..., newline='\n')` — critical for `git diff --exit-code` on any platform
- Upper-case 2-digit hex literals (`"0x%02X"` format)

The `--check` flag validates the catalog and exits 0/1 without writing files (LCAT-02 + LCI-04). The vector catalog codegen must expose the same `--check` flag for the CI validity step.

**Example CI integration (mirroring existing firmware `build.yml`):**

```yaml
- name: Vector catalog validity check
  run: python3 tools/catalog/codegen.py --catalog tools/catalog/frame-vectors.toml --check

- name: Codegen drift gate (frame_vectors.h)
  run: |
    python3 tools/catalog/codegen.py \
      --catalog tools/catalog/frame-vectors.toml \
      --target include/frame_vectors.h \
      --language cpp-vectors
    git diff --exit-code include/frame_vectors.h
```

Analogous for the host `ci.yml` with `--language python-vectors` → `firestarter/frame_vectors.py`.

### Pattern 3: Both-Legs Assertion Shape (D-02)

Each vector entry in the catalog drives two assertions in each repo:

**Firmware (C++ Unity):**
```cpp
// Source: test_cobs_cmd_frame.cpp — established pattern
// Leg 1: encode(payload) == frozen frame bytes
uint8_t encoded_buf[...];
size_t enc_len = test_cobs_encode_with_crc(
    vec.payload, vec.payload_len, encoded_buf);
TEST_ASSERT_EQUAL_size_t(vec.frame_len, enc_len + 1);   // +1 for 0x00 delimiter
TEST_ASSERT_EQUAL_MEMORY(vec.frame_bytes, encoded_buf, enc_len);

// Leg 2: decode(frozen frame) == payload
load_rx_queue(vec.frame_bytes, vec.frame_len);  // feeds the mock
int res = rurp_communication_read_data(data_buffer);
TEST_ASSERT_EQUAL_INT((int)vec.payload_len, res);
TEST_ASSERT_EQUAL_MEMORY(vec.payload, data_buffer, vec.payload_len);
```

**Host (Python pytest):**
```python
# Source: test_cobs.py — established pattern
# Leg 1: encode(payload) == frozen frame bytes
crc = _crc8_ccitt(vec.payload)
encoded = cobs_encode(vec.payload + bytes([crc]))
assert encoded + b'\x00' == vec.frame_bytes

# Leg 2: decode(frozen frame) == payload
body = vec.frame_bytes[:-1]   # strip 0x00 delimiter (cmd channel: no '#' prefix)
decoded = cobs_decode(body)
assert decoded[:-1] == vec.payload   # strip CRC byte
assert decoded[-1] == _crc8_ccitt(vec.payload)  # CRC matches
```

Note on `'#'` prefix: the data-block path frames use `b"#" + COBS(payload+CRC) + b"\x00"` (the `build_cobs_frame` helper in `test_cobs.py` includes the `'#'`). The command channel frames use `COBS(payload+CRC) + b"\x00"` only (no `'#'`). Golden vectors for data-block payloads must reflect which framing path they exercise. Both `rurp_communication_read_data()` (firmware) and `cobs_decode()` (host) operate on the COBS body AFTER the `'#'` marker has been consumed — so for test purposes the frame bytes stored in the vector catalog should be the COBS body + 0x00 only, consistent with what the Unity mock receives.

### Pattern 4: frame-vectors.toml Catalog Format (Claude's Discretion)

The v1.2 `messages.toml` schema is the model. A minimal but sufficient vector catalog entry shape (Claude's discretion on exact keys):

```toml
[catalog]
version = 1
project = "firestarter"

[[vectors]]
id          = 0x01
name        = "VEC_EMPTY_PAYLOAD"
description = "Empty payload — COBS(CRC8) + 0x00"
payload_hex = ""
frame_hex   = "0101 00"   # COBS body = [0x01 0x01] + delimiter 0x00
```

Key design rules for the catalog format:
- `payload_hex`: hex string of the raw payload bytes (empty string for zero-length)
- `frame_hex`: hex string of the complete frame bytes (COBS body + 0x00 delimiter)
- `id`: u8, unique within the catalog, sorted ascending before emission
- `name`: `VEC_[A-Z][A-Z0-9_]*` pattern (analogous to `MSG_*` rule)

The codegen emits these as frozen byte arrays. The TOML schema does not need severity or params fields — vectors have only payload and frame bytes.

### Anti-Patterns to Avoid

- **Soft-coding vector bytes as expressions:** Vector bytes MUST be hardcoded literals in the catalog. Computing them at codegen time defeats the "frozen" requirement — the whole point is that if the algorithm changes, the frozen bytes stay the same and the test fails.
- **Omitting the 253/254/255-run boundary vectors:** These are the highest-value corpus entries (the CR-01 byte-drop hid at the 254-run boundary). A corpus without them gives false confidence.
- **Adding the `'#'` marker to command-channel test frames:** The `'#'` marker is consumed upstream of `rurp_communication_read_data()`; the Unity mock receives only the COBS body. Inconsistency here would cause false-negative decode tests.
- **Separate `frame-vectors` codegen script:** Prefer extending the existing `codegen.py` with new `--language` values (`cpp-vectors`, `python-vectors`) over creating a separate script. This keeps the CI invocation pattern, the `--check` behavior, and the determinism contract identical to the proven model.

**KAT values (D-06, known-answer test):**
- `ref_crc8([0x01]) == 0x07` — pins poly 0x07, seed 0x00 (CRC8 of 0x01 is the polynomial itself)

**Important note on 512/1024-byte vectors and the command-channel decoder:**
`rurp_communication_read_data()` has a cap of `DATA_BUFFER_SIZE - 1 = 511 bytes` for the command channel (CR-01 from Phase 51). A 512-byte payload returns -2 (overflow). The 512/1024-byte vectors are intended for the **data-block path** (`rurp_communication_write()` encoder side and the host's `cobs_encode()` / `cobs_decode()`). The Unity leg-2 decode assertions for 512-byte and 1024-byte payloads must target `rurp_communication_write()` (the dormant encoder) rather than `rurp_communication_read_data()` for these sizes, OR the vectors must be framed as encoder-only (leg-1 only for the cmd-channel decoder side). The planner must clarify this split — see Open Questions.

## Common Pitfalls

### Pitfall 1: 254-Run Boundary (CR-01 repro class)
**What goes wrong:** A payload of exactly 254 consecutive non-zero bytes followed immediately by a 0x00 byte has a COBS encoding where the 254-run code (0xFF) does NOT imply an implicit zero. An encoder bug that treats the 0xFF run as "one implicit zero follows" silently drops the 0x00 byte from the decoded payload. This was the exact CR-01 encoder defect found in Phase 50.
**Why it happens:** Most COBS implementations special-case 0xFF runs correctly for decoding but not encoding.
**How to avoid:** VEC_RUN_254 and VEC_RUN_255 in the corpus catch this class. Both legs must pass.
**Warning signs:** Decoded payload differs from encoded payload at position 254.

### Pitfall 2: '#' Marker in Command-Channel Test Frame Bytes
**What goes wrong:** `test_cobs.py`'s `build_cobs_frame()` includes a `b"#"` prefix (for the data-path `MSG_DATA_CHUNK` dispatch). The firmware's `rurp_communication_read_data()` receives the COBS body AFTER the `'#'` has been consumed. If vector frame bytes include the `'#'`, the Unity mock will pass the `'#'` as the first COBS run-code, producing a corrupt decode.
**Why it happens:** The two frame paths have different leading bytes; the `test_cobs.py` helper was written for the data path.
**How to avoid:** The vector catalog frame bytes store COBS body + 0x00 only. For command-channel vectors, no `'#'` prefix. For data-block path vectors, the `'#'` is an application-layer concern outside the COBS layer being tested.
**Warning signs:** Leg-2 decode returns unexpected length or wrong bytes for the first vector.

### Pitfall 3: platformio.ini test_filter Allowlist Not Updated
**What goes wrong:** A new native test suite directory is created but not added to `test_filter` in `[env:native]`. PlatformIO's allowlist silently skips the new suite — `pio test -e native` exits 0 without running the vectors.
**Why it happens:** `[env:native]` uses a positive `test_filter` allowlist (not `test_ignore`) because of a PIO version quirk documented in the `platformio.ini` comment.
**How to avoid:** The planner must add the new suite to BOTH `test_filter` AND `build_flags -I` AND ensure the new suite has a `host_stubs.cpp` (even minimal).
**Warning signs:** `pio test -e native` output shows no test cases from the new suite.

### Pitfall 4: Git diff --exit-code Fails on Windows Line Endings
**What goes wrong:** If `codegen.py` is run on a system that produces CRLF output (Windows) instead of LF, `git diff --exit-code` fails because the working tree has CRLF but the committed file has LF.
**Why it happens:** Python's default text mode on Windows uses CRLF.
**How to avoid:** The existing `codegen.py` already uses `Path.write_text(..., newline='\n')` which forces LF on all platforms. The new vector codegen must do the same (it is part of the LCAT-05 determinism contract).
**Warning signs:** CI fails on `git diff --exit-code` but local file looks identical.

### Pitfall 5: cmd-channel (512-byte cap) vs data-block path (1024-byte allowed)
**What goes wrong:** Trying to decode a 512-byte or 1024-byte payload through `rurp_communication_read_data()` returns -2 (overflow cap = DATA_BUFFER_SIZE - 1 = 511). This is correct behavior, not a bug, but the test assertion `TEST_ASSERT_GREATER_OR_EQUAL_INT(0, res)` fails unexpectedly.
**Why it happens:** The command-channel decoder enforces the 511-byte cap (CR-01). The 512/1024-byte data-block transfers use the `MSG_DATA_CHUNK` magic-preamble path, which is UNCHANGED in v1.10 and NOT tested here.
**How to avoid:** Limit leg-2 decode assertions through `rurp_communication_read_data()` to payloads ≤ 511 bytes. For 512-byte and 1024-byte data blocks, only assert the encoder leg (`rurp_communication_write()` → `cobs_encode()`) in the vector suite.
**Warning signs:** Unity test for 512-byte vector fails with res = -2 on the decode leg.

### Pitfall 6: codegen.py --check Exit Code on Empty Catalog
**What goes wrong:** If `validate_catalog()` is not adapted for the frame-vectors schema, a valid vectors catalog may fail the `--check` gate because it doesn't have `[[messages]]` entries.
**Why it happens:** The current validator requires a non-empty `[[messages]]` array. A separate `[[vectors]]` table needs its own validation path.
**How to avoid:** Either add a `[[vectors]]`-aware validation branch to `codegen.py`, or create a separate `codegen_vectors.py` script with its own `--check` logic. The CI steps reference the correct script.
**Warning signs:** CI `--check` step fails even when the catalog is well-formed.

## Code Examples

### Example 1: ref_crc8 — independent table-free reference (C++)

Already present verbatim in both `test_cobs_cmd_frame.cpp` and `test_cobs_data_frame.cpp`. The vector suite can copy (or `#include`) this from the existing suites. [VERIFIED: source read]

```cpp
// Source: firestarter/test/native/avr/test_cobs_cmd_frame/test_cobs_cmd_frame.cpp lines 71-82
static uint8_t ref_crc8(const uint8_t* data, size_t n) {
    uint8_t crc = 0;
    for (size_t i = 0; i < n; i++) {
        crc ^= data[i];
        for (int k = 0; k < 8; k++) {
            crc = (crc & 0x80)
                      ? (uint8_t)((crc << 1) ^ 0x07)
                      : (uint8_t)(crc << 1);
        }
    }
    return crc;
}
```

```cpp
    size_t out = 0;
    size_t code_pos = out++;
    uint8_t code = 1;
    for (size_t i = 0; i < len; i++) {
        if (src[i] == 0x00) {
            dst[code_pos] = code;
            code_pos = out++;
            code = 1;
        } else {
            dst[out++] = src[i];
            code++;
            if (code == 0xFF) {
                dst[code_pos] = code;
                code_pos = out++;
                code = 1;
            }
        }
    }
    dst[code_pos] = code;
    return out;
}
```

## Open Questions (RESOLVED)

> All three resolved by the Phase 52 plans (committed `48ba414`): Q1 → new `test_frame_vectors/` directory; Q2 → encoder-only for >511-byte vectors; Q3 → separate `codegen_vectors.py`.

1. **RESOLVED — Extend existing cobs suites vs new `test_frame_vectors` directory**
   - What we know: The existing `test_cobs_cmd_frame.cpp` and `test_cobs_data_frame.cpp` already have the `build_cobs_frame_bytes` + `test_cobs_encode` + `ref_crc8` helpers and the `serial_read_mock.h` wiring. A new `test_frame_vectors/` directory would duplicate this setup.
   - What's unclear: Is a new directory cleaner (separation of concerns: existing tests cover behavior, new tests cover the frozen contract) or unnecessarily heavyweight?
   - Recommendation: Create a new `test_frame_vectors/` directory so the vector corpus is clearly identified as a Phase-52 addition. This also avoids perturbing the existing test counts in the two suites (which are guarded at Phase 50/51 GREEN baselines). Share `_shared/host_stubs_common.inc` and copy `serial_read_mock.h` locally (the established pattern per the comment in `test_cobs_cmd_frame`'s copy of `serial_read_mock.h`).

2. **RESOLVED — Encoder-only vs both-legs for 512/1024-byte data-block vectors**
   - What we know: `rurp_communication_read_data()` caps at 511 bytes (CR-01). The 512/1024-byte data-block transfers use the unchanged `MSG_DATA_CHUNK` magic-preamble path. The dormant `rurp_communication_write()` encoder is the firmware side of the data-block COBS path.
   - What's unclear: Should 512/1024-byte vectors assert only the encode leg (both repos), or also the decode leg of `rurp_communication_write()` via a read-back mechanism?
   - Recommendation: Assert encode-only for 512/1024-byte vectors. `rurp_communication_write()` writes to `SERIAL_PORT` directly — capturing its output in a Unity test requires mocking `SERIAL_PORT.write()`, which is heavier than the mock already in place for `rurp_communication_read_data()`. The host `cobs_encode()` / `cobs_decode()` round-trip for 512/1024 bytes is already covered by the existing `TestCobsFullBuffer` class in `test_cobs.py`. The golden-vector decode leg for large payloads can be omitted or deferred to Phase 53 bench verification.

3. **RESOLVED — Single codegen.py or separate script**
   - What we know: The existing `codegen.py` processes `[[messages]]` and `[[debug.messages]]` TOML tables with a rich schema (10 validation rules, param types, severity codes). The `[[vectors]]` table is structurally simpler (just `payload_hex` + `frame_hex`).
   - What's unclear: Whether extending `codegen.py` with a new `--language cpp-vectors` emitter and a new validator branch is cleaner than a new `codegen_vectors.py`.
   - Recommendation: Create a separate `codegen_vectors.py` with its own simpler schema, to avoid entangling the Phase-6 log-catalog machinery with the Phase-52 vector machinery. Use the same determinism contract (sorted, no timestamps, LF, upper-case hex). Mirror the `--check` flag interface exactly so CI step syntax is identical.
