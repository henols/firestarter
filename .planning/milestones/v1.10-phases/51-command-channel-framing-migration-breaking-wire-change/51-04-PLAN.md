## CR-01 — chosen fix: lower the decoder's effective overflow cap to DATA_BUFFER_SIZE-1

The verifier offered two fixes: (A) guard the NUL write at the call site
(`if (n < DATA_BUFFER_SIZE)`), or (B-preferred) lower the decoder's effective overflow cap to
`DATA_BUFFER_SIZE - 1` so the NUL-terminator slot is always free and `n <= DATA_BUFFER_SIZE-1`
always holds.

**Chosen: the decoder-cap fix, plus a belt-and-suspenders call-site guard.**

Rationale: the buffer is a fixed 512-byte array consumed by exactly one caller (the CMD_IDLE
branch) which ALWAYS NUL-terminates. Reserving the terminator slot at the single source of truth
(the decoder's PUSH overflow guard) makes the invariant `decoder return n <= DATA_BUFFER_SIZE-1`
hold unconditionally, so the NUL write at `data_buffer[n]` is in-bounds by construction — it
cannot be reintroduced by a future call site that forgets the guard. The PUSH overflow guard
today is `if (out >= DATA_BUFFER_SIZE)` (rurp_serial_utils.cpp ~line 113); changing it to
`if (out >= DATA_BUFFER_SIZE - 1)` means a payload of exactly DATA_BUFFER_SIZE now takes the
overflow/drain path (returns -2 + drains), and the largest *accepted* payload is
DATA_BUFFER_SIZE-1 (511 bytes). This is acceptable: the largest legitimate JSON command is
~422 B (CONTEXT.md / firestarter.h:23), well under 511. The belt-and-suspenders call-site guard
(`if (n < DATA_BUFFER_SIZE)` before the NUL write) costs nothing and documents the invariant at
the write site.

Note for the executor: `CMD_FRAME_MAX` in firestarter.h is `#define CMD_FRAME_MAX DATA_BUFFER_SIZE`
and is the *declared* max-frame constant. Do NOT change `CMD_FRAME_MAX`'s value — the host-side
parity constant (`constants.py CMD_FRAME_MAX = 512`) must stay equal, and the constant-parity rule
(CLAUDE.md) forbids drift. The decode cap is an INTERNAL invariant (`DATA_BUFFER_SIZE - 1`), not a
change to the public CMD_FRAME_MAX contract — so NO new firmware constant is introduced and NO
host mirror edit is required. Keep the existing comment block on the PUSH macro accurate by noting
the terminator-slot reservation.

## CR-02 — chosen fix: bounded mid-frame inter-byte deadline (approach B), armed on first byte, on BOTH spin sites

The verifier offered (A) restore D-06's non-blocking cross-loop accumulation (resumable decoder),
or (B) a `millis()`-based inter-byte deadline wrapping both `while (available() <= 0) {}` spins
with a negative-error return on expiry.

**Chosen: approach (B) — bounded inter-byte deadline armed only once a frame is in progress.**

### D-06 reconciliation (the load-bearing argument the re-verifier will scrutinize)

D-06 (CONTEXT.md) states two clauses relevant here:

1. *"the `CMD_IDLE` ingest accumulates bytes **non-blocking** across loop iterations"* — and
2. *"**No new idle wall-clock timer.** A stalled partial frame whose `0x00` never arrives is
   handled by the size cap, not a new timeout — keeps the idle loop free of new timer state."*

The shipped implementation honored NEITHER fully: it is a blocking spin (violates clause 1's
"non-blocking" letter), and clause 2's "size cap" only fires when bytes keep *arriving* and grow
`out` past the cap — it does NOT cover bytes that simply *stop arriving* mid-frame (the exact
CR-02 hole). So D-06's stated mechanism (size cap) is provably insufficient for the host-silence
failure mode. The operator explicitly delegated this call to the planner.

**Why approach (B) honors D-06's INTENT while consciously refining its letter:**

D-06's "no new idle wall-clock timer" was written to avoid reintroducing the OLD 2-second idle
timeout-cascade desync (the deleted `timeout_ms` loop — the SC1 win documented in
rurp_serial_utils.cpp:82). That concern is about the *truly-idle* path: a programmer sitting at
`CMD_IDLE` with NO frame in progress must not arm a wall-clock timer that fires on normal idle and
cascades into desync. Approach (B) preserves that exactly:

- The deadline is **armed only when a frame is already in progress** — specifically, it starts
  counting from the moment the FIRST byte of the frame has been consumed (decoding is underway).
  The truly-idle path is untouched: `loop()` still gates *entry* into the decoder on
  `rurp_communication_available() > 0` (firestarter.cpp:159), so the decoder is never entered on a
  truly-idle channel, and no timer runs while idle.
- This is a **mid-frame INTER-BYTE guard**, not an idle wall-clock timeout. It bounds only the gap
  between consecutive bytes of a frame that has started but stalled. The 2-second idle cascade
  D-06 forbade does not return — there is no timer on the idle path at all.
- Clause 1 ("non-blocking") is honored in spirit: the spin no longer blocks *unboundedly*; it now
  has a bounded escape. A full resumable cross-loop decoder (approach A) is the maximal
  interpretation of clause 1, but it is a large structural rewrite of the decode state machine
  (it would have to checkpoint `out`, `block_remaining`, `last_byte`, etc. across `loop()`
  iterations) — high regression risk for a defect whose minimal correct fix is a bounded wait. The
  operator delegated the call; the smallest fix that removes the hang and preserves the SC1 win is
  the right engineering choice for a hardware-safety patch.

**Conclusion:** approach (B) refines D-06's letter (it adds a bounded mid-frame deadline D-06 did
not name) while fully honoring D-06's intent (no reintroduced idle wall-clock timeout; SC1 win
preserved; bounded recovery). The plan states this refinement explicitly so the re-verifier sees a
deliberate, reasoned deviation, not an oversight.

### Mechanism

- Reuse the existing `TIMEOUT_MS` (`#define TIMEOUT_MS 1000` in firestarter.h) as the mid-frame
  inter-byte budget, or a dedicated smaller value — executor's discretion, but it MUST be a finite
  bound and MUST NOT reintroduce the 2 s idle behavior. Using `TIMEOUT_MS` avoids a new constant
  (no parity-mirror burden).
- Replace BOTH `while (rurp_communication_available() <= 0) {}` spins (line 92 in
  `_drain_to_delimiter`, line 125 in the main loop) with a bounded wait: record `millis()` when the
  wait begins, loop while `available() <= 0`, and break out with a negative error the moment
  `millis() - start >= TIMEOUT_MS`.
- On main-loop deadline expiry: drain (call `_drain_to_delimiter()` which is now ALSO bounded) and
  return a negative code (reuse `-1` read-underrun semantics, or a distinct negative — callers
  check `res < 0` only, per Assumption A4 in the file comment, so any negative is acceptable).
- On `_drain_to_delimiter` deadline expiry: simply return (stop draining) — the cursor stays where
  it is; the next `loop()` iteration re-gates on `available() > 0`. The drain must not itself hang.
- `command_done()` / VPP cleanup is not directly in this path (the decode happens before any
  command transitions out of CMD_IDLE), but returning bounded means the firmware returns to
  `loop()` and stays responsive instead of stranding — that is the hardware-safety win.

### Test strategy for CR-02

Every existing case feeds a complete stream ending in `0x00`; the mock's `available()` returns
remaining count and `read()` returns -1 only after exhaustion, but the existing tests never reach
exhaustion mid-frame. The new test feeds a **truncated frame (no trailing 0x00)** and relies on the
finite-stream mock: once the queue is exhausted, `available()` returns 0 forever and `read()`
returns -1. With the bounded deadline + the mock's incrementing `millis()` stub (already present in
setUp, lines 168-172, +100 ms per call), the deadline is reached deterministically and the call
RETURNS negative instead of spinning. The test asserts the call returns (a negative value) — proving
no infinite loop. No real wall-clock time is consumed; the `millis()` stub drives the deadline.
