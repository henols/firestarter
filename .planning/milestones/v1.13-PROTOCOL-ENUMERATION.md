## Open-Question Resolutions

### A1: Erase Scope — Does standalone `firestarter erase W27C512` already trigger the firmware erase electricals?

**Finding: YES — the standalone erase command already electrically works. The gap is in the write path only.**

Code trace (no hardware required):

1. **CLI path** (`cli_handlers.py:571-574`): `erase` command calls
   `app.eprom_operator.erase_eprom(eprom, eprom_data, operation_flags=_build_op_flags(blank_check=blank_check, force=force))`.
   `_build_op_flags` signature (`cli_handlers.py:216-246`) has no `FLAG_CAN_ERASE` parameter — it
   never sets that flag. This is correct and irrelevant for standalone erase (see below).

2. **Host operation setup** (`eprom_operations.py:219-222`): `_setup_operation` merges
   `command_dict["flags"] = eprom_data_dict.get("flags", 0) | operation_flags`.
   The `eprom_data_dict["flags"]` comes from `database.py:convert_to_programmer` which sets
   `FLAG_CAN_ERASE` if `full_eprom_data.get("info-flags", 0) & 0x00000010` (`database.py:594-597`).
   **Critical finding:** All 7 EE-EPROMs on protocol 0x07 (W27C512, W27E512, W27C257, W27E257,
   SST27SF256, SST27SF512, SST27VF256, SST27VF512) have `info-flags: 0x0` in
   `chip_database.json` — confirmed by DB query. Therefore `FLAG_CAN_ERASE` (bit 0x02) is
   **never set** in `flags` field sent to firmware for these chips.

3. **Firmware erase dispatch** (`eprom.cpp:46-56`): `configure_eprom` CMD_ERASE arm sets
   `handle->firestarter_operation_main = eprom_erase_execute` with no flag-gating.
   `eprom_erase_execute` (`eprom.cpp:88-91`) calls `eprom_internal_erase(handle)`
   **unconditionally** — there is no `FLAG_CAN_ERASE` guard on the erase execute path.

4. **Erase electricals** (`eprom.cpp:274-288`): `eprom_internal_erase` drives
   `CTRL_VPP_REGULATOR_ENABLE`, `CTRL_VPP_A9_ENABLE`, `CTRL_VPE_ENABLE` — the full
   hardware erase sequence.

**Conclusion:** A standalone `firestarter erase W27C512` already reaches the firmware erase
electricals via `COMMAND_ERASE` → `configure_eprom:CMD_ERASE` → `eprom_erase_execute` →
`eprom_internal_erase`. The erase gap is **not** in the standalone erase path.

**The real gap is in the write auto-erase path:** `eprom_write_init` (`eprom.cpp:100-106`) calls
`eprom_internal_erase` only `if (is_flag_set(FLAG_CAN_ERASE))`. Since `FLAG_CAN_ERASE` is never
set in `convert_to_programmer` (because `info-flags & 0x10` is 0 for all 7 EE-EPROMs), writing
a W27C512 never auto-erases before programming, even though those chips require electrical erase
before re-writing. The host `database.py:convert_to_programmer` checks `info-flags & 0x10`
(`database.py:594-597`) but the DB has `info-flags: 0x0` for all affected chips — the `info-flags`
field in `chip_database.json` carries the raw minipro XML flags, and `electrical.type = "EEPROM"`
is re-derived in `build_db.py:Step 7` (build_db.py:583-590) — but the `convert_to_programmer`
function reads `info-flags`, NOT `electrical.type`.

**Phase 75 scope (revised):** Phase 75 is not "wire standalone erase" — that already works. Phase 75
must wire `FLAG_CAN_ERASE` into `convert_to_programmer` based on `electrical.type == "EEPROM"`
(not `info-flags & 0x10`) so that `eprom_write_init` auto-erases 0x07 EE-EPROMs before programming.
The 14V rail question (W27C512 datasheet: erase mode OE/VPP=14V, A9=14V vs. 12V for write) remains
a Phase 75 bench verification item.

**Evidence citations:**
- `eprom.cpp:88-91` — `eprom_erase_execute` calls `eprom_internal_erase` unconditionally
- `eprom.cpp:100-106` — `eprom_write_init` calls `eprom_internal_erase` only if `FLAG_CAN_ERASE`
- `database.py:594-597` — `FLAG_CAN_ERASE` gated on `info-flags & 0x10`
- `chip_database.json` query (2026-06-17): all 7 `algorithm=0x07 + electrical.type=EEPROM` chips have `info-flags: 0x0`

### A2: 0x2B Identity — What protocol is dispatched at memory.cpp:108?

**Finding: 0x2B is a GAL/PLD family protocol. Exact IC2_ALG constant unconfirmed — `protocol-id.md` lacks a 0x2B row.**

Code trace:

1. **Firmware dispatch** (`memory.cpp:107-110`): The named infeasibility arm is:
   ```cpp
   if (handle->protocol == 0x11 || handle->protocol == 0x2A ||
       handle->protocol == 0x2B || handle->protocol == 0x2C) {
       configure_not_implemented(handle); return;
   }
   ```
   All four values are grouped together in a single comment "Named infeasibility arms (D-02):
   FWH and GAL/PLD — infeasible on RURP."

2. **`protocol-id.md` coverage** (`firestarter_app/doc/protocol-id.md`): The Excluded/Infeasible
   table has rows for `0x2A` (IC2_ALG_GAL16 — GAL16V8 PLD) and `0x2C` (IC2_ALG_GAL22 — GAL22V10
   PLD), but **no row for 0x2B**. The minipro `database.h` at commit `a8efaedc` would contain the
   `IC2_ALG_GAL20` constant if 0x2B is GAL20V8 — that source file is not in-repo and was not
   confirmed from the devcontainer filesystem.

3. **Pattern inference:** Given 0x2A = GAL16, 0x2C = GAL22, and the GAL device family sequence
   (GAL16V8 → GAL20V8 → GAL22V10), 0x2B is almost certainly `IC2_ALG_GAL20` (GAL20V8), but
   this is not confirmed from a citeable source.

**Conclusion:** 0x2B is in the GAL/PLD family, dispatched correctly as infeasible. The exact
IC2_ALG constant is likely `IC2_ALG_GAL20` by family sequence but is unconfirmed — `protocol-id.md`
does not have a 0x2B row, which is a documentation gap. No `build_db.py` DB chip reaches 0x2B
(PLD `type=3` chips are filtered before `KNOWN_PROTOCOLS` at `build_db.py:355`).

**Disposition:** The infeasible dispatch is correct. The `protocol-id.md` documentation gap
(missing 0x2B row) is a minor documentation debt — should be added to `protocol-id.md` with the
family-sequence inference and a note that IC2_ALG name is unconfirmed pending `database.h` lookup.
This is not a Phase 72 blocker; document as open in the Anti-Feature Block section below.

**Evidence citations:**
- `memory.cpp:107-110` — 0x2B in named infeasibility arm alongside 0x2A (GAL16) and 0x2C (GAL22)
- `firestarter_app/doc/protocol-id.md` — 0x2A and 0x2C listed, 0x2B absent (confirmed by grep)
- `build_db.py:355` — `type_int in [1, 4]` INFOIC2PLUS DIP filter excludes type=3 PLD chips

## Verdict Taxonomy

Three verdict buckets for per-protocol feasibility:

| Verdict | Meaning |
|---------|---------|
| `feasible-and-implemented` | RURP can physically drive this protocol; firmware handler exists and dispatches; chips can be programmed/read/erased today |
| `feasible-gap` | RURP can physically drive this protocol; a real gap exists — either (a) the firmware handler does nothing/is wrong, (b) the host doesn't wire a needed operation, or (c) the handler exists only in firmware but 0 DB chips use it; a specific downstream phase closes the gap |
| `infeasible` | RURP physically cannot drive this protocol; must remain fail-closed forever (hardware incompatibility, not a software gap) |

**Orthogonality note:** The feasibility verdict is **per-protocol-ID** (3 values). The `support_status`
field in `chip_database.json` is **per-chip** (4 values: `supported`, `protocol-not-implemented`,
`adapter-required`, `vpp-exceeds-max`). They are orthogonal axes:

| `support_status` | Maps to verdict | Notes |
|------------------|----------------|-------|
| `supported` | `feasible-and-implemented` | Chip reaches a working handler |
| `protocol-not-implemented` | `feasible-gap` or `infeasible` | X88C64 0x34 = `feasible-gap`; physically-impossible protocols = `infeasible` |
| `adapter-required` | `feasible-gap` (deferred) | AT28C04/16 — handler exists (0x0D), chip refused due to pin-map; adapter resolves it |
| `vpp-exceeds-max` | `infeasible` | 25V NMOS — RURP ceiling 22V, structurally blocked |

A chip can have `support_status: supported` and the protocol can still have an operation-level
gap (SRAM no-op example: all SRAM chips have `supported` but `configure_sram` is a near-no-op).

## v1.12 Claim Review

**Quoted v1.12 milestone goal** (ROADMAP.md, §v1.12 Milestone scope):

> "Framework + honest reporting only; **no new chip became programmable**. DB grew 743 → 744."

The broader v1.12 claim implied by the milestone scope is: _every RURP-feasible DIP parallel-memory
protocol already has a handler_, and the `support_status` taxonomy fully captures which chips cannot
be supported. The 14 non-supported chips (out of 744) were tagged and refused; the rest were assumed
to work correctly.

**Where the claim holds:**

- Every non-anti-feature protocol (0x05–0x10, 0x27–0x29) has a real firmware handler that
  dispatches correctly. No protocol is silently broken at the dispatch level.
- The fail-closed dispatch (`configure_not_implemented` for 0x11, 0x2A-0x2C, and generic non-zero)
  correctly prevents unknown protocols from reaching the VPP regulator.
- Anti-features (0x11 FWH, 0x2A-0x2C GAL/PLD, 25V NMOS) remain correctly infeasible.
- The `check_dispatch.py` CI gate correctly enforces that non-supported chips do not reach real
  handlers. [VERIFIED: CI gate passes on v1.13 branch]

**Where the claim was overstated:**

1. **SRAM no-op (0x0E/0x27/0x28/0x29):** `configure_sram` (`sram.cpp:15-17`) sets no operation
   pointers. All 76 SRAM chips (20 + 2 + 34 + 20 = 76 total, all `support_status: supported`) were
   counted as "working" in the v1.12 taxonomy. SRAM writes do proceed via the generic
   `memory_write_execute` path (set up by `configure_memory` before the protocol handler runs), but
   whether the generic path produces a correct JEDEC SRAM write is unconfirmed — no validation data
   exists. Code-state pointer: `sram.cpp:15-17` (3-line stub, no pointers set).

2. **Erase path for 0x07 EE-EPROMs (write auto-erase gap):** 7 chips on protocol 0x07 have
   `electrical.type = "EEPROM"` (W27C512, SST27SF512, etc.) and require electrical erase before
   re-programming. The v1.12 `supported` count includes these chips, but `convert_to_programmer`
   never sets `FLAG_CAN_ERASE` (because `info-flags & 0x10 == 0` for all 7) — meaning `eprom_write_init`
   never auto-erases before writing. Code-state pointer: `database.py:594-597` (FLAG_CAN_ERASE
   gating) + `eprom.cpp:100-106` (write-init erase guard).

3. **X88C64 0x34 re-classification:** The single `protocol-not-implemented` chip was implicitly
   treated as infeasible (like 0x11 FWH), but its physical package is DIP-24 5V parallel — RURP
   can drive the parallel bus. v1.12 never implemented the 0x34 handler (correct — out of scope),
   but the chip's `unsupported_reason` string ("protocol not implemented: 0x34 (XICOR NovRAM
   serial-parallel hybrid)") is misleading — it is a parallel interface chip. Code-state pointer:
   `chip_database.json` (1 chip, `protocol-not-implemented`) + `build_db.py:133-148` (0x34 in
   `KNOWN_PROTOCOLS` so it passes the gate, then gets classified as `protocol-not-implemented`).

## Ceiling Constraint

**RURP_VPP_CEILING_MV = 22000 (22V)**

[VERIFIED: `firestarter_app/tools/build_db.py:117`]

This constant is defined ONLY in `firestarter_app/tools/build_db.py:117`. It is NOT in
`firestarter/include/constants.py` or the firmware. Enforcement is at two points:

1. **DB-build time** (`build_db.py:607-617`): Chips with NMOS VPP > 22V receive
   `support_status: vpp-exceeds-max`. Classification is irreversible at build time.
2. **Check-dispatch gate** (`check_dispatch.py:79-85`): `_FAMILY_VPP_INVARIANTS` assertion
   for `configure_eprom: (0, 22000)` runs in CI.

**No runtime firmware enforcement:** The firmware does not check the ceiling — it trusts the
host (DB + `chip_resolver.py`) has pre-screened chips. This is the correct division of responsibility.

**Ceiling unchanged from v1.12.** Any Phase 75 work on the W27C512 erase rail (14V for erase
vs. 12V for write) is within the 22V ceiling. No ceiling relaxation is proposed or needed.
