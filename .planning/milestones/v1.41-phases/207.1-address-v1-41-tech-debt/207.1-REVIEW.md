## Warnings

### WR-01: D-03 comment misstates where the cycle-block path's `runs=1` tag comes from

**File:** `firestarter_app/firestarter/chip_test.py:2630-2640`
**Issue:** The new comment says it states the mechanism "precisely". It claims that on the cycle-block path, "the tag comes instead from the `hardware_refused` break after one cycle and `_aggregate_cycle_results` returning that single result." That is only one of two routes.

`_aggregate_cycle_results` sets `run_count=len(ran)` (`chip_test.py:1389`). `ran` is filtered to `_RAN_VERDICTS = {OK, BAD, MARGINAL}` (`:3928`), which excludes SKIPPED.

Take a cycle whose `_run_step` raises `SerialError` or `HardwareOperationError`. That cycle becomes SKIPPED with no `error_code`, so `hardware_refused` stays False and the loop does not break. The second cycle then runs normally. The fold gives `ran` one element, so `run_count == 1`, and `repeat_policy_tag` stamps `runs=1`. The same applies to an `EpromOperationError` whose `error_code` is `None`: `hardware_refused` keys on `error_code is not None` (`:1650`).

This comment is the record for a decision rated "costly to reverse". A future reader who fixes only the `hardware_refused` break will still see a default-policy run re-keyed into the `--fast` group through the SKIPPED-exclusion route. The claim that "reverting this branch alone would re-key none of them" still holds, because neither route depends on this `1`. Only the account of the mechanism is incomplete.
**Fix:** Name both cycle-block routes:
```python
            # ... On the cycle-block path this `1` equals the `runs` value
            # passed in; the tag comes instead from `_aggregate_cycle_results`
            # (`run_count=len(ran)`, SKIPPED excluded from `ran`) -- either the
            # `hardware_refused` break leaving one cycle, or a cycle that raised
            # here (SKIPPED, no error_code, no break) dropping out of `ran`
            # while the other cycle ran.
```

### WR-02: The lease's input drain runs outside the `SerialError` handler, so a drain failure never drops the held link (pre-existing, Phase 206)

**File:** `firestarter_app/firestarter/eprom_operations.py:695-706`
**Issue:** The leased branch calls `self.comm.consume_remaining_input()` at `:695`, BEFORE the `try:` whose `except SerialError` calls `_disconnect_programmer()` (`:696-706`). `consume_remaining_input` reaches `_read_and_parse_lines`, which raises `SerialError` on any `serial.SerialException` (`serial_comm.py:456-461`). A USB unplug or a stalled port produces exactly that exception.

When the drain raises, the `SerialError` escapes to `_run_step_untimed` (SKIPPED + ERROR) without dropping the lease's link. pyserial does not close the port on a read exception, so `is_connected()` (`connection.is_open`) stays True. Every later leased step then takes the same branch, re-drains the dead link and fails the same way. The rest of the plan is SKIPPED instead of cold-connecting.

This contradicts D-06 as `lease()` documents it, and T-206-12 in `206-SECURITY.md`, which state that a `SerialError` "disconnects the link and the next operation cold-connects". This phase's D-11 docstring (`serial_comm.py:834-848`) cites this exact site as the reason the new assert "is not affected", so the gap sits under text this phase wrote.
**Fix:** Move the drain inside the existing handler:
```python
            try:
                self.comm.consume_remaining_input()
                setup_ok = self.comm.setup_command(command_dict, self.config)
            except SerialError:
                self._disconnect_programmer()
                raise
```
Add a `test_session_lease.py` leg in which `consume_remaining_input` raises `SerialError`. It should assert that `operator.comm is None` afterwards and that the next leased operation calls `find_and_connect`.

### WR-03: `update_version.py --set-version` does not enter beta mode; the stable path silently ignores it and bumps the patch (pre-existing)

**File:** `firestarter_app/.github/scripts/update_version.py:55-64, 129-134, 148-156`
**Issue:** The `--set-version` help text calls it an "Alias for BETA_VERSION env var". The env var triggers beta mode (`is_beta_mode`, `:61`), but the alias does not: `is_beta_mode` never reads `args.set_version`.

Consider `update_version.py --set-version 3.0.0b50` invoked on a ref other than `beta`, without `--beta` or `BETA_VERSION`. It takes the STABLE branch (`:181-199`), discards the requested version, increments the patch and writes a stable `X.Y.(Z+1)` into `firestarter/__init__.py` and `$GITHUB_OUTPUT`.

This file is on the publish path. Per root `CLAUDE.md`, a PyPI version can never be reused and stable is operator-gated. No test covers this script (`grep -rl update_version tests/` is empty), and it sits outside every CI gate. D-12 touched the file, but only to reformat it.
**Fix:** Treat an explicit `--set-version` as a beta request, or refuse the combination:
```python
def is_beta_mode(args) -> bool:
    if args.beta or args.set_version:
        return True
    ...
```

## Info

### IN-01: Arm 4b names `--skip-sdp-unlock` as the cause but does not check that flag

**File:** `firestarter_app/firestarter/cli_handlers.py:977-987`
**Issue:** The arm's only condition is `attempt_verdict == 0`. It is correct today, because the ack block is the only thing that turns a verdict-0 write into `False`. However, the line hard-codes the cause. If a later check is added after the verdict is recorded in `write_eprom` (for example a post-write check), that check would silently print a false "did not acknowledge --skip-sdp-unlock" line. The local `skip_sdp_unlock` (including its auto-set at `:809-810`) is in scope.
**Fix:** `if attempt_verdict == 0 and skip_sdp_unlock:`. A verdict-0 `False` without the flag then falls through to arm 4, or gets its own defensive line.

### IN-02: The D-05 boundary legs duplicate the whole test body and `_FakeTime` three times, and share one docstring

**File:** `firestarter_app/tests/test_eprom_operations.py:858-968`
**Issue:** The two new legs are identical except for `check_time`. `_FakeTime` is now defined three times (`:820`, `:876`, `:932`). The "exactly at" leg reuses the "just inside" docstring word for word. It never says that its purpose is to pin the inclusive `<=` in `_drive_region_compare` (`eprom_operations.py:2820`), which is the one thing that separates it from the other leg.
**Fix:** Hoist `_FakeTime` to module level. Parametrize one test over `check_offset` in `(WINDOW - 0.001, WINDOW)` → verdict 1, and optionally `WINDOW + 0.001` → verdict 2. Give the `WINDOW` case an id or docstring that says it pins the inclusive bound.

### IN-03: `_write_blank_guard_refusal_message` is described as "directly unit-testable" but no direct test exists; the mismatch branch passes `int | None` as `int`

**File:** `firestarter_app/firestarter/eprom_operations.py:365-383`

The selection is exercised only through `test_write_with_incomplete_guard_read_is_refused_and_no_write_reaches_the_wire` and the existing mismatch-path tests. On the mismatch branch, `result.first_actual` (`int | None`) is passed to `refusal_text(value: int)`. Mypy would flag this, but mypy is not in CI.

### IN-04: The incomplete refusal reads vacuously when nothing was compared

**File:** `firestarter_app/firestarter/write_blank_guard.py:122-126`
**Issue:** When the firmware ends the read (MAIN) before sending any chunk, `compared == 0`, `bad == 0` and `total > 0`, so the verdict is 1. The line then says "read only 0 of N bytes; every byte it read was blank". It stays fail-closed, but "every byte it read was blank" is a vacuous claim that an operator may read as evidence.
**Fix:** Branch on `compared == 0`, for example "the blank check read no bytes of {total}; the region is not proven blank."
