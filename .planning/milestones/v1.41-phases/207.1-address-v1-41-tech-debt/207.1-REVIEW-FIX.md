### WR-01: D-03 comment misstates where the cycle-block path's `runs=1` tag comes from

**Files modified:** `firestarter/chip_test.py`
**Commit:** `82bba7a`
**Applied fix:** Verified the two underlying claims against source before rewriting:
`_aggregate_cycle_results` sets `run_count=len(ran)` where `ran` is filtered to `_RAN_VERDICTS =
{OK, BAD, MARGINAL}` (chip_test.py:3928), which excludes `SKIPPED`; and `_run_cycle_block`'s
`hardware_refused` flag keys strictly on `result.error_code is not None` (chip_test.py:1650),
never on verdict. Confirmed the `except (SerialError, HardwareOperationError)` branch (the one
this comment lives inside) always returns `verdict=VERDICT_SKIPPED` with `error_code` left at its
default (`None`), so such a cycle drops out of `ran` without ever setting `hardware_refused`. This
gives a second, independent route to `run_count == 1` on the cycle-block path beyond the
`hardware_refused` break the old comment named alone. Rewrote the comment to name both routes
explicitly: the `hardware_refused` break leaving one cycle, and a cycle that raised here (SKIPPED,
no `error_code`, no break) dropping out of `ran` while the other cycle ran. Did not fold in the
`EpromOperationError`-with-`error_code`-None case from the review's Issue prose: that except
clause (chip_test.py:2646-2653) always sets `verdict=VERDICT_BAD`, which stays inside
`_RAN_VERDICTS` regardless of `error_code`, so it is never excluded from `ran` — including it as a
third "SKIPPED" route would have been inaccurate. No code behavior changed; comment-only edit.

## WR-02: The lease's input drain runs outside the `SerialError` handler, so a drain failure never drops the held link

**Files modified:** `firestarter/eprom_operations.py`, `tests/test_session_lease.py`
**Commit:** `8596992`
**Applied fix:** Moved `self.comm.consume_remaining_input()` inside the existing `try:` whose
`except SerialError:` calls `self._disconnect_programmer()` and re-raises, so a `SerialError` from
the drain (raised by `_read_and_parse_lines` on a `serial.SerialException`, per
`serial_comm.py:456-461`) now drops the held link exactly like a `setup_command` failure already
did. Expanded the existing comment at that call site to state the new invariant and its rationale.
Checked the D-11 docstring in `serial_comm.py:812-857` (`setup_command`'s assert-precondition
text): its reasoning rests on the caller's `is_connected()` check at the outer `if` (line 690),
which this change does not touch, so the docstring still reads correctly — left unchanged.
Added `test_a_drain_failure_drops_the_lease_and_the_plan_continues` to `tests/test_session_lease.py`,
following the existing `_FakeComm`/`_make_find_and_connect` fixtures and the sibling
`test_a_mid_plan_serial_error_drops_the_lease_and_the_plan_continues` pattern: extended `_FakeComm`
with a `fail_drain: bool` constructor flag that makes `consume_remaining_input()` raise
`SerialError`, then asserted that after the drain-triggered raise `operator.comm is None` (link
dropped), `operator._leased is True` (lease itself survives), and the next leased operation
cold-connects (a fresh `find_and_connect` call recorded).
