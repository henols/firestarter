Five findings change how the plans should be written. Each is a correction to a CONTEXT.md premise, not a new decision:

1. **D-04 count is 7 issues (9 filed reports), not 0.** But none of them got the `runs=1` tag from the audit-named branch acting alone. All nine are cycle-block steps. `_run_cycle_block` calls `_run_step(..., runs=1)`, so on that path the except branch's `run_count=1` equals the `runs` value passed in. What produces the tag is the `hardware_refused` break after cycle 1, and `_aggregate_cycle_results` then returning the single result. **D-03's "Reversibility" note is therefore incomplete.** Setting `run_count` to the nominal `runs` in the two except branches would re-key only per-step-path ops, meaning the read step. It would not re-key any of the nine filed reports. The D-03 comment must describe this accurately.
2. **D-06: no existing test pins the wording for the WR-01 state.** The arm-4 CLI test uses `last_write_attempt_verdict = 1`, which keeps the no-write line. The only test of the state itself, `test_last_write_attempt_verdict_zero_when_skip_sdp_unlock_ack_check_fails`, pins the verdict value (0), not the wording. The test that pins a *fabricated diagnostic* is D-07's (`tests/test_write_blank_guard.py:661`). D-06 therefore **adds** a CLI arm test rather than editing one.
3. **D-08's premise is inverted.** Today a negative, page-*aligned* 0x05 address with an aligned length already gets the negative-address message (probed: `-128` with a 128-byte payload). The clearer message is lost when the address **or the length** is *misaligned* (probed: `-1` with 128 bytes, and `-128` with 64 bytes, both give `PageAlignmentError` with `start address is -0x1` / `-0x80`). The new test must use a misaligned negative address.
4. **D-11's assert breaks exactly 12 tests in 3 files.** Each harness patches `SerialCommunicator.__init__` to a no-op, so `self.connection` never exists. One added `patch.object(SerialCommunicator, "is_connected", return_value=True)` per harness restores all 50 tests in those files (proved on scratch copies). The assert also raises `AssertionError`, not `SerialError`. `_probe_port`'s `except Exception` swallows it into "Unexpected error while probing" plus `return None`. The `setup_command` docstring currently argues *against* this guard, so it must be rewritten.
5. **The WINDOWS verb `windows fixed <id>` takes no reason.** It sets `status`, `resolved_at` and the counts, then re-renders the whole file. A reason must be hand-edited afterwards, identically in the JSON block and the table row. Otherwise the next verb write refuses with `WINDOWS_LEDGER_TABLE_DRIFT`.

**Primary recommendation:** use three plans in the CONTEXT order: host fixes, then secure-phase, then records. Run D-02 at orchestrator level as a `checkpoint:human-action` (`autonomous: false`), not inside an executor. Every meta commit stages named paths only, because the meta working tree carries unrelated modifications.

### D-03 — the two except branches in `_run_step_untimed` (comment only)

- Function: `firestarter/chip_test.py:2543` `def _run_step_untimed(` [VERIFIED: chip_test.py:2543]
- Branches [VERIFIED: chip_test.py:2612-2627]:
  ```python
      except (SerialError, HardwareOperationError) as exc:
          return StepResult(
              op=step.op,
              verdict=VERDICT_SKIPPED,
              status=STATUS_ERROR,
              reason=str(exc),

              op=step.op,
  ```

- The block to stay consistent with, above `_REPEAT_POLICY_OPS` [VERIFIED: chip_test.py:1043-1055]:
  `# The ops whose \`StepResult.run_count\` is EXACTLY \`run_plan\`'s \`runs\` kwarg` … `_REPEAT_POLICY_OPS = _MULTI_RUN_OPS | {OP_READ}` … `REPEAT_POLICY_DEGRADED_TAG = "runs=1"`. `_MULTI_RUN_OPS = frozenset({OP_WRITE, OP_WRITE_PARTIAL, OP_ERASE, OP_VERIFY})` [VERIFIED: chip_test.py:865]. The op strings are `OP_READ = "read"`, `OP_WRITE = "write"`, `OP_WRITE_PARTIAL = "write-partial"`, `OP_VERIFY = "verify"` and `OP_ERASE = "erase"` [VERIFIED: chip_test.py:261-266].
- Tag rule: `if result.op in _REPEAT_POLICY_OPS and result.run_count == 1: return REPEAT_POLICY_DEGRADED_TAG` [VERIFIED: chip_test.py:1071-1073]. The tag is appended to the hash pre-image only when non-empty (`policy = repeat_policy_tag(report.results)` / `if policy: parts.append(policy)`) [VERIFIED: diagnostic_report.py:316-318].
- **What the comment must say accurately (new finding):** the tag reaches a default-policy report along two paths.
  - **Per-step path.** The read step and anything outside the cycle block go through `run_plan` → `_run_step(..., runs=runs)` [VERIFIED: chip_test.py:1837-1845]. Here the branch's hard-set `run_count=1` *is* the cause.
  - **Cycle-block path.** write, write-partial, verify, erase and blank-check go through `_run_cycle_block`, which calls `_run_step(..., runs=1, ...)` per cycle [VERIFIED: chip_test.py:1618-1631].
