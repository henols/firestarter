<objective>
Observe on silicon what this phase changed and what it did not, and record it precisely enough that
nobody has to trust it.

Purpose: criteria 3 and 5 say "confirmed on silicon" and "a bench regression … shows no behaviour change
other than where the refusal now comes from". Those words are there because both claims are easy to
argue from code structure and the milestone refuses that. Criterion 3 is a claim about what the firmware
now permits, which only the part can answer. Criterion 5 is a claim about the absence of a change, so
its whole value is in having been run. And D-07's skew leg is a claim about what a real user with an
un-reflashed board will experience after a `pip install -U`, which REL-04 is about to write down in the
wiki — 204's precedent is explicit that such a claim gets observed rather than argued.

The sequencing is forced by the hardware. The pre-205 firmware is on the board once, so the skew leg
runs before the reflash or not at all. The part is put into a known non-blank state once, by the Phase
201-06 `--skip-erase` rehearsal, and both the skew leg and the criterion-3 leg read from that same
state. And the erase legs are destructive to chip content, so digests bracket them.

One honest limit shapes the whole plan: no true UV part is available. The W27C512 is electrically
erasable and rides the UV handler — protocol `0x07`, the file FWBLANK-01 and FWBLANK-02 both change — so
the code path under test is identical and the silicon is not. Every leg that stands in for UV silicon
says so in the record.

Output: `205-BENCH-MATRIX.md` and `205-SESSION-COST.md`.
</objective>

<design_forks_resolved>
**Fork A — the pre-205 firmware is built from a detached worktree of a named pre-phase commit, not
recovered from a release asset.** Unlike Phase 204's D-08, where the old artifact had to be the published
wheel because the claim was about what a real user already has, the claim here is about firmware that is
merely un-updated. A local build of the phase-entry sha IS the pre-205 source, with no supply-chain
question and no version-string ambiguity. Build it in a detached worktree under the session scratch
directory so the live `firestarter_fw` tree is never checked out to a different commit mid-phase — a
dirty or moved working tree would invalidate every digest and sha this phase has recorded.

**Fork B — the skew leg is a rider on the criterion-3 sequence, not a second matrix (D-07, decided by
Claude and recorded in CONTEXT).** The part is already seated and already non-blank when B3 runs, the
Leonardo is exempt from the chip-out-before-sideload rule so the firmware swap needs no hands, and the
marginal cost is close to zero. The alternative — a separate matrix with its own setup — would re-create
the same non-blank state twice for no additional evidence.

**Fork C — `erase -b`'s added wall-clock is MEASURED here rather than derived.** CONTEXT leaves the
choice between a bench run and `tests/test_connect_cost_harness.py`. The bench run is taken because the
board is already in the loop for three other legs and because 203's D-17 handed Phase 206 a measured
figure rather than a derived one. The derivation over 203's cited per-open medians is recorded ALONGSIDE
it, labelled as a derivation, so Phase 206 can see whether the measurement agrees with the model.
</design_forks_resolved>
