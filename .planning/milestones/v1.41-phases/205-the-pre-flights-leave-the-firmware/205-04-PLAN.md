<objective>
Retire wire control-flag bit `0x08` from both ladders in a commit pair, re-plumb `write -b` as an
explicit host-side signal, and re-key the one frozen literal the re-plumb moves — in three commits,
each of which leaves its repository green.

Purpose: this is FWBLANK-04, and it is the requirement where measurement did NOT contradict the
roadmap. Phase 203 amended WRITE-02 and Phase 204 amended FWCMD-05 once measurement showed the written
form was wrong; here measurement only priced the requirement, so it stands as written and the price is
accepted knowingly. The price is a real regression in one skew direction: a post-205 host driving
pre-205 firmware stops suppressing the firmware's surviving pre-flight, so `write -b` on a non-blank UV
part is refused where it works today. That is the CLI-upgrades-faster-than-firmware direction, which is
the common one, and it is why D-04 files two obligations — a wiki line for Phase 207, and an observation
on silicon in this phase rather than an argument in a document.

The commit shape is dictated by two hard constraints that pull in opposite directions. The two constant
ladders must move as a pair, and the host's five production sites plus its test harness must move in one
commit or the suite cannot collect at all — deleting the host symbol alone produces 65 collection errors
because four modules import it at module level. Firmware first is the safe order for the pair: between
the two commits the host sets a bit the firmware ignores, which is harmless, rather than clearing one
the firmware still enforces, which is not.

Output: a wire flag that exists on neither side, a reserved record at both gaps, a host guard that keys
on an explicit parameter, and a documented, benchable skew.
</objective>

<design_forks_resolved>
**Fork A — firmware commit first, then host.** CLAUDE.md requires a commit pair but not an order. The
order matters: after plan 03 the firmware performs no pre-flight, so between the two commits of this
pair a host that still composes `0x08` is setting a bit nothing reads — harmless, and `FIELD_MASK`
already tolerates unknown bits. The reverse order would have a host that has stopped composing the bit
against a firmware that has not yet had its define removed, which is also harmless here but is the
wrong habit to establish: the general rule is that the side which ENFORCES loses the enforcement first.

**Fork B — the `-b` signal is a keyword-only parameter with a `True` default.** RESEARCH names the
precedent in the same file: Phase 203's `write_eprom(..., *, suppress_verdict_line: bool = False)`
added exactly such a parameter for WRITE-05 and left every existing caller byte-identical. The two
hazards CONTEXT names are neutralised by construction rather than by care — `build_flags`' own docstring
records that both production callers pass its first four parameters positionally, and
`chip_test.py:3221` passes its flag positionally too, and a keyword-only insertion cannot shift either.
`requires_blank_check` takes the signal as a third keyword argument with a `True` default, keeping its
signature stable for every existing caller.

**Fork C — `tests/fake_chip.py` KEEPS its firmware-pre-flight model and is renamed to say what it
models.** It currently reads the constant to decide whether to simulate the firmware refusal, which
models a firmware that will not exist after this phase. Retiring the model would lose the only bench-free
harness for the pre-205-firmware skew — the exact skew D-07 puts on silicon and D-08 keeps
`MSG_ERR_NOT_BLANK` alive for. So the model stays, keyed on an explicit constructor flag rather than on
the retired wire bit, and its name and docstring say it models pre-3.1.0 firmware. Its `:318` and `:340`
`MSG_ERR_NOT_BLANK` assignments stay correct either way.

**Fork D — the reserved-marker leg is re-anchored upward even though it would stay green.** Measured:
`test_verify_survival_source_contract.py::test_both_reserved_ordinal_gaps_carry_a_recorded_reason`
counts the `retired in 3.1.0` marker in the firmware header and asserts `count >= 2`. It is already a
floor, deliberately — its docstring says it counts the marker rather than parsing prose so a rewritten
sentence still passes and a deleted note still fails. Adding this plan's `0x08` record makes a third
marker, so the leg stays green with no edit at all.

Leaving it is the wrong call. A floor of 2 guarding three records means one of the three can be deleted
outright with the gate still green, which is exactly the guarantee the leg was written to provide. Move
the floor to 3 and rename the leg, which encodes "both gaps" and would now be wrong. Three coordinated
edits as always: the bound, the function name, and the docstring's census prose. This is a re-anchor
upward, not a relaxation — the shape stays the floor the leg's own docstring justifies.

</design_forks_resolved>
