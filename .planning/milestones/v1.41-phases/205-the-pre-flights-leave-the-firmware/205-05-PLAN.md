<objective>
Make the firmware refuse a negative wire address instead of silently clamping it to 0, scoped to the
address field, in its own commit.

Purpose: this is the folded todo `2026-09-16-reject-negative-write-start-address.md`, firmware half.
Phase 203 folded and landed the host half and left this one; Phase 203 and Phase 204 both deferred it
here by name, and 204's stated reason for choosing 205 over itself — "dual-repo and bench-gated" — was
equally true of 204. Phase 205 is the last dual-repo firmware phase in v1.41, because 206 is app-only
and 207 is a version bump plus wiki, so a third deferral leaves the fix with no named home and it goes
to backlog.

It is listed under FWBLANK-01 because it belongs to the same story: FWBLANK-01 empties the firmware's
write-init of its last input pre-flight, and this is the one input check on that same wire path that
must stay in the firmware. RESEARCH's security domain places it squarely in V5 Input Validation and its
threat register names it — a negative wire address clamping to 0 is Tampering with the destination. The
requirement mapping is stated here rather than inferred, because the fix's real driver is a todo, not a
roadmap line.

204's bisect objection — do not mix a parser fix into a pure removal — is honoured by the commit, not by
the deferral. A bisect lands on a commit, so an isolated commit inside this phase separates the removal
from the fix exactly as well as a separate phase would.

Output: a parser that refuses what it cannot represent, a native proof under both environments, and a
measured byte cost recorded separately from the sweep's.
</objective>

<design_forks_resolved>
**Fork A — the refusal is table-driven through a new policy bit, not a special case keyed on the key
name.** `json_parser.c` already expresses per-field policy as bits on the field descriptor's `width`
column: `FIELD_WIDTH_MASK` is 0x0F and `FIELD_POLICY_MASK` is 0x80, selecting saturate-versus-mask
semantics. Adding a third policy bit at 0x40, set only on the `key_address` row through a new macro
alongside `FIELD` and `FIELD_MASK`, keeps the file's own idiom and makes the scope visible in the table
rather than buried in the loop. It is inert in `store_field` by construction, because that function
masks the width with `FIELD_WIDTH_MASK` and tests only bit 7.

**Fork B — the refusal uses `json_parse`'s existing `-1` return, and mints no message id.**
`FIELD_MASK`'s own comment in this file records why: it declined to reject an out-of-range bitmask
because "`reject` needs a new message id, and message ids are generated from the catalog rather than
written here". That constraint applies unchanged. `-1` is the channel a non-JSON-object frame and a
malformed bus-config already use, and the dispatcher already handles it. Reusing it costs no catalog
change, no codegen run and no sub-repo sync.

**Fork C — the not-folded `region-end` json-parse coverage todo is NOT taken here.** CONTEXT notes that
`2026-09-20-region-end-wire-key-has-no-json-parse-coverage.md` cites this same native suite as its home
and that its ready-to-drop-in cases would be near-free if this plan stands up json-parse coverage, and
says taking them is "permitted, not required". They are not taken. The todo was never routed to this
phase, it adds coverage rather than fixing a defect this phase's removal touches, and `region_end`
demonstrably survives Phase 205 with two `mem_util_operation_end` callers, so the gap neither closes nor
widens here. Record the decision in the SUMMARY so the todo's next reader knows it was considered.
</design_forks_resolved>
