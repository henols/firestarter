<objective>
Give the host the post-erase blank check, through Phase 202's existing engine, before Phase 205's
firmware sweep takes the device-side one away.

Purpose: this is the tracer slice of the whole phase. Every other plan removes something; this one is
the only thing built, and it is built first because the roadmap states the ordering as a safety
property rather than a preference. `erase -b` is the one user-facing surface whose entire mechanism is
the `firestarter_operation_end = mem_util_blank_check` assignment FWBLANK-02 deletes, and no earlier
phase replaced it — Phase 203 covered write-init, Phase 202 covered the standalone `blank` and
`verify` commands, and neither touched erase-end. If the firmware sweep landed first, `-b` would go
silently inert on exactly the part class seated on the bench.

The slice is thin on purpose: one entry point (`firestarter erase <chip> -b`), one path through every
host layer it will ever use — Click option, CLI-tier pre-wire refusal, `EpromOperator`,
`check_eprom_blank`, `_drive_region_compare`, exit code — no new comparison code, and a real runnable
verify. It is production-quality rather than a prototype: the engine it calls is the one Phase 202
shipped and Phase 203 already leans on, and the exit-code contract it adopts is the one the `blank`
handler already publishes.

Output: `erase -b` that means what it has always meant, implemented one tier up, with its two new
contracts stated in the help text a user actually reads.
</objective>

<design_forks_resolved>
**Fork A — `erase_eprom` is NOT widened from `bool` to a verdict int.** RESEARCH offers the widening as
an analog (the `verify_eprom` to `sys.exit(verdict)` pair). Measured against what D-02 actually asks
for, the widening is unnecessary: D-02 introduces exit 2 for the CHECK, not for the erase. The erase's
own failure keeps exit 1, which is today's contract and which D-02 explicitly preserves — "plain
`erase` without `-b` keeps 0/1 unchanged". So the handler maps `erase_eprom`'s bool to 0/1 exactly as
it does now, and only when `-b` is set AND the erase succeeded does it call `check_eprom_blank` and
exit with that method's own verdict. `erase_eprom`'s signature and every one of its callers stay
byte-identical, which matters because the host suite has a measured collection cliff around this
module and plan 04 is about to move five production sites inside it.

**Fork B — the OQ-1 refusal lives in `cli_handlers.py` next to `_region_refusal_exit_code`, not in a
new pure-predicate module.** The project has both idioms: dedicated gate modules (`flash4_erase_gate`,
`jp5_gate`, `sdp_capability`) and in-file CLI-tier refusal helpers (`_region_refusal_exit_code` at
`cli_handlers.py:962`, shared by `verify` and `blank`). The gate modules exist because their policy is
non-trivial and needs its own reasoning and its own test surface — which protocol ids, which algorithm
value, what to do when the wire dict is incomplete. OQ-1's policy is one boolean conjunction over two
CLI options and reads no wire dict at all, so a module would be ceremony. The in-file helper is the
matching precedent and it already establishes the two properties OQ-1 needs: it returns an exit code
rather than raising, and it decides before `EpromOperator` is reached.

**Fork C — the OQ-1 refusal exits 2, not 1.** `_region_refusal_exit_code` returns 2 for both of its
pre-wire refusals, and this is the same class of thing: a usage refusal decided before the wire, not a
chip verdict. Reserving 1 for "erased but not blank" keeps D-02's three outcomes distinct. The code is
stated in the help text.

**Fork D — the check runs only when the erase actually succeeded.** If `erase_eprom` returns false the
handler exits 1 as it does today and opens no second port. Running a blank check after a failed erase
would produce a not-blank verdict describing a part that was never erased — the same
verdict-fabrication shape D-02 exists to refuse.
</design_forks_resolved>
