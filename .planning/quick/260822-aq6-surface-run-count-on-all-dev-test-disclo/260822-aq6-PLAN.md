# Quick Task 260822-aq6 — `run_count` disclosure + `dev test --fast`

## Problem

`dev test` has run every repeat-capable step **twice** since v1.21 Phase 121
(`run_plan(..., runs: int = 2)`, `firestarter/chip_test.py:1302`, with a
fail-closed `runs < 2` guard at `:1364`). Two policies ride on it:

- `read ×N` — SHA-compare the runs, report `divergence` as a metric only
  (`_dispatch_read`, D-06). Never a verdict flip.
- `write / write-partial / verify / erase ×N` — outcome disagreement across
  runs yields `MARGINAL` (`_dispatch_multi_run`). This is the detector that
  caught AM27C020 write#1 60/64 vs write#2 0/64 (v1.18 Phase 99).

So the observed wire order `id, read, read, blank-check, write, write,
verify, verify, …` is **by design**. But it is invisible:
`StepResult.run_count` (`chip_test.py:1211`) is populated on every step and
read by **nothing outside tests** — absent from `_step_dict`, therefore
absent from the JSON artifact, the saved markdown, and the filed issue body;
and the console table renders one row per step with no run indication. On a
clean run the only trace the repeat leaves is a *failure* (`marginal`, or the
read `divergence` dict).

Operator direction: time is not a constraint ("start it and do something
else"); **the most accurate test is the goal**. A fast mode may exist but the
default must stay the accurate one and the flag must say so.

## Scope

### Task 1 — surface `run_count` on all four disclosure surfaces

Found **three** other surfaces, not two (recorded rather than silently
narrowed):

1. `diagnostic_report._step_dict` → the JSON artifact + `to_json_block()`
   (which rides into the markdown file *and* the issue body).
2. `DiagnosticReport.render()` → the console table's per-step rows.
3. `cli_handlers.dev_test`'s saved `dev-test-<chip>.md` table.
4. `submit.build_body` → the filed GitHub issue body table.

- `_step_dict` gains `"run_count": result.run_count`. Additive **inside**
  `steps[]` only — the top-level shape stays pinned
  (`tools/parse_devtest_issue.py` consumes it).
- `SCHEMA_VERSION` `1.6` → `1.7`, following the same precedent the 1.5→1.6
  bump set for additive per-step keys. `test_schema_version_1_6_single_sourced`
  is renamed to `..._1_7_...` and its one quoted literal updated — the
  established rename-on-bump pattern, already applied twice.
- Console row value becomes `<verdict>  ×<N>  <took>`, rendered for every
  step that ran. No conditional: a step that ran once shows `×1`. The
  contrast (`read ×2` beside `blank-check ×1`) is the whole point.
- Both markdown tables gain a `Runs` column between `Verdict` and `Took`.
  Header becomes `| Step | Verdict | Runs | Took | Reason |`; the two tests
  pinning the old header literal (`tests/test_submit.py:217`,
  `tests/test_dev_test_cmd.py:918`) are updated.

### Task 2 — `dev test --fast`

- `run_plan` gains `allow_single_run: bool = False`. The `runs < 2` guard is
  **kept fail-closed for every existing caller** — an accidental `runs=1`
  still fails the whole plan. Only an explicit `allow_single_run=True`
  admits `runs=1`; `runs < 1` fails unconditionally.
- `dev test --fast` → `runs=1, allow_single_run=True`.
- Help text states the cost plainly: single-run mode cannot detect an
  intermittent write or a nondeterministic read, so **no step can report
  `marginal`** and no read divergence is computed. Omitting the flag is the
  accurate test.
- **D-05 reversal, stated not smuggled.** `dev test` has had a recorded
  *zero-option surface* since Phase 121 D-05, gated by
  `TestZeroOptionSurface::test_dev_test_accepts_no_options` asserting
  `options == []`. This task reverses that decision for exactly one option.
  The gate is **narrowed, not deleted**: it now asserts the option set is
  exactly `{fast}`, and the sibling tests proving `--destructive`,
  `--output-dir`, `--submit` and `-y` are still rejected are left untouched.

### Task 3 — a `--fast` run must not pollute the N≥2 promotion ladder

Direct consequence of Task 2, not scope creep. `tools/parse_devtest_issue.py
::count_agreeing` groups filed reports by the embedded `dedup_fingerprint`
and promotes a chip on N≥2 agreement. Phase 121 D-06/D-08 already established
the principle: `write-partial` hashes differently from `write` *specifically*
so a weaker run can never contribute to a full run's promotion count. A
`--fast` run is the same class of weaker run. Without this, two `--fast` runs
could promote a chip that no accurate run ever passed.

- New pure helper in `chip_test.py`: `repeat_policy_tag(results) -> str`.
  Returns `""` for the default policy; a degraded marker when any step whose
  op is in `_MULTI_RUN_OPS | {OP_READ}` reports `run_count == 1`. Restricted
  to exactly those ops because they are the only ones whose `run_count`
  equals `runs` — the SDP leg's ops are `run_count == 1` **by design** and
  must not read as degraded.
- `dedup_fingerprint` appends the tag **only when non-empty**. Consequence,
  chosen deliberately: every existing full-run fingerprint is **unchanged**,
  so no historical grouping or promotion count is reset (the cost the SDP
  re-key accepted in v1.30 is avoided here). Fast runs get their own group.

## Out of scope

- Changing the default `runs=2`. The operator's goal is accuracy; the default
  stays.
- Any firmware change. This is host-only.
- Bench validation. No hardware run is part of this task.

## Verification

- `pytest tests/` green in the app repo (`-o addopts=""` to see the count
  line — the doubled `-q` in `addopts` suppresses it).
- `ruff check` / `ruff format --check` clean; `mypy` per the repo's gate scope.
- `dev test --help` shows `--fast` with the weaker-test wording.
- A `--fast` invocation and a default invocation of the same chip produce
  **different** `dedup_fingerprint` values; two default runs of the same
  chip still produce the **same** value.
- `run_count` present in: the JSON `steps[]`, the console table, the saved
  markdown table, and `submit.build_body`'s table.

## Known hazards (from prior tasks)

- `dev test`'s console constants are triple-gated: two exact-equality gates
  scrape the handler body plus one syrupy help snapshot. Adding a click
  option changes `dev test --help`, so the snapshot may need regeneration.
- Devcontainer python is 3.12; app CI is 3.11 only. Nothing here is
  version-sensitive, but the local green is not the CI green.
