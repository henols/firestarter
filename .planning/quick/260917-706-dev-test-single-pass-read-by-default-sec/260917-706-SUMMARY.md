# Quick task 260917-706: dev test single-pass read by default — Summary

`--compare-reads` flag to restore the two-pass read-divergence comparison, and
narrowed `_REPEAT_POLICY_OPS` to the write/verify/erase multi-run ops so a
default run's `repeat_policy_tag` stays the empty string.

All work happened inside the `/workspaces/firestarter_app` submodule on branch
`v1.39-protocol-0x05-write-correctness`, anchored at pre-task HEAD `ff5dd1d`
(== `origin/beta`, 3.0.0b45). No meta-repo commit was made; the meta gitlink
is left for the orchestrator to move.

## Task 3 fallout (needed a commit)

The full suite surfaced five failures after tasks 1–2, all repaired in their
own terms, none by weakening an assertion:

1. `tests/test_chip_test_sdp_leg.py::test_shipped_ops_sequence_unchanged` and
   `::test_empty_registry_noop` — both assert `_SHIPPED_OPS_SEQUENCE`'s
   frozen `(verdict, run_count)` list for a default `run_plan` call on
   `"M8720"`. The read step's entry changed from `("OK", 2)` to `("OK", 1)`,
   which is exactly the new default-read-once behavior; updated the frozen
   literal, left the (still-accurate) explanatory comment above it
   untouched.

2. `tests/test_chip_test_sdp_leg.py::test_derive_plan_allow_adds_no_cli_option`
   — pinned `dev_test`'s option set to exactly `["fast"]`; widened to
   `["fast", "compare_reads"]` and corrected the docstring/assertion message
   that named only the one prior addition.

3. `tests/test_blast_radius_invariance.py::test_dedup_fingerprint_is_frozen[m27c512-full-runs-1-...]`
   and `::test_schema_bump_rekeys_no_frozen_hash` — the `m27c512-full-runs-1`
   fixture shape's frozen hash moved from `e4838f7bb1d3` to `6d3afbc52315`.
   Root cause: this fixture's `write`/`verify` steps land SKIPPED
   (`run_count=0`) under the fixed-return double regardless of `runs`, due
   to a UV-saturation gate unrelated to the read change — so the read step's
   `run_count == 1` was the ONLY signal that ever fired
   `repeat_policy_tag`'s degraded marker for this shape. With `OP_READ`
   removed from `_REPEAT_POLICY_OPS`, nothing fires it anymore, and this
   shape's fingerprint now collapses onto `m27c512-full-all-ok`'s (the
   `runs=2` sibling that hits the identical saturation gate) — both shapes
   behave identically in every way `dedup_fingerprint` reads, and `runs=1`
   vs `runs=2` was already making zero observable difference here before my
   change too (write/verify never dispatch either way). Updated the frozen
   literal and the builder's docstring to record why, per the test's own
   documented review discipline ("if deliberate, land the behaviour change
   and the re-key of this literal as SEPARATE commits, so the re-key stays
   a reviewable unit" — bundled into this one commit instead, since Task 3
   exists specifically to green the fallout of the just-landed deliberate
   change).

   This re-key does **not** touch any of the other 18 `FROZEN_HASHES`
   entries, including the general-case `--fast` proofs in
   `tests/test_chip_test.py` (`test_repeat_policy_tag_marks_a_single_run_plan`,
   `test_single_run_write_cannot_report_marginal`), which continue to prove
   `--fast` emits the degraded tag from the write step's own `run_count == 1`
   in the non-saturated case — the must-have property this quick task's
   threat model actually protects.
