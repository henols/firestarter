# Backlog 999.9 — repository rename: measured impact and sequencing

**Date:** 2026-09-13
**Raised during:** `/gsd-explore` — "what impact will it have if the repos are renamed so the meta repo is named firestarter and the fw repo is renamed to firestarter_fw"
**Status:** Analysis only. Nothing renamed, no code changed. Feeds Backlog **999.9** (gh#2), which already exists and is not superseded by this note.
**Method:** Direct inspection of the three working trees and the live GitHub / PyPI APIs on 2026-09-13. No research subagent was involved and no claim here is second-hand; every figure below is reproducible with the command noted beside it.

## The proposal

`firestarter_prom` → `firestarter`, and `firestarter` (firmware) → `firestarter_fw`. This is a **name swap**, not two independent renames: the slug `henols/firestarter` is vacated by the firmware repo and immediately re-occupied by the meta repo.

## Why it is worth doing — measured, not asserted

`gh api repos/henols/<repo>`, 2026-09-13:

| repo | role | stars | forks | watchers |
|---|---|---|---|---|
| `firestarter_prom` | intended front door since v1.35 | **0** | **0** | **0** |
| `firestarter` | firmware | 27 | 11 | 3 |
| `firestarter_app` | host CLI | 48 | 6 | 4 |

v1.35 made `firestarter_prom` the documented front door and moved all documentation to its wiki. Six weeks later it has no stars, no forks and no watchers, while 75 stars sit on the two components. The front door is not being found. That is the case for the rename, and it is stronger than a naming-aesthetics argument.

## The single destructive act

The two renames are **not** equally risky.

- `firestarter` → `firestarter_fw` breaks nothing. GitHub redirects git, web and API traffic from the old slug.
- `firestarter_prom` → `firestarter` breaks nothing **and its redirect is permanent**, because nothing will ever claim `firestarter_prom`. In particular `SUBMIT_REPO = "henols/firestarter_prom"` (`firestarter_app/firestarter/submit.py:62`) keeps working on every already-installed CLI, indefinitely.
- **Claiming `henols/firestarter` for the meta repo is the only destructive act in the plan.** It deletes the firmware repo's redirect. Everything in this note that can break, breaks at that moment and not before.

## Blast radius

### What actually breaks: three constants

`firestarter_app/firestarter/constants.py:8-16`:

```
FIRESTARTER_RELEASE_URL        = https://api.github.com/repos/henols/firestarter/releases/latest
FIRESTARTER_RELEASES_URL       = https://api.github.com/repos/henols/firestarter/releases
FIRESTARTER_RELEASE_BY_TAG_URL = https://api.github.com/repos/henols/firestarter/releases/tags/{tag}
```

They are consumed **only** by `firestarter_app/firestarter/firmware.py` — that is, only by the `fw` command. A stranded CLI loses firmware update and firmware version-check. Read, write, verify, erase, blank-check and `dev test` are untouched. The failure is one subcommand, not the tool.

### The failure is loud today, and that is not luck

`gh api repos/henols/firestarter_prom/releases --jq 'length'` returns **0**. The meta repo has git tags (`v1.35`, `v1.34`, …) but **zero published GitHub Releases**, and `/releases` lists Releases, not tags.

So after the claim, an un-updated CLI gets:

- `…/releases/latest` → **404** → `raise_for_status()` → caught at `firmware.py:268` → logged error, `(None, None)`.
- `…/releases` → **200 `[]`** → an empty firmware list.

Broken, but honestly broken. See the standing rule below for why this must stay true.

### What does not break at all

- **No CI.** No workflow in any of the three repositories hardcodes a repo slug. `grep -rn -A3 'actions/checkout' --include=*.yml` across all three returns no `repository:` line. The meta repo has **no `.github/workflows/` at all**. 999.9's goal text lists "CI/release workflows" among the things to repoint; that part is a no-op.
  - *Related staleness found in passing:* `.planning/codebase/STACK.md:140-150` describes a catalog-sync workflow that checks out `henols/firestarter` and `henols/firestarter_app` via `actions/checkout@v4`. That workflow does not exist. STACK.md is stale on this point.
- **Issue submission.** `SUBMIT_REPO` targets `firestarter_prom`, whose redirect is permanent (above). `submit.py` does not exist on `origin/main`, so this is a `beta`-only concern and is not urgent.
- **Package identity.** PyPI `firestarter` is the app and is unaffected by any GitHub rename.

### Reference counts in the meta repo

`grep -rInE 'henols/firestarter(\.git)?([^_a-zA-Z0-9]|$)'`, excluding `.git`, the submodules and the gitignored `.v1.34-arms/` scratch tree:

- **778** total references to the firmware slug.
- **672** of them under `.planning/milestones/` — archived milestone records.
- **~12 live tracked files**: `.gitmodules`, `README.md:27`, `.planning/PROJECT.md`, `.planning/STATE.md`, `.planning/ROADMAP.md`, and five `.planning/codebase/` documents (`STRUCTURE.md`, `STACK.md`, `INTEGRATIONS.md`, `ARCHITECTURE.md`, `TESTING.md`).

**The archived 672 should not be swept.** The standing rule that `.planning/`→`.planning/` citations are historical-by-intent applies with equal force here: those URLs record what the repository was called when the record was written. Repairing them destroys the evidence. This is a deliberate scoping decision, not an omission.

## The finding that changes the plan: `pip install firestarter` gives 2.0.7

`https://pypi.org/pypi/firestarter/json` → `info.version` = **`2.0.7`**.

The entire `3.0.0bNN` line (165 versions published, through `3.0.0b41`) is **prerelease** and therefore invisible to a default `pip install`. `origin/main` is that 2.0.7-era code: **948 commits** behind `origin/beta`, with no `submit.py` — but it *does* carry `FIRESTARTER_RELEASE_URL` pointing at `repos/henols/firestarter`.

Three consequences:

1. **The default-install population is the stranded population.** Not "users who neglect upgrades" — the ordinary result of following the install instructions.
2. **999.9's own validation plan is blind to this.** The item specifies *"full clean-environment install → query → locate release → download asset → flash → update-check."* A clean install resolves to 2.0.7, so that validation exercises `main`, not the branch being fixed. Repointing `beta` alone and validating this way would **pass while leaving the default install broken**.
3. **There is no in-band way to tell a stranded user to upgrade.** The app performs no self-version check of any kind — no PyPI probe, nothing (`grep -rn "pypi\|check_for_update\|version_check" firestarter/*.py`). The only signal a stranded user receives is `fw` failing.

## Standing rule this must produce

**Never publish a GitHub Release on the meta repo. Bare milestone tags only.**

Its present zero-Releases state is exactly what makes the post-claim failure a clean 404. Publish even one Release there and the failure mode inverts: `_compare_versions` (`firmware.py:272-288`) parses a tag like `v1.36` as PEP 440 `1.36`, evaluates `Version("3.0.0b28") >= Version("1.36")` as **true**, and reports the firmware as already up to date — for every stranded CLI, silently, forever. Loud-and-obvious becomes silent-and-permanent.

This risk is **latent today and armed by a single future action**, which is why it belongs in a durable rule rather than in the rename procedure.

## The `.gitmodules` archaeology trap

`.gitmodules:3` pins `url = git@github.com:henols/firestarter.git`. Git follows rename redirects, so this survives step 1 unaided. After the claim it does not: `git submodule update --init` resolves that URL to the **meta** repository and clones the parent into its own `firestarter/` child directory.

Fixing `.gitmodules` on `beta` and `main` does not fix **history**. Checking out `v1.35`, bisecting firmware history, or reading any pre-rename commit resurrects the old URL from that commit. This project does a great deal of archaeology, so the trap will be hit.

It cannot be solved — only documented and worked around. For an existing clone, `git config submodule.firestarter.url` in `.git/config` overrides `.gitmodules`. For a fresh clone at an old ref, clone with `--no-recurse-submodules` and set the URL by hand.

## Ordered procedure

**Phase A — nothing destructive; do whenever.**

1. Rename firmware `henols/firestarter` → `henols/firestarter_fw`. Redirect live; nothing breaks.
2. Meta: `.gitmodules` → new URL on `beta` and `main`; `git submodule sync --recursive`.
3. App **`beta`**: the three constants → `firestarter_fw`; also the two hardcoded URLs in `tests/test_firmware_install.py:383,494`. Leave `SUBMIT_REPO` alone — it is still correct.
4. App **`main`**: the three constants only (no `submit.py` on that branch). **Cut a 2.0.8 stable** whose sole change is the URL. This is the only thing that ever reaches today's default-install population, and it is operator-gated.
5. READMEs (firmware + app), `README.md:27`, and the five `.planning/codebase/` documents.

**Phase B — the gate.** Do not claim the slug on a calendar date. Gate it on a stable carrying the new URL having displaced 2.0.7. No telemetry exists; PyPI download-stats-by-version is the only available instrument. See the research question filed alongside this note.

**Phase C — the destructive act.**

6. Rename `firestarter_prom` → `firestarter`. The firmware redirect dies here.
7. Afterwards, at leisure: `SUBMIT_REPO` → `henols/firestarter` (cosmetic — the `firestarter_prom` redirect is permanent), the wiki URL, and the 102 in-repo `firestarter_prom.wiki` references.

## What 999.9 already covers

The existing item is sound. It already specifies firmware-first *"to free the name"*, requires that the app *"must not depend on GitHub's redirect"*, and requires a clear error when the endpoint is unreachable. This note does not replace it. The four gaps it does not encode are: the 2.0.7 validation blindness, the absence of a stated gate for the claim, the `.gitmodules` history trap, and that its "CI/release workflows" line is a no-op.

## Honest limits

- **Nothing reaches users who never upgrade.** Phase A and the gate shrink the stranded set; they do not empty it. The claim will permanently break `fw` for anyone who never moves off their installed version. The mitigating fact is the narrow scope — one subcommand, not the tool.
- **The gate has no precise instrument.** PyPI download stats are a proxy for installed base, not a measurement of it.
- **The `2.0.8` step is bounded in value.** It reaches users who upgrade *within* 2.x. It does nothing for someone pinned to 2.0.7 forever.
- **`firestarter_fw` as a name was not interrogated.** It is symmetric with `firestarter_app` and is what 999.9 already names, so it was taken as given. One residual incoherence worth noting: after the rename, GitHub `firestarter` means the meta repo while PyPI `firestarter` means the app.
