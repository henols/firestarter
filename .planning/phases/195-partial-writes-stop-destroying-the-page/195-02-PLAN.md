## Why a multi-chunk case is not optional

The host caps one `write_execute` call at the board's data-buffer size -- 512 bytes on `uno`, 1024
on `leonardo` -- and the firmware advances `handle->address` by `handle->data_size` between calls.
A single-call native case therefore cannot reach the boundary between two chunks, which is where
the third loss direction lives: with a start of `0x40`, a chunk of 512 and a page of 128, the first
chunk's final byte commits the page `0x200-0x27F` holding only `0x200-0x23F`, and the second chunk
re-opens and re-commits that same page holding only `0x240-0x27F` -- erasing bytes the first chunk
had just written, **inside** the range the operator asked for.

The existing `test_5v_page_write_execute_boundary_524288_512` already demonstrates the drive pattern:
call `firestarter_operation_main`, then reassign `h.address` and `h.data_size` and call again.
That is the faithful model of the chunked host path, and it is the documented workaround for the
buffer cap.

Recording density is three records per written byte plus eleven for the SDP prefix, so the 4096-entry
cap saturates at roughly 1361 data bytes. Every case below stays under it; assert
`bus_recording_saturated()` is false beside every count assertion anyway.

ASVS level 1; threats rated `high` or above block the phase.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host to firmware, one chunk at a time | The firmware sees `address` and `data_size` per chunk and never learns the total payload length, so it cannot reason about the write as a whole |
| chunk N to chunk N+1 | The firmware advances its own address between chunks; a chunk that is aligned is not evidence that its successor is |
| native stub recorder to the assertion | A saturated recorder silently truncates, which would make a count assertion pass on missing data |
| firmware source to the host gates that scan it | Two host test modules read firmware paths and fail open when a path moves |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-195-11 | Tampering | a chunk-boundary page destroyed inside the requested range | critical | mitigate | The multi-chunk case drives the handler twice with an advancing address and requires an error response and zero recording on both calls, so a fix that patched only the first and last byte of a single chunk cannot pass |
| T-195-12 | Repudiation | a boundary assertion passing vacuously on a truncated recording | high | mitigate | Every positive control asserts the saturation signal is false before asserting a count, and a verify leg counts the saturation assertions in the file |
| T-195-13 | Tampering | a guard written with a conjunction instead of a disjunction | high | mitigate | Three separate refusal cases -- start only, length only, both -- so a conjunction passes the single-clause cases and fails the combined one |
| T-195-14 | Denial of service | a zero-length chunk refused, regressing the empty-input path | medium | mitigate | An explicit acceptance case asserts an OK response and a zero recording count for `data_size` zero |
