## Tests

### 1. Decide how to correct the "release: published has never fired" claim, now known to be false

expected: The record is corrected, or a human explicitly accepts leaving it as-is.

**What the phase recorded (191-02, reused verbatim in 191-04 and the disposition record):**

> publish.yml has run 8 times in this repository's entire history, every one
> event=workflow_dispatch and zero release events ever
>
> — the trigger has literally never fired in this repository.

**What the live API actually returns** (`gh run list --workflow publish.yml --limit 30`,
re-checked independently during verification):

| run | event | conclusion | created |
|-----|-------|------------|---------|
| 34785081751 | workflow_dispatch | success | 2026-09-13T21:51:55Z |
| 34785081535 | **release** | failure | 2026-09-13T21:51:55Z |
| … 10 workflow_dispatch runs 2026-05-20 → 2026-08-02 … | | | |
| 20956549620 | **release** | **success** | 2026-01-13T12:22:40Z |

**13 runs total, not 8. Two of them are `release` events, not zero.** The claim is wrong on both
counts.

The 2026-01-13 `release`-event run is the load-bearing one: `displayTitle: "2.0.7"`,
`headBranch: 2.0.7`, `conclusion: success`. **That run is how 2.0.7 reached PyPI** — the same
2.0.7 this phase measured its fail-first baseline against in 191-01. The trigger did not merely
fire once; it fired and completed the publish, unaided.

**Probable root cause:** a `--limit` truncation. The sibling `release.yml` reading in
`evidence/191-stable-01-release-run.txt:10` was taken with `--limit 10`. Eleven `publish.yml`
runs existed before today, so a `--limit 10` listing shows the ten most recent and cuts exactly
one row — the oldest, which is the single `release`-event counterexample. The measurement was
truncated in precisely the place that inverted its conclusion.

**Why today's release-event run failed, and why that is not the old failure mode:** run
`34785081535` fired automatically when the operator created the GitHub release, at the same second
as the manual `workflow_dispatch` (`34785081751`). The two raced on the PyPI upload; the manual
run won and the automatic one failed with a "File already exists" collision on the sdist. It did
not fail because the trigger was suppressed. It failed because it was redundant.

**Consequences to weigh:**

1. The manual `gh workflow run publish.yml --field tag=2.0.9` step in 191-04 was most likely
   unnecessary — creating the GitHub release would have published 2.0.9 on its own, as it did for
   2.0.7. The manual dispatch is what caused the race.
2. The backlog item `2026-09-13-publish-yml-release-published-never-fires.md` rests on a false
   premise. Its title and body assert a defect that the evidence does not support. It should be
   corrected, re-scoped to the real (and much narrower) issue, or withdrawn.
3. The disposition record's D-05 item — "`main`'s stable release pipeline is left broken in two
   places" — is overstated by one. The `release.yml` auto-commit-vs-ruleset defect is real and was
   observed live this phase (`GH013`, run `34784468070`). The `publish.yml` trigger defect is not
   established.
4. None of this changes any ROADMAP success criterion. PyPI `2.0.9` is published and was verified
   independently, twice. This is an accuracy defect in the phase's record, not in its outcome.

**Why this needs a human:** amending a completed phase's evidence record is a judgement call, and
so is deciding what to do with a filed backlog item whose premise has collapsed. Note the irony
worth weighing: this phase was built end to end on the discipline of reading live state rather
than trusting a prior measurement, and this is a prior measurement it carried forward without
re-reading.
