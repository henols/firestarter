<objective>
Finish 999.9's chain on real hardware, and write down honestly what this phase did not do.

The fixture stopped at the downloaded asset. This plan takes a clean install of the stable this phase
just published, points it at the Leonardo on `/dev/ttyACM0`, and lets it do the thing the whole
milestone is about — check for firmware, fetch it from the renamed repository, and flash it. No guard,
no confirmation prompt, no question at flash time: D-09 is a standing operator instruction and the
board is a test board.

Then the phase record states, in words, the three things this does not achieve — because criterion 4
asks for exactly that, and a record naming only the obvious one papers over the other two.

Purpose: STABLE-02's chain is install → query → locate release → download asset → update-check, run
against the stable rather than a prerelease. The first four are 191-01/191-04's fixture. This is the
fifth, and it is the only leg that touches a board.
Output: a bench transcript and the phase disposition record.
</objective>

`-c/--avrdude-config-path`; there is **no** `--list`, no `--json` and no `--stable`/`--pre`.

`firestarter_leonardo.hex`, so the board/asset match is total. `HOME_PATH` is
`/home/vscode/.firestarter`, defined in `firmware.py`, and that directory also holds the operator's
own `config.json` and `reports/`.

**On `origin/main`'s `manage_firmware_update`, read directly and quoted so nothing is invented:** the
`Confirm.ask` prompt lives in the arm reached when **no flag** is passed and both a current and a
latest version were resolved. The `--install` arm proceeds without any prompt. A third arm proceeds
when no current version could be read and `--install` or `--force` was passed. After a successful
install the method removes the downloaded `.hex` itself.

**A Leonardo is exempt from this project's chip-out-before-sideload rule** — that rule is Uno-class
only. No chip handling is required for this leg.
