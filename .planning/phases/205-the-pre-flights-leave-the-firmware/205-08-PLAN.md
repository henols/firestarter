<objective>
Close CR-01: make the host write guard's erase exemption address-aware for protocol `0x06`, so a
`write -a <non-zero>` on an AMD/JEDEC NOR-unlock part is no longer exempted from every blank check —
and record, in the phase record, that this landed in Phase 205 rather than being deferred.

Purpose: Phase 205's whole premise is the roadmap's ordering rule — the host must gain the capability
before the firmware loses it. Plan 205-03 deleted an unconditional whole-device `mem_util_blank_check`
from `flash_nor_unlock_write_init` (commit `1cf1b22`). That call was the backstop that made the host's
address-blind exemption safe in practice: the firmware's own erase there is `flash_nor_unlock_erase_execute`,
which erases the WHOLE chip only when `handle->address == 0` and erases a single SECTOR otherwise. The
host's `is_erase_exempt` cannot tell those two cases apart, so for any non-zero `-a` on a
`FLAG_CAN_ERASE` protocol-`0x06` part — 190 of 190 shipped rows resolve erase-capable — the guard runs
no check at all against a region the erase may never have touched. That is a silent, irreversible
overwrite hazard reachable through an ordinary CLI option, and it is the one failed truth in
205-VERIFICATION.md.

The same hazard shape is already recognised and handled one command over: `cli_handlers.py`'s
`_erase_sector_blank_refusal_exit_code` (plan 205-01) refuses `erase -s <addr> -b` for exactly this
sector-versus-whole-device reason. It was never extended to `write`. This plan extends it — and takes
the opposite disposition, for a reason the code makes available: `write`'s guard is region-scoped and
`erase -b`'s is not.

Output: an address-aware predicate, a regression matrix that would have caught this, and a decision
record.
</objective>

<design_decisions>
Three points of latitude the gap left open, resolved here so no executor has to invent them. Each
carries a reversibility rating per REVERSIBILITY_GATES.

## D-G1: the predicate lives in `is_erase_exempt`, with a keyword-only `address`, threaded through `requires_blank_check`

**Decision.** Add a keyword-only `address: int = 0` parameter to BOTH `is_erase_exempt` and
`requires_blank_check`, the latter forwarding to the former. `write_eprom` resolves its own start
address once and passes it.

**Why the predicate and not only the caller.** `is_erase_exempt` is the function that makes the false
claim. Its docstring asserts "a part whose erase actually ran is exempt" — an assertion about the
erase's SCOPE that it has no input to justify. Fixing only `requires_blank_check` or only `write_eprom`
would leave a public, separately-tested, separately-importable predicate that still answers the
scope question wrong for the next caller who reaches for it. `write_blank_guard.py` is deliberately a
reusable pure-predicate module with its own public test surface; the wrong answer belongs to the
function that gives it.

**Why keyword-only with a default of `0`.** It is this phase's own established idiom: 205-04 added
`blank_check_requested: bool = True` as a keyword-only parameter to `write_eprom` and
`requires_blank_check` for exactly this reason, itself following Phase 203's `suppress_verdict_line`.
The default `0` is not an arbitrary sentinel — `0` IS the whole-chip-erase case, the one where the
exemption is genuinely sound, so every existing caller and all three existing direct tests keep their
current verdict without being edited.

**Reversibility: `reversible`.** An additive keyword-only parameter on an internal pure predicate,
with two production call sites, no wire change, and behaviour identical to today at the default.
Removing it later is a two-line revert.

## D-G2: a non-zero-address `0x06` write falls back to the ordinary region-scoped blank check, it is NOT refused

**Decision.** When the exemption is withdrawn, `requires_blank_check` returns `True` and the write
takes the ordinary guarded path: `_run_write_blank_guard` reads `[address, address + region_length)`
and refuses only if those bytes are actually non-blank.

**Why checking works here and refusal was necessary for `erase -b`.** `erase -b`'s post-erase check is
WHOLE-DEVICE and the host is told no sector size (`-s` takes only an address; no sector-size field is
threaded to the CLI), so after a sector erase a whole-device check fails by construction — a reliable
false negative. That is why `_erase_sector_blank_refusal_exit_code` refuses rather than checks, and its
docstring records the rejected alternative in exactly those terms. `write`'s guard has the property
`erase -b` lacks: it is REGION-SCOPED (Phase 203 D-04), reading precisely the bytes the write is about
to program. It therefore needs no sector-size knowledge at all, and the check it performs is strictly
more precise than the whole-device firmware check plan 205-03 deleted — same safety property, fewer
false refusals.

**Why not refuse anyway.** Refusal would be a new user-visible behaviour regression on 190 shipped
rows with no compensating safety benefit, on a family whose ordinary use includes `-a`.

**Reversibility: `reversible`** for the route taken — it withdraws an exemption and restores a check
that already exists and already ships; the only user-visible delta is that a genuinely non-blank target
region is now refused, which IS the restored safety property, and `-b` remains the documented escape.
**The REJECTED route — refusing a non-zero-address `0x06` write outright — would have been `one-way`:**
a user-facing contract change on 190 chip models, the kind that becomes load-bearing in scripts within
one release and cannot be walked back without a second contract change. It is recorded here as
considered and declined, which is why this plan carries no `checkpoint:decision`.

## D-G3: no sector-size model is invented; the conservative branch is taken

**Decision.** Any non-zero address on protocol `0x06` withdraws the exemption. No attempt is made to
narrow further by asking whether the write region lies inside the erased sector.

**Why.** Sector geometry is not knowable host-side. The chip database carries no sector-size field, and
205-RESEARCH.md § "Hazard: `erase -s <sector> -b` on protocol `0x06`" already recorded scoping-to-the-
sector as blocked in practice for that exact reason. Inventing a sector-size model the database does
not carry would be guessing in the unsafe direction on an irreversible operation. The conservative
branch costs one region-scoped read, which the write path already performs for every non-erase-capable
guarded part today.

**Reversibility: `reversible`.**

## D-G4: an absent or unparseable `-a` resolves to address `0`

**Decision.** `write_eprom` resolves `address_str` through `parse_address`; `None` yields `0`, and a
`ValueError` is caught and also yields `0`.

**Why this is not a fail-open hole.** An unparseable address cannot reach the wire at all: the write's
own `_setup_operation` calls `parse_address` on the same string, raises `ValueError`, returns
`(None, 0)`, and `write_eprom` returns `False` before any programming command is composed. No write
happens, so there is no exemption hazard to guard against — and treating a malformed address as
"non-zero, therefore check" would open a port and produce a verdict-2 transport failure in place of
today's clean argument error. This follows `require_non_negative_address`'s own explicitly stated rule
in this same module: a malformed address stays the existing handlers' job, and this module must not
change that established error contract. A NEGATIVE address is already refused earlier, by
`require_non_negative_address`, at both the CLI tier and inside `write_eprom`.

**Reversibility: `reversible`.**
</design_decisions>

<threat_model>
Configured level: **ASVS L1**, block on **high**. This gap is a **local data-integrity hazard** — a
silent, irreversible overwrite of a non-blank flash region on a family of shipped chip models, reached
through a legitimate CLI option by the machine's own operator. It is not a network, authentication or
session surface, and it is modelled at that shape rather than padded with inapplicable web controls.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator's `-a <addr>` -> `handle->address` (host -> firmware, serial) | The single field that decides whether `flash_nor_unlock_erase_execute` erases the whole chip or one sector. It crosses unvalidated in scope terms: the host sends it, the firmware branches on it, and before this plan no host-side code read it back to reason about what the erase actually covered. |
| the host guard's verdict -> the physical device | Since plan 205-03 deleted the firmware's write-init `mem_util_blank_check`, `requires_blank_check`'s answer is the ONLY thing between a `CMD_WRITE` and a non-blank flash region. There is no second opinion downstream. |
| `FLAG_CAN_ERASE` (a capability claim) -> "this region is blank" (a state assertion) | The defect's actual shape: a bit describing what the part CAN do was read as evidence of what the device IS. The two are different kinds of statement and the boundary between them is where the safety property leaked. |
| firmware erase-scope knowledge -> the host predicate that mirrors it | Duplicated knowledge across two repositories with no automated parity gate. Only a comment on each side and a test named after the firmware branch hold them together. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

Mitigated by task 1: the exemption is withdrawn when the algorithm is `NOR_UNLOCK_PROTOCOL_ID` and the resolved write address is non-zero, so the write takes the existing region-scoped guard read over exactly the bytes it is about to program.
