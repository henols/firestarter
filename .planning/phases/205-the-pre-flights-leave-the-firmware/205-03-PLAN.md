<objective>
Delete the four blank-check call sites and then the machinery itself, in two commits, each carrying
every gate its own edits redden.

Purpose: this is FWBLANK-01, FWBLANK-02 and FWBLANK-03. The ordering inside it is not stylistic. The
call sites go first because a function cannot be deleted before its callers, and because the four
deletions together are what move the branch-inventory golden and retire the region-scoped census gate —
one coherent, reviewable unit that a bisect can land on. The machinery goes second, in the commit that
also replaces the retired gate's structural legs with absence legs and repairs every comment whose
referent has just disappeared.

The measured hazards this plan exists to avoid are specific. `memory.cpp`'s deletion is two
non-contiguous spans with a permanent survivor sitting between them, so a single-range cut takes
`mem_util_operation_end` with it. CONTEXT's span for the region form is four lines long and would orphan
the wrapper's doc comment while leaving five lines of the wrapper. The two golden sites this sweep
removes share an identical signature triple, so a dictionary-keyed golden comparison silently keeps only
one of them. And the module whose own docstring instructs it to retire here holds the only mechanical
fence around a symbol that must survive the phase.

Output: a firmware with no blank-check pre-flight and no blank-check machinery, a re-derived golden, a
surviving gate that now proves absence rather than shape, and two green commit boundaries.
</objective>

The bounded cost, stated rather than discovered: between task 1 and task 2 the definitions of the

never absent.

the same question and chose re-anchor, with the reasoning that retiring would drop the survivor fence
"for the whole of Phase 204 into Phase 205, and Phase 205 is the phase most likely to widen it", and
that "Phase 205 deletes the functions and retires the module then, which is the phase where retiring it
is free". This is that phase, and the migration is what makes the retirement free.

Measured: both have their only callers inside `mem_util_blank_check_region`, so after task 2 nothing in

guards become always-true. Removing them changes `operation_utils.cpp`'s control flow, which is outside
FWBLANK-01 through 05, for zero flash — they are `static inline` in a header and an uncalled one emits
no code. The measured −518 B delta was taken with them kept. What this plan owes is honesty at the site,
not a deletion: the guard comments must say the mechanism is vestigial rather than restate a live claim.

**Fork D — `PROTOCOLS.md:321` and `firestarter.h:61-64` are rewritten HERE, in task 2, not deferred to

04. Measured against the gate this plan installs, deferral is not available: task 2's absence check is a
repository-wide `git grep` including documentation and comments, exactly as the survival module's own

in a case label". `PROTOCOLS.md:321` names `mem_util_blank_check`, and `firestarter.h:61-64` names both
`mem_util_blank_check` and `mem_util_blank_check_region`, so either one left behind turns task 2's
