READING 2 -- the threshold boundary
------------------------------------

capture_date: 2026-09-14T10:27:15Z
command: curl -s --max-time 90 --fail-with-body -G 'https://sql-clickhouse.clickhouse.com/' --data-urlencode "user=play" --data-urlencode "query=SELECT (fixed + at_risk) > 0 AND fixed * 10 >= 9 * (fixed + at_risk) AND at_risk <= 10 AS trigger_met FROM values('fixed UInt64, at_risk UInt64', (90,10), (89,10), (99,11), (0,0)) FORMAT TSV" | paste -sd, -

output: 1,0,0,0

This predicate is character-identical to the trigger expression the script carries. The four
tuples cover the boundary and one step either side.
(90,10): exactly 90% share with the floor exactly at 10. Reads MET.
(89,10): 89.0% share with the floor satisfied. Reads NOT MET.
(99,11): the share leg satisfied, with the floor exceeded by one. Reads NOT MET.
(0,0): the zero-denominator case. Reads NOT MET. The leading `(fixed + at_risk) > 0` conjunct
stops it before any division happens.
The boundary is inclusive on both legs. No result here depends on float rounding. Every
comparison is exact integer arithmetic.

`rows_matched` is 0. `fixed_share_pct` is the null marker `\N`. `trigger_met` is 0.
`window_end` degenerates to the 1970-01-01 epoch — the result of `max(date)` over an empty set.

An aggregate-only query always returns exactly one row. Counting output lines can therefore
never detect an empty window on its own. The `rows_matched` column carried inside the query is
what detects it instead.

In the script, that column is read before any verdict line prints. On zero rows the script
exits 2 and prints no verdict.

This shell-side branch was proven by two things: the source of the script, and the line-order
assertion in the plan's verify block, which shows the `rows_matched` guard appears in the file
before the `TRIGGER:` line. It was not proven by running the script itself against a
substituted project name — the script takes no argument and holds one fixed query, so that path
cannot run through the committed tool directly. No claim is made here that this shell branch
ran. Only the SQL-layer behaviour it depends on ran, and its result is recorded above.

output: curl_error_rc=22

`curl --fail-with-body` turns a ClickHouse server error into a non-zero exit status. It still
prints the server's own message.

This is why the script captures the call as `if ! body="$(curl ...)"; then`, rather than
letting `set -e` abort silently. The failure branch reads `$body`. The server's own
`UNKNOWN_FUNCTION` text, or any future error text, reaches whoever reads the terminal. The
branch also names the two recorded fallbacks — PyPI's BigQuery public dataset and the raw
`pypi.pypi_raw` table. A reader who meets a dead endpoint has a route instead of a dead end.

As with READING 3, this error arm was proven by source inspection. The `if !` capture form and
the fallback text are present in the file. It was not proven by forcing the committed script
itself to fail — its query is fixed, so this probe used a deliberately broken query instead.

All three readings agree with the script committed in task 1. No adjustment to the script was
needed.
