Set the override BEFORE `submodule update --init`. This order is the point: `git submodule init`
preserves an existing `submodule.<name>.url` in .git/config instead of re-copying it from
.gitmodules. Setting the override first means the update honours it. Setting it after `init` (or
after `update`) would already have cloned the wrong repository.

  $ git config submodule.firestarter.url git@github.com:henols/firestarter_fw.git

config_url(firestarter) AFTER override: git@github.com:henols/firestarter_fw.git

  $ git submodule init firestarter
  (no output)
  $ git config --get submodule.firestarter.url
  git@github.com:henols/firestarter_fw.git

`submodule init` did not clobber the override -- it preserved the value already in .git/config
rather than re-reading .gitmodules. This is the mechanism the workaround depends on.

  $ git submodule update --init --depth 1 firestarter
  Cloning into '/.../fresh/firestarter'...
  From github.com:henols/firestarter_fw
   * branch            4f73c80cfa2915fb22812dde55b2923a86120c5f -> FETCH_HEAD
  Submodule path 'firestarter': checked out '4f73c80cfa2915fb22812dde55b2923a86120c5f'

Child directory confirmed non-empty before reading its remote (an empty firestarter/ would cause
`git -C firestarter <cmd>` to silently walk up and answer for the parent repository instead):

  $ [ -n "$(ls -A firestarter)" ] && echo non-empty

  $ git -C firestarter remote get-url origin

  $ git -C firestarter rev-parse HEAD

Discriminator: the checked-out ref's own .gitmodules names the OLD slug
(git@github.com:henols/firestarter.git), and the child ended up cloned from the NEW one
(git@github.com:henols/firestarter_fw.git) purely because the .git/config override was set before
the update ran. That gap between what the ref declares and what actually got fetched is the entire
workaround.
