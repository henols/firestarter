<objective>
Land the host-side pre-write blank guard as one working end-to-end path: a write to a non-blank
region of a guarded, non-erase-exempt part is refused by the host, in one line, naming the first
non-blank address and its value, before any programming command reaches the wire — and a write into
a blank region of that same non-blank part still proceeds.

Purpose: this is the tracer slice for Phase 203. It wires every layer the phase touches — a new pure
predicate module, an additive field on Phase 202's compare accumulator, an additive reporting switch
on the one compare drive, the guard call inside `EpromOperator.write_eprom`, and a fake-serial test
harness that drives the genuine operator through a real READ main phase. Proving the architecture
end-to-end here means a dead end costs one commit, not five.

Output: `firestarter/write_blank_guard.py`, `CompareResult.first_actual`, an `on_result` switch on
`_drive_region_compare`, the guard block in `write_eprom`, and `tests/test_write_blank_guard.py`
carrying the wire-level ordering assertions criterion 1 and criterion 5 need.
</objective>

<design_forks_resolved>
The five open forks RESEARCH reported without deciding. Each is resolved here, with the reasoning
recorded so the executor does not re-litigate it and a later reader can see why.

**Fork A — predicate shape: form A2 (allowlist, plus absent-key fail-closed).**
`is_guarded_protocol` returns True when the wire dict's `algorithm` is one of the five ids D-01
names, and True when `algorithm` is absent or `None`. A known-shaped but unlisted id (only reachable
through a user-supplied `~/.firestarter` database override — every shipped row resolves to one of the
twelve censused ids, and the one `0x34` row is refused by `resolve_chip` before a wire dict exists)
is **not** guarded. Where D-01 and D-05 disagree, D-01 wins: "preserve today's coverage" is the
operator's load-bearing instruction, and an id the firmware never blank-checked is by definition
outside today's coverage. D-05's absent-key clause is honoured in full, because that is the clause
D-05 can actually reach from the `dev` and test callers that hand-build dicts. D-02's pinning test
(plan 02) encodes this exact choice.

**Fork B — refusal mechanism: a `False` return, not a typed exception.**
`ClickException.exit_code == 1` for every type `map_typed_errors` maps, so an exception cannot express
D-13's exit 2 anyway. More decisively: `write_eprom` today never raises on a not-blank refusal — it
returns `False`, and `tests/test_chip_test_uv_slot_write.py` documents that non-raising contract as
the thing its double models. `chip_test._dispatch_multi_run` and `write_cycle_eprom` both call
`write_eprom` expecting a bool; a raising guard would turn a recorded failed step into a traceback,
which is exactly the `dev test` behaviour change D-07 forbids. So: the guard logs the D-10 sentence at
`logger.error` and returns `False`. The `return False` sits **before** the `with
self._operation_context(...)` block, so the generic `Write to X failed.` line at the end of
`write_eprom` never runs and D-11's one-line property holds structurally. The transport arm is carried
as a return value on the new `last_write_guard_verdict` attribute (plan 03 reads it).

**Fork C — `--verify` placement: the CLI tier** (decided here, implemented in plan 03). `write_eprom`
keeps `-> bool`, so the ~40 bool-valued test sites and the documented `chip_test.py` PRECONDITION
contract are untouched.

**Fork D — the guard read shows no progress bar.** A bar appears by default. Suppress it with the
`consistency_check_eprom` precedent (swap `progress_callback` to a truthy no-op, restore in a
`finally`). Reason recorded at the site: the guard read is not an operation the operator asked for,
and a bar that stops part-way and is then followed by a refusal reads as a failure of the read rather
than a refusal of the write. `--verify`'s own read keeps its bar — that one the operator did ask for.

**Fork E — D-17's figure is a derivation over a recorded measurement**, written up in plan 04.
</design_forks_resolved>

Build the whole refusal path, production quality, in one slice. Five edits and one new test module.

**(1) New module `firestarter_app/firestarter/write_blank_guard.py`.** Copy `flash4_erase_gate.py`'s
file shape verbatim: the project/copyright header, then a module docstring with four movements —
title, why this policy exists, why it is a pure predicate (wire dict in, decision out, no I/O, no
serial, no environment reads), and why its fail polarity is what it is. The fourth movement is the
mirror of `flash4_erase_gate`'s: this module fails **CLOSED**, and it must name
`flash4_erase_gate.is_flash4`'s opposite polarity explicitly, exactly as `page_size_gate` already
does for its own case. The reason the polarities differ is D-05's and belongs in that paragraph:
`flash4_erase_gate` guards an availability property, this guard is the whole safety net after Phase
205, and its worst case is an unnecessary read plus a refusal the operator clears with the documented
bypass flag.

Module constants, as `frozenset` literals following `page_size_gate._WRITE_OPERATIONS` and
`jp5_gate.DAMAGE_CAPABLE_OPERATIONS`:
- `GUARDED_PROTOCOL_IDS = frozenset({0x06, 0x07, 0x08, 0x0B, 0x10})` — carry a comment block naming
  what each id is and the firmware file whose write-init blank-checks it (`eprom.cpp` for
  0x07/0x08/0x0B, `flash_nor_unlock.cpp` for 0x06, `flash_intel.cpp` for 0x10). Per D-01 this set is
  defined by what the firmware pre-flights today, not by `FLAG_CAN_ERASE`.
- `SRAM_PROTOCOL_IDS = frozenset({0x0E, 0x27, 0x28, 0x29})` — the SRAM/FRAM named exemption. Reason
  at the site: no blank state exists for these parts.
- `NAMED_EXEMPT_PROTOCOL_IDS` — the union of `SRAM_PROTOCOL_IDS`, `{FLASH4_PROTOCOL_ID}` and
  `{SDP_PROTOCOL_ID}`. Import `FLASH4_PROTOCOL_ID` from `firestarter.flash4_erase_gate` and
  `SDP_PROTOCOL_ID` from `firestarter.sdp_capability` — D-06 forbids a second copy of either
  literal. Reason at the site for each: 0x05 auto-erases per page and its `FLAG_CAN_ERASE` is
  deliberately cleared for a hardware-safety reason so the flag can never be read as a blank-state
  signal; 0x0D auto-erases per page too. `NAMED_EXEMPT_PROTOCOL_IDS` is documentation and the pinning
  test's other half — the decision itself is the allowlist.
- `_REFUSAL_FORMAT = "Refusing write to {chip_name}: not blank at 0x{address:06X}, v: 0x{value:02X}."`

Functions, all fully annotated (`from __future__ import annotations`, `from typing import Any,
Mapping` with a live `# noqa: UP035`, matching `flash4_erase_gate`):
- `effective_flags(programmer_data, operation_flags) -> int` — returns
  `int((programmer_data or {}).get("flags", 0) or 0) | operation_flags`. This reproduces
  `_setup_operation`'s own effective-flags expression; a comment here must name that site and the
  comment there must name this function, because two expressions for one quantity is how drift
  starts. `flags` is a key `convert_to_programmer` always emits, and defaulting it to 0 is the
  fail-closed direction (no erase capability claimed means no exemption).
- `is_guarded_protocol(programmer_data) -> bool` — reads `algorithm` and nothing else. Absent,
  `None`, or a falsy dict all return True (D-05 fail-closed); otherwise
  `algorithm in GUARDED_PROTOCOL_IDS`. The docstring must record Fork A's resolution: an id in
  neither the guarded set nor the named exemptions is **not** guarded, because D-01's "preserve
  today's coverage" outranks D-05's unrecognised-id clause for an id the firmware never checked, and
  that case is only reachable through a user-supplied database override.
- `is_erase_exempt(programmer_data, operation_flags) -> bool` — True when `effective_flags` has
  `FLAG_CAN_ERASE` set and `FLAG_SKIP_ERASE` clear. The docstring states that this is the static
  per-invocation form of D-01's "a part whose erase actually ran is exempt", derived from the
  firmware's own `if FLAG_CAN_ERASE and not FLAG_SKIP_ERASE` erase gate, and that `dev write-cycle`
  reaches the same conclusion through the flag proxy rather than by observation.
- `requires_blank_check(programmer_data, operation_flags) -> bool` — False when `FLAG_SKIP_BLANK_CHECK`
  is set in `effective_flags` (WRITE-03 / D-09: the documented bypass is the blank-check flag, and
  `FLAG_FORCE` is deliberately not consulted here), False when `is_erase_exempt`, False when not
  `is_guarded_protocol`, True otherwise.
- `refusal_text(chip_name, address, value) -> str` — per D-12 the refusal text belongs in this
  module and is built from `_REFUSAL_FORMAT` rather than assembled at the raise site, so a test can
  assert the exact sentence instead of a substring of a log line. Built from `_REFUSAL_FORMAT` with
  `chip_name.upper()`, following the house style at all three sibling sites. Its docstring states
  D-10's three properties: host-voiced, carries the first non-blank address and its value, and
  carries no remedy clause — an operator who reads the way out at the refusal site can route around a
  correct refusal.

The module must read **only** the `algorithm` and `flags` keys. Never `electrical-type`, never
`protocol-id`: the programmer wire dict carries neither, which is why `check_eprom_blank`'s SRAM
short-circuit is inert in production today. State that at the site.
