<objective>
Give `write` an opt-in `--verify` that reads the written region back through Phase 202's comparison
engine, reports one combined verdict line that never says "successful", and carries Phase 202's
0/1/2 exit contract for that invocation only. `--full` rides along with the meaning it already has on
`verify` and `blank`.

Purpose: WRITE-04 and WRITE-05, and roadmap criterion 4. This is also the phase's one-way door — the
exit-code contract is a published CLI surface that Phase 207's REL-04 will document in the wiki — so
it opens with a decision checkpoint.

Output: `--verify` and `--full` on `write`, four verdict-line constants, `suppress_verdict_line` on
both operator methods, and `tests/test_write_verify.py`.
</objective>

<exit_code_contract_resolved>
D-13's text cannot be implemented as written, because two of its clauses overlap on one real case.
It says exit **1** means "the write failed or the comparison mismatched" and exit **2** means "a
transport or hardware failure anywhere in the invocation, including the guard read". A write that
fails *because the port drops mid-write* satisfies both. The overlap has to be resolved before any
code is written, and the resolution is recorded here rather than left to the executor, because it is
the substance of the one-way door Task 1 puts to the operator.

**Resolved by cause, not by phase.** The exit code says *why the invocation ended*; the verdict line
says *what happened to the chip*. Under `--verify`:

| # | What happened | Verdict line | Exit |
|---|---|---|---|
| 1 | the guard refused — the region was not blank | the guard's own one line, nothing after it | 1 |
| 2 | the guard read failed for a transport or hardware reason; the write never ran | did-not-write | 2 |
| 3 | the write was attempted and failed for a transport, connection or hardware reason | did-not-write | 2 |
| 4 | the write was attempted and failed for a firmware-decided or host-decided reason | did-not-write | 1 |
| 5 | the write landed; the read-back failed for a transport or hardware reason | could-not-verify | 2 |
| 6 | the write landed; the read-back completed and mismatched | mismatch | 1 |
| 7 | the write landed; the read-back matched | verified | 0 |

Three consequences follow, and each is load-bearing:

**Arm 3 is the one a plan review found missing, and it is the arm that matters most.** The write is the
longest leg of the invocation and the one under hardware stress, so it is the *likeliest* place for a
transport failure, not an exotic one. Excluding it would make the mandated `--verify` help sentence —
"a transport or hardware failure anywhere in the invocation" — false on the most probable case, and it
would bake in exactly the outcome this plan's own threat register rates high and undertakes to
mitigate (T-203-11: a caller that treats 2 as 1 retries a write onto a chip whose state is unknown).
A product that hands a script exit 1 after a mid-write port drop *is* that caller's bug, committed on
the caller's behalf.

**Arm 2 changes an earlier reading of this plan.** A guard-read transport failure previously mapped to
the could-not-verify line. Nothing was written in that case, so that line asserted a landing that never
happened — the same class of claim WRITE-05 and T-203-10 exist to prevent. It now maps to the
did-not-write line, keeping exit 2.

**No fifth constant is minted.** Arms 2, 3 and 4 share the did-not-write line and differ only in exit
code, so the four constants named above still cover D-14's three-way distinction plus the
split-by-cause fourth. The underlying cause is already visible in the log — `_run_state_machine`
emits `Communication error during …` or `Programmer error during …` — so the operator is not asked to
infer it from the exit code.

**What this does not do.** It does not reopen Fork B. `write_eprom` keeps its `-> bool` return type;
the cause travels on a transient attribute, the shape the codebase already uses for
`last_firmware_error_code` and the shape plan 01 already chose for `last_write_guard_verdict`. The
roughly forty bool-valued test sites and `chip_test.py`'s documented PRECONDITION contract are
untouched, and `dev test` still records a failed step rather than raising (D-07).

**If the operator picks `narrow-d13` at Task 1 instead**, arm 3 collapses into arm 4 (exit 1), the
`last_write_attempt_verdict` work in Task 2 is dropped, and the narrowing must then be stated
explicitly in the `--verify` help text — it may not keep the words "anywhere in the invocation" — and
recorded in the phase record as a deliberate reduction of D-13's stated scope. A silently narrowed
contract is not an acceptable outcome of that option.
</exit_code_contract_resolved>

  <name>Task 1: Confirm the `--verify` exit-code contract before it is published</name>
  <decision>
`firestarter write --verify` will opt that invocation into Phase 202's three-code contract, while
plain `firestarter write` keeps its existing **0 / 1** contract unchanged. One command will therefore
carry two exit contracts, selected by a flag, and the `--verify` help text will say so.

D-13's own wording has to be disambiguated before it can be implemented: "1 the write failed" and
"2 a transport or hardware failure anywhere in the invocation" both describe a write that fails
because the port drops mid-write. This plan resolves the overlap **by cause, not by phase** — the exit
code says why the invocation ended, the verdict line says what happened to the chip:

- **0** — the write landed and the read-back matched.
- **1** — the invocation ended for a reason the host or the firmware decided: a blank-guard refusal, a
  firmware ERROR frame during the write, a malformed address, or a read-back that completed and
  disagreed.
- **2** — the invocation ended because the transport or the hardware failed, in **any** phase: the
  guard read, the write itself, or the read-back.

The full seven-arm table is in this plan's `exit_code_contract_resolved` section. The third bullet is
the part a plan review found missing on the first pass: the write is the longest and most
hardware-stressed leg of the run, so a transport failure there is the likeliest one, and reporting it
as a plain failure would be the same mistake this plan's threat register (T-203-11) undertakes to
prevent.
  </decision>

  <action>
Add one additive keyword-only parameter to each of the two operator methods, and prove the
`last_write_guard_verdict` tri-state the CLI tier will read.

**`write_eprom`.** Add `suppress_verdict_line: bool = False` as a keyword-only parameter. When true,
skip the whole verdict block at the end of the function — both the success line and the failure line.
The default keeps every existing caller byte-identical. Document at the site that this exists so the
`--verify` path can print one combined line instead of two, that D-14 requires the word `successful`
to be absent from a `--verify` run, and that suppressing the line rather than rewording it is what
makes the absence structural: a later edit to one of the CLI's verdict lines cannot reintroduce the
word, because the word does not live on that path at all.

**`verify_eprom`.** Add the same keyword-only parameter with the same default and the same treatment
of its own two verdict lines. Do **not** touch the compare range lines — those come from
`_drive_region_compare`'s renderer and are the report `--verify` is supposed to produce on a
mismatch.

**`last_write_guard_verdict`.** Plan 01 introduced the attribute. Confirm and pin its four states with
tests here, because the CLI tier's exit-code branch depends on them: `None` when the guard did not
run (exempt part, bypass flag, no region), `0` when the guard read completed and the region was blank,
`1` on the refusal, `2` when the guard read hit a setup or transport failure. Add a short docstring on
the attribute stating that it is transient per-invocation operator state in the same family as
`last_firmware_error_code`, that the CLI tier must read it immediately after the `write_eprom` call,
and that it is what lets `write_eprom` keep its `-> bool` return type instead of forcing a bool-to-int
migration across the roughly forty test sites and the documented PRECONDITION contract in
`chip_test.py`.

**`last_write_attempt_verdict`.** Add a second transient attribute beside `last_write_guard_verdict`,
initialised to `None` in `__init__` and reset to `None` at the very top of `write_eprom` — before the
pure gates — so a prior invocation can never leak into this one and a gate that raises leaves it
`None`. It carries the write phase's own failure cause the way the guard attribute carries the guard
read's. It exists because D-13's exit 2 covers a transport failure in *any* phase, the write included,
while Fork B keeps `write_eprom` returning `bool` and therefore leaves it no return channel for a
cause. Assign it on every path through the write phase:

- At the `if not cmd_data:` test inside the context, classify before returning. For a `COMMAND_WRITE`
  only two of `_setup_operation`'s three `(None, 0)` returns are reachable — the `parse_address`
  `ValueError` arm, reachable only when `address_str` is truthy, and the connect-failure arm. The
  `parse_size` arm is gated on `cmd == COMMAND_READ`. So: when `address_str` is truthy and calling
  `parse_address` on it raises `ValueError`, the cause was the operator's input — record 1. Otherwise
  the connection failed — record 2. Do the classification by calling `parse_address` a second time
  inside a `try`/`except ValueError`, purely to read the cause. Do not change `_setup_operation`, do
  not move or duplicate its log line, and do not alter the order in which anything is reported.
  `parse_address` is already imported in this module.
- Immediately after the `_run_state_machine` call and **before** the `--skip-sdp-unlock` ack block:
  when `is_ok` is false, record 2 if `self.last_firmware_error_code` is `None` and 1 otherwise; when
  `is_ok` is true, record 0. `_run_state_machine` clears that field on entry and sets it only on its
  `EpromOperationError` arm — a real firmware ERROR frame — while its `(SerialError,
  SerialTimeoutError)` arm deliberately leaves it `None`. This reads an existing, already-narrow
  contract that `__init__`'s own comment states; it does not invent one, and it must not widen it.
- Record the ordering reason at the site: the ack block flips `is_ok` to false after a run that
  succeeded on the wire, and because the verdict is already 0 by then that failure surfaces as exit 1.
  Nothing on the wire failed, so calling it a transport failure would be wrong.

Give the attribute a docstring line naming its four states and stating that the CLI tier must read it
immediately after the `write_eprom` call, in the same breath as `last_write_guard_verdict`, and that
the pair is what lets `write_eprom` keep its `-> bool` return type.

**Exhaustiveness pin.** Add a test asserting `_setup_operation`'s source carries exactly three
`(None, 0)` returns, and a source-order test asserting that the post-state-machine verdict assignment
in `write_eprom` precedes the `MSG_WARN_SDP_UNLOCK_SKIPPED` block. Both are cheap, and both protect a
claim the classification depends on: a fourth failure arm added to `_setup_operation` later would
otherwise be silently classified as a connection failure, and a verdict assignment that drifted below
the ack block would silently reclassify a host-decided failure as hardware trouble. Say at each test
what it protects — a source-shape assertion with no stated purpose reads as noise and gets deleted.

**Tests.** Create `firestarter_app/tests/test_write_verify.py` and author the ten `behavior` cases
there, on plan 01's fake-serial harness for the drive cases and with `caplog` for the line-suppression
cases. Assert suppression by the **absence of the whole line**, not by a substring of it, and add one
case asserting that a default-parameter `write_eprom` still logs its success line — otherwise a
suppression that fires unconditionally passes every other leg.
