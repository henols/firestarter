<objective>
Observe both host-firmware compatibility directions on real silicon, and record what was observed
with enough precision that nobody has to trust it.

Purpose: criteria 4 and 5 say "observed on the bench". That wording exists because the refusal path
and the compatibility claim are both easy to argue from code structure and the milestone explicitly
refuses that. The new-host-against-old-firmware direction proves the ABSENCE of a problem, so its
value is entirely in having been run (D-11). The old-host-against-new-firmware direction proves a
refusal a real user can act on, which is a claim about the artifact a real user actually has — the
published wheel, not a reconstruction (D-08). And the no-hardware-side-effect half is proven by
read-back equivalence on a part with known content, because the failure a blank-check ordinal retiring
badly would produce is a silent erase, which no amount of reasoning about where the refusal fired can
rule out (D-09).

Plan 01 already proved the upload path works and ran a single-ordinal version of the refusal leg with
the other ordinal as a live control. This plan runs the full four-role matrix with both ordinals
retired, and produces the record D-07 requires: the substitution statement, the sha of every artifact
that played a role, three whole-device digests, two refusal transcripts, and the Leonardo-only
coverage gap stated rather than hidden.

Output: `204-BENCH-MATRIX.md`, plus the per-target flash and RAM figures that give Phase 205's own
measurement a real baseline.
</objective>

<design_forks_resolved>
**Fork A — the pre-204 firmware is a LOCAL BUILD of the pre-204 commit, from a detached worktree.**
CONTEXT.md leaves the choice between a released asset and a local build. The local build wins on three
counts: the released asset was never fetched and is an assumption; the beta build workflow has a
recorded zero-asset failure mode that a rerun cannot repair; and a build of the exact pre-204 sha IS
the pre-204 source rather than a plausible stand-in, which is what D-07's "name the sha that played
each role" is actually asking for. A worktree is safe here because this repository has no nested
submodules.

**Fork B — the bench sequence is a single unattended run with the part seated throughout.** Leonardo
is exempt from the chip-out rule, so the four-role matrix needs no operator hands between legs, and
running it as one sequence is what makes the three read-back digests comparable: the part never leaves
the socket between the first read and the last.

**Fork C — two firmware flashes, no chip swaps.** Flash pre-204, run the new-host leg, flash post-204,
run the old-host legs. A third flash would buy nothing, and every flash is a moment where the record
of which artifact is on the board can be lost.

**Fork D — `~/.firestarter/` is snapshotted by MOVE and restored by move, with the restore made
robust to a failure in between.** The environment variable does not prevent the write, so isolation
has to be filesystem-level. Never delete: if the directory exists at the start it is the operator's,
and it must be in the same state at the end.

**Fork E — the flash and RAM figures are recorded as a DATA POINT, not claimed as a requirement.**
Phase 205's criterion 4 owns the measured reclaim. Recording the Phase 204 figures here gives that
measurement a real baseline instead of a Phase 201-era one, and costs one build per target.
</design_forks_resolved>

<probe_disposition>
This plan owns three rows of the spec-less probe ledger recorded in full in `204-01-PLAN.md`. All
three are `unclassified` and therefore stay **unresolved**; they are surfaced here as flagged
assumptions rather than auto-resolved.

**Flagged assumption (probe row 8, FWCMD-06, unclassified).** "An explicit refusal with no hardware
side effect — never silence, never a hang" is read as three separately observable properties: a
non-empty coded message reaches the operator's terminal; the part's content is byte-identical
afterwards; and the command returns within a bounded time rather than stalling. Each is measured
separately. "No hardware side effect" is deliberately NOT read as "no rail was energised", because the
voltage monitors do not route to the socket and a reading from them proves nothing about what the part
saw — that is why D-09 chose read-back equivalence instead.

**Flagged assumption (probe row 9, REL-02, unclassified).** "Performs `verify` and `blank` correctly"
is read as: each command completes, returns an exit code consistent with what is actually on the part,
and its output describes the part rather than reporting a protocol failure. The W27C512 carries
content, so `blank` is expected to report not-blank and `verify` against a matching image is expected
to report a match; both are "correct" outcomes and neither is a refusal.

**Flagged assumption (probe row 10, REL-03, unclassified).** "A refusal the user can act on" is read
as: a message that names the failure and the offending ordinal, distinguishable from a transport
error, delivered promptly. It is NOT read as a message that names the version boundary — D-05 records
that the operator sees an unknown-command message, that this reads more like a corrupt frame than a
version boundary, that the cost was accepted deliberately, and that Phase 207 owns naming the boundary
for a human in the wiki. Record the actual wording verbatim so that phase has real text to work from.

**Flagged assumption (A1, the shared host config).** The claim that the app writes to the home config
directory regardless of the environment variable was carried from the project record and not re-probed
against the published wheel specifically. This plan does not rely on the variable: it isolates by
moving the directory.

**Flagged assumption (A4, the flash ceiling).** A pure removal can only shrink the image, so the
post-sweep build fitting the Leonardo's real ceiling is near-certain rather than measured. It is
measured here anyway, because the milestone premise is flash reclaim and no gate measures it.
</probe_disposition>
