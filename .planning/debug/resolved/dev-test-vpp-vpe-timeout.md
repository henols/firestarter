  implication: "This is a THIRD, more severe variant of hazard (a)/(b) that our repro runs did not trigger (because in every trial, `consume_remaining_input`'s 0.5s+ drain window happened to fully outlast the watchdog before the real JSON command was sent, so the new command was never sent WHILE handle.cmd was still non-idle). But it is a live latent hazard: if a probe or command send happened to race INTO the still-busy window (e.g. a faster host, a shorter CONNECTION_STABILIZE_DELAY, or a firmware watchdog that takes longer for other reasons), `hw_read_voltage`'s own `op_get_message` scan could partially or fully consume the NEW connection's COBS-framed JSON bytes as junk (falling through 'default: read and discard'), corrupting/desyncing the new command's frame before the CMD_IDLE parser ever sees it -- a genuine instance of hypothesis (b), just not the one we observed today. ## Recommended Fix Direction

CONFIRMED MECHANISM: Hypothesis (a) -- reopening /dev/ttyACM0 on this Leonardo does NOT reset the MCU -- is the primary, hardware-confirmed cause (5/5 reproductions, byte-level evidence of a live second firmware command instance leaking frames onto the new connection). Hypothesis (b) (stale bytes desyncing the NEW connection's own handshake) was NOT observed today in its strong form (the JSON-corruption variant) but a documented, plausible, unconfirmed residual variant exists (see last Evidence entry) where the OLD command's op_get_message scan could consume the NEW connection's own JSON command bytes as junk if timing shifts. The two mechanisms are not mutually exclusive; (a) is the precondition that makes (b) possible, and today's evidence sits on the "leaks harmless extra frames" side of that spectrum rather than the "corrupts the next command" side -- but both stem from the same root defect: handle.cmd/operation_state are process-global, not connection-scoped, and there is no host-sendable stop signal for CMD_READ_VPP/VPE.

Verdict on the current mitigation (f7ab92a drain + 2352b5f delayed retry): HELPS, netting a real reliability improvement (self-verified 10/10 clean under exclusive access in the prior round, and every trial in this round's repros eventually returned a correct value, never a silent wrong value) -- but it is NOT free and NOT fully closing the gap:
- It converts what used to be a full, scary 10s `ProgrammerNotFoundError`-style failure into a much-more-likely ~1s "quiet" recovery (via the ALREADY-EXISTING, older `consume_remaining_input()` drain that was not written for this purpose but happens to help) -- this part is a genuine, low-cost win and requires no further change.
- BUT its own added drain step (`_drain_pending_command`, the f7ab92a code) races the firmware's watchdog with a margin measured today at ~1-2ms in the failing case, not the ~500ms the docstring assumes -- so it intermittently "fails" its own drain (silently, by design) and falls through to the 1.5s `VOLTAGE_SAMPLE_RETRY_DELAY_S`-gated retry. In today's 2 live full-call-pattern trials, BOTH sample_vpp_mv() and sample_vpe_mv() individually hit this exact near-miss, each paying ~6.7-6.8s instead of ~2.5s (no operator-visible error text this time because it's fully inside the "expected" drain-timeout debug log, not an exception) -- meaning on a real dev-test run, EVERY voltage sample pair is now likely to run noticeably slower even when nothing is reported as failing. Root cause of the near-miss: catching an intermediate in-flight DATA frame first consumes part of the deadline's real-time budget without the firmware's watchdog clock moving proportionally slower -- the 500ms nominal buffer is not actually 500ms of true margin once an extra frame is caught mid-drain.
- Net effect vs. doing nothing at this call site: strictly better (never regresses a previously-working case; the worst case is now bounded latency, not indefinite hang) -- but "helps" should not be read as "closes the race," and the added latency (now confirmed, not just theorized) may itself be worth fixing regardless of correctness, since a `dev test` run doing two voltage samples that each take ~7s instead of ~2.5s adds ~9s of unexplained, unreported slowness to every single non-destructive run.

Ranked fix directions for the operator to choose from:

1. **Firmware DONE/cancel for CMD_READ_VPP/VPE (root-cause fix, firmware change).** Mirror the EXISTING `OP_MSG_DONE` pattern already used by `eprom_write` (eprom_operations.cpp:81) into `hw_read_voltage` (hardware_operations.cpp): check `op_get_message(handle) == OP_MSG_DONE` alongside `OP_MSG_ACK` and call `set_operation_to_done`-equivalent (return `true` to finish the command) when DONE is seen. Host side: `_sample_one_voltage_attempt` calls the ALREADY-EXISTING `comm.send_done()` instead of just stopping acks, right before disconnecting. This closes the race at its source -- handle.cmd properly returns to CMD_IDLE within one command round-trip (~ms) instead of waiting up to 1000ms for a watchdog, and no stray frames are ever produced because the firmware never times out in the first place. Low implementation risk (small, additive change mirroring an already-shipped, already-tested pattern in the same codebase) but requires a firmware rebuild+reflash, native+live-hardware retest of the existing voltage-read paths (standalone `vpp`/`vpe`, `dev test`), and is out of scope for a host-only PR. Tradeoff: highest engineering cost (touches firmware + requires reflash + revalidation of a shipped protocol surface) but is the only option that actually eliminates the underlying defect rather than racing around it.

2. **Host-only: lengthen/parameterize the drain deadline and fix the margin math (incremental, low-risk, host-only).** Increase `_drain_pending_command`'s buffer past the empirically-observed ~1-2ms real margin (e.g. 1000ms buffer instead of 500ms, so deadline = FIRMWARE_CMD_TIMEOUT_MS + 1000ms), and/or restart the deadline's zero-point every time an intermediate DATA frame is caught (so catching an extra in-flight frame doesn't eat into the true watchdog-wait budget). This directly targets today's confirmed near-miss without touching firmware. Tradeoff: cheap, safe, ships today, but is still fundamentally racing a moving target -- a slower USB stack, different board, or firmware timing change could reopen the same near-miss at a different margin; does not address the (weaker, unconfirmed) hypothesis (b) JSON-corruption variant at all.

3. **Host-only: single-connection reuse across a dev-test run's voltage samples (structural, host-only).** Instead of `sample_vpp_mv()` and `sample_vpe_mv()` each doing their own `find_and_connect`/disconnect (2 full reconnects, each paying the 2.0s stabilize delay AND each capable of leaving/inheriting a dangling command), open ONE connection for the whole voltage-sampling phase of `dev test`, send state=11, ack in place for VPP's samples, `send_done()` (once firmware supports it, see option 1) or otherwise cleanly transition state, then send state=12 on the SAME still-open connection for VPE, then disconnect once at the end. Removes one whole reconnect cycle (and its 2.0s tax) and removes one whole dangling-command opportunity between VPP and VPE specifically (though NOT the one between the prior blank-check step and the first voltage sample, and NOT between dev-test invocations). Tradeoff: meaningful latency and race-surface reduction for the always-paired VPP+VPE case (the exact pattern cli_handlers.py:1854-1855 uses) with no firmware change, but is a larger host-side refactor (hardware.py's connection lifecycle currently assumes one-command-per-connection throughout; CMD_READ_VPP and CMD_READ_VPE are handled by the SAME `hw_read_voltage` function but are distinct `handle->cmd` values, so switching mid-connection needs the same command-transition semantics as option 1 to be safe) and does not fully close the gap against the FIRST sample's own precondition (still races whatever teardown happened before dev test's voltage-sampling phase even starts).
