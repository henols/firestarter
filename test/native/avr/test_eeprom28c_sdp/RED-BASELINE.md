Mechanism: `eeprom28c_write_init`'s SDP-disable sequence is emitted by
`flash_execute_command` → `flash_util_byte_flipping` → `fu_flash_fast_address`
(`flash_utils.cpp`), which writes the LITERAL `{0x5555, 0x2AAA}` magic
addresses as raw LSB/MSB register writes and never consults
`handle->bus_config`. The FIX-01 target (`memory_set_data`, driven by the
suite's `drive_reference_emitter` helper) is remap-aware and additionally
calls `rurp_chip_input()` (OUTPUT_ENABLE high) *before* the address write,
where the shipped path calls it *after* the payload — so every case
diverges at **index 0** already, before any address-value difference is even
reached: expected `{kind=2 (PIN), pin=4 (OUTPUT_ENABLE), value=1}`, recorded
`{kind=1 (DATA), pin=0, value=0x55}`. On AT28C64/AT28C16 the address VALUES
also differ from the shipped ones (e.g. AT28C64's `remap(0x5555)` MSB is
`0x15`, not `0x55`) — a real, not merely reordered, divergence — but since
the comparator reports only the *first* divergence, index 0's ordering
difference is what every case's captured message shows.

## Cases 4-5 — DIP32_28C512_EEPROM, deliberate stale-upper-address state (CORRECTION 3, TRACE-02, D-09)

Verbatim captured output:

```
test/native/avr/test_eeprom28c_sdp/test_eeprom28c_sdp.cpp:88:test_case4_at28c010_stale_direct_seed:FAIL: Expected 54 Was 57. test/native/avr/test_eeprom28c_sdp/test_eeprom28c_sdp.cpp:88:test_case5_at28c040_stale_via_real_read:FAIL: Expected 54 Was 57. Case 5: AT28C040/DIP32_28C512_EEPROM, stale CTRL_ADDRESS_LINE_17 reached via a REAL preceding read (memory_get_data, not a directly-seeded cache) -- shipped path must clear the write-inhibit bit like the fixed reference emitter does
```

**Why a plain DIP32 trace would be decorative (CORRECTION 3, confirmed by
116-05-SUMMARY.md's own `test_fixed_guard_at28c010`/`at28c040` cases):** under
a zero-seeded CONTROL register, `mem_util_remap_address_bus` returns `0x5555`
**unchanged** for this pinout (`address_mask == 0xFFFF`; the `rw_line`=20 bit
folds in `WRITE_FLAG == 0` on a write, contributing nothing) — so the shipped
and fixed streams share byte-identical LSB/MSB/data values, differing only
by the SAME incidental `/OE`-ordering artifact described above for Cases 1-3.
A future fix that happened to preserve that ordering would leave a plain
DIP32 trace GREEN with nothing about the real bug proven.

**The real bug, made visible by seeding the stale state deliberately:**
DIP32's `rw_line` (20) folds `READ_FLAG` into CONTROL bit `0x10`
(`CTRL_ADDRESS_LINE_17`) — the write-enable line this 32-pin pinout
repurposes an upper address line for. `fu_flash_fast_address` (the shipped
emitter) writes **only** LSB/MSB and **never** writes `CONTROL_REGISTER` at
all, so whatever a preceding operation left in CONTROL's upper-address bits
stays stuck for the entire SDP sequence: `/WE` inhibited, and (for
`CTRL_ADDRESS_LINE_18`) the chip's real upper address wrong. The reference
emitter (`memory_set_data`, the FIX-01 target) recomputes and writes
`CONTROL_REGISTER` on every address change via `mem_util_set_address`, and
**does** clear those stale bits.

**Comparison design (why these two numbers, 54 and 57):** both cases
dynamically drive the reference emitter under the identical stale seed the
shipped path was driven under (not the canonical zero-seed
`SDP_FIXED_DIP32_28C512_EEPROM` constant in `_shared/sdp_expected.h`, which
would only reproduce the same decorative `/OE`-ordering divergence and prove
nothing — see the previous paragraph). The stale-seeded reference emitter
emits **3 extra entries** (a `DATA` write of the new CONTROL value plus its
`PIN`-high/`PIN`-low latch strobe) the first time it recomputes CONTROL and
finds it differs from the stale cached value — 54 (unelided baseline) + 3 =
**57**. The shipped path's recorded stream stays **54** in both cases
(unaffected by the CONTROL seed, since `flash_util_byte_flipping` never
depends on it beyond an always-cache-hit `CTRL_READ_WRITE` toggle). This is
the "large, unambiguous divergence" CORRECTION 3 calls for: a difference in
**kind** (an entire extra CONTROL-clearing event), not merely incidental
ordering — and it is **self-repairing**: once Phase 117 rebuilds
`eeprom28c_write_init` on the same remap-aware, CONTROL-writing emitter,
driving the "shipped" handle will produce byte-identical output to driving
the reference handle, and the assertion passes with no further edit.

**Stale-state mechanism, established two different ways (RESEARCH Open
Question 1) — a reviewer cannot object that a directly-seeded cache is
unrepresentative:**
- **Case 4 (AT28C010, 128 KB): direct seed.** `reset_register_cache(0x00,
  0x00, CTRL_ADDRESS_LINE_17 | CTRL_ADDRESS_LINE_18)` seeds both bits
  directly through the cache-reset seam before driving the sequence.
- **Case 5 (AT28C040, 512 KB): a real preceding read.** The case performs an
  ACTUAL `memory_get_data()` call (through the handle's real,
  production-assigned `firestarter_get_data` pointer, before it is
  reassigned to the address-keyed mock) at an arbitrary probe address
  (`0x0000` — deliberately not `0x5555`/`0x2AAA`, the SDP sequence's own
  magic addresses, to avoid also pre-warming the LSB/MSB latch cache to a
  value the sequence's own first write would otherwise hit, which is a real
  but SEPARATE elision effect that would have muddied this comparison).
  `mem_util_remap_address_bus` folds `READ_FLAG=1` into bit 20 for *any*
  read, regardless of address value, which resolves to `CTRL_ADDRESS_LINE_17`
  (only) after `mem_util_calculate_top_address_register`'s `>>16` shift —
  case 5 therefore reaches a **strict subset** of case 4's seeded bits
  (`0x10` only, not also `0x20`) via a genuinely-executed production read
  path, not a hand-seeded value.

## Design decisions this suite embodies

- **Full-stream equality, not a prefix assertion (resolves RESEARCH Open
  Question 2 in favour of the stronger claim).** The plan's own text directs
  this: assert the **complete** recorded stream against the FIX-01 target,
  not just the 54-entry SDP-command prefix followed by a "no seventh command
  write" scan. This is possible **only** because every case reassigns
  `firestarter_get_data`/`firestarter_set_data` to the address-keyed mock
  (Pattern 3) before driving `eeprom28c_write_init`: the mock satisfies no
  bus traffic at all, so `eeprom28c_wait_for_write`'s 2000-iteration timeout
  loop contributes **zero** additional strobes to the recorded stream.
  `strobe_overflowed()` is asserted `0` in every trace case as a load-bearing
  precondition for this to be trustworthy (RESEARCH measured 6057 strobes
  for the same drive using the REAL, unmocked `memory_get_data` — the mock
  is what collapses that back to exactly the command window).
- **Which mechanism established the stale upper-address state, per case**
  (RESEARCH Open Question 1): Case 4 = direct cache seed; Case 5 = a real
  preceding `memory_get_data` read. See §Cases 4-5 above for the full
  mechanism and why case 5's probe address was chosen to avoid an unrelated
  LSB/MSB cache-elision confound.
- **Why the DIP32 cases are stale-upper-address cases at all, rather than
  plain traces** (CORRECTION 3): a plain DIP32 trace against the zero-seed
  `SDP_FIXED_DIP32_28C512_EEPROM` array is GREEN-decorative both before and
  after a hypothetical Phase 117 fix that happens to preserve `/OE`
  ordering — it would prove nothing about the actual write-inhibit bug. See
  §Cases 4-5 above for the full argument and the dynamically-derived
  comparison target this suite uses instead.
- **The CORRECTION 4 per-pinout inhibit table — 66 of 84 chips affected, not
  "all 84".** `REQUIREMENTS.md` §Framing and an earlier `SUMMARY.md` finding
  both overstated this as "all 84 `0x0D` chips" have at least one write
  emitted with `/WE` HIGH. Measured (116-RESEARCH.md CORRECTION 4):

  | Pinout | Chips | `rw` bus line | Register domain | Writes inhibited (of 6) |
  |---|---|---|---|---|
  | `DIP28_28C64` | 35 | 14 | MSB bit 6 | **4** (the four `0x5555` loads) |
  | `DIP24_2816` | 19 | 11 | MSB bit 3 | **2** (the two `0x2AAA` loads) |
  | `DIP28_28C256` | 12 | 14 | MSB bit 6 | **4** (the four `0x5555` loads) |
  | `DIP32_28C512_EEPROM` | 18 | 20 | CONTROL bit `0x10` | **0** at INIT-time register state |
  | **total** | **84** | | | **66 chips affected** |

  **`DIP24_2816` is inhibited on the *opposite* writes from the DIP28
  pinouts** — the `0x2AAA` loads, not the `0x5555` loads, because `0x2A` has
  bit 3 set while `0x55` does not. Any prose that says "the `0x5555` writes
  are inhibited" is wrong for 19 chips. `DIP32_28C512_EEPROM`'s 18 chips are
  inhibited **0 of 6** at plain INIT-time register state (CONTROL starts
  clean) — which is exactly why Cases 4-5 above had to construct a
  *deliberately* stale precondition to make this pinout's real hazard
  observable at all; it is not visible from a fresh boot.

## Declined widening, recorded as an open hook (D-07 scoping)

116-RESEARCH.md §F5 observed that `fu_flash_flip_data` calls
`rurp_set_data_output()` (setting the data bus to drive) while
`memory_set_data` does not call it at all — so the FIXED path's data-bus
direction currently relies on whatever state a prior operation left behind.
Recording the two direction calls (`rurp_set_data_output`/
`rurp_set_data_input`) as a third strobe kind would make that reliance
visible in this suite's traces.

**Phase 116 declines this widening for now** — the research did not verify
that adding the additional stub guards would compile cleanly, and D-07
scoped this phase's strobe recording to exactly what the `0x0D` SDP path
touches (`rurp_write_data_buffer` + `rurp_set_control_pin`), not the whole
bus-direction surface. This is stated here as an **open, named hook** for
Phase 117/118 to revisit deliberately — not silently dropped.
